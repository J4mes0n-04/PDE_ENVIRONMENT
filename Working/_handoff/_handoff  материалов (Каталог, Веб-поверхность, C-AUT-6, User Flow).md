## 1. Каталог графических элементов интерфейса

### Статус
Не создан. Три блокирующих вопроса ниже — причина, не забывчивость.

### Дом и назначение
Продуктовый документ, не привязан к одному компоненту. Используется совместно: `C-PRJ-1` (design-time — как элемент создаётся и настраивается), `C-ROOM-*` (runtime — как элемент ведёт себя у пользователя), `C-PRJ-5` (тема и стили), `C-AUT-6` (словарь событий элемента для программинга).

### Согласованный формат карточки (жанр B — справочник, не спецификация)
Обсуждён и зафиксирован явно, включая два поля по требованию PM:

- **Идентификатор и имя** — `GUI-*` + название
- **Покрываемая потребность** — какую потребность пользователя закрывает *(требование PM)*
- **Обоснование для MVP** — входит ли в MVP, почему; если нет — что откладывает *(требование PM)*
- **Назначение** — что за элемент, когда применяется
- **Свойства** — таблица: свойство / тип / значение по умолчанию
- **Design-time** (сторона `C-PRJ-1`) — какие свойства редактируемы, с чем связывается, какие состояния настраиваются
- **Runtime** (сторона `C-ROOM-*`) — как ведёт себя при взаимодействии, как реагирует на изменение связанного значения
- **Состояния** — перечень поддерживаемых состояний
- **События** — перечень событий, которые элемент порождает *(добавлено после решения по программингу — поле нужно для `C-AUT-6`)*
- **Наследие Studio** — аналог в Studio, иконка
- **Ссылки** — какие `US-*`/`OB-*` конфигуратора и клиента задействуют элемент

**Разделение design-time/runtime внутри карточки предложено мной и не переспрошено PM явно** — в последующих документах (`C-PRJ-1`, функциональная структура) я исходил из того, что оно принято, но прямого «да» на этот конкретный вопрос в переписке нет. Стоит подтвердить перед стартом, а не считать решённым по умолчанию.

### Материал из аудитов, готовый к использованию
- **Studio States** («несколько вариантов внешнего вида на элемент») — вердикт легаси-аудита «Сохранить и расширить». Принятая трактовка (зафиксирована в функциональной структуре, §7.3): концепт наследуется, но подчиняется единой теме проекта с локальными переопределениями (`C-PRJ-5`), а не остаётся полностью независимой ручной настройкой каждого элемента, как в легаси.
- **Chameleon Image** (перекрашиваемые изображения) — вердикт «Переосмыслить». Принятое направление — иконочные шрифты (`US-29` в `C-PRJ-1`), которые масштабируются и перекрашиваются без подготовки вариантов; закрывает исходную задачу иначе.
- Легаси-инвентарь элементов — только «Page / Popup / Graphic Item со States». **Недостаточен как основа каталога** — это не список типов элементов, а структурная модель проекта.

### Блокирующие вопросы (по убыванию важности)
1. **Инвентаря элементов нет.** Ни в одном источнике не зафиксирован список типов графических элементов (кнопка, слайдер, индикатор, список и т.д.) для нового продукта. Это первый шаг перед оформлением документа — нужен список от PM.
2. **Design-time/runtime разделение внутри карточки** — не переспрошено явно (см. выше).
3. **Открытый вопрос ⚑-3 из `C-AUT-6`** (см. раздел 3 ниже): где живёт словарь действий и событий — карточка каталога / спецификация `C-AUT-6` / единый документ. Блокирует наполнение поля «События» и вообще границу каталога с `C-AUT-6`.
4. Иконочные шрифты (`US-29`) пересекаются с полем «иконка» в карточке — на момент написания каталога нужно решить, где документируется связь конкретного элемента с иконочным шрифтом.

### Что изменилось с первого черновика — сводка для быстрой ориентации
1. Undo/redo нашёл дом (`C-PRJ-1/US-11`) — раздел D.
2. Synchronize нашёл дом (`C-PRJ-1/US-21`) — раздел C.
3. Появился `C-AUT-6` — новая строка в разделе C, которой не было в природе на момент первого черновика.
4. Пять пунктов раздела E частично закрыты через дополнение к «Принципы UI/UX» (`UXP-A1`–`UXP-A11`) — но сами способности (не принципы) там не описаны, только вынесены как «не вошло» и остались в реестре идей. Карта при оформлении должна на них ссылаться, а не переоткрывать.

Развести до наполнения обоих документов, иначе материал разъедется.

Формально не конфликт (словари действий разные), но нужно явное правило выбора для интегратора («команда оборудованию → сервер; изменение вида интерфейса → клиент» — моя гипотеза, не решение PM) |
| ⚑-2 | Конфликт с `C-ROOM-4` / `FM-20` | В карте v1.0 `C-ROOM-4` описан с «открытием нужной страницы по событию» — это действие программинга. | ⚑-3 | Словарь действий и событий | Где живёт: события — атрибут элемента (карточка каталога), действия — словарь `C-AUT-6`, или единый документ «элементы + события + действия», как предполагалось изначально. Блокирует и каталог (раздел 1 выше), и полноту спецификации `C-AUT-6` (полный список действий пока не приведён, известны только три от PM: уведомление, показ страницы, блокировка экрана) |

## 4. User flow (`FLOW-*`)

### Статус
Дважды отложено решением PM: сперва «пока пропустим блок, оставим для сложных тем», затем подтверждено при формировании итогового списка документов. Раздел зарезервирован пустым в функциональной структуре `C-PRJ-1` (§8).

### Согласованный формат карточки
- **Идентификатор** — `FLOW-*`
- **Действующее лицо и цель** — кто и зачем
- **Предусловие** — с чего начинается
- **Шаги** — нумерованная последовательность «действие → отклик системы», со ссылками на `BLK-*` (блоки функциональной структуры)
- **Ветвления** — где сценарий расходится
- **Результат** — чем заканчивается
- **Ссылка на спецификацию** — какую `US-*` реализует

Решено вести текстом на старте (не диаграммой) — правится без дополнительного инструмента; диаграмма — когда flow устоится.

### Кандидаты, всплывшие по ходу работы (не оформлены, черновой список для старта)

1. **Мастер настройки.** Групповое добавление устройств → одновременное порождение серверного и панельного проекта. Источник: `US-3`, `US-6b`, `INV-3`; экран `Э-5`, блок связей с `Э-2`/`Э-3` в функциональной структуре.
2. **Ручное создание панельного проекта из готового серверного.** Источник: `US-6`; блок `BLK-16`.
3. **Добавление устройства из каталога с предложением готового интерфейса**, включая ветвление «устройство из каталога» vs «драйвер настроен вручную» (в последнем случае автоподбор UI не гарантирован из-за непредсказуемых имён тегов). Источник: `US-5`; блоки `BLK-7`, `BLK-8`.
4. **Копирование сущностей между проектами** (замена легаси-merge). Источник: `US-25`.
5. **Synchronize** — приведение состава тегов панельного проекта в соответствие с изменённым серверным. Источник: `US-21`; блок `BLK-16`.
6. **Параллельная работа с несколькими открытыми проектами** — переключение, изоляция истории. Источник: `US-9`, `US-10`; блок `BLK-1`.
7. **Настройка программинга: событие → действие**, с веткой «событие элемента» / «событие изменения тега» и веткой «с условием» / «без условия». Источник: `C-AUT-6` (`OB-1`–`OB-3`); блоки `BLK-17`, `BLK-18`. **Зависит от разрешения ⚑-3** — пока словарь действий не определён, flow можно описать только на уровне шагов, без конкретных примеров действий.

Ветвление под пунктом 3 — единственное, для которого формат явно предусматривает раздел «Ветвления» с содержательным наполнением уже сейчас; остальные кандидаты в основном линейны.

## 5. Сквозные незакрытые темы (не привязаны к одному документу выше)

Для полноты — то, что упоминалось как «обсудим отдельно» и не было закрыто до конца чата:

- **Противоречие «закрытие сессии по бездействию vs потеря несохранённых данных при редактировании».** Договорились обсуждать отдельным заходом; отдельный заход не состоялся. Частично снято с одной стороны — `C-PRJ-1/US-17` (автосохранение) и `US-18` (защита от потери) — но сама механика сессии (`C-SEC-1`) не проработана.
- **Деплой (публикация) проекта** — кандидат на самостоятельный компонент, зафиксирован в реестре идей с первоначальным `US-a`/`OB-a`, дом не определён с самого первого упоминания.
- **`FM-*` для новых способностей `C-PRJ-1`** (`US-2, 6, 6b, 8, 9–12, 14–36`) — ни один не заведён в Product Scope; решение по способу трассировки не принято.
