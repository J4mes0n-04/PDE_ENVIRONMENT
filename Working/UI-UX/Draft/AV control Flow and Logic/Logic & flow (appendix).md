# Logic & User Flows — AV Control

**Рабочий черновик v0.3 · для итерации**

> **Назначение.** Развернуть продуктово-наблюдаемую логику работы системы и пользовательские потоки по ролям: состояния, переходы, условия (guards), системные реакции, откаты, деградацию, синхронизацию — детальнее use cases, но не на уровне реализации.
> 
> **Уровень.** Только то, что наблюдает пользователь и за что отвечает продукт. Реализационные детали (атомарность, watchdog, health-check, механика синхронизации, пороги) не решаются здесь — вынесены в §9 «Решения совместно с тех.лидом».
> 
> **Что не включаем.**
> 
> - Матрицу прав `профиль × действие × ресурс` → **ACM**.
> - ER-модель, схемы конфигурации/телеметрии, состав backup и diagnostic bundle → **Information Architecture & Data Schema**.
> - Контракты API, Driver Engine (sandbox, lifecycle) → **Core & API & Integration Specs**.
> - Архитектуру, протоколы, ОС → **PSD**.
> - «Историю актора» → **Use Case Specification (UC)**.

## §0. Стык блока

### Продуктовая рамка

AV Control — **инструмент**. Конкретное поведение объекта собирает **интегратор**: сценарии, расписания, пресеты, условия, привязку к брони/ВКС. L&F описывает **примитивы платформы и потоки работы с ними**, а не политики конкретного объекта.

Следствие для всего документа: где «правило» на деле настраивается интегратором (что делает «Завершить», когда стартует следующая встреча, какое оборудование критично), L&F описывает **механизм и точку настройки**, а не фиксированное поведение.

### Закрыто выше — ссылаться, не пересматривать

- **Роли.** Единый источник — 7 операционных профилей PRD §2: `End User`, `Support Operator`, `IT Admin`, `Integrator Engineer` (Инж), `Lead Integrator` (Lead), `Security Auditor` (ИБ), `Vendor Support` (Вендор) + машинные пользователи API. Предварительный список ролей в PSD — интеримный; здесь не используется.
- **Режимы и принципы** — PSD §5 и §1 ниже.
- **Уровни ошибок** —  в мониторинг (v1) эскалируются Error / Critical.

### Границы

- **UC ↔ L&F.** UC — наблюдаемая актором история; L&F — механика и ветвления. Flow не пересказывает UC и не перерисовывает state-machine PSD; flow — это поведенческий разрез с конечной целью.
- **L&F ↔ тех.лид.** Всё техническое — в §9.

### Маркеры

- `[? — продукт]` — открытый продуктовый вопрос (сведены в §7).
- `[→ §9]` — решение совместно с тех.лидом.
- `[? — аналитика]` — отдельная аналитическая проработка.

### Сознательно вне документа

Decision log / ADR, полная многоколоночная traceability-матрица, версионирование решений и каталог пользовательских сообщений в L&F не ведутся — это либо governance-артефакты пакета, либо уровень UX/Data Schema.

## §7. Открытые вопросы (продукт)

- **Строгий режим обновления при сессии.** Настраиваемое на сервере условие более строгого поведения — в каком релизе, какие условия (окно обслуживания, принудительно по политике).
- **Граница JS.** Только серверная логика или и клиентская; что точно нельзя через JS в первом релизе.
- **Scope брони/ВКС.** Целевые системы бронирования и платформы ВКС; обязательный набор команд ВКС.
- **Аудит вывода объекта.** Как фиксировать аудит при удалении данных — отправка в SIEM до очистки достаточна.
- **Маркировка IP.** Нужна ли видимая отметка «защищённый проект».
- **Preview bundle.** Должен ли пользователь видеть состав bundle до экспорта.

_В аналитику (не L&F):_ addon-лицензия при замене контроллера.

## §8. Статус блока

**Готово к ревью:** §0 рамка и терминология, §1 объектная модель и состояния, §2 стейт/экшн-матрица, §3 формат, §4 каталог с трассировкой, §5 потоки (P0 — с критериями приёмки), §6 ролевые разрезы, Приложение А.

**Требует решений §7:** строгий режим обновления, граница JS, scope брони/ВКС, аудит вывода, маркировка IP, preview bundle.

**Совместно с тех.лидом §9.** **В аналитику:** addon-лицензия при замене.

## §9. Решения совместно с тех.лидом

> Варианты предлагает тех.лид, окончательное решение — за продакт-менеджером. Это не консультации, а блокирующие развилки: формулировки — предложения.

|Вопрос|Что блокирует|
|---|---|
|Перечень и значения объектов состояния runtime|§1, §2, все Recovery-потоки|
|Атомарность операций: деплой, update, restore|FL-PRJ-DEPLOY, FL-UPD-CORE, FL-UPD-RESTORE|
|Кольцо откатов: глубина, выбор при авто-откате, критерий исправного|§1.4, FL-PRJ-DEPLOY|
|Watchdog / recovery: что детектируется, retry/restart/disable|§1.2, FL-ERR-SAFE|
|Safe Mode: порог серии стартов и нарастающий таймаут, удалённый вход/выход|§1.2, FL-ERR-SAFE|
|Health-check после деплоя/обновления|FL-PRJ-DEPLOY, FL-UPD-CORE|
|Compatibility-check драйвер↔ядро и проект↔ядро|FL-DRV-RELEASE, FL-PRJ-DEPLOY|
|Механика синхронизации нескольких клиентов|FL-PNL-LIFECYCLE|
|Что уходит в аудит, что в системный лог|§2.2, FL-SEC-ACCESS|

|Какие команды API считаются write|FL-BVC-BOOKING|
