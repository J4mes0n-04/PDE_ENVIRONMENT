## 1. Закрыто — не пересматривать

1. **Объектная модель.** Управляемая единица — серверный проект, исполняющий набор оборудования. Сущности «комната» нет; «переговорка/помещение» — физический контекст. Состояния принадлежат проекту, оборудованию, сессии, панели, драйверу, лицензии (§1).
2. **Две независимые оси.** Режимы контроллера (Boot / Норма / Safe — редкие) и занятость переговорки (Свободна / Занята — ежедневная) не связаны; зависимость односторонняя. PSD §5 «Стандартный/Активный» = свободна/занята (§1.2).
3. **Продуктовая рамка.** Платформа — инструмент; поведение объекта собирает интегратор (сценарии, расписания, пресеты, условия, бронь). L&F описывает примитивы и точки настройки, не политики объекта.
4. **Окончание встречи.** Сценарий интегратора по двум триггерам: явное действие пользователя и таймаут по расписанию. «Следующая встреча стартует, не завершив предыдущую» — настройка интегратора через бронь, не продуктовое правило (FL-AUT-SCENARIO).
5. **Кольцо откатов.** Механизм: хранится ограниченное число последних задеплоенных серверных проектов, откат на любой, при переполнении циклическая очистка. Конкретные числа — не в L&F (§1.4).
6. **Safe Mode.** Механизм входа: серия неуспешных стартов по watchdog / критический сбой / удалённая команда. Команды на оборудование в Safe Mode запрещены; выход — действием администратора. Пороги — не в L&F (§1.2, FL-ERR-SAFE).
7. **Оперативный слой без редеплоя.** Расписания, сценарии, пресеты меняются без публикации проекта; переживают перезапуск; сбрасываются при загрузке нового проекта или удалении текущего; правят Инж и IT под аудитом (FL-OPS-OPER).
8. **Офлайн панели.** Оверлей «нет связи» опционален по проекту (флаг + страница, выбирает интегратор); панель кэширует последнее состояние и ждёт сервер; очередь офлайн-событий не строится, при реконнекте — ресинхронизация (FL-PNL-LIFECYCLE).
9. **Деградация.** Необязательная зависимость недоступна → продолжение; критичная (помечена интегратором при проектировании) → деградация или останов по настройке сценария. «Минимально работающий» набор определяет интегратор (§2.2, FL-OPS-DAY).
10. **Структура блока.** Каталог из 14 сводных flow с приоритетами, глубиной и BPMN-пометками; критерии приёмки для P0; стейт/экшн-матрица как поведенческий ролевой разрез режимов контроллера.

## 2. Передано вперёд

### → Information Architecture & Data Schema

- Формализовать объектную модель в ER и схемы: проект; оборудование (Доступно / Недоступно / Деградировано); сессия (Нет / Идёт / Завершается); панель; драйвер (версия, диапазон совместимости, capabilities и ограничения); лицензия (Valid / Invalid / LimitsExceeded / EmulatorActive / Missing).
- Модель тегов (драйверные, системные, пользовательские, persist-значения), связей и преобразований Expression Evaluator.
- Хранение кольца откатов: структура ограниченного набора задеплоенных проектов.
- Персистентность оперативного слоя: расписания, сценарии, пресеты — отдельно от проекта, переживают перезапуск, сброс при смене проекта.
- Состав и формат backup; состав diagnostic bundle (ограничения ИБ — см. §9 L&F).
- Журналируемые события: поля «Логи / события» из каждого flow и классы событий §2.2 свести в схему событий/телеметрии; развести аудит и системный лог.

### → Core & API & Integration Specs

- Scenario Engine: модель `событие → условие → действие`, задержки, обработка ошибки, возврат оборудования в состояние.
- Driver Engine: sandbox, lifecycle, подпись, compatibility-check драйвер↔ядро.
- Атомарность деплой / update / restore; post-deploy health-check; выбор проекта из кольца; совместимость проект↔ядро.
- Watchdog / recovery; пороги Safe Mode и нарастающий таймаут; реализация удалённого входа/выхода.
- Механика синхронизации нескольких панелей.
- API: бронь/календарь (создание брони обязательно уже сейчас), команды ВКС, мониторинг/SIEM; перечень write-команд.
- Поведение клиента в офлайне (оверлей, без очереди событий) — подтвердить при реализации.

### → Product Scope & Technical Boundaries

- Распределение P0/P1/P2 по flow; v1 против отложенного: standalone-панель — post-v1; UI брони с панели — P2; строгий режим обновления при встрече — позже; JS — опциональное расширение.
- Открытые продуктовые вопросы §7 L&F как границы scope.
- Список §9 L&F (решения совместно с тех.лидом) — технические границы к разрешению.
- Addon-лицензия при замене контроллера — отдельная аналитическая проработка.

## 3. Не включать / не переописывать

- Роли (PRD §2), режимы (PSD §5 + L&F §1.2), поведенческие flow (L&F) — downstream не переопределяет.
- Один и тот же процесс не описывать трижды: PSD — архитектура и принципы, L&F — поведенческий и пользовательский вид, Core&API — механика. Diagram-в-трёх-местах запрещён.
- Матрица прав `профиль × действие × ресурс` — только ACM; L&F её сознательно не специфицирует.
- Тексты пользовательских сообщений — UX и Data Schema, не внутри flow.
- В L&F сознательно отсутствуют decision log/ADR, полная traceability-матрица, версионирование решений и каталог сообщений — downstream не ожидать их в L&F.

## 4. Открыто на момент закрытия

**Продуктовые вопросы (§7 L&F):** строгий режим обновления при встрече; граница JS (серверная/клиентская); scope систем брони и платформ ВКС и обязательный набор команд; аудит вывода объекта при удалении данных; маркировка защищённого проекта; preview состава bundle.

**Совместно с тех.лидом (§9 L&F):** перечень и значения объектов состояния runtime; атомарность операций; параметры кольца откатов; watchdog/recovery; пороги Safe Mode и удалённый вход/выход; health-check; compatibility-check; механика синхронизации; аудит против системного лога; состав bundle; write-команды API.

**Аналитика:** addon-лицензия при замене контроллера.

**Косметика (не дефект):** при желании унифицировать словарь «Свободна/Занята» вместо «Стандартный/Активный» во всех flow.
