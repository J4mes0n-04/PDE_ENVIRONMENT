
# 2.4 Logic & User Flows

## Логика и пользовательские потоки

### 2.4.0 Назначение блока

**Logic & User Flows** описывает не сами пользовательские кейсы, а механику их исполнения: переходы состояний, ветвления, условия, системные реакции, откаты, предупреждения, деградацию, синхронизацию клиентов, логику деплоя, обновлений, восстановления и взаимодействия ролей.

Use Case Specification уже фиксирует акторов, цели, предусловия, основной поток, альтернативы и ошибки. Этот блок должен раскрывать то, что в Use Cases специально вынесено в `→ L&F`: детальная логика ветвлений, связи тегов, флоу деплоя, Safe Mode, update-flow, driver-release-flow и recovery-flow.

**Не включать в этот блок:**

- формальную матрицу прав `профиль × действие × ресурс` — это Access Control Model;
- ER-модель, схемы хранения, формат backup, telemetry/log schema — это Information Architecture & Data Schema;
- контракты API, sandbox/lifecycle драйверов, watchdog/recovery на уровне реализации — это Core & API & Integration Specs;
- архитектурные принципы и компоненты — уже закрыты в PSD.

### 2.4.1 Опорные решения, которые не пересматриваются

В этом блоке считаются зафиксированными следующие решения:

|Решение|Как учитывать в flows|
|---|---|
|Акторы = 7 операционных профилей PRD + машинные акторы API|Все флоу строятся от профилей действий, а не от должностей|
|`Lead Integrator` используется точечно|В основном в шаблонах, защите IP, handover|
|Лицензия вшита заводски и непереносима|Нет отдельного флоу «активация при первом включении»|
|Истечение эмулятора — штатное событие|Не описывать как аварию|
|Функция панели задаётся выбором проекта|Не вводить отдельный flow «назначение комнаты панели»|
|Теги, связи, Expression Evaluator — часть ручного создания проекта|Не выносить это в автоматизацию|
|Любой проект/шаблон редактируем после создания|Flows должны поддерживать возврат к редактированию|
|Сервисное действие при активной встрече → предупреждение|Обновление, перезагрузка, снятие проекта не должны молча прерывать встречу|
|Diagnostic bundle собирается локально|Вендор может анализировать bundle без доступа в контур|
|Расширение лимита лицензии идёт через вендора/дистрибьютора|Пользователь видит запрос/статус, но не механизм расширения|
|Уровни событий: Info / Warning / Error / Critical|В мониторинг v1 эскалируются Error/Critical|

Эти решения прямо зафиксированы в handoff Use Cases → docs и должны использоваться ниже как ограничения downstream-документа.

# 2.4.2 Формат описания flow

## Формат карточки flow

Каждый flow описывается по единому шаблону:

|Поле|Содержание|
|---|---|
|**Flow ID**|`LF-<область>-NN`, например `LF-PRJ-01`|
|**Название**|Краткое действие или процесс|
|**Связанные Use Cases**|ID кейсов из Use Case Specification|
|**Акторы**|Профили PRD / машинные акторы|
|**Тип flow**|Пользовательский / системный / смешанный / аварийный|
|**Цель flow**|Что должен обеспечить поток|
|**Начальное состояние**|Состояние системы до запуска|
|**Триггер**|Что запускает flow|
|**Основной поток**|Последовательность шагов|
|**Ветвления / guards**|Условия, альтернативы, запреты|
|**Системные реакции**|Что делает система автоматически|
|**Пользовательская обратная связь**|Что видит пользователь / инженер / IT|
|**Логи / аудит / события**|Что фиксируется|
|**Конечное состояние**|Чем flow должен завершиться|
|**Открытые вопросы**|Что нужно подтвердить|
|**Трассировка**|PRD / PSD / UC / Core&API / Data Schema|

## Типы flow

|Тип|Когда использовать|
|---|---|
|**Role Flow**|Последовательность действий конкретной роли: интегратор, IT, пользователь, поддержка|
|**System Flow**|Внутренняя логика: деплой, откат, проверка совместимости, Safe Mode|
|**Runtime Flow**|Поведение в рантайме: запуск сценария, обратная связь, синхронизация панелей|
|**Error / Recovery Flow**|Ошибки, деградация, восстановление, rollback, last-known-good|
|**Integration Flow**|API / внешняя система / машинный актор|
|**State Flow**|Переходы между состояниями: Стандартный → Активный → Safe Mode → Recovery|

# 2.4.4 Черновики flow, которые уже можно заполнить

## `LF-PRJ-01` Создание проекта через wizard помещения

**Связанные UC:** PRJ-01, PRJ-02, PRJ-04, PRJ-06  
**Актор:** `Integrator Engineer`  
**Тип:** Role Flow + System Flow  
**Цель:** собрать типовую комнату без ручного создания устройств, тегов, связей и базовых сценариев.

### Начальное состояние

- В системе создан проект.
- Пользователь имеет права настройки проекта.
- В каталоге есть готовый шаблон комнаты или устройства.
- Активный проект на сервере не изменяется до публикации.

### Основной поток

1. Интегратор выбирает создание комнаты через wizard.
2. Система предлагает тип комнаты / шаблон.
3. Интегратор выбирает оборудование: вендор, модель, роль устройства в комнате.
4. Система автоматически создаёт:
    - устройства;
    - драйверы;
    - теги;
    - связи;
    - базовые сценарии;
    - элементы интерфейса;
    - единый стиль блока.
5. Интегратор корректирует адреса, параметры подключения, состав оборудования.
6. Система выполняет первичную проверку полноты.
7. Проект сохраняется как черновик.
8. Проект передаётся в preflight flow `LF-PRJ-03`.

### Ветвления

|Условие|Реакция|
|---|---|
|Нет готового шаблона комнаты|Переход к wizard добавления устройств|
|Нет нужного устройства|Переход к запросу драйвера `LF-DRV-01`|
|Автосвязь конфликтует с уже существующей связью|Система показывает конфликт и предлагает выбрать источник истины|
|Требуется нестандартная логика|Переход к ручному редактированию / `LF-PRJ-02`|
|Требуется визуальная кастомизация|Переход к настройке интерфейса, без deep customization|

### Логи / события

- создание комнаты;
- добавление устройства;
- автосоздание тегов и связей;
- ошибки автосвязей;
- сохранение проекта.

### Конечное состояние

Проект сохранён и готов к preflight-проверке.

## `LF-PRJ-02` Ручное создание проекта: устройства, теги, связи, Expression Evaluator

**Связанные UC:** PRJ-03, PRJ-04, AUT-01  
**Актор:** `Integrator Engineer`  
**Тип:** Role Flow + System Flow  
**Цель:** дать интегратору контролируемый ручной путь сборки проекта, когда wizard недостаточен.

PRD фиксирует, что AV Control должен поддерживать единую сущность «тег», пользовательские и системные теги, связи между тегами и элементами интерфейса, защиту от зацикливания и нативный Expression Evaluator для простых преобразований без JavaScript.

### Начальное состояние

- Есть пустой или существующий проект.
- Интегратор имеет права редактирования.
- Не требуется публикация изменений до завершения проверки.

### Основной поток

1. Интегратор создаёт или открывает проект.
2. Добавляет устройства вручную.
3. Для каждого устройства выбирает драйвер или generic-протокол.
4. Система создаёт драйверные теги:
    - командные;
    - обратной связи;
    - статуса;
    - ошибок.
5. Интегратор создаёт пользовательские теги, при необходимости отмечает persist-значения.
6. Интегратор связывает теги устройств, пользовательские теги и элементы интерфейса.
7. Для преобразований значений использует Expression Evaluator.
8. Система проверяет:
    - типы данных;
    - диапазоны;
    - циклы;
    - отсутствующие источники;
    - несогласованные направления связи.
9. Интегратор добавляет сценарии помещения.
10. Проект сохраняется и уходит в preflight.

### Ветвления

|Условие|Реакция|
|---|---|
|Невозможно выразить логику через Expression Evaluator|Переход к JS-расширению `LF-AUT-03`|
|Связь создаёт цикл|Система блокирует сохранение связи или требует явного решения|
|Тип значения не совпадает|Ошибка преобразования с указанием входного и ожидаемого типа|
|Значение должно переживать перезапуск|Тег помечается как persist|
|Ошибка возникает только в рантайме|Событие уходит в диагностику и `ERR-02`|

### Конечное состояние

Проект собран вручную, но не опубликован. Следующий обязательный поток — `LF-PRJ-03`.

## `LF-PRJ-04` Деплой активного проекта и откат

**Связанные UC:** PRJ-07, ERR-05, ERR-10, ERR-11  
**Актор:** `Integrator Engineer`, частично `IT Admin`  
**Тип:** System Flow + Error / Recovery Flow  
**Цель:** безопасно сделать проект активным без риска поломки текущей рабочей конфигурации.

PSD фиксирует принцип атомарного деплоя проекта с откатом, хранение предыдущей рабочей версии и предсказуемое поведение при превышении лимитов: публикация блокируется, runtime не ломается.

### Начальное состояние

- Есть проект, прошедший preflight.
- Есть текущий активный проект или стандартный режим.
- Лицензия валидна.
- Система не находится в процессе обновления / восстановления.

### Основной поток

1. Интегратор выбирает проект для публикации.
2. Система проверяет:
    - совместимость проекта с версией ядра;
    - совместимость драйверов;
    - наличие обязательных связей;
    - лимит лицензии;
    - состояние активной встречи;
    - доступность целевого сервера.
3. Если идёт активная встреча, система показывает предупреждение.
4. При подтверждении система создаёт точку отката.
5. Новый проект публикуется атомарно.
6. Клиенты получают новую версию проекта.
7. Система выполняет post-deploy check.
8. При успехе новая версия становится active.
9. Событие фиксируется в журнале.

### Ветвления

|Условие|Реакция|
|---|---|
|Превышен лимит лицензии|Публикация блокируется, текущий runtime не меняется|
|Активная встреча|Предупреждение, требуется явное подтверждение или перенос действия|
|Ошибка публикации|Откат к предыдущему активному проекту|
|Проект опубликован, но работает некорректно|Возврат к last-known-good|
|Клиент не получил проект|Клиент показывает старое/ошибочное состояние, событие уходит в диагностику|
|Драйвер несовместим|Публикация блокируется или предлагается обновить драйвер|

### Конечное состояние

- Успех: новый проект активен.
- Неуспех: прежний проект остаётся active или восстановлен last-known-good.
- В обоих случаях есть запись в журнале.

## `LF-AUT-01` Создание и исполнение сценария помещения

**Связанные UC:** AUT-01, AUT-02, OPS-01, OPS-05, ERR-02  
**Актор:** `Integrator Engineer`, `End User`, система  
**Тип:** Runtime Flow  
**Цель:** обеспечить сценарии помещения: запуск комнаты, ВКС, переключение источника, управление в звонке, завершение.

PRD фиксирует, что сценарии должны включать последовательность команд, задержки, условия, обработку ошибок и возврат помещения в штатное состояние; типовые сценарии должны собираться без программирования, а JavaScript остаётся расширением.

### Конфигурационный поток

1. Интегратор создаёт сценарий из шаблона или вручную.
2. Добавляет команды устройствам.
3. Добавляет задержки и условия.
4. Указывает ожидаемую обратную связь.
5. Настраивает обработку ошибки:
    - повтор команды;
    - пропуск необязательного устройства;
    - останов сценария;
    - переход в деградированный режим;
    - сообщение пользователю.
6. Настраивает финальное состояние комнаты.
7. Сохраняет сценарий.
8. Тестирует сценарий до публикации.

### Runtime-поток

1. End User нажимает сценарий в клиенте.
2. Клиент отправляет запрос на сервер.
3. Сервер проверяет роль, активный проект и состояние комнаты.
4. Scenario Engine запускает последовательность.
5. Driver Runtime отправляет команды через HAL.
6. Обратная связь устройств обновляет теги.
7. Клиент показывает состояние выполнения.
8. При успехе система переводит комнату в целевое состояние.
9. При ошибке запускается error branch.

PSD уже фиксирует базовый поток управления: пользователь выбирает пресет в клиенте, сервер проверяет роль и активный проект, Scenario Engine передаёт команды в Driver Runtime, HAL управляет устройством, обратная связь возвращается в теги и клиент.

### Error branches

|Ошибка|Реакция|
|---|---|
|Устройство offline|Показать понятную ошибку пользователю, открыть инженерные детали в диагностике|
|Нет обратной связи|Повторить / ждать timeout / перейти к деградации|
|Необязательное устройство недоступно|Продолжить сценарий с предупреждением|
|Критичное устройство недоступно|Остановить сценарий или предложить частичную работоспособность|
|Ошибка JS|Изолировать ошибку, логировать, не ронять ядро|
|Сценарий не завершился|Перевести комнату в безопасное или last-known-good состояние|

## `LF-OPS-01` Маршрут типового дня комнаты

**Связанные UC:** OPS-01..07, BVC-01..04, ERR-01/07/20  
**Актор:** `End User`, система, API  
**Тип:** State Flow + Runtime Flow  
**Цель:** описать, как комната живёт в течение дня.

### Состояния комнаты

|Состояние|Описание|Доступные действия|
|---|---|---|
|`Idle / Ready`|Комната свободна и готова|Начать встречу, начать ВКС, выбрать источник|
|`Reserved / Waiting`|Есть ближайшая встреча|Показ встречи, начать по расписанию|
|`Active Session`|Встреча идёт|Переключение источника, громкость, mute, камера, layout|
|`Ending`|Завершение встречи|Сброс сценария, выключение, возврат источников|
|`Maintenance Warning`|Планируется сервисное действие|Предупреждение пользователю / IT|
|`Degraded`|Часть устройств недоступна|Продолжить с доступным оборудованием|
|`No Connection`|Клиент не видит сервер|Показ инструкции, ожидание синхронизации|
|`Safe Mode`|Система ограничена после серии сбоев|Только восстановление / диагностика|

### Типовой поток

1. Утром комната находится в `Idle / Ready`.
2. Если есть событие бронирования, система переходит в `Reserved / Waiting`.
3. Пользователь входит и запускает сценарий.
4. Система переходит в `Active Session`.
5. Во время встречи пользователь выполняет типовые действия.
6. При завершении запускается `End Session`.
7. Система возвращает оборудование в штатное состояние.
8. Комната возвращается в `Idle / Ready`.

### Ветвления

|Событие|Переход|
|---|---|
|Пользователь начинает ВКС|`Idle / Ready` → `Active Session`|
|Внешняя система передаёт команду начать встречу|`Reserved / Waiting` → `Active Session`|
|Пользователь завершает встречу|`Active Session` → `Ending` → `Idle / Ready`|
|Устройство offline|`Active Session` → `Degraded` или ошибка сценария|
|Потеря связи клиент-сервер|Клиент → `No Connection`, сервер сохраняет состояние|
|Серия неуспешных стартов|Система → `Safe Mode`|
|Сервисное действие во время встречи|Предупреждение, действие требует подтверждения|

## `LF-DRV-01` Запрос, выпуск и установка драйвера

**Связанные UC:** DRV-01, DRV-02, ERR-09  
**Актор:** `Integrator Engineer`, `Vendor Support`, `IT Admin`  
**Тип:** Integration / Release Flow  
**Цель:** добавить или обновить драйвер без релиза ядра.

PRD фиксирует независимое обновление драйверов, версионирование совместимости с ядром и описание драйвером команд, обратной связи, статусов, возможностей и параметров подключения. PSD дополнительно фиксирует driver-release-flow: запрос → подготовка нативным инструментом → стендовая проверка → Driver ID / версия / диапазон совместимости → упаковка → offline-доставка → установка без обновления ядра → проверка → каталог и журнал.

### Основной поток

1. Интегратор обнаруживает неподдержанное устройство.
2. Формирует запрос драйвера:
    - вендор;
    - модель;
    - версия прошивки;
    - протокол;
    - требуемые команды;
    - документация протокола;
    - проектный контекст.
3. Vendor Support / внутренняя команда готовит драйвер.
4. Драйвер проходит стендовую проверку.
5. Драйвер получает ID, версию и диапазон совместимости.
6. Драйвер упаковывается в offline-пакет.
7. Интегратор / IT устанавливает драйвер.
8. Система проверяет совместимость с ядром.
9. Драйвер появляется в каталоге.
10. Установка фиксируется в журнале.

### Ветвления

|Условие|Реакция|
|---|---|
|Нет протокольной документации|Запрос не принимается в SLA «1 день»|
|Драйвер несовместим с ядром|Установка блокируется|
|Установка неуспешна|Откат к предыдущей версии драйвера|
|Драйвер нестабилен|Отключение/откат драйвера, ядро не затрагивается|
|Покрытие устройства частичное|Маркируется capabilities и ограничения|

## `LF-UPD-01` Offline-обновление ядра с откатом

**Связанные UC:** UPD-01, UPD-02, ERR-08  
**Актор:** `IT Admin`  
**Тип:** System Flow + Recovery Flow  
**Цель:** безопасно обновить ядро в offline-контуре.

PRD требует offline-пакеты с проверкой целостности, rollback при неуспешном обновлении и журнал установленных обновлений. PSD задаёт продуктовый update-flow: загрузка пакета, проверка целостности, точка восстановления, установка, проверка работоспособности, фиксация версии при успехе или откат при сбое, запись в журнал и diagnostic bundle.

### Основной поток

1. IT загружает offline-пакет обновления.
2. Система показывает патчноут.
3. Система проверяет:
    - подпись;
    - целостность;
    - совместимость;
    - свободное место;
    - активную встречу;
    - наличие точки восстановления.
4. Если комната используется, система показывает предупреждение.
5. IT подтверждает установку.
6. Система создаёт точку восстановления.
7. Обновление устанавливается.
8. Система выполняет health-check.
9. При успехе версия фиксируется в журнале.
10. При сбое выполняется rollback.
11. Результат попадает в журнал и diagnostic bundle.

### Конечные состояния

|Состояние|Итог|
|---|---|
|Успех|Новая версия активна|
|Сбой до установки|Обновление не применено|
|Сбой после установки|Откат к предыдущей версии|
|Сбой отката|Переход в recovery / Safe Mode|

## `LF-MON-01` Триаж инцидента и diagnostic bundle

**Связанные UC:** MON-01, MON-02, MON-03, SUP-01, SUP-02  
**Актор:** `IT Admin`, `Support Operator`, `Vendor Support`  
**Тип:** Role Flow + Support Flow  
**Цель:** закрывать большинство типовых инцидентов первой линией без выезда и без постоянного доступа в контур.

PRD описывает monitoring/diagnostics как панель состояния, системные логи, логи оборудования/драйверов, аудит, фильтрацию и diagnostic bundle в один клик. Use Cases handoff фиксирует, что diagnostic bundle собирается локально, а вендор может изучать его без доступа в контур.

### Основной поток

1. Пользователь сообщает о проблеме или система формирует Error/Critical.
2. Support Operator открывает health dashboard.
3. Проверяет:
    - сервер;
    - клиент;
    - комнату;
    - устройства;
    - драйверы;
    - сценарии;
    - последние изменения.
4. Фильтрует логи по комнате, устройству, сценарию, времени, уровню ошибки.
5. Определяет класс проблемы:
    - пользовательская;
    - устройство offline;
    - ошибка сценария;
    - ошибка драйвера;
    - ошибка сети;
    - ошибка обновления;
    - ИБ-событие.
6. Если проблема типовая — выполняет сервисное действие.
7. Если нужна эскалация — формирует diagnostic bundle.
8. Bundle передаётся в Vendor Support без доступа в контур.
9. Vendor Support даёт рекомендацию.
10. При необходимости IT выдаёт временный сервисный доступ.

# 2.4.5 Flow, которые требуют доработки формата

## A. Safe Mode / Recovery

**Почему требует отдельного формата:** это не пользовательский flow, а state-machine. Нужны пороги, условия входа, доступные действия и выход.

**Рекомендуемый формат:** матрица состояний + таблица переходов.

|Состояние|Условие входа|Что доступно|Что запрещено|Условие выхода|Логи/аудит|
|---|---|---|---|---|---|
|Normal|Успешная загрузка|Все штатные функции|—|Ошибка/обновление/сбой|Info|
|Degraded|Часть устройств offline|Частичные сценарии|Критичные сценарии|Устройства восстановлены|Warning/Error|
|Safe Mode|Серия неуспешных стартов / невалидный проект|Диагностика, восстановление, откат|Runtime-сценарии|Успешный rollback / restore|Critical|
|Recovery|Восстановление из backup|Restore, проверка совместимости|Обычная эксплуатация|Успешное восстановление|Error/Critical|

**Нужны решения:** порог количества неуспешных стартов, перечень действий в Safe Mode, кто может вручную вывести систему из Safe Mode.

## B. Booking / VC flows

**Почему требует отдельного формата:** часть логики находится во внешних системах, а AV Control не является ни системой бронирования, ни VCS.

**Рекомендуемый формат:** swimlane `User / AV Control / External Booking / VCS`.

|Шаг|User|AV Control|Booking API|VCS|
|---|---|---|---|---|
|1|Нажимает «Начать встречу»|Проверяет событие|Возвращает текущую встречу|—|
|2|Подтверждает|Запускает сценарий|—|Готовит endpoint|
|3|Управляет звонком|Отправляет команды|—|mute/camera/layout|

**Нужны решения:** конкретные платформы ВКС и бронирования, обязательные команды MVP, поддержка брони с панели в UI.

## C. JS-расширение

**Почему требует отдельного формата:** продуктово нужно описать, где JS допустим, но контракт JS API и sandbox должны уйти в Core&API.

**Рекомендуемый формат:** decision table.

|Случай|Нативный сценарий|Expression Evaluator|JS|Вне scope|
|---|---|---|---|---|
|Преобразовать диапазон 0–255 ↔ 0–100|—|Да|Нет|Нет|
|Простое условие события|Да|Да|Нет|Нет|
|Сложная бизнес-логика|Нет|Нет|Да|Возможно|
|Драйвер типового устройства|Да|Нет|Нет|Нет|
|Низкоуровневый нестандартный протокол|Нет|Нет|Возможно|Возможно|

**Нужны решения:** объём JS в первом релизе, доступность JS на сервере/клиенте, ограничения API.

## D. API / машинные пользователи

**Почему требует отдельного формата:** L&F должен показать логику взаимодействия, но не endpoint-контракт.

**Рекомендуемый формат:** flow + таблица разрешённых действий.

|Машинный актор|Может читать|Может писать|Типовые команды|Ошибки|
|---|---|---|---|---|
|Monitoring/SIEM|health, audit, Error/Critical|Нет|—|auth/version|
|Booking/calendar|текущая встреча, статус комнаты|start/extend/end/book|meeting commands|auth/conflict|
|VCS terminal|статус ВКС|mute/camera/layout/call|VC commands|unsupported command|

**Нужны решения:** версии API, обязательность создания брони через API, перечень команд ВКС.

# 2.4.6 Вопросы к тебе

## Критичные для фиксации L&F

1. **Расписания:** после сдачи объекта кто имеет право менять расписание — только интегратор, только IT Admin или оба профиля?
2. **Safe Mode:** считаем ли Safe Mode полностью инженерным режимом, или End User должен видеть ограниченный пользовательский экран «комната временно недоступна»?
3. **Порог Safe Mode:** после скольких неуспешных стартов / падений / failed deploy система входит в Safe Mode?
4. **Частичная работоспособность:** какие устройства считаются критичными для продолжения встречи? Например: дисплей, аудио, ВКС endpoint, матрица, панель.
5. **Degraded mode:** разрешаем ли пользователю продолжать встречу при недоступности части устройств, или это решает только сценарий/интегратор?
6. **JS в первом релизе:** JS нужен только для серверной логики или также для клиентской логики?
7. **JS-граница:** что точно нельзя делать через JS в MVP?
8. **Booking:** какие системы бронирования целевые в первом релизе?
9. **ВКС:** какие ВКС-платформы и команды обязательны: start call, end call, mute, camera, layout, dial by address?
10. **Бронь с панели:** UI-бронирование свободной комнаты остаётся P2, но API должен уметь создавать бронь уже сейчас — подтверждаем?
11. **Project Tool:** какой формат выгрузки ожидается: JSON, CSV, API, файл проекта, спецификация оборудования?
12. **Project Tool auto-setup:** что должно подставляться автоматически: устройства, драйверы, адреса, сценарии, UI, комнаты?
13. **Handover:** после передачи объекта интегратор полностью теряет доступ или остаётся сервисная роль по договору?
14. **Защита IP:** нужна ли отдельная видимая маркировка «защищённый проект / защищённый шаблон»?
15. **Diagnostic bundle:** должен ли пользователь перед экспортом видеть, какие данные попадут в bundle?
16. **Vendor Support:** временный доступ в контур — обязательная возможность или optional для клиентов, которые это разрешают?
17. **Update при активной встрече:** достаточно предупреждения или нужно технически блокировать обновление до завершения встречи?
18. **Last-known-good:** кто может вручную вернуть прошлый проект — Integrator Engineer, IT Admin или оба?
19. **Эмулятор:** при истечении 20 минут активный проект снимается автоматически — нужно ли сохранять пользовательское состояние интерфейса после повторного деплоя?
20. **Клиенты/панели:** при потере связи с сервером панель только показывает «нет связи» или может продолжать отображать last-known-state?

## Вопросы к тех. лиду / Core&API

1. Какие точные системные состояния поддерживает runtime: Boot, Standard, Active, Update, Recovery, Safe, Degraded?
2. Какие операции атомарны: deploy проекта, update ядра, update драйвера, restore?
3. Какая механика watchdog: retry, restart, disable component, Safe Mode?
4. Как определяется health-check после деплоя / обновления?
5. Какой формат compatibility check для драйвера и ядра?
6. Какие действия доступны в Safe Mode?
7. Какие события уходят в audit, а какие только в system log?
8. Какой состав diagnostic bundle допустим с точки зрения ИБ?
9. Какие API-команды считаются write-командами и требуют повышенных прав?
10. Как синхронизируются несколько клиентов одной комнаты?
