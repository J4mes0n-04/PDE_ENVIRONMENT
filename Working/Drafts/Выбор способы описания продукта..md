Я бы не делал **классический CJM главным артефактом**. Для AV Control он полезен, но решает не ту задачу, которая сейчас болит.

Проблема действительно глубже: у вас уже достаточно хорошо описано **«что пользователь хочет сделать»** через JTBD/User Stories и **«как выполняется отдельный сценарий»** через Use Cases и Logic & User Flows. Но отсутствует слой между ними:

**в каком контексте пользователь попал в продукт → в каком состоянии находится система → какие пути ему доступны → куда каждый путь приводит.**

Именно этот слой сейчас надо добавить.

## 1. Где образовался разрыв в текущей документации

Сейчас цепочка примерно такая:

**JTBD → требования → Use Case → Flow → будущий UI**

Но между JTBD и Use Case фактически отсутствует **end-to-end пользовательский путь**.

Например, документация уже отдельно содержит:

- `ADM-01` — первое включение и создание администратора;
- `UPD-04` — восстановление/замена контроллера из backup;
- `PRJ-09` — перенос проекта между контроллерами;
- `PRJ-14` — handover;
- `PRJ-15` — вывод объекта;
- отдельные потоки мониторинга, Safe Mode, обновлений и т. д.

Logic & User Flows при этом уже очень хорошо описывает состояния сущностей, режимы контроллера и локальные потоки. Например, отдельно существуют Boot/Normal/Safe, состояния проекта, лицензии, оборудования и т. д.

Но нигде нет вопроса верхнего уровня:

> Пользователь открыл IP-адрес контроллера. Что теперь?

Текущий `ADM-01` отвечает только на один вариант: **контроллер новый → создать первого администратора**.

`UPD-04` предполагает уже совершенно другой контекст: у пользователя есть backup и он выполняет восстановление.

А ваше новое «масштабирование переговорки» вообще семантически не является восстановлением: при restore мы хотим получить **тот же контроллер**, а при scale — **новый экземпляр на основе существующего**.

Вот это и есть настоящий blind spot.

Причём на командной синхронизации 29 июля уже было зафиксировано правильное направление: UX должен строиться **«по пути пользователя, Jobs to be Done, без лишних страниц»**, а веб-интерфейс контроллера был первым приоритетом.

# 2. Какие методологии здесь вообще можно применить

|Метод|Что показывает хорошо|Что показывает плохо|Для AV Control|
|---|---|---|---|
|**Classic CJM**|Цель, действия, touchpoints, боли, ожидания, эмоции|Системные состояния, сложные развилки, recovery|★★★☆☆|
|**User Journey Map**|Путь пользователя от контекста к результату|Детальную механику каждого экрана|★★★★★|
|**Experience Map**|Полный жизненный цикл независимо от конкретной функции|Может стать слишком абстрактной|★★★★★|
|**User Story Map**|Backbone продукта, приоритизацию, MVP/release slicing|Не отвечает, какие экраны нужны и почему|★★★☆☆|
|**Task Flow / User Flow**|Конкретные действия, ветвления, экраны|Не даёт обзора всего жизненного цикла|★★★★★, но уровнем ниже|
|**State Machine / State Map**|Состояния системы и допустимые переходы|Не показывает намерения пользователя|★★★★★ как второй слой|
|**Service Blueprint**|Пользователь + UI + backend + процессы поддержки|Очень тяжёлый для систематической проработки всего продукта|★★★☆☆|
|**BPMN**|Сложные процессы нескольких участников/систем|UX и структуру интерфейса|★★☆☆☆ как локальный инструмент|

Поэтому выбор «CJM или User Flow» здесь ложный.

Вам нужны **оба уровня, но для разных задач**.

# 3. Что я рекомендую

Я бы ввёл новый артефакт:

# **AV Control · UX Lifecycle & Journey Map**

Не классический маркетинговый CJM с графиком «счастлив/грустен», а **карта жизненного цикла продукта с пользовательскими путями и состояниями системы**.

Она должна занять место:

То есть она **не заменяет ни один существующий документ**.

Это как раз позволит обнаруживать ошибки вроде Welcome Page **до начала дизайна**.

# 4. Почему именно такой формат лучше CJM

У AV Control есть несколько особенностей.

Во-первых, продукт **stateful**. Один и тот же пользователь, открыв один и тот же адрес, может попасть в принципиально разные ситуации:

`Uninitialized`

`Initialized / no project`

`Active`

`Degraded`

`Safe Mode`

`Restore`

`Update in progress`

и т. д.

Во-вторых, продукт **многоролевой**. Integrator Engineer, IT Admin, Support Operator и Security Auditor заходят в один Admin Web UI, но решают разные задачи и обладают разными правами. Это уже закреплено в продуктовой модели.

В-третьих, это не SaaS, где почти каждый пользователь проходит примерно:

`Sign up → onboarding → dashboard → use`.

У вас пользователь может впервые встретиться с AV Control:

- при установке нового контроллера;
- после аварии;
- при замене контроллера;
- при масштабировании объекта;
- при передаче объекта от интегратора IT;
- когда его вызвали расследовать инцидент.

Поэтому **одна линейная CJM здесь просто начнёт лгать**.

# 5. Правильная структура: три уровня

Я бы сделал три связанных уровня, но главным артефактом оставил первый.

## Уровень 1. Lifecycle Map — карта всего продукта

Здесь никаких кнопок и полей.

Только крупные этапы существования системы:

|Этап|Смысл|
|---|---|
|0. Получение доступа|Пользователь впервые открывает контроллер|
|1. Bootstrap / Provisioning|Определяем, что это за ввод в эксплуатацию|
|2. Initial Setup|Сеть, время, доступ, безопасность|
|3. Configuration|Проект, оборудование, сценарии, UI|
|4. Validation|Preflight, тестирование|
|5. Deployment / Commissioning|Публикация, проверка помещения|
|6. Handover|Передача заказчику|
|7. Operation|Штатная эксплуатация|
|8. Maintenance|Мониторинг, драйверы, обновления|
|9. Change / Scale|Новые помещения, изменение конфигурации|
|10. Recovery|Backup, restore, rollback, Safe Mode|
|11. Decommission|Очистка/вывод контроллера|

Это фактически **скелет продукта**.

А существующие Use Cases уже раскладываются по нему.

Сразу становится видно, например, что ваши текущие категории `Настройка / Эксплуатация / Обслуживание / Аварии` полезны для классификации UC, но слишком крупные для проектирования интерфейса.

# 7. Уровень 3. User Flow

Только после того как Journey утверждён, детализация конкретной части превращается в User Flow:

`Page → Action → Decision → Page → Error → Success`.

Здесь уже появляются:

- конкретные страницы;
- wizard steps;
- модальные окна;
- redirect;
- empty states;
- error states;
- disabled states;
- back/cancel;
- confirmation.

У вас `Logic & User Flows` частично делает именно это, но преимущественно с точки зрения **поведения продукта**, а не полной навигационной архитектуры Admin Web UI. Это хороший downstream-документ, его не надо выбрасывать.

# 8. На вашем примере сразу видно, как это работает

Сегодня логика могла подразумеваться такой:

`Открываю контроллер → если первый запуск → Create admin`

Но Journey заставляет начать на шаг раньше:

**Пользователь открыл новый/неинициализированный контроллер. Что он хочет сделать с этим физическим устройством?**

И появляется:

```
Controller detected
        │
        ▼
   Controller setup
        │
        ├── Set up as new
        │
        ├── Restore controller
        │
        └── Set up from existing room
```

Это не три функции на одной странице.

Это **три разных пользовательских намерения**.

### New

`Welcome → Create administrator → Initial settings → Project/configuration → Preflight → Deploy → Ready`

Это соответствует существующему `ADM-01`, но теперь мы понимаем, **почему ADM-01 вообще появляется**.

### Restore

`Welcome → Restore → Select backup → Validate → Apply → Restart/check → Ready`

Но здесь Journey моментально обнаруживает новый продуктовый вопрос, которого текущий Use Case фактически не решает:

**если пользователь ещё не создал администратора, кто имеет право восстановить backup?**

Сейчас `ADM-01` предполагает:

`сначала создать admin`.

А `UPD-04` предполагает уже существующего IT/Integrator, имеющего права на restore.

Если restore доступен непосредственно с Welcome Page, появляется **bootstrap security problem**.

Это именно тот класс проблемы, который отдельные User Stories почти никогда не обнаруживают.

### Scale

И третий путь:

`Welcome → Set up from existing room → Import source → Apply reusable data → Enter controller-specific data → Validate → Deploy → Ready`

И здесь возникает ещё один важный продуктовый объект:

**правила наследования данных при клонировании.**

Для каждого типа данных должно быть определено:

|Политика|Пример|
|---|---|
|Copy|сценарий|
|Copy + allow edit|состав проекта|
|Ask again|адрес конкретного устройства|
|Generate new|идентификатор контроллера|
|Reset|runtime-состояние|
|Do not copy|диагностические данные|

То есть одна проработка Journey внезапно порождает требования не только к UI, но и к **Data Schema, backup format и проектной модели**.

Это хороший признак правильно выбранного уровня анализа.

# 9. Классический CJM я бы всё-таки оставил

Но для другого.

CJM особенно полезен там, где нужно исследовать:

**что пользователь думает, чего боится, где теряет время и какие workaround использует.**

Например, для интегратора:

`получил проект → подготовил до объекта → приехал → ПНР → сдача → поддержка → масштабирование`.

Это отлично ложится на стратегическую цель проекта: интегратор должен зарабатывать на тиражировании, снижать зависимость от senior-инженеров и запускать типовое помещение быстро.

Там я бы добавлял классические CJM-поля:

`Goal / Action / Tool / Pain / Workaround / Expectation / Time / Opportunity`.

И уже проводил исследования с реальными интеграторами.

Но **не надо пытаться через такой CJM проектировать все страницы Admin Web UI**.

---

# 10. Самая важная вещь: строить карту не по модулям

Это ловушка.

Сейчас Use Cases сознательно организованы по PRD-модулям: PRJ, AUT, DRV, ADM, SEC, MON, UPD и т. д. Это хорошо для проверки покрытия требований.

Но пользователь никогда не думает:

> Теперь я выполню M-SEC, потом M-ADM, потом M-UPD.

Он думает:

> Я устанавливаю новый контроллер.

И один такой Journey пересекает:

`ADM → SEC → LIC → PRJ → DRV → MON`.

Именно поэтому **Journey должен быть поперёк модулей**.

Это, на мой взгляд, главный методологический вывод.

# 11. Какую детализацию выбрать

Не надо описывать на Journey уровне каждое нажатие. Иначе вы просто второй раз напишете Use Case Specification.

Правило хорошего уровня детализации:

**один шаг Journey = изменение намерения пользователя, контекста или значимого состояния системы.**

Например:

`Выбрать способ инициализации` — Journey step.

`Загрузить backup` — Journey step.

`Система проверяет совместимость` — Journey step.

Но:

`нажать Browse → выбрать файл → нажать Open` — уже User Flow/UI specification.

Для AV Control я бы ориентировался примерно на **5–15 шагов на Journey**. Если получается 30–40 — вы ушли слишком глубоко.

# 12. Какие Journeys я бы проработал первыми

В первую очередь не все существующие User Stories, а **входные точки и переходы жизненного цикла**, потому что именно там выше риск пропущенных интерфейсов:

1. **Первый доступ к контроллеру:** New / Restore / Scale.
2. **Создание и первый деплой нового проекта.**
3. **Повторное помещение из существующего.**
4. **Ввод панели/клиента в эксплуатацию.**
5. **Передача объекта Integrator → IT.**
6. **Обычная эксплуатация IT после сдачи.**
7. **Инцидент → диагностика → исправление → эскалация.**
8. **Обновление контроллера.**
9. **Аварийная замена контроллера.**
10. **Safe Mode / recovery.**
11. **Изменение работающего проекта.**
12. **Вывод контроллера из эксплуатации.**

Это единственный список, который я бы сейчас сделал достаточно полным. Остальные сценарии можно потом добавлять по мере обнаружения.

# 13. Ещё один артефакт, который сильно поможет дизайнеру

После построения Journey я бы автоматически получал **Screen × State Matrix**.

Например:

|Surface|Uninitialized|Normal / no project|Active|Degraded|Safe|
|---|---|---|---|---|---|
|Welcome / Provisioning|✓|—|—|—|—|
|Login|—|✓|✓|✓|✓|
|Controller overview|—|✓|✓|✓|✓|
|Project|—|✓|✓|✓|read/blocked|
|Monitoring|—|✓|✓|✓|✓|
|Restore|✓?|✓|✓|✓|✓|
|Update|—|✓|✓|✓|✓|

Знак `?` здесь чрезвычайно ценен.

Он означает не «дизайнер забыл страницу», а:

> У продукта ещё нет решения.

Для вашего Welcome/Restore это именно такой случай.

# 14. Как это связать с тестированием гипотез

Journey не должен сразу превращаться в «истину».

Помечайте каждый важный переход:

**C — confirmed:** прямо следует из требования/реального поведения.

**H — hypothesis:** продуктовая гипотеза.

**V — validation required:** надо проверить на пользователе.

У вас этот подход уже используется в PRD для требований, поэтому я бы не вводил новую систему обозначений.

Например:

`После первого входа пользователь хочет сразу выбрать New / Restore / Scale` — **H/V**.

Проверить можно дешёвым кликабельным прототипом на 5–8 опытных интеграторах:

показываем новый контроллер и даём задачу:

> «Вы устанавливаете 20-ю переговорку, первые 19 уже работают. Что будете делать?»

Не спрашиваем «понятна ли кнопка Scale».

Смотрим, **какой путь человек ожидает найти сам**.

## Мой выбор

Для AV Control я бы выбрал **не CJM, а гибрид `Lifecycle Experience Map + User Journey Map` как основной продуктовый UX-артефакт**.

А под ним использовал бы существующие Use Cases и User Flows.

Это решает главное противоречие: вам нужна одновременно **картина всего продукта**, чтобы ничего не пропустить, и **достаточная детализация**, чтобы понять, какие интерфейсы нужны. Один огромный CJM будет слишком расплывчатым, а сотни User Flows не дадут увидеть белые пятна между сценариями.

И ваш кейс с Welcome Page — практически идеальное доказательство: проблема была не в том, что недостаточно подробно описан `ADM-01`. Проблема в том, что **не существовало Journey «контроллер попал в руки пользователя»**, внутри которого `ADM-01` оказался бы лишь одной из трёх веток.
