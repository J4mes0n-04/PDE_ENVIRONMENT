## 1. Что называют «PWA‑оболочкой»

Термин употребляется в двух разных смыслах — их полезно разделять, потому что решения из них не пересекаются.

|Значение|Что это|Где встречается|
|---|---|---|
|**A. PWA как обёртка приложения** (progressive web app — «прогрессивное веб‑приложение»)|Набор метаданных и фонового скрипта, которые превращают обычный веб‑сайт в устанавливаемое приложение: собственная иконка, запуск без адресной строки браузера, работа офлайн|Обычно имеется в виду, когда говорят «завернуть UI в PWA»|
|**B. App Shell** (архитектурный паттерн «оболочка приложения»)|Разделение интерфейса на статический каркас (навигация, шапка, layout), закэшированный намертво, и динамический контент, подгружаемый отдельно|Про производительность первого запуска, не про установку|

Дальше — про значение A, с упоминанием B там, где оно работает внутри.

## 2. Как это работает технически

|Компонент|Роль|Ключевые детали|
|---|---|---|
|**Web App Manifest** (`manifest.json`)|Декларация «я приложение»|`name`, `icons`, `start_url`, `scope`, `display` (`standalone` / `fullscreen` / `minimal-ui`), `theme_color`, `orientation`|
|**Service Worker** (сервис‑воркер — фоновый скрипт‑посредник)|Перехватывает все сетевые запросы страницы и решает, отдать из кэша или из сети|Жизненный цикл `install → activate → fetch`; работает в отдельном потоке, без доступа к DOM|
|**Cache Storage API**|Хранилище ответов на запросы (HTML, JS, CSS, шрифты, изображения)|Управляется вручную из воркера; версионируется через имена кэшей|
|**IndexedDB**|Хранилище структурированных данных приложения|Для состояния, очередей операций, локальных справочников|
|**Secure context** (защищённый контекст)|Условие работы SW|Только HTTPS либо `localhost`/`127.0.0.1`. Самоподписанный сертификат — только если он добавлен в доверенные в ОС/браузере|

**Стратегии кэширования**, которые задаёт воркер:

|Стратегия|Поведение|Для чего|
|---|---|---|
|Cache‑first|Сначала кэш, сеть только при промахе|Статика оболочки, шрифты, иконки|
|Network‑first|Сначала сеть, кэш как запасной вариант|Данные, которые должны быть свежими|
|Stale‑while‑revalidate|Мгновенно из кэша + фоновое обновление|Списки, справочники, «почти‑свежие» данные|
|Network‑only|Кэш не используется|Команды на запись, действия|

**Модель обновления** — самая недооценённая часть. Браузер сравнивает байты нового `sw.js` со старым; при отличии новый воркер устанавливается, но остаётся в состоянии `waiting`, пока не закрыты все вкладки старой версии. Отсюда классический эффект «пользователь неделю сидит на старой версии». Обходится через `skipWaiting()` + `clients.claim()` и явный UI‑баннер «доступна новая версия, перезагрузить».

## 3. Плюсы и минусы

|Плюсы|Минусы|
|---|---|
|Одна кодовая база на все платформы, один цикл сборки|Обязателен HTTPS с доверенным сертификатом — в закрытом контуре это отдельная задача (внутренний УЦ или сертификат в доверенных на каждом клиенте)|
|Установка без магазинов приложений и без подписи дистрибутива|Пользователь ставит вручную; на iOS — только через меню «Поделиться → На экран "Домой"», программного вызова установки нет|
|Работа офлайн и мгновенный старт после первого запуска|Кэш может быть вытеснен ОС при нехватке места, если не запрошен `navigator.storage.persist()`|
|Обновление доставляется мгновенно, без переустановки|Модель обновления неявная; нужен продуманный UX принудительного обновления|
|Полноэкранный режим без хрома браузера — визуально «как приложение»|Нет произвольных TCP/UDP‑сокетов, нет multicast‑обнаружения устройств, нет доступа к произвольным портам|
|Малый вес, нет тяжёлого рантайма|Фоновое исполнение не гарантировано; ОС усыпляет воркер|
|Управляемо централизованно (обновил сервер — обновились все)|Различия платформ: половина «продвинутых» API — только Chromium|

## 4. Альтернативные варианты

|Вариант|Суть|Когда осмысленно|
|---|---|---|
|**Обычная вкладка браузера**|Ничего не оборачиваем|Админ‑интерфейс на десктопе, где полноэкранность и офлайн не критичны|
|**Kiosk‑режим браузера**|Chromium с `--kiosk`, автозапуск, скрытый интерфейс|Стационарная панель на фиксированном железе под контролем интегратора|
|**WebView‑обёртка** (Capacitor, Cordova, Tauri Mobile)|Тот же веб‑код внутри нативного контейнера|Нужен доступ к железу/сети, недоступный из браузера; нужна установка как APK|
|**Electron / Tauri (desktop)**|Веб‑UI + полноценный нативный процесс рядом|Десктопный клиент с доступом к файлам, сокетам, портам; Tauri заметно легче Electron|
|**Полностью нативное приложение**|Отдельная кодовая база на платформу|Максимум производительности, жёсткие требования к отклику, глубокая работа с железом|
|**Тонкий клиент на встроенном железе**|Прошивка панели рендерит UI сама|Когда контроллируется весь стек «железо + прошивка»|

Практическая развилка: **если клиенту нужно самому открывать TCP‑соединения к устройствам, PWA отпадает сразу** — вся работа с протоколами должна уйти на серверную сторону, а клиент общается с сервером по WebSocket/HTTP.

## 5. Возможности и ограничения по API

|Возможность|Статус|Оговорки|
|---|---|---|
|Офлайн‑работа, кэш ресурсов|Полноценно|Ограничена квотой хранилища|
|Локальное хранилище данных (IndexedDB)|Полноценно|Десятки–сотни МБ типично; квота зависит от свободного места|
|Полноэкранный режим, свои иконка и splash|Полноценно|На iOS splash требует отдельной разметки|
|Push‑уведомления|Условно|Требуют внешнего push‑сервиса (FCM/APNs) → **неприменимо в изолированном контуре**|
|Фоновая синхронизация (Background Sync)|Только Chromium|Ненадёжна, ОС может отложить надолго|
|Камера, микрофон, геолокация|Есть|По разрешению пользователя, только в защищённом контексте|
|WebSerial / WebUSB / WebBluetooth|Только Chromium|Требуют явного жеста пользователя и выбора устройства в диалоге; в Safari нет|
|**Произвольные TCP/UDP‑сокеты**|**Нет**|Есть только HTTP(S), WebSocket, WebRTC|
|**Обнаружение устройств в сети (mDNS/SSDP/broadcast)**|**Нет**|Только через серверную сторону|
|Доступ к файловой системе|File System Access API, только Chromium|В Safari — ограниченный обмен файлами|
|Автозапуск при старте ОС|Нет штатного механизма|Решается настройками ОС/киоска, а не самим PWA|
|Работа без сети с самого первого запуска|Нет|Первая загрузка обязана пройти по сети|

## 6. Что стоит проверить, если рассматривать это для закрытого контура

Три вопроса, которые определяют применимость сильнее всех остальных:

1. **Сертификаты.** Без доверенного HTTPS сервис‑воркер не зарегистрируется, и весь офлайн исчезает. Нужен либо внутренний удостоверяющий центр, либо процедура установки сертификата на каждое клиентское устройство — это операционная нагрузка на интегратора, а не разовая настройка.
2. **Первичная установка.** Устройство должно хотя бы один раз достучаться до контроллера по сети. Сценарий «привезли планшет, он ни разу не видел сервер» не работает.
3. **Что именно должно жить офлайн.** Оболочка и статика — да. Актуальное состояние устройств — по определению нет, оно приходит из сети. Значит нужен явный дизайн состояния «данные устарели, соединение потеряно», а не просто белый экран.

Если нужно, могу отдельно разобрать применимость под конкретный сценарий — админ‑веб контроллера или клиентская панель. Требования у них расходятся достаточно сильно, чтобы вывод получился разный.



## 1. Что это по сути

**SPA** (single page application — одностраничное приложение): сервер отдаёт один HTML‑каркас и JS‑бандл; дальше вся навигация происходит внутри страницы без перезагрузки, а данные подтягиваются по API. Vue отвечает за компонентную модель и реактивность — при изменении данных перерисовывается только затронутая часть DOM.

Базовая единица кода — **SFC** (single file component — однофайловый компонент, `.vue`): в одном файле разметка, логика и стили компонента.

## 2. Из каких слоёв обычно состоит

|Слой|Что решает|Типичный выбор|
|---|---|---|
|Сборщик|dev‑сервер, горячая перезагрузка, продакшн‑бандл|Vite|
|Язык|типизация контрактов с API|TypeScript|
|Ядро|компоненты, реактивность|Vue 3, Composition API|
|Роутинг|маршруты, вложенные layout, guards (защита маршрутов)|Vue Router|
|Состояние|общее состояние между экранами|Pinia|
|Транспорт|запросы и подписки|fetch/axios + нативный WebSocket|
|Кэш серверных данных|инвалидация, повторные запросы, фоновое обновление|TanStack Query (опционально)|
|UI‑слой|готовые компоненты либо своя библиотека|PrimeVue, Naive UI, Element Plus, Vuetify — или собственные компоненты на дизайн‑токенах|
|Таблицы|виртуализация, сортировка, фильтры|TanStack Table, AG Grid|
|Формы|валидация и схемы|VeeValidate + Zod|
|Локализация|вынос строк|vue‑i18n|
|Тесты|юнит и e2e|Vitest + Vue Test Utils, Playwright|

Для админ‑интерфейса с большим числом таблиц и форм два слоя решают больше всех остальных: **таблицы** и **UI‑библиотека**. Именно они определяют, сколько кода придётся писать руками и насколько плотно получится лечь на собственные токены дизайна.

## 3. Варианты компоновки — от простого к сложному

|Уровень|Что представляет собой|Когда осмысленно|
|---|---|---|
|**1. Без сборки**|`vue.global.js` подключён файлом, компоненты в объектах|Прототип, встраиваемый виджет, демо|
|**2. Vite‑SPA**|Полноценный проект, сборка в статический `dist/`, раздаётся любым сервером или встраивается в бэкенд|Основной вариант для админки за логином|
|**3. Nuxt в режиме SPA/SSG**|Каркас поверх Vue: файловый роутинг, соглашения о структуре, автоимпорты|Когда нужна дисциплина структуры; SSR за авторизацией обычно избыточен|
|**4. Монорепозиторий**|Несколько приложений + общий пакет UI‑компонентов и токенов|Когда админ‑веб и панель делят одну дизайн‑систему|

## 4. Что происходит в рантайме

`index.html` → загрузка бандла → `createApp()` → Router разбирает URL → монтируется компонент маршрута → запросы к API → реактивное обновление. Маршруты подключаются лениво (`() => import('...')`), чтобы первый бандл содержал только каркас и точку входа, а экраны догружались по требованию.

Отсюда типичная структура проекта:

```
src/
  app/          точка входа, глобальные провайдеры, тема
  router/       маршруты, guards
  stores/       Pinia — сессия, права, справочники
  api/          клиент, типы DTO, обработка ошибок
  shared/       примитивы UI, композаблы, утилиты
  widgets/      составные блоки (таблица-журнал, панель деталей)
  pages/        экраны, по одному на маршрут
```

## 5. Плюсы и минусы

|Плюсы|Минусы|
|---|---|
|Богатый интерфейс без перезагрузок, мгновенные переходы между экранами|Первая загрузка тяжелее, чем у серверного рендеринга|
|Чёткая граница «клиент ↔ API»: бэкенд не занимается разметкой|Состояние живёт в памяти и теряется при обновлении страницы, если не сохранять явно|
|Реактивность Vue проще в чтении, чем ручные обновления DOM|Нужна дисциплина: без правил слои расползаются, логика оседает в компонентах|
|Готовая база для офлайн‑режима и установки как приложения|Обработка потери соединения — отдельная работа, «само» не появляется|
|Один статический артефакт сборки, простой деплой|Требуется явная стратегия аутентификации и обновления токенов на клиенте|
|Экосистема зрелая, порог входа ниже, чем у альтернатив|Отладка ошибок реактивности требует привычки|

## 6. Что критично именно в закрытом контуре

Четыре пункта, которые ломаются чаще всего, если о них не подумать заранее:

|Пункт|Требование|
|---|---|
|**Никаких CDN**|Все зависимости, шрифты и иконки — в репозитории и в бандле. Один внешний `<link>` на шрифт даёт секундные таймауты на каждом запуске в изолированной сети|
|**Сборка без сети**|Зафиксированный `lockfile` + внутреннее зеркало пакетов, иначе сборка невоспроизводима|
|**Единый origin**|Раздача статики тем же сервером, что отдаёт API, снимает вопрос CORS и упрощает сертификат|
|**Явный статус соединения**|В офлайн‑первом продукте отсутствие связи с контроллером — штатное состояние экрана, а не ошибка. Нужен видимый индикатор «данные от HH:MM» и правило, какие действия блокируются|

## 7. Связь с предыдущим вопросом

SPA — естественная основа для PWA: каркас приложения (навигация, layout, стили) как раз и есть тот самый **app shell**, который кэшируется намертво, а данные ходят отдельно. Технически это добавление одного плагина сборки (`vite-plugin-pwa`) плюс продуманная стратегия кэша — то есть решение «делать ли PWA» можно принимать позже, уже имея работающий SPA, и оно не влияет на выбор стека сейчас.

Если полезно, могу разложить конкретный вариант стека под админ‑веб контроллера — с обоснованием выбора UI‑библиотеки против собственных компонентов на ваших токенах. Это развилка, которая дороже всего обходится при позднем пересмотре.
