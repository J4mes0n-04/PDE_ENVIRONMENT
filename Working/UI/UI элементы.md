### Общие идеи.

### MVP
* стили и классы для проекта по умолчанию (like a css)
* классы для элементов (like a css)
* инлайн стили для каждого элемента (legacy i3Pro)
* Разделение отображаемого и отдаваемого значения с внутренней конвертацией, например для слайдеров: отдают 0..255, а отображают 0..100 -  наивное решение без использование преобразования данны для таких простых решений (как реализовано в OpenAVC)
* Стандартные страницы для:
	* оверлеев -заглушки поверх страниц при срабатывании событий
	* заглушки для режима ожидания

### Релиз

* Запрет на изменения типа элемента после создания (избавляемся от проблем сброса свойств или остаточного воздействия скрытых свойств - их не видно. а они влияют на работу элемента)
* разные skeleton при добавлении элемента в workspace - сейчас это одинаковые прямоугольники, что мешает визуально различать элементы при работе в рабочей области.
* свойства делить по блокам, с возможностью сворачивать: текст. изображение, границы, заливка и т.д. - референс - Figma 
* Умные направляющие в рабочей области - динамически проявляющие направляющие на основе положения соседних элементов, расстояние между ними. референс - Figma
* Возможность выравнивать относительно элемента. а не только границ выделения.
* Логическая группировка с отображением групп  в дереве, это же идея- основа пресетов. Сейчас в прошке никак не отображаются группы и для них нет индивидуальной конфигурации: общих стилей, ипорта/*экспорта и т.д
* Использование шрифтовых иконок.
### На будущее

* состояния: от/off и промежуточные(например waiting), например для ожидания значения или блокировки  элемента, пока нет значения или других условий
* [Спорно]Условия отображения элемента - условный if/else (как реализовано в OpenAVC) - вопрос к реализации, базовый набор реализуется через программинг
* Гибкое форматирование текста в любом блоке, с элементами разметки (курсив, выделение жирным и т.д для отдельных символов, а не блока целиком)
* но думаем над отображением различных динамических значений в рамках одного текста, а не только $v - value самого элемента, необходимо проработка кейса, пока на ум только уведомления.
* создание полигональных, круглых элементов - отличных от прямоугольных нативным способом.

### Основные элементы.

**Страница**  - основной элемент, используется как холст, всегда равен размеру проекта, всегда на заднем плане, не может быть скрыт - только замещен другой страницей.
**Попап** - всплывающий элемент вне зависимости от страницы, помимо прочего имеет z-ocь, для определения наложений
**Всплывающие уведомления**  - не требуют действий от пользователя, используются для информирования пользователя о события. в отличии от попапов имеют механизм само закрытия по таймеру, принципиальное отличие от попапов - не привязаны к страницам и всегда на переднем фоне, не могут отображаться поверх друг друга, даже с частичным перекрытием, расположение и стиль выбирает интегратор.

### Элементы управления.

**Кнопка** - стандартный элемент, копируем функционал из i3pro с минимальными изменениями
**Лейбл** - элемент для  отображения данных, наследуем из i3Pro, служит основой отображения текста, изображений, иконок.
**Триггерная кнопка** - кнопка с 2 состояниями, для каждого свой стиль и отправляемое значение, значение не ограничении типом данных Integer - используем integer, string, boolean, float/ За основу берем i3Pro со всеми соременными доработками.

**Кнопка Вверх/вниз** - отправляет не установленное значение, а измененная на указанный шаг, копируем из i3Pro, важно для управления звуком

**Уровень** - за основу берем элемент i3Pro , но с существенными доработками:
* Отдельные шкалы для отображаемого значения и реального (например отображаем 0..100%, отдаем значении 0.255), почему именно наивное решение, а не Evaluator? частый кейс от света до звука, построение динамических шкал
* Нативное отображение шкалы (не В mvp)
* Нативная реализация динамических шкал (для управления звуком) В MVP ИЛИ версии 1
* ~~Hазделение на 2 типа поведения - slider, fader~~ Исключено, т.е фейдер - это фактически вертикальный слайдер с логарифимической шкалой
* Авто остановка движения (щелчок), при движении ползунка на определенных порогах (за рамками версии 1)

**Круговой уровень** - аналогично обычному уровню, но по кругу, наследуем из i3Pro, пока с простым функционалом.

**Джойстик** - наследуем из I3Pro, применимо к выбору цвета и управлению камерами, оценить текущую реализацию нативным способом получать цвет, без скриптов (сложность в передачи с джойстика сразу нескольких] команд R- G- B- W- A)

**Поле для ввода текста** - клаccиxеский input& наследуем из i3Pro, но с доработками и правилами форматирования текста, с возможностью нативного выбора. с возможностью выбора какую системную клавиатуру вызывать (полную, только цифровую, для ввода пинкодов и т.д)
**Область  для ввода текста** многострочное поле для ввода текст с переносом строк. 
**Virtual key** - эмуляция ввода с клавиатуры для текстовых полей (изучить можно ли в MVP заменить стандартной клавиатурой Android + нужна оценка как будет работать в браузере при вводе с клавиатуре)  

**Списки** - тут нужно полное переосмысление, в общих чертах пока видео - как элемент, который динамически заполняется данными по шаблону. Кейсы - Работа с системой бронирования, которая может отдавать списки и статусы помещений.


#### Нет сейчас в Прошке
**Выпадающий список** - список из нескольких преданстроенных или заполняемых динамически элементов

**Нативные часы**, -  переосмыслить классические часы, с возможностью обратного отсчета без скриптов, быстрым выбором формата отображаемой даты, с автоматической привязкой к системному времени устройства. Можно обыграть как единый системный токен взамен множеству разных системных токенов с разным форматом времени. Но остается открытый вопрос таймера обратного отсчета (Кейс - сколько осталось времени для текущей сессии в переговорке)
**Нативный  элемент выбора даты**  - календарь.
**Нативный элемент выбора времени** - часы, минуты, секунды.
**Выбор цвета из палитры** - нативный элемент без JS костылей, требует отдельной проработки (за рамками MVP)

### Программинг

Программинг прописывается отдельной задачй, вкртаце: 

Привязка действий на клиенте к событиям элементов. Реализуем programming(для графичеких элементов) и key programming (для тегов).

* Переосмысляем и добавляем условия через IF (like a KRAMER), например при привязке к triiger button, в зависимости от нового состояния можем показать разные попапы, или при изменения значения уровня при преодолении порога отображаем попап. 
* Аналогично для тегов, при изменении значений .
* Программинг реализуется отдельно для каждого интерфейса
