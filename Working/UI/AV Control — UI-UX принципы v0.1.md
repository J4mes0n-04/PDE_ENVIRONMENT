# AV Control — Принципы UI/UX (черновик v0.1)

> **Статус.** Черновик для итеративной доработки. У продукта пока нет зафиксированного визуального видения — этот документ фиксирует отправную рамку, дальше дорабатывается правками поверх этой версии.
>
> **Назначение.** Единый источник правды по визуальным и поведенческим принципам интерфейса AV Control. Компонентные спецификации и будущие макеты должны ссылаться на пункты этого документа по ID (**UXP-\***), не дублируя формулировки — по аналогии с тем, как компоненты уже ссылаются на INV-\*/DP-\* конкурентного аудита.
>
> **Вне области документа.** Конкретные экраны, пиксельные макеты, конкретная библиотека компонентов — выводятся из этих принципов позже (см. §5), здесь не фиксируются.

---

## 0. Три поверхности

Продукт содержит три разных дизайн-объекта с разной аудиторией и разным весом наследия. Дальше по документу каждый принцип помечен, к какой поверхности относится: **К** (веб-конфигуратор), **М** (системное меню веб-клиента), **П** (дефолтный стиль элементов панели), **∀** (все три).

| Поверхность | Кто пользователь | Вес наследия | Ориентир по тону |
|---|---|---|---|
| **К — веб-конфигуратор** (управление и конфигурация проекта) | Интеграторы — те же, кто работал в iRidi Studio | Высокий: это их ежедневный рабочий инструмент | Плотный профессиональный редактор (тип Figma / VS Code / Q-SYS Designer) |
| **М — системное меню веб-клиента** | Инсталлятор/IT на объекте, служебный экран | Низкий: встроенная системная утилита | Предельно утилитарно, надёжно, без декора (тип system settings панелей Crestron TSW / Extron TouchLink) |
| **П — дефолтный стиль элементов панели** | Участник встречи в переговорной | Средний: узнаваем по логике, не обязан копировать внешний вид | Спокойно, читаемо на расстоянии, низкая когнитивная нагрузка |

Три поверхности используют **один набор дизайн-токенов** (token — атомарное значение стиля: цвет, отступ, радиус, типографика), но **разную плотность и грамматику** — компромисс "один язык на всё" не подходит ни одной из них идеально.

## 1. Базовый принцип: наследие — это workflow, а не шкурка

Разбор аудита наследия iRidi показывает: почти все пункты "сохранить" касаются **структуры и поведения** (дерево проекта, drag&drop, инспектор свойств, модель состояний, hotkeys), а не внешнего вида. Интегратор не переучивается, если:

1. вещи находятся **там же логически** (дерево слева, инспектор справа);
2. **действия делаются тем же способом** (перетащил тег — привязал, а не через модальное окно с полями);
3. **термины те же**.

Визуальная "шкурка" при этом может и должна меняться свободно — устаревший вид не создаёт узнаваемости, он создаёт ощущение устаревшего продукта. Принцип: **recognition, а не replication** — пользователь должен думать "это тот же принцип работы", а не "это буквально та же кнопка".

## 4. Как выбираем стиль дальше (процесс)

1. **Функциональный бриф прежде эстетики.** Зафиксировать 5–6 прилагательных, которые продукт обязан внушать (например: доверенный / enterprise-grade / offline-secure / плотный, но не перегруженный / профессиональный инструмент, не игрушка) — каждое решение по стилю проверяется вопросом «усиливает это ощущение или нет».
2. **Токены прежде компонентов.** Сначала цветовая система (с привязкой к семантике статусов DP-2), типографика, шкала отступов, шкала радиусов, принципы motion (анимация переходов) — независимо от конкретных компонентов. Компоненты собираются из токенов, а не придумываются по отдельности.
3. **Деконструкция референсов, не копирование.** 5–8 инструментов с сильным, не шаблонным характером (часть из AV-домена: Q-SYS Designer, Crestron Toolbox; часть смежных pro-инструментов: Figma, Linear, VS Code, Grafana) — для каждого сформулировать *принцип*, а не переносить пиксели.
4. **Легаси-проход по визуальным паттернам** — отдельно от уже сделанного поведенческого аудита наследия: что из визуального языка Studio несёт узнаваемость и достойно переосмысления (см. §2–3 выше), а что было костылём под старые ограничения.
5. **Сигнальные экраны раньше полной системы стилей.** 3–5 «знаковых» экранов (дерево+инспектор конфигуратора, system menu с диагностикой, экран панели с реальными функциональными блоками) как прототип — провалидировать на CustDev с интеграторами: узнаваемо ли это как та же логика работы, не выглядит ли шаблонно.
6. **Формализация.** Итог процесса пополняет этот документ (или выделяется в отдельный "AV Control — Дизайн-система" при появлении конкретных токенов и компонентов) как единственный источник правды.

## 5. Чтобы не выглядеть «как у всех» (anti-generic-AI guardrails)

Отдельный практический риск: команда веб-части, вероятно, будет активно использовать AI-инструменты разработки без глубокой веб-дизайн экспертизы (в команде нет веб-дизайнера с фронтенд-компетенцией среди разработчиков) — без явных запретов результат по умолчанию потянет к шаблонному "AI-generated" виду.

| Маркер шаблонности | Анти-ход для AV Control |
|---|---|
| Фиолетово-синий градиент на кнопках/акцентах | Один акцентный цвет, привязанный к домену AV/broadcast, не дефолтный "AI-стартап" градиент |
| Glassmorphism (эффект матового стекла), мягкие "плавающие" тени без смысловой нагрузки | Тень/обводка — только как сигнал состояния, не украшение |
| Огромный border-radius (скругление углов) на всём подряд без правки | Собственная шкала радиусов по типу элемента |
| Дефолтная гарнитура (Inter/Geist) без адаптации на весь интерфейс | Пара гарнитур: нейтральный гротеск для UI + моноширинный шрифт для ID/тегов/IP/логов |
| Дженерик-иконки "как есть" из типовой библиотеки | Минимальный набор кастомных иконок под AV-домен, единый stroke-width (толщина линии) для остальных |
| Низкая плотность информации, много пустого пространства | Плотность как в профессиональных инструментах — у продукта 66 компонентов и живая диагностика, воздух здесь не роскошь стиля, а потеря полезной информации |
| Цвет как decorative badge, а не сигнал | Цвет строго семантический (см. UXP-7), один и тот же код всегда означает одно и то же во всех модулях |
| Bouncy spring-анимации по умолчанию | Сдержанный, "механический" easing (плавность перехода), без игривости |
| Маркетинговый тон текста ("Welcome to the future of X") в служебных экранах | Служебный тон: статус → действие → объект, без "продающих" формулировок |

Рекомендация: закрепить эти запреты как отдельный короткий чек-лист, проверяемый на каждом изменении веб-части — это дешевле и надёжнее, чем субъективная оценка "выглядит стильно".

## 6. Открытые вопросы

- [?требует уточнения] Точный FM-ID и формулировка фичи предиктивной проверки проекта перед деплоем (см. UXP-10) — для явной перекрёстной ссылки на Scope.
- [?требует уточнения] Нужен ли отдельный каталог визуальных элементов панели (аналог компонентной карты, но для UI-примитивов клиента) — или он войдёт как раздел в этот документ.
- [?требует уточнения] Итоговый акцентный цвет и шрифтовая пара — предмет отдельного прохода по референсам (§4, шаг 3), не фиксируются в этой версии.
- CustDev-проверка: что из визуального языка Studio интеграторы реально считают "своим", а что не имеет значения — до финализации §2.
