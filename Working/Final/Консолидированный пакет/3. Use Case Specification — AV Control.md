 
**Назначение.** Описать сценарии использования AV Control «с точностью технического задания»: кто (актор), при каких условиях, какими шагами достигает цели, что происходит в альтернативных и нештатных ситуациях. Покрытие: первичная настройка, ежедневная эксплуатация, обслуживание и удалённый мониторинг, обработка ошибок и критических ситуаций.
> 
> **Что это НЕ заменяет (не дублируем).** Детальная пошаговая механика логики, ветвления, связи тегов, флоу деплоя, вход/выход Safe Mode, продуктовые update-/driver-release-флоу → **Logic & User Flows**. Формальная матрица прав `профиль × действие × ресурс` → **Access Control Model**. Контракт API, Driver Engine (sandbox, lifecycle), механика watchdog/recovery → **Core & API & Integration Specs**. Схемы данных/хранение → **Information Architecture & Data Schema**. Архитектура, протоколы, ОС, состояния → **PSD**.


## §1. Модель и формат

Раздел задаёт модель акторов и единый формат описания кейсов: как они организованы, размечены и связаны между собой.

### 1.1 Акторы (из PRD §2)


| Актор                                       | Роль в сценариях                                                              | Где действует                         |
| ------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------- |
| `End User` (конечный пользователь)          | Запуск сценариев, источник, громкость, mute, завершение                       | Клиент на панели/смартфоне/в браузере |
| `Integrator Engineer` (AV-инженер)          | Настройка проекта, устройств, драйверов, сценариев, тест                      | Admin Web UI                          |
| `Lead Integrator` (ведущий интегратор)      | Шаблоны, защита наработок, пакет передачи объекта                             | Admin Web UI                          |
| `IT Admin` (IT-администратор)               | Сеть, пользователи, сертификаты, обновления, бэкап/восстановление, интеграции | Admin Web UI                          |
| `Support Operator` (поддержка 1-й линии)    | Статусы, логи, панель состояния, diagnostic bundle                            | Admin Web UI (огранич.)               |
| `Vendor Support` (поддержка вендора, iRidi) | Помощь при инциденте через временный явный доступ                             | Удалённый доступ                      |
| `Security Auditor` (ИБ-офицер)              | Read-only: аудит, ИБ-события, выгрузка в SIEM                                 | Admin Web UI (read-only)              |
| Машинные акторы (через API)                 | Мониторинг/SIEM, бронирование/календарь, терминал ВКС                         | API                                   |


**Чтение акторов.** Запись через «/» (например `Инж/IT`) означает, что кейс выполняет любой из указанных профилей по политике объекта; стрелка (`Lead→IT`) — передачу между профилями. `Lead Integrator` задействован в сценариях точечно (шаблоны, защита наработок, передача объекта) — основной объём настройки несёт `Integrator Engineer`. Машинные акторы действуют через API: у них нет интерфейса, но есть аутентификация, роли и версии.

### 1.2 Организация и нумерация

Кейсы сгруппированы по **рабочим областям продукта**, каждая соответствует модулю PRD (PRJ, AUT, DRV, PNL, OPS, BVC, ADM, SEC, MON, UPD, LIC, INT/API, SUP, ERR). Группировка по областям гарантирует полноту: каждый модуль представлен. ID кейса — `<область>-NN` (например `PRJ-07`). Этап (категория методологии) указывается тегом, поэтому кейс одновременно привязан и к области, и к этапу.

### 1.3 Категории и приоритеты

| Тег | Категория (этап) |
|---|---|
| Н | Настройка (первичная) |
| Э | Эксплуатация (ежедневная) |
| О | Обслуживание и мониторинг |
| А | Ошибки и аварии |

Приоритет: **P0** — критично для MVP · **P1** — важно · **P2** — последующие версии.

### 1.4 Уровни детализации

| Уровень | Что содержит | Для чего |
|---|---|---|
| Полная | метаданные + цель, предусловия, основной поток, альтернативы, ошибки, итог | критичные и многоветочные кейсы |
| Краткая | метаданные + цель + поток 3–7 шагов + ссылки | важные, но линейные кейсы |
| Заглушка | назначение, границы, открытые вопросы | будущие или неопределённые по scope |

### 1.5 Формат карточки кейса

Под названием — **строка метаданных**, отделённая от тела: `Категория · Приоритет · Детализация · Актор(ы) · Трассировка`. Тело — помеченные списки (Цель, Предусловия, Основной поток, Альтернативы, Ошибки, Итог; для «Кратких» — сокращённый набор). Пример строки метаданных:

> PRJ-07 · Настройка · P0 · Полная · Инж · FR-PRJ, PSD §7 → L&F

### 1.6 Перекрёстные ссылки и границы

Чтобы не дублировать, кейсы ссылаются друг на друга по ID: «Краткая» отсылает к родственной «Полной», типовые ошибки вынесены в область **ERR**, а внутренняя механика — ссылкой в смежные документы (`→ L&F` — Logic & User Flows; `→ Core&API`; `→ ACM` — Access Control Model). Что именно описывается здесь, а что в смежных документах, задано во вводном разделе «Что это НЕ заменяет». Маркер `[?]` — открытый вопрос или нерешённый scope.

#### PRJ-01 · Создание проекта через wizard помещения

> Настройка · P0 · Полная · Инж · FR-PRJ-02/03, OBJ-1/2 → L&F

**Цель.** Собрать конфигурацию типового помещения из готовой комнаты, без ручной сборки связей и кода. 
**Предусловия.** Активен проект; в каталоге есть подходящая готовая комната.

**Основной поток.**
1. Открывает конфигуратор, выбирает «создать готовую комнату».
2. Заполняет список оборудования в комнате: вендор/модель, необходимые сценарии, выбирает общий стиль.
3. Система разворачивает комнату — устройства, драйверы, теги, связи, базовые сценарии, единый стиль — автоматически.
4. Корректирует состав под объект (адреса, фактическое оборудование).
5. Сохраняет проект.
   
**Альтернативы.** Нет нужного типа → wizard устройств (PRJ-02) или вручную (PRJ-03). Нужна правка логики/вида → PRJ-04, PRJ-05.
**Ошибки.** Конфликт связей/тегов → система показывает проблему и следующий шаг. Нет драйвера на устройство → DRV-01.
**Итог.** Комната собрана, готова к preflight (PRJ-06).

### PRJ-02 · Создание проекта через wizard добавления устройств

> Настройка · P0 · Краткая · Инж · FR-PRJ-02/03 · как PRJ-01

**Цель.** Собрать комнату при отсутствии готового шаблона — добавляя устройства по одному.
**Поток.**
1. «Добавить устройство». 
2. Выбирает устройство из каталога; система подключает драйвер(вендор/модель), элементы и связи.
3. Повторяет для остальных.
4. Достраивает сценарии и интерфейс (AUT-01, PRJ-05), сохраняет.

**Отличия от PRJ-01.** Готовой комнаты нет — состав собирается поустройственно; теги и связи подключаются автоматически на каждом шаге. Альтернативы, ошибки, итог — как в PRJ-01.

### PRJ-03 · Создание проекта полностью вручную

> Настройка · P0 · Полная · Инж · FR-PRJ-01, M-VAR/M-AUT → L&F

**Цель.** Собрать проект с нуля, задавая устройства, теги, связи и преобразования вручную, когда wizard-ы не подходят. **Предусловия.** Активен проект.
**Основной поток.**

1. Создаёт пустой проект (серверный + клиентский).
2. Добавляет драйверы
3. Заводит пользовательские теги (в т.ч. persist-значения).
4. Связывает теги устройств с элементами интерфейса.
5. Задаёт преобразования значений через Expression Evaluator.
6. Собирает сценарии (AUT-01) и интерфейс (PRJ-05), сохраняет.
**Альтернативы.** Нативной логики не хватает → JS-расширение (AUT-04).
**Ошибки.** Ошибка связи/преобразования → система указывает место и причину (рантайм — ERR-02).
**Итог.** Проект собран вручную; готов к preflight (PRJ-06).

### PRJ-04 · Доработка проекта или шаблона после создания

> Настройка · P0 · Краткая · Инж · FR-PRJ (редактируемость) → L&F

**Цель.** Изменить любой проект/экземпляр шаблона после создания — состав, теги, связи, логику, интерфейс.
**Поток.** 1. Открывает проект. 2. Меняет состав/связи/сценарии/стили. 3. Проверяет (PRJ-06), сохраняет.
**Ключевой принцип.** Шаблонность не блокирует правки; экземпляр редактируется свободно. Ошибки — как при создании.

### PRJ-05 · Настройка интерфейса: стили, пресеты, кастомизация

> Настройка · P0 · Краткая · Инж · FR-PRJ-07/09 → L&F

**Цель.** Оформить клиентский интерфейс через глобальные и поэлементные стили (без обязательных inline-стилей, в отличие от i3Pro).
**Поток.**
1. Задаёт глобальный стиль проекта (тема).
2. При необходимости переопределяет стиль отдельного элемента.
3. Настраивает пресеты, видимость, порядок, подписи.
4. Проверяет на превью, сохраняет.

**Итог.** Понятный интерфейс без инженерных сущностей.

### PRJ-06 · Preflight-проверка полноты проекта

> Настройка · P0 · Краткая · Инж · FR-PRJ-08 → L&F

**Цель.** Убедиться, что проект готов к запуску, в т.ч. без полного комплекта оборудования.
**Поток.** 1. Запускает проверку. 2. Система перечисляет незакрытые пункты (несвязанные теги, отсутствующие драйверы, неполные сценарии). 3. Исправляет, перезапускает проверку.
**Итог.** Проект валиден; можно публиковать (PRJ-07).

### PRJ-07 · Публикация активного проекта (деплой)

> Настройка · P0 · Полная · Инж · FR-PRJ, PSD §7 → L&F

**Цель.** Сделать собранный проект активным на сервере.
**Предусловия.** Проект прошёл preflight (PRJ-06).
**Основной поток.**
1. Выбирает проект для публикации.
2. Система проверяет совместимость и лимит лицензии.
3. Публикует атомарно; прежний активный проект сохраняется как точка отката.
4. Подтверждает, что комнаты работают на новом проекте.
**Альтернативы.** Публикация при активной встрече → предупреждение (UPD-02 по аналогии).
**Ошибки.**
* Лимит лицензии превышен → ERR-05.
* Деплой не удался → откат (ERR-10).
* Опубликован, но работает некорректно → last-known-good (ERR-11).
**Итог.** Новый проект активен; есть точка отката.

### PRJ-08 · Снять активный проект / вернуть стандартный режим

> Обслуживание · P1 · Краткая · Инж/IT → L&F

**Ошибки.** Идёт активная встреча → предупреждение (как UPD-02).

### PRJ-09 · Импорт/экспорт и перенос проекта

> Настройка · P1 · Краткая · Инж · FR-PRJ-06 → L&F

**Цель.** Перенести проект или собственные шаблоны между проектами, контроллерами и эмулятором (переиспользование наработок).
**Поток.**
1. Экспортирует проект/шаблон (серверная и клиентская части — раздельно).
2. На целевом контроллере импортирует.
3. Адаптирует под объект (PRJ-04).
**Ошибки.** Несовместимая версия/лицензионные ограничения → понятное сообщение. Защищённые наработки не извлекаются как редактируемые (PRJ-11).

### PRJ-10 · Сохранение блока/комнаты как шаблона

> Настройка · P1 · Краткая · Lead/Инж · FR-PRJ-05 → L&F

**Цель.** Зафиксировать настроенную комнату/блок как переиспользуемый шаблон.
**Поток.**
1. Выбирает комнату/блок.
2. Сохраняет как шаблон (с метаданными, единым стилем, логикой).
3. Шаблон доступен в каталоге для PRJ-01/09.

### PRJ-11 · Защита проекта от копирования/редактирования

> Настройка · P1 · Краткая · Lead → ACM, L&F

**Цель.** Защитить авторские наработки (графика, медиа, скрипты, шаблоны) от извлечения и редактирования.
**Поток.**
1. Помечает проект, вводит пароль для защиты проекта.
2. Система ограничивает копирование/редактирование вне прав (без ввода пароля)
3. Защита сохраняется при экспорте и handover (PRJ-09, PRJ-14).
**Граница.** Это сдерживание копирования, не абсолютная криптозащита.

### PRJ-12 · Настройка без доступа к оборудованию

> Настройка · P1 · Краткая · Инж · PP-COM-03 · режим offline → L&F

**Цель.** Продвинуть настройку, когда оборудование недоступно — на эмуляторе (до выезда) или на объекте с неполным комплектом.
**Поток.**
1. Работает локально без устройств.
2. Недоступные устройства можно свободно настраивать.
3. Сохраняет прогресс.

**Итог.** Конфигурация частично готова; прогресс сохранён.

### PRJ-13 · Импорт спецификации из Project Tool и авто-настройка

> Настройка · P2 · Заглушка · Инж · зависит от Project Tool

**Назначение.** Получить из Project Tool рассчитанную спецификацию оборудования и автоматически развернуть проект — как wizard помещения, но с авто-подстановкой данных.
**Границы.** Project Tool в разработке; формат выгрузки и глубина авто-настройки не определены.
**Вопросы.** Формат спецификации; что подставляется автоматически vs вручную; запуск из AV Control или из Project Tool.

### PRJ-14 · Передача объекта IT-службе заказчика (handover)

> Настройка · P1 · Полная · Lead→IT · INT-F6 → ACM, L&F

**Цель.** Передать эксплуатацию без зависимости от подрядчика и без утечки авторских наработок.
**Предусловия.** Проект завершён; роли заказчика заведены.

**Основной поток.**
1. Lead формирует пакет передачи: переносимая эксплуатационная конфигурация, роли, документация.
2. Авторские наработки защищены (PRJ-11) и не могут редактироваться без ввода пароля.
3. IT принимает систему, получает админ-права; права интегратора отзываются/понижаются.
4. IT проверяет доступ к эксплуатации (статусы, обновления, бэкап).

**Альтернативы.** По договору интегратор сохраняет ограниченный сервисный доступ → временная отзывная роль (SEC-04). **Итог.** Заказчик эксплуатирует систему самостоятельно; IP защищён.

### PRJ-15 · Вывод объекта: очистка пользовательских данных

> Обслуживание · P1 · Краткая · IT → L&F

2. Система удаляет пользовательские данные/настройки по политике.
3. Действие фиксируется в аудите (SEC-05) и отправляются в SIEM систему перед очисткой
**Вопросы.** Как фиксировать в аудите процесс очистки, учитывая что и он удаляется.

2. Задаёт условия по времени.

## DRV · Драйверы

### DRV-01 · Запрос и получение драйвера на неподдержанное устройство

> Обслуживание · P0 · Полная · Инж→Вендор · PP-DRV-01/04, PSD §7.5 → Core&API

**Цель.** Получить рабочий драйвер на устройство, которого нет в каталоге, не блокируя сроки объекта.
**Предусловия.** Доступна протокольная документация устройства.
**Основной поток.**

1. Обнаруживает отсутствие драйвера в каталоге.
2. Оформляет запрос (устройство, протокол, нужные функции/capabilities), прикладывает документацию.
3. Вендор готовит драйвер и проводит стендовую проверку.
4. Присваивается Driver ID, версия, диапазон совместимости; offline-доставка инженеру.
5. Установка по DRV-02.
**Альтернативы.** Драйвер есть, но неполный → доработка покрытия (DRV-03).
**Ошибки.** Закрытый протокол / спец-сертификация → отдельный SLA как исключение, не «1 день».
**Итог.** Драйвер в каталоге; «нет драйвера» — редкое исключение.

### DRV-02 · Установка/обновление драйвера без релиза ядра

> Обслуживание · P0 · Полная · Инж/IT · FR-DRV-02, FR-UPD-01, PSD §7.5 → Core&API

**Цель.** Установить/обновить драйвер независимым потоком, не трогая ядро.
**Предусловия.** Драйвер подписан; объявлен диапазон совместимости.
**Основной поток.**

1. Загружает offline-пакет драйвера; система проверяет подпись и совместимость версий.
2. Показывает патчноут.
3. Устанавливает без перезапуска ядра.
4. Фиксирует в каталоге и журнале, свободно драйвер доступен в каталоге драйверов.
   
**Альтернативы.** Доставка в закрытый контур вручную (носитель/локальная сеть).
**Ошибки.** Несовместимая версия → установка блокируется с понятным сообщением. Драйвер падает после установки → ERR-04; откат → ERR-09.
**Итог.** Устройство управляется новым драйвером; ядро не затронуто.

### DRV-03 · Частичная поддержка устройства (доработка покрытия)

> Обслуживание · P1 · Краткая · Инж/Сап · PP-DRV-01 → Core&API

**Цель.** Расширить набор поддержанных функций устройства, когда драйвер не покрывает нужное.
**Поток.**
1. Фиксирует отсутствующую функцию.
2. Оформляет запрос на доработку покрытия (как DRV-01).
3. Получает обновлённый драйвер (DRV-02), отличающийся версией.
4. В системе доступна новая версия драйвера, доступ к предыдущим версиям остается.

### PNL-01 · Подключение панели/клиента и загрузка проекта

> Настройка · P0 · Полная · Инж/IT · FR-ROOM-01/02 → L&F

4. Проверяет отображение состояний и управление.

**Поток.**

2. Сервер доставляет его на панель.
3. Проверяет.

### PNL-03 · Замена панели и повторная загрузка проекта

> Обслуживание · P1 · Краткая · IT/Инж → L&F

**Поток.**

2. Загружает тот же клиентский проект.
3. Проверяет. Доп. ручной донастройки не требуется.

### PNL-04 · Согласованное состояние нескольких панелей одной комнаты

> Эксплуатация · P1 · Краткая · End User/Система → L&F

## OPS · Эксплуатация помещения

### OPS-01 · Начать встречу

> Эксплуатация · P0 · Полная · End User · FR-ROOM-04/08, OBJ-2 → L&F

**Цель.** Начать встречу вовремя, без обращения в IT и без инструкции.
**Предусловия.** Комната в стандартном режиме; панель доступна.

**Основной поток.**
1. Видит сценарии («Начать встречу», «ВКС», «Презентация»), не устройства.
2. Нажимает сценарий (1 действие).
3. Система координированно готовит технику и переходит в активный режим.
4. Видит готовность, начинает встречу.

**Альтернативы.** Запуск со смартфона. Комната уже активна → OPS-02.
**Ошибки.** Часть устройств недоступна → частичная работоспособность (ERR-20). Идёт обновление → UPD-02.
**Итог.** Комната готова; время «вход → готовность» в пределах ожидания.

### OPS-02 · Войти в уже активную комнату

> Эксплуатация · P1 · Краткая · End User → L&F

**Цель.** Корректно подключиться к комнате, где сессия уже идёт или не была завершена.
**Поток.**
1. Видит, что комната активна.
2. Продолжает текущую сессию или завершает её и начинает свою (OPS-05 → OPS-01).

### OPS-03 · Переключить источник / BYOD

> Эксплуатация · P0 · Полная · End User · FR-ROOM-05/07, EU-F2 → L&F

**Цель.** Вывести своё устройство или сменить источник без знания схемы коммутации.
**Предусловия.** Комната активна; источник физически подключён.

**Основной поток.**
1. Подключает ноутбук к доступному входу (при необходимости — подсказка по физическому подключению).
2. Система автоопределяет источник либо пользователь выбирает по понятному имени.
3. Изображение и звук выводятся.

**Альтернативы.** Источник — видеопоток (RTSP/MJPEG) → выбирается как обычный источник.
**Ошибки.** Нет сигнала/звука → понятная подсказка на языке действия (OPS-07), без инженерных терминов.
**Итог.** Нужный источник на экране; вызов IT не потребовался.

### OPS-04 · Управление в ходе встречи

> Эксплуатация · P0 · Краткая · End User · EU-F · → L&F

**Цель.** Управлять громкостью, mute, камерой, раскладкой во время встречи.
**Поток.**
1. На панели/смартфоне выбирает нужное управление.
2. Система применяет; пользователь видит результат без задержек.

### OPS-05 · Завершить сессию

> Эксплуатация · P0 · Краткая · End User · EU-F5 → L&F

**Цель.** Корректно завершить встречу, чтобы следующий начал с чистого состояния.

**Поток.**
1. Нажимает «Завершить».
2. Система закрывает ВКС, очищает пользовательские данные, переводит технику в дежурное состояние, возвращает стандартный режим
3. Выдает уведомление о успехе

**Альтернативы.** Авто-завершение по таймауту/расписанию (AUT-03).
**Ошибки.** ВКС не закрылся штатно → принудительное завершение; «оставленная техника» не возникает как класс инцидента.

### OPS-06 · Свободная комната / по расписанию / заглушка

> Эксплуатация · P1 · Краткая · End User/Система · FR-ROOM-09 → L&F

**Цель.** Понятное поведение комнаты вне встреч.
**Суть.** Вне сессии комната показывает дежурный экран/заглушку; по расписанию (AUT-03) может входить/выходить из режимов. Пользователь видит, свободна ли комната.

### OPS-07 · Действия пользователя при сбое

> Эксплуатация/Ошибка · P0 · Полная · End User · FR-ROOM-05 → L&F

**Цель.** Дать пользователю понятный следующий шаг при сбое, без инженерной диагностики.

**Поток пользователя.**
1. Видит понятное состояние: «нет сигнала», «нет звука», «устройство недоступно».
2. Получает подсказку на языке действия (проверьте кабель, выберите источник, вызовите поддержку).
3. Продолжает на доступном (ERR-20) либо завершает.

**Связь с поддержкой.** Инженерные детали того же события видит поддержка (MON-01/02), пользователю они не показываются.
**Итог.** Пользователь понимает, что делать; инцидент не блокирует встречу целиком.

3. Меняет runtime-настройку временно (сбрасывается при перезапуске).

**Граница.** Изменения не сохраняются в проект; всё под правами и в аудите (SEC-05).

### ADM-04 · Удалённая перезагрузка/выключение контроллера по LAN

> Обслуживание · P1 · Краткая · IT · §2.5 → Core&API

**Поток.**

2. Подтверждает перезагрузку/выключение.
3. Действие фиксируется в аудите.

**Ошибки.** Идёт активная встреча → предупреждение (как UPD-02).

### ADM-05 · Настройка хранения логов/дампов

> Обслуживание · P1 · Краткая · IT → L&F

**Связь.** Переполнение хранилища → ERR-15.

> Обслуживание · P0 · Полная · IT/Сап · FR (диагностика) → L&F

**Цель.** Быстро локализовать причину инцидента силами IT/первой линии.
**Предусловия.** Есть доступ к состоянию и логам (MON-01).

**Основной поток.**
1. Видит проблемную комнату/устройство (статус, событие).
2. Фильтрует логи по времени/устройству/уровню (ADM-03).
3. Определяет затронутый компонент (устройство, драйвер, сценарий, сеть).

**Альтернативы.** Не воспроизводится / нужен вендор → MON-03 → SUP-01.
**Итог.** Причина локализована либо подготовлена эскалация.

### MON-03 · Формирование и экспорт diagnostic bundle

> Обслуживание · P0 · Полная · IT/Инж/Сап · PSD §7.6 → L&F

**Цель.** Собрать пакет диагностики для эскалации (в закрытом контуре — вручную).
**Предусловия.** Инцидент локализован настолько, насколько возможно (MON-02).

**Основной поток.**
1. Запускает формирование bundle (логи, состояние, версии, конфигурация по политике).
2. Система собирает пакет с учётом приватности/состава.
3. Экспортирует на носитель/во внутреннюю сеть.
4. Передаёт вендору (SUP-01).

**Граница.** Bundle собирает IT/Инж/Сап, **не вендор**; удалённого доступа в контур может не быть.
**Итог.** Пакет готов к передаче; вендор работает по нему без доступа в контур.

### MON-04 · Мониторинг в закрытом контуре (syslog/Zabbix локально)

> Обслуживание · P1 · Краткая · IT/API · §2.5 → Core&API

3. «Удалённость» — в пределах закрытой сети, не интернет-доступ.

## UPD · Обновления, бэкап, восстановление

### UPD-01 · Обновление ядра

> Обслуживание · P0 · Полная · IT · FR-UPD-01/02/03, PSD §7.4 → L&F

**Цель.** Обновить ядро/ПО контроллера offline, с возможностью отката.
**Предусловия.** Получен offline-пакет; есть актуальный backup (UPD-03).


**Основной поток.**
1. Загружает пакет; система проверяет целостность.
2. Показывает патчноут.
3. Создаёт точку восстановления и устанавливает.

**Альтернативы.** Комната в активной встрече → UPD-02.
**Ошибки.** Обновление не удалось → откат (ERR-08).
**Итог.** Ядро обновлено; есть точка отката и запись в журнале.

### UPD-02 · Обновление при активной встрече

> Обслуживание · P1 · Краткая · IT → L&F

**Цель.** Не сорвать идущую встречу обновлением.

**Поток.**
1. Система обнаруживает активную сессию.
2. **Предупреждает, что помещение используется.**
3. Администратор откладывает до освобождения комнаты или подтверждает осознанно.

**Итог.** Решение принимается с пониманием риска; встреча не прерывается неожиданно.

### UPD-03 · Резервное копирование

> Обслуживание · P0 · Краткая · IT · FR-UPD-04, PSD §7.3 → L&F

**Цель.** Иметь проверяемую резервную копию для восстановления.

**Поток.**
1. Запускает backup (вручную или по расписанию).
2. Система сохраняет проект, настройки, роли, драйверы и критичные параметры.
3. Подтверждает целостность.

### UPD-04 · Восстановление / замена контроллера из backup

> Обслуживание · P0 · Полная · IT/Инж · FR-UPD-04/05, PSD §7.3 → L&F

**Цель.** Восстановить работу после сбоя или замены контроллера.
**Предусловия.** Есть проверяемый backup (UPD-03).
**Основной поток.**

1. Устанавливает контроллер из ЗИП (при замене).
2. Восстанавливает конфигурацию из backup.
3. Система проверяет backup на совместимость до применения.
4. Применяет; комната работает без ручной донастройки.

**Альтернативы.** Замена только устройства → UPD-05.
**Ошибки.** Backup повреждён/несовместим → восстановление прерывается (ERR-12), текущая конфигурация сохраняется. Лицензия вшита в контроллер — при замене учитывается (LIC-01).
**Итог.** Контроллер восстановлен; downtime минимизирован.

### UPD-05 · Замена устройства в комнате

> Обслуживание · P1 · Краткая · Инж/IT → L&F

**Цель.** Восстановить работу комнаты после выхода устройства из строя.

**Поток.**
1. Устанавливает устройство из ЗИП.
2. Изменяет сетевые настройки, если это необходимо.
3. Проверяет (ADM-03).

> Обслуживание · P1 · Краткая · Инж · PSD §6 → L&F

**Цель.** Корректно отработать конец срока эмулятора — это штатный механизм, не ошибка.
**Суть.** По истечении эмулятор сообщает об окончании срока и ограничивает работу. Не для продакшена. Для боевой эксплуатации — заводская лицензия.

## INT/API · Интеграции и машинные пользователи

> У машинных пользователей нет UX, но есть аутентификация, роли и версии API. Контракт — в Core & API.

### INT-01 · Подключение внешней системы по API

> Настройка · P1 · Краткая · IT/Инж · §2.5 → Core&API

**Цель.** Подключить мониторинг/SIEM/booking к AV Control.
**Поток.**
1. Регистрирует внешнюю систему, выдаёт API-токен/ключ.
2. Настраивает доступ под ролью.
3. Проверяет связь.
**Ошибки.** Ошибка auth/версии/связи → ERR-18.

### API-01 · Чтение состояния/health внешней системой

> Обслуживание · P1 · Краткая · API (мониторинг/SIEM) → Core&API

**Суть.** Внешняя система по разрешённому токену читает состояние комнат/устройств и health-метрики.

### API-02 · Получение аудита/ИБ и Error/Critical-событий

> Обслуживание · P1 · Краткая · API (SIEM/syslog) → Core&API

**Суть.** Внешняя система получает аудит и ИБ-события; в v1 эскалируются уровни Error/Critical (SEC-06).

### API-03 · Команды от внешней системы

> Эксплуатация · P1 · Краткая · API (booking) → Core&API

**Суть.** Разрешённые действия извне: запуск разрешённых сценариев из white-list (API-DOM-05) и чтение состояния/логов. Только в пределах прав машинного пользователя. Бронь и управление внешними системами выполняются через драйверы (слой C), не через API.
### API-04 · Отказ API-запроса

> Ошибка · P1 · Краткая · API → Core&API

**Суть.** Запрос без прав/с неверной версией/без auth отклоняется с понятным кодом; событие доступно для диагностики.

## SUP · Поддержка вендора

### SUP-01 · Вендор изучает bundle и даёт рекомендацию

> Обслуживание · P1 · Краткая · Вендор → L&F

**Цель.** Помочь с инцидентом без доступа в закрытый контур.
**Поток.**
1. Получает diagnostic bundle (MON-03).
2. Анализирует.
3. Передаёт рекомендацию IT/первой линии.

**Граница.** Доступ в контур часто недоступен — это основной путь поддержки.

### SUP-02 · Вендор работает в рамках временного доступа

> Обслуживание · P1 · Краткая · Вендор/IT → ACM

**Цель.** Точечно помочь, когда временный доступ выдан.
**Поток.**
1. IT выдаёт временный доступ (SEC-04).
2. Вендор работает в его рамках.
3. По завершении доступ отзывается; всё в аудите (SEC-05).

**Граница.** Не постоянный скрытый суперпользователь.

## ERR · Ошибки и аварии

**Уровни:** Info / Warning / Error / Critical. В мониторинг (v1) эскалируются Error/Critical (SEC-06, API-02).

**Принцип реакции по уровням:**

|Уровень|Реакция системы|Что видит пользователь|
|---|---|---|
|Critical|защита ядра, деградация/Safe Mode, событие|понятное состояние + действие|
|Error|локализация, попытка восстановления, событие|уведомление/подсказка|
|Warning|работа с пометкой деградации|подсказка на языке действия|
|Info|запись в журнал|обычно не видно|

> Каждый кейс ниже: что произошло, реакция системы, что видит актор. Детекция и механика восстановления → Core&API / L&F.

### ERR-01 · Устройство offline / error

> Ошибка · P0 · Полная · End User/Сап → Core&API, L&F

**Что происходит.** Устройство не отвечает (таймаут) или вернуло ошибку.
**Реакция системы.** Retry-политика; пометка «устройство недоступно»; комната продолжает на доступном (ERR-20).
**Поток пользователя.** Видит понятное состояние, при необходимости — подсказку (OPS-07); встреча не падает целиком. **Поток поддержки.** Видит устройство, событие, лог; локализует (MON-02), при необходимости — bundle (MON-03).
**Итог.** Инцидент локализован; пользователь не блокирован.

### ERR-02 · Ошибка выполнения сценария

> Ошибка · P0 · Краткая · End User/Сап → L&F

**Суть.** Сценарий прервался/отработал некорректно. Система фиксирует событие, по возможности возвращает комнату в штатное состояние. Пользователь видит понятное состояние; поддержка — детали и шаг сценария (MON-02).

### ERR-03 · Ошибка JS-скрипта

> Ошибка · P1 · Краткая · Инж/Сап → Core&API

**Суть.** JS-расширение упало. Ошибка изолируется и логируется, не роняя ядро/проект. Инженер видит лог и место ошибки.

### ERR-04 · Сбой/зависание драйвера

> Ошибка · P0 · Краткая · Система/Сап → Core&API

**Суть.** Драйвер упал/завис. Система перезапускает его; после серии отказов — деградация устройства (ERR-01) и диагностическое событие.

### ERR-05 · Превышен лимит лицензии при публикации

> Ошибка · P0 · Краткая · Инж → L&F

**Суть.** Публикация (PRJ-07) превышает лимит устройств/комнат/клиентов. Система блокирует деплой проекта с понятным сообщением и текущим использованием (LIC-01); путь решения — расширение лимита (LIC-02).

### ERR-06 · Невалидная/повреждённая лицензия

> Ошибка · P0 · Краткая · Инж/IT → L&F

**Суть.** Лицензия не проходит проверку (повреждение/нарушение привязки). Серьёзная ошибка: ограниченный режим, событие, эскалация в поддержку (SUP-01). (Истечение эмулятора — не сюда, это LIC-03.)

### ERR-07 · Потеря связи клиент/панель ↔ сервер

> Ошибка · P0 · Краткая · End User/IT → L&F

**Суть.** Клиент/панель потеряли связь с сервером. Показывают состояние «нет связи» и инструкции; при восстановлении состояние синхронизируется. Несколько панелей — независимо (PNL-04).

### ERR-08 · Неуспешное обновление ядра → откат

> Ошибка · P0 · Полная · IT · FR-UPD-02, PSD §7.4 → L&F

**Что происходит.** Обновление ядра (UPD-01) завершилось ошибкой.
**Реакция системы.** Автоматический откат к точке восстановления; запись в журнал.
**Поток IT.** Видит уведомление и причину; при необходимости собирает bundle (MON-03).
**Итог.** Контроллер на прежней рабочей версии; данные сохранены.

### ERR-09 · Неуспешное обновление драйвера → откат

> Ошибка · P1 · Краткая · IT/Инж → Core&API

**Суть.** Установка/обновление драйвера (DRV-02) неуспешна или драйвер нестабилен. Откат к предыдущей версии драйвера; ядро не затронуто.

### ERR-10 · Неуспешный деплой проекта → откат

> Ошибка · P0 · Краткая · Инж · PSD §7 → L&F

**Суть.** Публикация (PRJ-07) не удалась. Атомарный откат к прежнему активному проекту; комнаты продолжают на нём.

### ERR-11 · Проект опубликован, но работает некорректно → last-known-good

> Ошибка · P1 · Краткая · Инж/IT → L&F

**Суть.** Деплой прошёл, но сценарии работают неверно. Возврат к last-known-good проекту; разбор причины (MON-02).

### ERR-12 · Неуспешное восстановление из backup

> Ошибка · P1 · Краткая · IT → L&F

**Суть.** Восстановление (UPD-04) прервано из-за повреждённого/несовместимого backup. Текущая конфигурация сохраняется; нужен другой backup.

### ERR-13 · Серия неуспешных стартов → вход в Safe Mode и выход

> Ошибка · P0 · Полная · IT/Сап · PSD §5 → Core&API, L&F

**Что происходит.** Активный проект многократно не запускается (runtime не поднимается).
**Реакция системы.** Вход в Safe Mode: минимально работоспособное состояние, защита ядра, событие. Создание crus dumps.

**Поток IT.** Диагностирует причину (MON-02), исправляет проект/откатывает (ERR-11), выводит из Safe Mode.
**Итог.** Контроллер управляем; есть путь восстановления штатной работы.

### ERR-14 · Невалидный активный проект

> Ошибка · P1 · Краткая · IT/Система → L&F

**Суть.** Активный проект повреждён/невалиден. Система откатывается к исправному или уходит в админ/Safe-режим (ERR-13); комната не остаётся в неопределённом состоянии.

### ERR-15 · Переполнение хранилища

> Ошибка · P1 · Краткая · IT → L&F

**Суть.** Хранилище логов/дампов переполнено. Система останавливает некритичные записи и чистит по ретенции (ADM-05); уведомляет администратора.

### ERR-16 · Истёкший сертификат

> Ошибка · P1 · Краткая · IT/ИБ → L&F

**Суть.** TLS/SSL-сертификат истёк. Предупреждение заранее; при истечении — ограничение защищённых соединений; продление (SEC-03).

### ERR-17 · Критическое ИБ-событие

> Ошибка · P1 · Краткая · ИБ/IT → ACM, Core&API

**Суть.** Зафиксирована попытка несанкционированного доступа/нарушение политики. Блокировка по политике, аудит-событие, эскалация в SIEM (API-02).

### ERR-18 · Ошибка внешней интеграции

> Ошибка · P1 · Краткая · IT/Сап/API → Core&API

**Суть.** Внешняя система не проходит auth/версию или связь потеряна. Понятное сообщение администратору; запрос отклоняется (API-04); разбор — MON-02.

### ERR-19 · Аварийное восстановление перед рабочим днём

> Ошибка · P1 · Краткая · IT/Инж → L&F

**Суть.** Комната/контроллер найдены в нерабочем состоянии до начала дня. Быстрый путь: диагностика (MON-02) → откат/восстановление (ERR-11, UPD-04) → проверка готовности (MON-01).

### ERR-20 · Частичная работоспособность комнаты

> Ошибка · P0 · Полная · End User/Сап → L&F

**Что происходит.** Во время сессии часть оборудования недоступна.
**Реакция системы.** Комната продолжает работать на доступных устройствах; недоступные функции скрыты/помечены; ядро и сценарии не падают.
**Поток пользователя.** Видит понятное состояние (например «микрофон недоступен»), а не инженерную ошибку; встреча продолжается в доступном объёме (OPS-07).
**Поток поддержки.** Видит, какие устройства выпали, и диагностирует (MON-01/02).
**Итог.** Встреча не сорвана; инцидент локализован.
