# Core & API & Integration Specs — AV Control

## §1. Три интерфейсных слоя

> Базовая ось документа. Каждый внешний или внутренний обмен СУ относится ровно к одному слою.

| Слой                                      | Направление                                   | Кому служит                      | Что входит                                                                                                                                                                   | Где в документе |
| ----------------------------------------- | --------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| **C · Драйверы и интеграции**             | СУ **управляет** внешним устройством/сервисом | конечному пользователю (комната) | устройства (ТВ, камера, проектор, DSP, источники, коммутация, реле/входы) **+ сервис-драйверы: ВКС, бронирование**                                                           | §2, §10         |
| **B · Открытый API**                      | СУ **отдаёт своё внутреннее наружу**          | внешним авторам / IT-системам    | health/мониторинг, выгрузка логов и аудита (SIEM/syslog), базовое управление контроллером, статус лицензии, открытый API как универсальная точка интеграции локальных систем | §3, §5, §6, §10 |
| **A · Внутренний контракт Клиент↔Сервер** | внутри продукта                               | собственному UI СУ               | управление сессией, чтение/запись тегов, обновление состояния панели                                                                                                         | §4              |

**Определения (governing):**

- **Драйвер** — управление или интеграция с внешним устройством/сервисом, нужным конечному пользователю (телевизор, система ВКС, система бронирования). То, **чем СУ управляет**.
- **Открытый API** — доступ к системам самой СУ для внешних авторов (выгрузка логов, базовое управление контроллером, монитор здоровья). Точки, где СУ **отдаёт своё внутреннее наружу**.
- **Внутренний контракт** — защищённый протокол обмена данными между Клиентом и Сервером. **Только внутренний**, наружу не публикуется.

**Модель расширяемости СУ исчерпывается тремя механизмами:** драйверы (слой C), JS-расширения (§7), открытый API (слой B). Иного механизма расширения нет.

## §2. Драйверы и интеграции (слой C)

> Driver Engine — продуктовые требования. Sandbox-runtime, ресурсные лимиты, lifecycle-механика, подпись — `TL-CORE-*`. Каталог устройств и матрица совместимости — PSD §4 / этап драйверов (не здесь).

### 2.1 Изоляция и инкапсуляция

|ID|Требование|Источник|
|---|---|---|
|`DRV-ENG-01`|Каждый драйвер исполняется в изолированной среде: сбой драйвера не останавливает ядро и не аффектит другие драйверы|`FR-DRV-01`; PSD §1.1|
|`DRV-ENG-02`|Драйвер не имеет прямого доступа к файловой системе, сети вне разрешённого транспорта и к ресурсам другого драйвера|методология|
|`DRV-ENG-03`|**Драйвер пишет только в собственные (драйверные) теги.** Запись в чужие драйверные, пользовательские и системные теги — невозможна|IA `Q4`; `M-VAR`|
|`DRV-ENG-04`|Проброс значения драйверного тега в пользовательский тег выполняется **только через связи (ENT-08)**, настраиваемые интегратором; сам драйвер этого не делает|IA `Q4`, ENT-08|
|`DRV-ENG-05`|Команды драйвера на устройство идемпотентны: повторный одинаковый вызов не вызывает дублирующий эффект|PSD §1.1|

> **Критерий приёмки (`DRV-ENG-01/03`):** инъекция отказа в один драйвер не прерывает работу комнаты; попытка драйвера записать вне своих тегов отклоняется и фиксируется диагностическим событием (`EVT-04`).

### 2.2 Жизненный цикл (продуктовый уровень)

|ID|Требование|Источник|

|`DRV-ENG-09`|`Stop` освобождает ресурсы, закрывает соединения, сохраняет persist-значения тегов|ENT-07|
|`DRV-ENG-10`|Обновление драйвера атомарно: новая версия успешно стартует **либо** откат на предыдущую|`FR-DRV-02`; Logic|
|`DRV-ENG-11`|При смене ядра — compatibility-check; несовместимый драйвер не запускается, событие `EVT-04`, IT видит понятный статус|`FR-DRV-03`; UC `ERR-09`|

## §4. Внутренний контракт Клиент↔Сервер (слой A)

> Защищённый протокол обмена данными между Клиентом и Сервером. **Только внутренний, наружу не публикуется.** Контракт (протокол, сериализация, ресинхронизация) — `TL-CORE`.

Продуктовые свойства слоя:

- Управление сессией (источник, громкость, mute, сценарий), чтение/запись разрешённых тегов, обновление состояния панели идут по этому контракту, не через открытый API.
- Состояние Клиента обновляется по обратной связи после каждой команды (поток PSD §1.3); механизм — `TL-CORE-04`.
- При потере связи Клиент↔Сервер очередь офлайн-событий **не строится**; при реконнекте — ресинхронизация состояния (Logic FL-PNL-LIFECYCLE); механизм — `TL-CORE-05`.
- Синхронизация нескольких клиентов одной комнаты (через сервер) — `TL-CORE-20`.
- Сторонние клиенты на этом контракте **не строятся** (он закрыт); кастомные интеграции работают через открытый API (§3).
