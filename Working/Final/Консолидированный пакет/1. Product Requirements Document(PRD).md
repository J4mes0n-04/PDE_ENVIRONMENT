# Product Requirements Document(PRD) — AV Control

> **Назначение.** Продуктовые требования к AV Control: цели, персоны и права, функциональные требования по модулям, нефункциональные требования, North Star (полярная метрика), критерии готовности.
> **Что живёт в других документах (здесь не дублируется).** Архитектура, протоколы, ОС, аппаратура → PSD (§2.2). Схемы данных и хранение → §2.5. Контракты API → §2.6. Пошаговые сценарии → Use Case Spec (§2.3). Область, границы, MVP-матрица, лимиты ресурсов → Scope (§2.7).
> **Условные обозначения.** Приоритет P0/P1/P2 — важность (раскладка по релизам — в §2.7). Статус: **C** — подтверждено источником, **H** — гипотеза, **V** — на валидации. Обоснование — трасс-тег к цели (OBJ). `[?уточнить]` — нужно решение или цифра.

# 2. Персоны и уровни прав (User Personas & Permissions Levels)

Описываются как **профили действий и прав**, а не должности: один человек может совмещать профили.

| Профиль                                        | Кто (персона)                 | Главная задача                       | Права (направление)                                                                                   |
| ---------------------------------------------- | ----------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `End User` (конечный пользователь)             | Участник встречи              | Управлять помещением во время сессии | BYOD, запуск сценариев, источник, громкость, mute, завершение. Без настроек и изменения конфигурации  |
| `Support Operator` (поддержка 1-й линии)       | Сервис-инженер заказчика      | Диагностировать типовые проблемы     | Статусы, логи, панель состояния, пакет диагностики; сервисные действия — по политике                  |
| `IT Admin` (IT-администратор)                  | Эксплуатация в инфраструктуре | Сопровождать систему                 | Пользователи, роли, сертификаты, сеть, время/NTP, обновления, бэкап/восстановление, аудит, интеграции |
| `Integrator Engineer` (AV-инженер интегратора) | Настройщик объекта            | Настроить помещение                  | Проект, устройства, драйверы, сценарии, интерфейс, теги, связи, тест команд, импорт/экспорт           |
| `Lead Integrator` (ведущий интегратор)         | Владелец проекта              | Управлять проектом и шаблонами       | + шаблоны, защита авторских наработок, пакет передачи объекта                                         |
| `Security Auditor` (ИБ-офицер)                 | Контроль ИБ                   | Проверять соответствие и действия    | Read-only: аудит, ИБ-события, политики, выгрузка в SIEM. Без правки проекта                           |
| `Vendor Support` (поддержка вендора)           | ТП iRidi                      | Помогать при инцидентах              | Временный явный доступ через удаленного доступа. Без постоянного скрытого доступа                     |

**Машинные «пользователи» (через API):** системы мониторинга/SIEM, бронирование/календарь, терминалы ВКС. Важен контракт, не UX.

**Принципы доступа.** Минимально необходимые права; разделение проектных и эксплуатационных действий; критичные действия — в аудит; сервисный доступ временный, отзывной и видимый IT/ИБ; конечный пользователь не видит инженерных сущностей.

**Экономические роли и ЛПР (вне матрицы прав).** IT-директор/CIO, дистрибьютор и заказчик-владелец — не операционные персоны: систему не эксплуатируют и уровней прав не имеют. Их операционные «руки» представлены здесь (IT-директор → `IT Admin`; гарантийная поддержка дистрибьютора → `Support Operator` / `Vendor Support`). Их собственные цели обслуживаются продуктовыми целями §1 (трассировка выше) и детально описаны в стратегическом пакете (JTBD, карта ЛПР/ЛВР). Коммерческие цели в PRD не дублируются.

**Формальная матрица прав** (профиль × действие × ресурс) формализуется с тех. лидом отдельно.

# 5. North Star Metric (Полярная метрика)

**Метрика.** Время до n-й рабочей комнаты — от начала настройки типовой комнаты серии до стабильного состояния, готового к сдаче (Time to Working Room, на тираже). 
**Формула.** Время от создания/импорта проекта до прохождения глобальных критериев приёмки (§6); целевой замер — на n-й однотипной комнате, а не на первой. 
**Целевое состояние.** Спецификация ≤ 1 раб. день; запуск ≤ 1 раб. день; n-я комната серии существенно быстрее первой; типовой сценарий без JavaScript; новый/исправленный драйвер без ожидания релиза ядра.
**Приоритет при конфликте:** переносимость/тираж важнее скорости первой комнаты.

**Поддерживающие метрики** (Template Reuse Rate — главная):

| Метрика                     | Что измеряет                                                               |
| --------------------------- | -------------------------------------------------------------------------- |
| Template Reuse Rate         | Доля проектов, собранных из шаблонов — главный показатель масштабируемости |
| Driver Lead Time            | Срок от заявки на драйвер до стендовой проверки                            |
| Commissioning Success Rate  | Доля комнат, запущенных без эскалации к senior-инженеру                    |
| First-line Resolution Rate  | Доля инцидентов, закрытых первой линией без R&D                            |
| Diagnostic Bundle Usage     | Доля инцидентов с полным пакетом диагностики с первого раза                |
| Security Baseline Pass Rate | Доля пилотов, прошедших базовый ИБ-фильтр без доработок                    |
| Rollback Success Rate       | Успешность восстановления после обновления/сбоя                            |

# 6. Критерии готовности (Definition of Done & Global Acceptance Criteria)

### 6.1 Definition of Done (критерии завершённости — внутренний взгляд)

DoD — внутренний чек-лист готовности. AV Control готов к MVP-пилоту, если выполнены все условия:

- **Функциональная полнота.** Реализованы и связаны между собой все требования **P0** модулей §3.
- **Сквозной путь.** Работает цепочка «создать/импортировать проект → запустить помещение → управлять → завершить».
- **Механизмы управления** (проверяются внутри, а не как внешний результат): преднастроенный сценарий отрабатывает (последовательность команд, задержки, условия); команда уходит оборудованию, обратная связь принимается, обновляется и отображается; при переключении источника состояние обновляется по обратной связи; завершение возвращает помещение в штатное состояние с записью события; единичный отказ устройства/драйвера не роняет помещение — ошибка фиксируется и понятно отображается; преобразования и связи тегов (с защитой от зацикливания) работают без JavaScript.
- **Жизненный цикл и эксплуатация.** Автозапуск сервера и серверного проекта после проверки целостности; безопасная остановка; переход в безопасный режим после серии неуспешных стартов; перезапуск без потери проекта; offline-обновление с проверкой целостности и откатом; проверяемое восстановление из бэкапа на совместимом устройстве.
- **ИБ-baseline и наблюдаемость на месте.** Аутентификация веб-интерфейса и API, RBAC, TLS (самоподписанный сертификат при отсутствии внешнего, без незашифрованного доступа), защищённые от удаления аудит-логи; панель состояния, логи с уровнями, пакет диагностики в один клик, автоочистка логов, сбор крэш-дампов.
- **JavaScript** (если включён в объёме первого релиза): изоляция скриптов, базовая проверка перед исполнением, логирование ошибок.
- **Offline-контур.** Все базовые функции работают в закрытой сети без облака.
- **Внешняя приёмка.** Пройдены все глобальные критерии приёмки §6.2.
