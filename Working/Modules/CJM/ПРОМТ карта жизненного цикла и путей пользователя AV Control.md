# 1. Задача

Нужно последовательно проработать конкретные пользовательские пути `JRN-*` для проектирования **веб-админки сервера AV Control**.

Работаем строго по одному пользовательскому пути за раз:

1. обсуждаем границы кейса;
2. уточняем основной пользовательский путь;
3. выявляем существенные развилки;
4. после согласования оформляем готовую карточку;
5. переходим к следующему `JRN`.

Не генерируй сразу множество карточек и не переписывай уже утверждённые блоки документа без необходимости.

# 2. Что это за документ

Документ условно можно назвать CJM, но это **не классический Customer Journey Map**.

Он ближе к многоуровневой **карте жизненного цикла и пользовательских путей профессионального продукта**:

1. верхний уровень — жизненный цикл системы;
2. следующий уровень — реестр пользовательских задач `JRN-*` и матрица ролей;
3. детальный уровень — конкретный пользовательский путь внутри веб-админки с действиями пользователя, реакциями системы и визуальной схемой.

В классическом CJM часто описываются:
- эмоции;
- ожидания;
- точки контакта с брендом;
- каналы;
- боли;
- удовлетворённость.

Здесь это не является основной задачей.

Документ создаётся прежде всего для **аналитика и дизайнера веб-админки**, поэтому главное:

> что пользователь хочет сделать → что конкретно делает → что происходит в системе → где меняется маршрут → в каком состоянии пользователь заканчивает задачу.

Карточки `JRN-*` находятся между:
- User Journey;
- Task Flow / User Flow;
- упрощённым Use Case Flow.

Не нужно искусственно добавлять эмоциональные шкалы и другие элементы классического CJM, если они не помогают проектированию интерфейса.

# 4. Область текущей работы

CJM прорабатывается для создания **веб-админки сервера AV Control**.

Поэтому:

- описываем действия пользователя внутри веб-админки;
- не исследуем действия до входа в веб-админку;
- не добавляем вопросы вроде «как пользователь узнал IP контроллера»;
- не детализируем процессы после выхода за границы веб-админки;

# 5. Основная терминология

## Контроллер

Физическое устройство AV Control, на котором работает серверная часть продукта.

## Сервер

Серверная часть AV Control, работающая на контроллере.

## Комплект

Утверждённый термин.

**Термин «проект» в новой документации не использовать.**

Комплект содержит:
- серверную часть логики;
- отдельные пользовательские интерфейсы;
- общую медиабиблиотеку интерфейсов;
- другие данные, относящиеся непосредственно к конфигурации решения.

## Динамические данные экземпляра

Часть уникальных данных конкретного контроллера/помещения должна находиться **вне комплекта, на уровне сервера**.

Это необходимо для масштабирования:

> один и тот же комплект можно использовать на нескольких самостоятельных контроллерах без создания новой версии комплекта.

Примеры таких данных могут включать адреса конкретного оборудования и клиентов, но полный набор ещё не определён.

**Открытый вопрос:** полный состав динамических данных экземпляра и правила их хранения/переноса.

## Изменение комплекта

Изменение:
- состава;
- логики;
- сценариев;
- интерфейсов;
- драйверов;
- других данных самого комплекта.

Приводит к новой версии комплекта.

## Масштабирование

Создание нового самостоятельного экземпляра системы на основе существующего комплекта **без изменения самого комплекта**.

## Восстановление

Возврат **той же системы/того же объекта** к сохранённому состоянию.

Восстановление и масштабирование — разные пользовательские задачи, даже если технически используют общие механизмы.

# 6. Важные утверждённые продуктовые решения

## Первый запуск

У нового или очищенного контроллера есть три основных намерения пользователя:

1. создать систему с нуля — `JRN-ACC-01`;
2. восстановить существующую систему — `JRN-ACC-02`;
3. создать новый экземпляр существующей системы — переход к `JRN-SCL-01`.

Обычный вход в уже настроенный контроллер сюда не относится.

`JRN-ACC-04` — отдельный сквозной путь доступа.

---

## Масштабирование

Масштабирование имеет два самостоятельных пути.

### `JRN-SCL-01`

Масштабирование на новом/очищенном контроллере.

Общая идея:

- пользователь входит в режим первого запуска;
- выбирает масштабирование;
- задаёт необходимые сетевые настройки;
- загружается существующий комплект;
- максимально переиспользуются данные существующего экземпляра;
- ролевая система, пользователи, панели и назначенные им интерфейсы должны максимально переноситься из исходных данных;
- пользователь задаёт только данные, уникальные для нового помещения, например фактические адреса оборудования/клиентов;
- создаётся новый самостоятельный экземпляр.

Цель:

> минимум ручных действий и максимум переиспользования существующей конфигурации.

### `JRN-SCL-02`

Масштабирование на уже инициализированном контроллере.

Контроллер уже имеет как минимум:
- административный доступ;
- собственную ролевую систему.

Пользователь применяет готовый существующий комплект и задаёт динамические данные нового экземпляра.

**Открытый вопрос:** что происходит с существующей ролевой системой, пользователями и другими серверными данными при применении данных исходного экземпляра.

---

## Драйверы

Есть два разных типа.

### Нативный драйвер

Поставляется вместе с ядром.

Отдельного пользовательского пути обновления нет — обновляется вместе с ядром через `JRN-MNT-03`.

### Конфигурационный драйвер

Поставляется отдельно файлом.

`JRN-DRV-02` — установка или обновление конфигурационного драйвера.

Пользователь может загрузить его:
- из общего управления драйверами;
- непосредственно во время создания или изменения комплекта.

Система должна проверить файл и совместимость драйвера с установленной версией ядра/универсального драйвера.

Получение нового ещё не существующего драйвера — организационный процесс вне веб-админки и отдельным `JRN` не является.

---

## Замена оборудования

`JRN-MNT-04` — замена управляемого устройства без изменения комплекта.

Если устройство заменяется эквивалентным и меняются только уникальные данные экземпляра на сервере — комплект не изменяется.

Если требуется изменение самого комплекта — используется `JRN-CHG-01`.

---

## Клиенты

`JRN-PNL-01` — первоначальное подключение клиентов и деплой интерфейсов.

`JRN-PNL-02` — замена существующего клиента или подключение нового клиента при эксплуатации.

Клиент и управляемое оборудование — разные пользовательские пути.

---

## Обычный вход

`JRN-ACC-04` — вход в уже настроенный контроллер.

Это **сквозной путь**, а не этап жизненного цикла.

Он может предшествовать:
- изменению комплекта;
- масштабированию;
- интеграции;
- обслуживанию;
- диагностике;
- восстановлению;
- другим административным задачам.

# 7. Уровень детализации карточек

Нужно писать **конкретные пользовательские действия**, а не абстрактные формулировки.

Плохо:

> Пользователь получает доступ к контроллеру.

Хорошо:

> Пользователь открывает в браузере веб-админку сервера по `IP:PORT`.

Плохо:

> Пользователь начинает первоначальную инициализацию.

Хорошо:

> Пользователь вводит логин и пароль первого администратора и подтверждает его создание.

Каждый шаг должен отвечать на два вопроса:

1. **Что конкретно делает пользователь?**
2. **Что в результате происходит или становится доступно в системе?**

При этом конкретность не должна превращаться в преждевременное проектирование интерфейса.

Хорошо:

> Пользователь выбирает восстановление контроллера.

Не нужно без утверждённого дизайна:

> Пользователь нажимает синюю кнопку «Восстановить» в правом нижнем углу карточки.

Фиксируем пользовательское действие и результат, но не придумываем:
- расположение кнопок;
- дизайн страниц;
- внешний вид элементов;
- внутреннюю техническую реализацию.

# 8. Главный принцип карточки

Основной материал для аналитика:

> **Основной путь + визуализация.**

Вся информация после них является вспомогательной и справочной.

Не дублируй основной путь в последующих разделах.

# 9. Утверждённый шаблон карточки

Используй следующий порядок:

## `JRN-XXX-00 · Название`

**Актор:**  
Кто выполняет задачу.

**Триггер:**  
Почему пользователь начинает путь.

**Начальное состояние:**  
В каком состоянии находится система и пользователь в момент начала.

**Цель:**  
Какого результата пользователь хочет достичь.

**Граница пути:**  
Где именно начинается и где заканчивается этот `JRN`. Что явно не входит в него.

---

## Основной путь

Используй таблицу:

| Шаг | Действие пользователя | Реакция системы / результат шага |
|---|---|---|
| 1 | Конкретное действие пользователя | Наблюдаемая реакция или новое состояние |
| 2 | ... | ... |

Основной путь должен содержать и существенные развилки.

Если пользователь выбирает другой самостоятельный путь, прямо указывай:

> переход к `JRN-XXX`.

---

## Визуализация

Располагается **сразу после основного пути**.

Это второе основное представление пользовательского сценария для аналитика и дизайнера.

Используй простую Mermaid-схему.

Требования:
- одна схема на один `JRN`;
- отображает основной путь;
- показывает только существенные развилки;
- без BPMN;
- без UML;
- без внутренней технической логики;
- без дублирования несущественных ошибок.

---

## Результат

Опиши достигнутое состояние пользователя и системы.

Не навязывай следующий сценарий.

Например:

> пользователь находится в обычной веб-панели с административными правами и может выполнять любые доступные ему операции.

А не:

> пользователь переходит к созданию комплекта.

---

Не превращать этот блок в подробное техническое задание.

# 10. Что НЕ использовать в карточках

Не создавать отдельный обязательный раздел:

> «Ключевые развилки и исключения».

Он был исключён сознательно.

Причины:
- он дублировал основной путь;
- существенно раздувал документ;
- превращался в аналитику поведения системы;
- уводил фокус от продуктового пользовательского пути.

Правило:

> если информация уже присутствует в основном пути или однозначно видна на визуализации, второй раз её не повторять.

Системные ошибки, внутренние проверки и валидации подробно не описывать, если они:
- не меняют пользовательский маршрут;
- не создают отдельную пользовательскую задачу;
- не создают существенную UX-проблему.

# 11. Работа с развилками

Существенная пользовательская развилка должна находиться непосредственно в основном пути.

Например:

> Пользователь выбирает:
> - запуск с нуля;
> - восстановление → `JRN-ACC-02`;
> - масштабирование → `JRN-SCL-01`.

И та же существенная развилка может быть показана на визуализации.

Не нужно после этого ещё раз создавать несколько абзацев с пересказом тех же вариантов.

# 12. Рабочий процесс

Для каждого следующего `JRN` работаем так:

### Шаг 1. Обсуждение

Я своими словами описываю, как вижу пользовательский путь.

Ты:
- проверяешь последовательность;
- находишь пропущенные продуктово значимые действия;
- отделяешь пользовательский путь от аналитической/технической детализации;
- указываешь спорные места;
- предлагаешь правки.

На этом этапе **не нужно сразу писать финальную карточку**, если есть значимые вопросы.

### Шаг 2. Фиксация

После согласования ты оформляешь полный Markdown-блок по утверждённому шаблону.

### Шаг 3. Вычитка

Я его проверяю и вношу замечания.

Правим только текущий `JRN`.

Не переписываем предыдущие карточки и разделы 1–4, если новая информация не создаёт реального противоречия.

# 13. Эталон уровня детализации

`JRN-ACC-01` уже проработан и является образцом уровня конкретики.

Его логика:

1. пользователь открывает веб-админку по `IP:PORT`;
2. система показывает экран первого запуска;
3. основной сценарий экрана — создание первого администратора;
4. на этом же экране доступны альтернативные пути:
   - восстановление;
   - масштабирование;
5. пользователь создаёт первого администратора;
6. далее может опционально настроить:
   - дату, время, часовой пояс, переход летнее/зимнее время;
   - логирование, уровни, лимиты и политику очистки;
   - сеть;
7. настройку времени, логирования и сети можно пропустить и выполнить позднее;
8. сеть настраивается последней, поскольку смена IP может потребовать переподключения;
9. после завершения пользователь оказывается в полноценной веб-панели с полными правами администратора;
10. путь не заставляет его сразу переходить к созданию комплекта или другой конкретной задаче.

Способ автоматической авторизации после создания администратора и механизм продолжения работы после смены IP оставляются аналитику.

# 14. Уже проработанный JRN-ACC-02

`JRN-ACC-02` — восстановление существующей системы при первом доступе к новому или очищенному контроллеру.

Принята следующая продуктовая логика:

1. пользователь открывает веб-админку по `IP:PORT`;
2. выбирает восстановление контроллера;
3. загружает резервную копию:
   - основной вариант — локальный файл;
   - гипотеза — получение из внутреннего сетевого хранилища по указанному адресу;
4. система проверяет резервную копию перед применением;
5. пользователь выбирает сетевые настройки:
   - основной вариант — применить настройки из резервной копии;
   - альтернативный — задать их вручную;
6. поведение при изменении IP аналогично `JRN-ACC-01`;
7. система автоматически приводит контроллер максимально близко к состоянию из резервной копии;
8. полный перечень автоматических действий определяют аналитик и технический лидер;
9. после восстановления пользователь **не считается автоматически вошедшим**;
10. система переводит его на страницу авторизации;
11. пользователь входит под одной из учётных записей, восстановленных из резервной копии;
12. если права позволяют, пользователь видит результат восстановления;
13. при полном успехе показывается успешный результат;
14. если есть проблемы — отображается список проблем и доступных действий;
15. резервная копия может быть значительно старше состояния системы перед аварией, поэтому обнаружение несоответствий после восстановления является нормальным сценарием;
16. результат восстановления и список проблем должны быть постоянно доступны, а не исчезать после закрытия одноразового окна;
17. пользователь устраняет проблемы средствами, доступными ему по его ролевой модели;
18. итог пути — полностью работающая восстановленная система.

В карточке `JRN-ACC-02` визуализация должна находиться **сразу после основного пути**, а уже после неё:
- результат;
- связанные пути;
- открытые вопросы;
- связанные требования.

# 15. Важный принцип восстановления

Не считать:

> «резервная копия успешно распакована»

равным:

> «система успешно восстановлена».

Для пользователя итогом восстановления является **рабочая система**.

После применения старой резервной копии могут возникнуть реальные расхождения:
- изменились адреса клиентов;
- клиент недоступен;
- оборудование было заменено;
- изменилась сеть;
- состояние физической инфраструктуры уже не соответствует резервной копии.

Веб-админка должна позволять пользователю увидеть такие проблемы и продолжить их устранение.
