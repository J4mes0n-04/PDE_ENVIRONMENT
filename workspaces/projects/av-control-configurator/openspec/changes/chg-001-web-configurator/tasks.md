# Срезы поставки для ASE

Задачи не являются источником истины Pack. После Ready они могут войти в `ase-handoff.md`.

## 1. Библиотека и каркас рабочего пространства

- [ ] 1.1 Реализовать возможность открытия конфигуратора через веб-браузер без необходимости установки отдельного настольного приложения. Обеспечить корректную загрузку на поддерживаемых платформах (Windows, macOS, Linux) по локальному адресу контроллера.
- [ ] 1.2 Разработать экран `Э-1`:
    - Отобразить полный список доступных комплектов с основными атрибутами (название, статус, дата последнего изменения).
    - Добавить функционал создания нового комплекта с возможностью ввести название и принадлежность к проекту.
    - Реализовать возможность входа в уже существующий комплект из списка для последующего редактирования.
    - Добавить предварительный просмотр состава комплекта перед входом.
- [ ] 1.3 Разработать экран `Э-2`, включающий три рабочие зоны:
    - Дерево элементов (структура комплекта и его компонентов).
    - Холст/состав комплекта для визуального редактирования схемы и интерфейса.
    - Инспектор свойств для просмотра и изменения параметров выбранных элементов.
    - Сделать интерфейс таким образом, чтобы блоки серверной части и клиентских интерфейсов были явно различимы визуально.
    - Обеспечить одновременное отображение всех трёх зон, возможность выделения и взаимодействия между ними.
- [ ] 1.4 Реализовать механизм сохранения пользовательских настроек по границам/размерам областей рабочего пространства между сессиями:
    - Хранить размеры и конфигурацию компоновки в Local Storage браузера.
    - При следующем входе пользователя автоматически восстанавливать предыдущую компоновку интерфейса.
- [ ] 1.5 Добавить отображение индикатора наличия несохранённых изменений по открытому комплекту:
    - В явном виде выводить предупреждение о несохранённых изменениях (например, иконка или панель уведомлений).
    - Сделать информирование о риске потери данных при попытке закрыть или переключить комплект с несохранёнными изменениями.
- [ ] 1.6 Запретить сохранение комплекта без заполненного названия:
    - Реализовать валидацию на уровне интерфейса и бекенда.
    - Разрешить сохранение комплекта с неполным/черновым составом только если введено название, с явным предупреждением о неполноте.
- [ ] 1.7 Организовать механизм совместной работы:
    - Если один пользователь начал редактирование комплекта, остальные могут только просматривать его в режиме «только чтение» с соответствующим указанием статуса (например, надпись «редактирует: [ФИО]», блокировка кнопок редактирования).
    - Предоставить возможность получить права на редактирование после сохранения текущим пользователем или если он явно завершил сеанс («отпустил» комплект).
    - Хранить информацию о текущем редакторе и времени последнего изменения.
    - В случае закрытия браузера без сохранения предусмотреть таймаут, после которого комплект снова доступен для редактирования другому пользователю.

## 2. Ручная сборка и связи

- [ ] 2.1 Ограничить добавление серверной части:
    - Разрешить пользователю добавить в состав комплекта ровно одну серверную часть (компонент backend).
    - Если серверная часть уже добавлена, заблокировать возможность добавить вторую серверную часть, отобразить информативное предупреждение.
    - Разрешить добавлять неограниченное количество интерфейсных частей (frontend UI), порядок добавления — произвольный.
    - Обеспечить визуальное отображение состояния: сколько серверных частей и интерфейсов включено в текущий комплект.
- [ ] 2.2 Создание связей между сущностями:
    - Реализовать механизм перетаскивания (drag-and-drop) для создания связей между элементами комплекта.
    - Разрешать создание связи только между существующими на данный момент сущностями, подходящими по типу (например, device ↔ interface).
    - При попытке создать невалидную связь информировать пользователя о причине невозможности (несовместимость типов, отсутствие сущности и т. п.).
    - Поддерживать возможность просмотра всех существующих связей между сущностями на холсте или в отдельном списке.
- [ ] 2.3 Работа с зависимостями при удалении:
    - При попытке удалить сущность, которая имеет активные связи с другими элементами:
        - Автоматически отображать список всех элементов и компонентов, зависящих от данной сущности (например, всплывающее окно со схемой/таблицей зависимостей).
        - Разрешать или запрещать удаление в зависимости от типа зависимости (критичная/некритичная), с подробным предупреждением о возможных последствиях.
        - Реализовать переход по зависимостям для быстрого просмотра и правки затронутых связей.
- [ ] 2.4 Подсветка ошибок и ведение сводного списка:
    - Если на этапе сборки выявлены ошибки или некорректные связи, автоматически подсвечивать соответствующие элементы на холсте или в дереве элементов (например, красным контуром, иконкой ошибки).
    - Собрать общий (сводный) список всех текущих ошибок и предупреждений, доступный из основной панели управления.
    - Предоставить быстрый переход от строки ошибки в списке к соответствующему элементу на экране для оперативного исправления.
    - Для каждой ошибки/предупреждения предоставлять краткое описание и возможные пути решения.
- [ ] 2.5 Типовой сценарий без JavaScript:
    - Обеспечить возможность сборки и визуального проектирования стандартных сценариев работы комплекта без необходимости писать или редактировать JavaScript.
    - Предусмотреть визуальный редактор для создания сценариев (настройка событий, условий, последовательности действий через UI).
    - Гарантировать, что все базовые функции и связи между элементами комплекса достигаются средствами интерфейса, без ручного кода.
    - Описать в документации типовые сценарии, которые должны быть выполнимы полностью средствами визуального редактора.

## 3. Мастер (детализировано)

- [ ] 3.1 Интеграция мастера внутрь экрана `Э-2`:
    - Мастер должен появляться прямо на экране `Э-2` (рабочая зона приложения) в следующих случаях:
        - При создании нового комплекта — запускать мастер автоматически после нажатия на кнопку создания.
        - При добавлении любых новых устройств в уже открытый комплект — мастер инициируется для добавления и базовой настройки новых устройств.
    - Необходимо обеспечить, чтобы мастер не перекрывал и не затмевал полностью остальные рабочие зоны; интеграция в виде всплывающего окна/панели поверх `Э-2` или сбоку (на усмотрение UX).
    - При завершении работы мастера изменения моментально отображаются в составе комплекта на `Э-2`.

- [ ] 3.2 Автоматическое создание интерфейса по умолчанию (MVP):
    - Когда пользователь создаёт комплект через мастер, автоматически добавлять один базовый интерфейс (экран пользователя).
    - Для первого экрана автоматически размещать основные виджеты (например, обычные управляющие элементы для устройств, добавленных в комплект).
    - Обеспечить минимальный набор виджетов для управления устройствами без дополнительных действий пользователя.
    - Реализовать простую структуру страницы: если устройство добавлено, его первичные управляемые функции должны отобразиться на экран автоматически через соответствующие виджеты.

- [ ] 3.3 Применение или корректировка состава одним действием:
    - В мастере отображать предложенный состав комплекта (устройства, интерфейс, связи, виджеты) в виде списка/превью с возможностью редактирования.
    - Пользователь должен принять предложенный состав целиком, либо внести коррективы (например, убрать или заменить некоторые элементы), после чего подтвердить действие.
    - Только после подтверждения вносить изменения в основной комплект; если мастер закрыт без подтверждения, никаких изменений сохраняться не должно.
    - Предусмотреть ясную кнопку/действие для финального принятия или отмены изменений, с соответствующим предупреждением при попытке закрыть мастер без сохранения.

- [ ] 3.4 Обработка ошибок в мастере:
    - Все ошибки, возникающие во время работы мастера, должны быть явно разделены на блокирующие (не позволяют завершить шаг/мастер) и предупреждающие (не обязательные к исправлению).
    - Блокирующие ошибки (например, некорректная конфигурация устройства, обязательные поля не заполнены) должны отображаться с указанием причины и не давать продолжить до исправления.
    - Для пустых или неполных конфигураций ("пустая основа") мастер должен запросить явное подтверждение завершения, показывая предупреждение о потенциальных проблемах или необходимости донастройки.
    - Все сообщения должны быть лаконичны, понятны и привязаны к конкретным полям/шагам.

- [ ] 3.5 Унификация команд для результатов мастера и ручной сборки:
    - Все изменения, которые получил комплект через мастер (создание, добавление устройств, связывание, создание интерфейса и виджетов), должны формироваться теми же командами/действиями, что и при ручной сборке через UI.
    - Необходимо обеспечить, чтобы последующая история изменений комплекта (history/undo/redo) отображала действия, совершённые через мастер, наравне с ручной работой пользователя.
    - Это обеспечит единообразие аудита, отмены действий и поддержки сценариев совместной работы.

- [ ] 3.7 Имя и описание для создаваемого экрана:
    - При создании интерфейсного экрана в мастере запрашивать у пользователя только поля "Имя" и "Описание" экрана.
    - Не включать на этом шаге поля о правах доступа/допуске (например, не спрашивать, кому экран доступен — управление этим предусмотрено только на продвинутых этапах настройки).
    - Предусмотреть валидацию на заполнение имени (без него создание не разрешать) и, по желанию, ограничение по длине и символам.

## 4. Гигиена, неполное железо, версия (детализация)

- [ ] 4.1 Автоматически искать и предлагать на удаление:
    - Реализовать сканирование состава комплекта и проекта на наличие элементов, которые больше не используются ни в одном из интерфейсов/сценариев:
        - неиспользуемые связи между устройствами/виджетами,
        - устройства, отсутствующие в связях и интерфейсах,
        - элементы интерфейса, не привязанные к сценариям или устройствам,
        - медиаресурсы (иконки, изображения, файлы), не используемые в визуальных компонентах.
    - Для найденных неиспользуемых элементов показывать список с возможностью индивидуального или массового подтверждения удаления.
    - Удаление необязательное (не блокирует деплой), но сопровождается предупреждением о лишнем "мусоре".
    - Предусмотреть журнал/трассировку очистки для аудита: кто/когда удалил, что удалено.

- [ ] 4.2 Ведение и визуализация статусов устройств:
    - Для каждого устройства в составе хранить статус: "доступно" (готово к работе), "ожидается" (отсутствует или будет подключено позже), "эмуляция" (в режиме софт-эмуляции).
    - На основном экране и в дереве устройств явно отображать текущий статус (иконка, цвет, пояснение).
    - В списках очистки не относить устройства со статусом "ожидается" к неиспользуемым/мусорным — их нельзя удалять автоматически.
    - Для элементов в статусе "ожидается" предусмотреть отдельно отслеживаемый список для напоминаний, но без предупреждений о "ненужности".

- [ ] 4.3 Управление командами к устройствам со статусом "ожидается":
    - При генерации команд управления и взаимодействия устройства, которые находятся в статусе "ожидается", должны быть исключены из всех процессов отправки команд (не отсылаются на стенд и в менеджер устройств).
    - Для случаев, когда пользователь явно пытается управлять "ожидающим" устройством, выводить информативное уведомление ("Данное устройство еще не подключено, команды не отправляются").
    - Логировать попытки автоматических/ручных команд к "ожидающим" устройствам для диагностики.

- [ ] 4.4 Управление версиями комплекта:
    - При каждом существенном изменении состава (правки, добавления, удаления устройств/медиа/связей/сценариев) автоматически или по команде пользователя сохранять новую версию комплекта с привязкой к истории изменений (описание, кто и что изменил).
    - Обеспечить интерфейс просмотра списка всех версий комплекса с датами и комментариями.
    - Реализовать возможность отката к любому прежнему состоянию комплекта — с отображением перечня отличий между версиями (diff; в том числе автоматический предпросмотр).
    - При откате версии показывать предупреждение о потенциальных потерях данных, требовать подтверждение у пользователя.
    - Версии хранить с уникальными идентификаторами и возможностью восстановления даже в случае сложных изменений (например, удалённых конфигов или устройств).

## 5. Визуал поверхности «К» (Детализация)

- [ ] 5.1 Применить тёмную тему:
    - В качестве основной фоновой поверхности использовать глубокий тёмный цвет (`#202226` или аналогичный).
    - Для выделения акцентов использовать цвет `#4F8FA6` (кнопки действия, выделение элементов, чипы, тумблеры, ссылки, а также текстовые выделения и иконографика акцентов).
    - Стандартный цветовой набор для текста, линий, вспомогательных элементов (разделители, тени, подложки) привести к согласованному виду с основной тёмной цветовой схемой.
    - Для типографики использовать семейство IBM Plex Sans для основного текста и IBM Plex Mono — для технических и кодовых вставок, информационных табличек.
    - Обеспечить читаемость межстрочного интервала и кеглей для основных форм и таблиц, не менее 16px для базового текста.
    - Проработать состояние фокуса/hover/active – акцент не должен сливаться с основой, предусмотреть полупрозрачные подложки/обводки для интерактивных элементов.
    - Макеты/стили координально тестировать на реакцию освещения и разметку, чтобы избежать “замыливания” или малоразличимых оттенков.

- [ ] 5.2 Проверка соответствия чек-листу по визуальному банку:
    - Провести пошаговую проверку всех пунктов чек-листа `VIS-BAN-01`…`VIS-BAN-18` на макетах экранов `Э-1` и `Э-2`:
        - Убедиться, что каждый критерий (отступы, размеры кнопок, скругления, границы областей, читабельность, цветовые соответствия, пиксель-перфект адаптация) выполнен в точности, в т.ч. на панелях мастера.
        - Документировать любые найденные несоответствия с привязкой к конкретному макету или компоненту.
        - По результатам оформить отдельное ревью с отмеченными пунктами чек-листа, которые выполнены/требуют доработки.
        - Особое внимание уделить отображению акцентных и фоновых элементов (нет ли паразитных бликов/некорректных наложений слоёв).
        - Зафиксировать дату и участников визуального тестирования.

- [ ] 5.3 Проверка кириллической локализации и контраста:
    - На всех макетах и рабочих прототипах пройтись по всем надписям на кириллице (русский и английский):
        - Проверить корректность отображения шрифтов (нет ли подмены решений типа fallback).
        - Убедиться, что заглавные, строчные, спецсимволы, технические обозначения отображаются читаемо и в едином стиле.
        - Прогнать тест на контрастность акцентных элементов (`#4F8FA6`) на фоне тёмной базы (`#202226`) — не менее 4.5:1 для важных и 3:1 для менее значимых элементов (WCAG AA).
        - Задокументировать результаты проверки, приложить скриншоты спорных/граничных мест.
        - Внести необходимые правки до финальной приемки визуала, повторно подтвердить соответствие чек-листу по результатам исправлений.

## 6. Доработка холста, мастера и устранение дефектов `DC-001` (детализация)

- [ ] 6.1 Реализовать создание связи методом drag&drop устройства на виджет:
    - Пользователь должен иметь возможность перетащить элемент типа "устройство" (device) на виджет, находящийся на холсте.
    - Также поддержать перетаскивание из дерева устройств в структуре проекта на конкретный виджет на холсте.
    - Осуществлять создание только допустимых связей: разрешать только направление device → widget. Перетаскивание других типов элементов, а также создание обратных связей должны быть явно заблокированы — с выдачей подсказки о недопустимости действия.
    - После создания связи визуально отображать соединение на холсте (стрелка, линия, маркер).
    - Добавить всплывающие подсказки или визуальные маркеры при наведении, указывающие на возможность соединения.

- [ ] 6.2 При открытии мастера (окон/панелей настройки):
    - Исключить ситуацию, при которой элементы управления (кнопки) на холсте перекрываются окнами мастера, особенно если это затрудняет или делает невозможным доступ к управляющим элементам.
    - Реализовать логику динамического позиционирования мастера: окно мастера должно отображаться в той области UI, где оно не перекрывает важные части рабочего пространства (таск-бары, кнопки, боковые панели).
    - При необходимости добавлять затемнение/блюр или визуальное отделение для фона, но не скрывать базовые элементы управления.
    - При изменении размера окна или масштабировании холста мастер обязан корректно перерасполагаться без выхода за пределы видимой области.

- [ ] 6.3 Корректное сохранение состояния редактора сценария:
    - После того, как пользователь редактирует шаг сценария и затем выбирает другой шаг, все внесенные значения должны сохраняться автоматически или с понятным триггером (например, при подтверждении действия).
    - При возврате к ранее отредактированному шагу редактор должен подгружать ранее сохраненные изменения без потери данных.
    - Реализовать механизм уведомления пользователя о необходимости сохранения, если имеются незавершенные изменения перед переключением шага.
    - Добавить автоматическое тестирование сохранения значений сценария при навигации между шагами.

- [ ] 6.4 Автоматическая очистка и валидация сценариев при удалении сущностей:
    - При удалении любого объекта (устройства, виджета, связи) автоматически искать и удалять все связанные с ним элементы и шаги в сценариях.
    - Производить проверку всех ссылок (references) в сценарных конструкциях — запрещать сохранение сценария, если присутствуют "битые" или пустые ссылки.
    - Реализовать информирование пользователя о том, какие шаги или элементы сценария были автоматически очищены или требуют ручной правки из-за удаления сущностей.
    - Хранить в логе всю информацию об автоматических чистках — для последующего разбора ошибок.

- [ ] 6.5 Хранение уникальных версионных снимков и организация серверной блокировки:
    - Для каждого важного изменения (создание связи, перемещения, удаления, изменения сценариев и др.) автоматически создавать уникальный снимок состояния (version snapshot) всей рабочей области.
    - Хранить снимки с уникальными идентификаторами, датой времени, а также метаданными о пользователе и типе изменения.
    - Реализовать механизм серверной блокировки: при открытии и редактировании комплекта пользователем, остальные участники должны видеть предупреждение о блокировке, а попытки конкурирующего изменения блокируются и логируются.
    - Предусмотреть интерфейс управления версиями: просмотр списка снимков, восстановление любой предыдущей версии с отображением diff.
    - В случае критических сбоев/конфликтов предоставить ручной режим "force unlock" с обязательным журналированием действий.

- [ ] 6.6 Локальная отдача шрифтов и подтверждение визуальной части:
    - Все используемые в проекте шрифты (например, IBM Plex Sans и Mono) загружать и отдавать с серверов/каталогов проекта, исключая загрузку со сторонних CDN. Проверить корректность локального подключения на всех целевых средах (dev, stage, prod).
    - При каждом релизе обязателен скриншот/видео-контроль факта локального отображения всех шрифтов на основных экранах.
    - Для блока визуального контроля итоговой реализации добавить отдельный VIS-подтверждающий документ (evidence): фиксировать результаты визуальных тестов и проверки соответствия визуальному банку, включая образцы скриншотов и перечень участников проверки.
