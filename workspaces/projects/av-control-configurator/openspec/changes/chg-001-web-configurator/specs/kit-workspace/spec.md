# Delta for kit-workspace

## ADDED Requirements

### Requirement: AC-001 Конфигуратор в браузере
The system SHALL позволять инженеру настраивать комплект в браузере без установки настольного приложения.

#### Scenario: Вход без Studio
- **GIVEN** инженер находится у контроллера в закрытом контуре
- **WHEN** он открывает веб-конфигуратор в браузере
- **THEN** доступны библиотека комплектов и рабочее пространство без настольной среды разработки

### Requirement: AC-002 Библиотека комплектов
The system SHALL предоставлять экран `Э-1` как точку входа: выбрать существующий комплект или создать новый.

#### Scenario: Старт работы
- **WHEN** инженер открывает конфигуратор
- **THEN** домашний экран показывает библиотеку комплектов и действие создания нового комплекта, а не аналитический дашборд

### Requirement: AC-003 Одно рабочее пространство
The system SHALL собирать и править комплект на экране `Э-2` в одном окне: дерево, холст или состав, инспектор.

#### Scenario: Данные одной задачи
- **GIVEN** инженер открыл комплект
- **WHEN** он собирает серверную часть и интерфейсы
- **THEN** нужные данные доступны без цепочки вкладок и вложенных блокирующих окон

#### Scenario: Границы областей
- **GIVEN** инженер изменил ширину дерева и инспектора
- **WHEN** он закрывает и снова открывает комплект
- **THEN** границы областей восстановлены

### Requirement: AC-004 Различимость частей комплекта
The system SHALL явно различать серверную часть и клиентские интерфейсы составом блоков на всём протяжении работы.

#### Scenario: Не два приложения
- **WHEN** инженер работает в `Э-2`
- **THEN** серверная часть и клиентские интерфейсы видны как части одного комплекта, а не как отдельные приложения

### Requirement: AC-005 Нелинейный порядок сборки
The system SHALL позволять добавлять серверную часть и интерфейсы в любом порядке, который задаёт инженер.

#### Scenario: Сначала интерфейс
- **GIVEN** новый комплект ещё без серверной части
- **WHEN** инженер сначала создаёт клиентский интерфейс
- **THEN** система не требует предварительно создать серверную часть

### Requirement: AC-006 Два способа сборки
The system SHALL поддерживать ровно два способа сборки — мастер и ручной режим — и их произвольное сочетание в одной работе. «Готовое устройство» SHALL быть механизмом внутри способов, не третьим режимом.

#### Scenario: Чередование
- **GIVEN** комплект создан мастером
- **WHEN** инженер продолжает сборку вручную
- **THEN** оба способа действуют над одним комплектом

#### Scenario: Не третий режим
- **WHEN** инженер добавляет устройство из каталога с автоподстановкой состава
- **THEN** это не отдельный корневой режим сборки и не «готовая комната»

### Requirement: AC-007 Несохранённые изменения
The system SHALL показывать несохранённые изменения по каждому открытому комплекту.

#### Scenario: Грязность комплекта
- **GIVEN** инженер изменил комплект и не сохранил
- **WHEN** он смотрит на шапку или библиотеку этого комплекта
- **THEN** видно, что есть несохранённые изменения

### Requirement: AC-008 Сохранение по названию
The system SHALL блокировать сохранение комплекта без названия и SHALL разрешать сохранение неполного комплекта, если название задано.

#### Scenario: Нет названия
- **GIVEN** у комплекта нет названия
- **WHEN** инженер пытается сохранить
- **THEN** сохранение блокируется

#### Scenario: Неполный с названием
- **GIVEN** у комплекта есть название и отсутствует часть устройств
- **WHEN** инженер сохраняет
- **THEN** прогресс сохраняется

### Requirement: AC-009 Модалка только для разрушения
The system SHALL использовать модальное окно только для необратимого подтверждения и только на одном уровне.

#### Scenario: Подтверждение удаления
- **WHEN** инженер подтверждает необратимое удаление
- **THEN** открывается не более одной модалки

#### Scenario: Обычная правка
- **WHEN** инженер правит свойства в инспекторе
- **THEN** модалка не открывается

### Requirement: AC-010 Экраны без назначения доступа
The system SHALL позволять задать у экрана имя и описание как свойства комплекта и SHALL NOT задавать, кому этот экран доступен. Назначение доступа полностью решает админка доступа вне конфигуратора.

#### Scenario: Нет поля для кого
- **WHEN** инженер создаёт или правит клиентский экран
- **THEN** он задаёт имя и описание экрана и не видит поля привязки к роли, пользователю или правилу доступа

#### Scenario: Доступ снаружи
- **WHEN** нужно решить, кто увидит экран в помещении
- **THEN** это не делается в конфигураторе комплекта

### Requirement: AC-011 Типовой сценарий без скрипта
The system SHALL позволять собрать типовой сценарий комплекта без JavaScript. Скрипт остаётся запасным путём сложного случая.

#### Scenario: Типовая комната
- **WHEN** инженер собирает типовой сценарий средствами конфигуратора
- **THEN** для завершения не требуется писать JavaScript

### Requirement: AC-012 Одна серверная часть
The system SHALL допускать не более одной серверной части в комплекте и SHALL не ограничивать число клиентских интерфейсов.

#### Scenario: Вторая серверная часть
- **GIVEN** в комплекте уже есть серверная часть
- **WHEN** инженер пытается добавить ещё одну
- **THEN** система не создаёт вторую серверную часть

#### Scenario: Несколько интерфейсов
- **WHEN** инженер добавляет дополнительные клиентские интерфейсы
- **THEN** число интерфейсов не ограничивается конфигуратором

### Requirement: AC-013 Связь перетаскиванием
The system SHALL создавать связь только между существующими совместимыми сущностями. Перетаскивание SHALL быть основным способом связывания с полным покрытием, не частичным.

#### Scenario: Совместимые сущности
- **GIVEN** две существующие совместимые сущности
- **WHEN** инженер перетаскивает связь между ними
- **THEN** связь создаётся

#### Scenario: Несовместимые или несуществующие
- **WHEN** инженер пытается связать несовместимые сущности или сущность, которой нет в комплекте
- **THEN** связь не создаётся

### Requirement: AC-014 Удаление с зависимостями
The system SHALL перед удалением связанной сущности показать зависимости и SHALL NOT удалять её молча.

#### Scenario: Сущность со связями
- **GIVEN** устройство связано с виджетами
- **WHEN** инженер инициирует удаление устройства
- **THEN** система показывает зависимости и ждёт подтверждения

### Requirement: AC-015 Ошибка на элементе
The system SHALL подсвечивать ошибку на элементе, а не только фокусом или тостом, и SHALL вести сводный список ошибок.

#### Scenario: Ошибка свойства
- **WHEN** у элемента некорректное значение
- **THEN** ошибка видна на элементе и в сводном списке
