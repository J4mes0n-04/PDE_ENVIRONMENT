# Срезы поставки для ASE

Статус: `draft`.

Задачи не являются источником истины Pack и не разрешают реализацию из PDE. После подтверждения change они могут стать основой delivery slices — срезов поставки — в `ase-handoff.md`. Каждый пункт ниже требует наблюдаемого результата и отдельной трассировки к требованию.

## 0. Discovery-срез до реализации

Название среза: получить решения и измерения, без которых базовый слой (foundation) нельзя перевести в Ready.

- [ ] 0.1 Проверяющий открывает протокол `MET-UI-001` и видит отдельные foundation-пути: вход в разрешённую оболочку, переход через sidebar, решение dirty state и распознавание базового состояния; для каждого пути записаны валидный старт, успешный результат и исключения (`MET-UI-001`, `AC-001`, `AC-004`, `AC-005`, `AC-007`).
- [ ] 0.2 Исследователь проверяет доступный текущий продукт или прототип и фиксирует воспроизводимый baseline `MET-UI-001`; если измеряемого интерфейса нет, протокол содержит «не измерено» с причиной, а не нулевое или придуманное значение (`MET-UI-001`).
- [ ] 0.3 После назначения уполномоченных владельцев рецензент видит в контракте `MET-UI-001` утверждённые target, минимальную выборку, сегменты, источник, validation window, владельца данных и правило решения; до этого все поля явно остаются блокирующими (`MET-UI-001`).
- [ ] 0.4 Security- и Product-рецензенты получают версионированную матрицу «роль × действие × ресурс»; Security Auditor имеет доступ к аудиту только для чтения, а неизвестная комбинация получает запрет по умолчанию, без выдуманных прав Support Operator или Room Operator (`AC-002`, `AC-003`, `NFR-002`).
- [ ] 0.5 Product и UX-рецензенты получают утверждённый перечень верхнеуровневых разделов и порядок sidebar; до решения прототип проверяет механику навигации на тестовом реестре, не объявляя его финальной информационной архитектурой (`AC-004`).
- [ ] 0.6 UX- и Security-рецензенты фиксируют требуемый WCAG-уровень и перечень сочетаний текста, элементов управления, фокуса и семантических состояний; отсутствие решения остаётся блокером выпуска (`NFR-004`).
- [ ] 0.7 QA фиксирует кандидатную матрицу совместимости с точными браузерами, ОС, viewport, zoom, системным масштабом и целевым оборудованием Admin Web UI; ни одна комбинация ещё не помечена поддерживаемой без прогона (`NFR-005`).
- [ ] 0.8 Engineering и Product фиксируют сценарии, среду, объём данных, cold/warm режим и метод сбора сырых performance-измерений; числовой порог до замера отсутствует (`NFR-006`).
- [ ] 0.9 UX-рецензент видит draft-каталог семантических токенов с ролями поверхностей, текста, границ, фокуса и состояний; спорный акцент имеет открытое решение и не помечен baseline (`AC-010`, `NFR-004`).
- [ ] 0.10 Рецензент выпуска видит, что Outcome Owner, Data Owner, Risk Owner, Release Owner и Evidence Owner остаются «не назначены», а Redmine — `Не создана`; агентские или условные имена отсутствуют.

## 1. Единая оболочка, роли и навигация

Название среза: аутентифицированная административная роль открывает только разрешённые разделы в одной оболочке.

- [ ] 1.1 IT Admin входит в Admin Web UI, выбирает разрешённый раздел и видит его в области содержимого той же оболочки; sidebar и сессия не создаются повторно (`AC-001`).
- [ ] 1.2 При искусственном отказе данных выбранного раздела IT Admin видит error state внутри области содержимого, а общая оболочка и разрешённая навигация остаются доступными (`AC-001`).
- [ ] 1.3 Security Auditor входит с серверным разрешением только на чтение аудита и видит разрешённый пункт без элементов изменения пользователей, ролей или аудита (`AC-002`).
- [ ] 1.4 После отзыва права во время сессии запрещённый пункт исчезает, открытая область показывает permission-denied, а повтор изменяющего действия не уходит на сервер как разрешённое (`AC-002`).
- [ ] 1.5 Security Auditor вводит прямой URL маршрута управления пользователями и видит permission-denied без защищённых данных и элементов управления (`AC-003`).
- [ ] 1.6 После отзыва права пользователь применяет back/forward браузера к ранее открытой странице и не видит кешированное запрещённое содержимое (`AC-003`).
- [ ] 1.7 Пользователь с двумя разрешёнными разделами одним действием выбирает второй пункт sidebar и видит новый контент и единственный корректный active indicator — индикатор активного пункта (`AC-004`).
- [ ] 1.8 Пользователь проходит назад и вперёд по двум разрешённым маршрутам и на каждом шаге видит синхронные URL, содержимое и active state sidebar (`AC-004`).
- [ ] 1.9 Аутентифицированный пользователь выполняет разрешённое действие; сетевой протокол показывает серверную проверку субъекта, действия и ресурса до подтверждённого результата (`NFR-002`).
- [ ] 1.10 Проверяющий подменяет роль в клиентском состоянии и отправляет защищённый запрос; сервер отказывает, ресурс не изменён, оболочка показывает безопасное auth или permission состояние (`NFR-002`).

## 2. Защита dirty state

Название среза: редактируемый контекст не теряется и не сохраняется без явного решения пользователя.

- [ ] 2.1 Инженер изменяет разрешённое поле, выбирает другой раздел и видит три различимых действия «Сохранить», «Не сохранять» и «Отмена» до смены маршрута (`AC-005`).
- [ ] 2.2 Инженер выбирает «Сохранить» при доступном сервере и переходит в новый раздел только после подтверждённого сохранения; dirty indicator снимается после ответа (`AC-005`).
- [ ] 2.3 Инженер выбирает «Не сохранять», переходит в новый раздел, затем возвращается и видит последнюю подтверждённую версию без отправки сохранения (`AC-005`).
- [ ] 2.4 Инженер выбирает «Отмена» и остаётся на прежнем маршруте с теми же введёнными значениями и dirty indicator (`AC-005`).
- [ ] 2.5 При fault injection сохранения инженер остаётся в исходном разделе, видит ошибку, а все введённые значения доступны для повтора, discard или cancel (`AC-005`).
- [ ] 2.6 Повторное нажатие «Сохранить» после уже подтверждённого результата не создаёт вторую запись и не повторяет завершённый переход (`AC-005`).

## 3. Базовые состояния и модель ошибок

Название среза: пользователь различает загрузку, отсутствие данных, ошибку, offline и отсутствие разрешения.

- [ ] 3.1 Пользователь открывает разрешённый раздел с задержанным локальным ответом и видит loading внутри сохранённой оболочки; элементы, зависящие от данных, недоступны (`AC-006`).
- [ ] 3.2 Локальный сервер успешно возвращает ноль объектов, и пользователь видит фактическое empty-состояние с разрешённым действием либо без действия, если права его запрещают (`AC-006`).
- [ ] 3.3 Локальный API возвращает отказ вместо списка, и пользователь видит error с retry, а не empty или бесконечный loading (`AC-006`).
- [ ] 3.4 Авторизованный пользователь запускает разрешённую операцию, получает доменную ошибку и видит безопасное сообщение, следующее действие и сохранённое подтверждённое состояние (`AC-007`).
- [ ] 3.5 При разрыве локальной связи пользователь видит offline, неактуальные данные явно помечены, изменяющие элементы управления заблокированы, а скрытая очередь команд отсутствует (`AC-007`).
- [ ] 3.6 После восстановления связи offline остаётся до resync; затем пользователь видит новое подтверждённое серверное состояние, а не старый snapshot — снимок состояния (`AC-007`).
- [ ] 3.7 Пользователь без права на маршрут видит permission-denied с разрешённым выходом и без сведений о защищённых объектах (`AC-007`).
- [ ] 3.8 Support Operator с диагностическим разрешением открывает ошибку и видит отдельно severity, безопасное сообщение, следующее действие и разрешённый technical context (`AC-009`).
- [ ] 3.9 Пользователь без диагностического разрешения открывает ту же ошибку и не видит трассировку стека, секрет, внутренний адрес или защищённые данные запроса и ответа (`AC-009`).
- [ ] 3.10 Сервер возвращает ненормализованный технический текст; пользователь видит безопасное локализованное резервное сообщение, а запись дефекта содержит факт нарушения контракта без раскрытия текста в UI (`AC-009`).

## 4. RU/EN, semantic tokens и доступность

Название среза: foundation остаётся понятным на двух языках и управляемым с клавиатуры, не закрепляя черновой visual baseline.

- [ ] 4.1 Пользователь переключает RU и EN и видит на выбранном языке sidebar, dirty-state действия, loading, empty, error, offline и permission-denied без изменения маршрута, прав и введённых данных (`AC-008`).
- [ ] 4.2 На утверждённом viewport и масштабе рецензент подставляет длинные русские критические строки и видит полный смысл без наложения, потери элемента управления и необозначенного обрезания (`AC-008`).
- [ ] 4.3 Проверка удаляет обязательный перевод и получает явный fail локализации; необработанный ключ, пустая подпись и серверный текст не принимаются как готовый UI (`AC-008`).
- [ ] 4.4 UX-рецензент проверяет sidebar, dirty-state выбор и error-состояние и для каждого значения видит ссылку на семантический токен, а не локальный цвет, тень или размер (`AC-010`).
- [ ] 4.5 Reviewer меняет draft mapping акцента в одном месте и видит согласованное изменение всех foundation-потребителей без локальных копий прежнего значения (`AC-010`).
- [ ] 4.6 До UX approval протокол token audit показывает статус `draft`, открытый accent и блокирующий contrast check; использованный в прототипе цвет не помечен baseline (`AC-010`).
- [ ] 4.7 Клавиатурный пользователь проходит все разрешённые пункты sidebar через Tab, Shift+Tab и Enter или Space, видит focus на каждом шаге и открывает раздел без мыши (`NFR-003`).
- [ ] 4.8 Клавиатурный пользователь открывает dirty-state выбор, достигает всех трёх действий и после «Отмена» получает focus обратно на инициатор перехода (`NFR-003`).
- [ ] 4.9 Независимый рецензент измеряет все утверждённые сочетания текста, границ элементов управления, фокуса и семантических состояний и получает отдельный результат по каждому (`NFR-004`).
- [ ] 4.10 Если WCAG-уровень не утверждён либо хотя бы одно обязательное сочетание имеет fail или not-run, Ready review показывает `NFR-004` как blocking, а не pass (`NFR-004`).

## 5. Offline, совместимость и производительность

Название среза: foundation работает в локальном контуре, а заявления о поддержке и скорости опираются на измерения.

- [ ] 5.1 Проверяющий блокирует весь исходящий интернет при доступном локальном контроллере и видит полностью загруженные shell, local fonts, icons, RU/EN и базовые состояния (`NFR-001`).
- [ ] 5.2 Сетевой аудит основного и краевого foundation-пути не содержит обязательных обращений к CDN, внешнему шрифту, облачному API или телеметрии (`NFR-001`).
- [ ] 5.3 Отключение DNS и внешней сети не меняет успешность локального пути и не вызывает внешнее резервное обращение (`NFR-001`).
- [ ] 5.4 QA выполняет foundation-набор в каждой кандидатной комбинации compatibility-матрицы и для каждой фиксирует точные версии, pass, fail, partial или not-run (`NFR-005`).
- [ ] 5.5 Рецензент выбирает среду вне утверждённой матрицы и видит, что она не помечена поддерживаемой и не используется как положительное evidence без отдельного решения (`NFR-005`).
- [ ] 5.6 Если обязательная кандидатная среда не прогнана, Ready review показывает конкретный compatibility blocker, а не общее утверждение о поддержке (`NFR-005`).
- [ ] 5.7 Рецензент производительности на зафиксированном commit SHA выполняет согласованные cold/warm прогоны загрузки shell, перехода sidebar, dirty-state выбора и resync и получает сырые измерения с описанием среды (`NFR-006`).
- [ ] 5.8 Engineering/Product после discovery фиксируют показатель, способ агрегации и порог; до этого протокол явно показывает `NFR-006` как not-run для acceptance, даже если функциональные тесты прошли (`NFR-006`).
- [ ] 5.9 Повторный performance-прогон по той же методике на том же классе оборудования даёт сопоставимый набор данных и не заменяется субъективным наблюдением «быстро» (`NFR-006`).

## 6. Доказательство срезов

- [ ] 6.1 Для каждого `AC-001`…`AC-010` существует минимум одно evidence основного пути и одно evidence краевого или запрещённого пути; каждый элемент содержит requirement ID, метод, результат, commit SHA, время, среду, автора и ограничения.
- [ ] 6.2 Для каждого `NFR-001`…`NFR-006` существует отдельный воспроизводимый протокол; общий зелёный конвейер проверки без прямой трассировки не закрывает NFR.
- [ ] 6.3 Security evidence содержит серверный отказ прямого URL и подделанного запроса, подтверждение неизменности ресурса и отсутствие защищённых данных в UI (`AC-003`, `NFR-002`).
- [ ] 6.4 Offline evidence содержит сетевой trace — трассу обращений — и запись UI до потери связи, в offline и после resync (`AC-007`, `NFR-001`).
- [ ] 6.5 Accessibility evidence содержит keyboard-only запись, focus order и отчёт контраста по утверждённому WCAG-уровню (`NFR-003`, `NFR-004`).
- [ ] 6.6 Compatibility и performance evidence содержат точные версии среды, raw measurements — сырые измерения — и неизменяемую ссылку на артефакт (`NFR-005`, `NFR-006`).
- [ ] 6.7 Протокол `MET-UI-001` содержит исходные данные каждого валидного usability-прогона и позволяет независимо пересчитать долю завершённых foundation-путей.
- [ ] 6.8 Любой fail, partial или not-run остаётся видимым и связан с дефектом, открытым вопросом или решением владельца; скрытый пропуск не закрывает срез.
- [ ] 6.9 Все доказательства собраны на одном принятом SHA для конкретного кандидата либо явно объясняют различие SHA; скриншот без даты, среды и идентификатора не считается evidence.
- [ ] 6.10 Перед передачей ASE рецензент подтверждает, что change всё ещё не содержит Pack, продуктовый код, archive или результаты `/opsx:apply`.
