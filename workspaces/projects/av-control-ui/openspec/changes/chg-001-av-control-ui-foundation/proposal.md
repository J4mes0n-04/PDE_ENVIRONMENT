# Предложение: базовый слой единой оболочки Admin Web UI

Статус change: `draft`.

- Change: `chg-001-av-control-ui-foundation`.
- Будущий Outcome: один; идентификатор не назначен.
- Предполагаемый риск: `R2`; итоговая классификация требует подтверждения владельцем риска.
- Владельцы бизнес-результата, продукта, данных метрики, риска, выпуска и доказательств: не назначены.
- Связанная задача Redmine: `Не создана`.
- Этот документ не является Pack, baseline или разрешением на реализацию.

## Why — зачем

Integrator Engineer, Lead Integrator, IT Admin, Support Operator и Security Auditor должны работать в единой оболочке Admin Web UI — административного веб-интерфейса. Сейчас целевое поведение распределено между продуктовым описанием, сценариями и черновыми UI-материалами, а единого проверяемого контракта базового слоя для оболочки, доступа, навигации и общих состояний нет.

- Кто страдает:
  - Инженер интегратора рискует потерять несохранённые изменения при переходе между разделами.
  - IT Admin и Support Operator могут получить несогласованные способы навигации, ошибок и восстановления.
  - Security Auditor может увидеть действие изменения либо открыть запрещённый маршрут, если видимость ошибочно станет единственным контролем доступа.
  - Команда реализации может независимо трактовать loading, empty, error, offline и permission-denied состояния, локализацию и визуальную семантику.
- Что происходит сейчас: единого работающего UI, принятого за baseline, во входном документе не зафиксировано. Ролевая матрица, полный перечень верхнеуровневых разделов, WCAG-уровень, матрица совместимости и пороги производительности остаются открытыми.
- Чем подтверждено: `workspaces/projects/av-control-ui/inputs/REQ-UI-001-av-control-interface.md`, разделы 2–5, 8–9, 12–19, 21–25 и 27–31.
- Цена проблемы: запрещённый доступ, потеря черновика, ложный успех при ошибке или offline, зависимость от внешней сети, несогласованный язык состояний и невозможность воспроизводимо принять UI.
- Что пока не доказано:
  - числовой исходный уровень и цель `MET-UI-001`;
  - финальная матрица role × action × resource;
  - полный перечень пунктов боковой навигации;
  - точные визуальные значения токенов;
  - требуемый уровень WCAG;
  - поддерживаемые браузеры, ОС, разрешения, масштаб и целевое оборудование;
  - числовые пороги производительности.

## What — что меняется

Для административных ролей фиксируется единый контракт базового слоя (foundation) Admin Web UI:

- После успешной аутентификации разрешённые разделы открываются внутри одной общей оболочки, а отказ отдельного раздела не разрушает оболочку (`AC-001`).
- Пользователь видит только разделы и действия, разрешённые эффективными правами, полученными от сервера (`AC-002`).
- Прямой URL, история браузера или подмена клиентского состояния не открывают запрещённый раздел и его данные (`AC-003`).
- Верхнеуровневые разрешённые разделы доступны через постоянную боковую навигацию; активный раздел синхронизирован с маршрутом (`AC-004`).
- Переход из dirty state — состояния с несохранёнными изменениями — требует явного выбора «Сохранить», «Не сохранять» или «Отмена», а ошибка сохранения не теряет введённые данные (`AC-005`).
- Область контента различает загрузку, отсутствие данных и ошибку запроса; оболочка не превращается в пустой экран (`AC-006`).
- Ошибка, offline и отсутствие разрешения показываются как разные состояния с допустимым следующим действием и без ложного успеха (`AC-007`).
- Foundation-тексты и критические подписи доступны на русском и английском без потери смысла на согласованных средах (`AC-008`).
- Критичность ошибки отделена от пользовательского содержания и технического контекста; подробности доступны только разрешённой роли (`AC-009`).
- Семантические токены — именованные роли визуальных значений — задаются как draft-контракт без объявления конкретного акцентного цвета утверждённым baseline (`AC-010`).
- Штатная работа не зависит от интернета, CDN, внешних шрифтов или обязательных облачных API (`NFR-001`).
- Аутентификация и серверный RBAC — управление доступом на основе ролей — обязательны для маршрутов, данных и действий (`NFR-002`).
- Основные foundation-пути доступны с клавиатуры и имеют видимый управляемый фокус (`NFR-003`).
- Утверждение WCAG-уровня и положительная проверка контраста являются блокерами Ready (`NFR-004`).
- Матрица совместимости формируется отдельным исследованием и не подменяется фразой «современные браузеры» (`NFR-005`).
- Порог производительности формируется по результатам измерения на целевом оборудовании; число до исследования не устанавливается (`NFR-006`).

Проверяющий увидит одну оболочку, разрешённую боковую навигацию, корректный активный пункт, явный dirty-state выбор, отдельные базовые состояния, RU/EN и ролевое раскрытие ошибки. Сетевой и security-прогоны подтвердят отсутствие обязательных внешних ресурсов и невозможность обойти серверную авторизацию.

После изменения не должно происходить следующее:

- отдельный раздел не создаёт вторую независимую Admin-оболочку;
- скрытие пункта меню не считается достаточной авторизацией;
- прямой URL не раскрывает запрещённый контент;
- навигация не теряет изменения без решения пользователя;
- failed request не показывается как empty или success;
- offline-команда не ставится в скрытую очередь;
- сырой серверный текст или секрет не становится пользовательским сообщением;
- черновой акцентный цвет не становится утверждённым только потому, что применён в макете;
- отсутствие числовых порогов не трактуется как успешное прохождение NFR.

## Измеримый результат

Основная метрика будущего Outcome — `MET-UI-001`, доля успешно завершённых критических UI-путей: число успешно завершённых валидных P0-путей делится на число начатых валидных P0-путей. Для этого change измеряются только foundation-пути: вход в разрешённую оболочку, переход между верхнеуровневыми разделами, решение dirty state, распознавание и восстановление из базового состояния.

- Исходный уровень: не измерен.
- Период исходного уровня: не определён.
- Цель: не определена.
- Минимальная выборка: не определена.
- Сегменты: административные роли из утверждаемой матрицы; точный состав прогона должен быть подтверждён.
- Источник: протоколы usability-прогонов и записи сценариев на конкретном commit SHA.
- Окно проверки: после пилотного выпуска; длительность не определена.
- Владелец данных и ответственный за расчёт: не назначены.
- Правило: первый срез является discovery-срезом — исследовательским срезом, который фиксирует измеримый baseline, target, выборку, источник и validation window. Числа до этого среза не подставляются.

Change не может перейти в Ready только на основании наличия интерфейса или успешных автоматических тестов. Контракт метрики и блокирующие NFR должны быть утверждены отдельно.

## Scope — область действия

### Входит

- Общая оболочка Admin Web UI для уже аутентифицированного пользователя.
- Боковая верхнеуровневая навигация, сформированная из разрешённых сервером маршрутов.
- Отображение активного раздела и синхронизация с разрешённым маршрутом.
- Ролевая видимость разделов и действий.
- Безопасный отказ при прямом URL, истории браузера и изменении прав во время сессии.
- Общий guard — защитный переход — для dirty state с вариантами save, discard и cancel.
- Базовые loading, empty, error, offline и permission-denied состояния области контента.
- RU/EN для foundation-текстов, состояний и доступных действий.
- Разделение severity, пользовательского сообщения, следующего действия и технического контекста ошибки.
- Черновой каталог семантических токенов для оболочки, текста, границ, фокуса и состояний.
- Проверки offline, auth/RBAC, keyboard/focus, контраста, совместимости и производительности.
- Discovery-срез `MET-UI-001` и план воспроизводимых доказательств.
- Данные, которые change читает:
  - аутентифицированную сессию и эффективные разрешения;
  - реестр доступных маршрутов и локализованные подписи;
  - результат локальных API-запросов и нормализованное состояние ошибки;
  - выбранную локаль и черновой каталог токенов.
- Данные, которые change изменяет:
  - только состояние навигации и представления;
  - доменные данные — лишь через явно выбранное сохранение и существующий серверный контракт.

### Не входит

- Реализация продуктового кода, `/opsx:apply`, архивирование OpenSpec и создание Pack.
- Финальная матрица прав и назначение владельцев вместо уполномоченных лиц.
- Полный утверждённый перечень верхнеуровневых разделов до решения владельца продукта.
- Функциональность конфигуратора: мастер, ручная сборка, preflight, preview, deploy и rollback проекта; это отдельный change.
- Room Client, киоск, pairing и управление встречей; это отдельный change.
- Health, triage, diagnostic bundle, Safe Mode, обновление, backup и restore; это отдельный change.
- Серверная реализация auth, RBAC, API, хранилища, аудита и транспорта; change фиксирует UI-контракт с ними.
- Облачный кабинет, CDN, внешние шрифты, обязательные облачные API и внешняя телеметрия.
- Утверждение конкретного акцентного цвета, шрифта, постоянного header, notification center или точного skeleton-паттерна.
- Мобильное системное меню и клиентские panel-layout.
- Числовые значения метрик, WCAG, совместимости или производительности без результатов discovery.

## Пользователи и ситуации

- Основной пользователь: Integrator Engineer. Он уже прошёл аутентификацию, открывает разрешённый раздел Admin Web UI, перемещается между разделами и не должен потерять редактируемый черновик.
- Основной административный пользователь: IT Admin. Он должен видеть только разрешённые системные разделы и получать безопасный отказ для чужого маршрута.
- Затронутые роли:
  - Lead Integrator использует расширенные проектные права после утверждения матрицы.
  - Support Operator видит только разрешённый эксплуатационный контекст и технические подробности по праву.
  - Security Auditor использует разделы только для чтения и не получает элементы управления изменением.
  - Vendor Support не получает постоянного скрытого доступа; временный доступ проектируется отдельным change.
- End User и Room Operator не являются пользователями Admin foundation в этом change; их клиентские поверхности относятся к отдельному change.
- Ситуации отказа:
  - прямой переход в запрещённый раздел;
  - отзыв права во время открытой сессии;
  - неуспешная загрузка;
  - отсутствие данных;
  - потеря локальной связи;
  - ошибка сохранения dirty state;
  - отсутствующий перевод;
  - неподтверждённый контраст или неподдержанная среда.

## Зависимости

- Сервис аутентификации и серверная проверка RBAC.
- Серверный контракт эффективных разрешений и доступных действий.
- Реестр маршрутов Admin Web UI с устойчивыми ключами и локализуемыми подписями.
- Контракты доменных API, которые возвращают ready, empty, error, offline и permission outcomes.
- Контракт сохранения редактируемого объекта и возможность восстановить последнее подтверждённое состояние при discard.
- Локальная поставка шрифтов, иконок, переводов и других статических ресурсов.
- Решения UX/UI Owner по токенам и WCAG.
- Решения Product/QA по совместимости и Engineering/Product по производительности.
- Следующие changes наследуют foundation-контракт, но не меняют его молча.

## Риски этого change

- Ролевая видимость может быть ошибочно реализована как единственная граница безопасности.
- Неутверждённая матрица прав может привести к случайному раскрытию раздела или чрезмерному запрету.
- Dirty-state guard может сохранить не тот объект, удалить черновик при discard либо создать цикл навигации.
- Empty может скрыть ошибку загрузки, а offline — показать устаревшие данные как актуальные.
- Сырой серверный текст может раскрыть инженерный контекст или секрет.
- Черновые токены могут быть приняты за окончательный визуальный baseline.
- Неизвестные WCAG и compatibility границы могут отложить Ready после реализации.
- Неправильно выбранная методика performance-измерения создаст несравнимые результаты.
- Scope foundation может поглотить конфигуратор, operations или Room Client.
- Остаточный риск до закрытия вопросов остаётся повышенным; draft не разрешает реализацию или выпуск.

## Выпуск и откат

- Предварительная последовательность: discovery → проверяемый foundation-прототип → тестовый стенд → пилотный сегмент → ограниченный production. Переход между этапами требует отдельных решений владельцев после их назначения.
- Условия продолжения:
  - утверждены матрицы ролей, совместимости и WCAG;
  - для каждого `AC-001`…`AC-010` и `NFR-001`…`NFR-006` есть воспроизводимое evidence;
  - нет раскрытия запрещённого раздела, потери dirty data и обязательного внешнего запроса;
  - `MET-UI-001` имеет утверждённый контракт.
- Стоп-условия:
  - запрещённый маршрут или действие доступны;
  - изменения потеряны без явного discard;
  - UI показывает ложный success, актуальность offline-данных или необработанный технический текст;
  - foundation требует интернет, CDN, внешний шрифт или облачный API;
  - контраст, клавиатура или поддерживаемая среда не проходят утверждённую проверку.
- Предварительный rollback: вернуть предыдущий проверенный артефакт Admin Web UI, не изменяя серверные доменные данные; затем повторить критические ролевые и dirty-state прогоны.
- Способ staged rollout, полномочия на rollback, максимальное время восстановления и конкретный артефакт предыдущей версии не определены. Их нельзя выдумывать до назначения Release Owner и появления Pack.

## Трассировка

- Сигнал: `SIG-UI-001` из основного input.
- Change: `chg-001-av-control-ui-foundation`.
- Будущий Outcome: один, идентификатор не назначен.
- Redmine: `Не создана`.
- Pack, ASE handoff, Evidence Bundle и release-запись на этом шаге не создаются.

## Non-goals — нецели

- Нецель: реализовать код или запустить OpenSpec apply. Причина: текущий этап — intake. Куда относится: будущая поставка после подтверждённого change и Pack.
- Нецель: создать Pack или Outcome. Причина: change ещё `draft` и содержит blocking-вопросы. Куда относится: `pde-create-pack` после человеческого подтверждения.
- Нецель: спроектировать конфигуратор. Причина: самостоятельный измеримый change. Куда относится: `chg-002`.
- Нецель: спроектировать Room Client и kiosk. Причина: иные пользователи, пути и recovery. Куда относится: `chg-003`.
- Нецель: спроектировать operations, Safe Mode, diagnostic bundle, update, backup и restore. Причина: отдельная эксплуатационная область. Куда относится: `chg-004`.
- Нецель: утвердить роли, владельцев, метрики, WCAG, compatibility или performance по догадке. Причина: источники оставляют их открытыми. Куда относится: решения соответствующих владельцев и discovery.
- Нецель: утвердить акцентный цвет или точные token values. Причина: визуальные источники конфликтуют и имеют статус draft. Куда относится: UX approval.
- Нецель: добавить облачный кабинет, CDN, внешние шрифты, обязательные облачные API или внешнюю телеметрию. Причина: противоречит offline-first ограничению. Куда относится: только отдельный Definition Change, если когда-либо будет предложен.
