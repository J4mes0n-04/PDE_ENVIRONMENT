# Delta for ui-foundation

Статус: `draft`. Все требования относятся к одному будущему Outcome. Открытые числовые и ролевые решения не считаются закрытыми этим документом.

## ADDED Requirements

### Requirement: AC-001 Единая оболочка Admin Web UI

The system SHALL после успешной аутентификации показывать разрешённые административные разделы внутри одной общей оболочки Admin Web UI с постоянной областью верхнеуровневой навигации и областью содержимого.

#### Scenario: Разрешённый раздел открывается в общей оболочке

- **GIVEN** IT Admin успешно аутентифицирован, сервер подтвердил доступ к выбранному административному разделу, общая оболочка уже загружена
- **WHEN** пользователь выбирает этот раздел в верхнеуровневой навигации
- **THEN** содержимое раздела появляется в области содержимого той же оболочки
- **AND** идентичность пользователя и общая навигация остаются видимыми и не инициализируются повторно
- **Не происходит:** отдельное окно, вторая независимая оболочка или повторный вход не заменяют переход внутри Admin Web UI

#### Scenario: Отказ раздела не разрушает оболочку

- **GIVEN** аутентифицированному пользователю разрешён маршрут, но загрузка данных выбранного раздела завершается ошибкой
- **WHEN** Admin Web UI получает отказ доменного запроса
- **THEN** ошибка отображается только в области содержимого выбранного раздела
- **AND** оболочка, разрешённая навигация и текущая сессия остаются доступны
- **Не происходит:** весь экран не становится пустым и пользователь не переносится в отдельное приложение

### Requirement: AC-002 Ролевая видимость разделов и действий

The system SHALL показывать в оболочке только те разделы, объекты и действия, которые разрешены эффективными правами текущего пользователя, полученными от сервера.

#### Scenario: Security Auditor видит read-only поверхность

- **GIVEN** сервер подтвердил Security Auditor право читать аудит и не подтвердил право изменять пользователей, роли или записи аудита
- **WHEN** пользователь открывает Admin Web UI
- **THEN** в навигации виден разрешённый раздел аудита, а элементы управления изменением в нём отсутствуют или недоступны согласно принятой матрице
- **AND** остальные показанные пункты и действия соответствуют тем же эффективным правам этой сессии
- **Не происходит:** клиент не добавляет действие изменения по названию роли, локальному кешу или предположению разработчика

#### Scenario: Право отозвано во время сессии

- **GIVEN** пользователь открыл разрешённый раздел, после чего сервер отозвал соответствующее право
- **WHEN** оболочка получает обновлённые эффективные права или следующий защищённый запрос получает отказ авторизации
- **THEN** запрещённый пункт и его изменяющие действия перестают быть доступными
- **AND** открытая область переходит в permission-denied состояние с разрешённым следующим действием
- **Не происходит:** ранее показанный элемент управления не сохраняет возможность выполнить защищённую операцию

### Requirement: AC-003 Запрет доступа по прямому URL

The system SHALL безопасно отказывать в открытии любого маршрута, ресурса или действия, для которого сервер не подтвердил разрешение, независимо от прямого URL, истории браузера или клиентской подмены состояния.

#### Scenario: Прямой URL запрещённого раздела

- **GIVEN** Security Auditor аутентифицирован, а серверная политика запрещает этой сессии маршрут управления пользователями
- **WHEN** пользователь вводит прямой URL этого зарегистрированного маршрута
- **THEN** оболочка показывает permission-denied состояние и сохраняет доступ только к разрешённой навигации
- **AND** защищённые данные и элементы управления пользователями не загружаются и не отображаются
- **Не происходит:** знание адреса не открывает запрещённый раздел и не повышает права

#### Scenario: Возврат к кешированному запрещённому маршруту

- **GIVEN** ранее разрешённый маршрут остался в истории браузера, но право на него уже отозвано
- **WHEN** пользователь выполняет переход назад, вперёд или восстанавливает сохранённый адрес
- **THEN** маршрут повторно проходит проверку и получает безопасный отказ
- **AND** кешированное содержимое удаляется из доступного представления или закрывается permission-denied состоянием
- **Не происходит:** история браузера или изменение клиентского реестра восстанавливают запрещённые данные и действия

### Requirement: AC-004 Боковая верхнеуровневая навигация

The system SHALL предоставлять постоянную боковую навигацию по разрешённым верхнеуровневым разделам, выполнять переход за одно явное действие и синхронизировать активный пункт с текущим маршрутом.

#### Scenario: Переход между разрешёнными разделами

- **GIVEN** аутентифицированному пользователю разрешены два верхнеуровневых раздела и текущий контекст не содержит несохранённых изменений
- **WHEN** пользователь один раз активирует второй пункт в sidebar
- **THEN** область содержимого открывает соответствующий разрешённый маршрут
- **AND** второй пункт получает активное состояние, а первый перестаёт быть активным
- **Не происходит:** для обычного перехода не требуется промежуточный домашний экран или повторная аутентификация

#### Scenario: Навигация браузера синхронизирует sidebar

- **GIVEN** пользователь последовательно открыл два разрешённых верхнеуровневых раздела
- **WHEN** пользователь применяет штатное действие браузера «Назад» или «Вперёд»
- **THEN** содержимое и активный пункт sidebar соответствуют фактическому разрешённому маршруту из истории
- **AND** набор видимых пунктов по-прежнему определяется текущими эффективными правами
- **Не происходит:** sidebar не показывает активным раздел, отличный от открытого содержимого

### Requirement: AC-005 Явное решение для несохранённых изменений

The system SHALL при попытке покинуть dirty-контекст требовать явный выбор «Сохранить», «Не сохранять» или «Отмена» и менять маршрут только в соответствии с подтверждённым результатом этого выбора.

#### Scenario: Сохранение перед переходом

- **GIVEN** пользователь изменил данные в разрешённом разделе, dirty indicator видим, а сервер доступен
- **WHEN** пользователь выбирает другой раздел, затем выбирает «Сохранить», и сервер подтверждает сохранение
- **THEN** изменения становятся подтверждённым состоянием и открывается выбранный раздел
- **AND** dirty indicator для покинутого контекста снимается только после успешного ответа
- **Не происходит:** навигация не выполняется до подтверждения сохранения и не создаёт вторую запись

#### Scenario: Явный отказ от изменений

- **GIVEN** пользователь изменил данные, последнее подтверждённое состояние доступно для восстановления
- **WHEN** при попытке перехода пользователь выбирает «Не сохранять»
- **THEN** локальные несохранённые изменения отбрасываются и открывается выбранный разрешённый раздел
- **AND** при повторном открытии исходного контекста видна последняя подтверждённая сервером версия
- **Не происходит:** discard не отправляет сохранение и не удаляет подтверждённую версию

#### Scenario: Отмена перехода

- **GIVEN** пользователь находится в dirty-контексте и вызвал переход в другой раздел
- **WHEN** пользователь выбирает «Отмена»
- **THEN** выбор закрывается, текущий маршрут остаётся открытым
- **AND** введённые значения и dirty indicator сохраняются без изменений
- **Не происходит:** маршрут не меняется и серверное сохранение или discard не запускаются

#### Scenario: Ошибка сохранения

- **GIVEN** пользователь находится в dirty-контексте и выбрал «Сохранить» перед переходом
- **WHEN** сервер не подтверждает сохранение или связь теряется до подтверждённого результата
- **THEN** пользователь остаётся в исходном разделе и видит ошибку с допустимым следующим действием
- **AND** введённые значения и dirty indicator сохраняются для повтора, discard или отмены
- **Не происходит:** ложный success, смена маршрута и молчаливая потеря изменений не допускаются

### Requirement: AC-006 Различимые loading и empty состояния

The system SHALL явно различать загрузку и подтверждённое отсутствие данных в области содержимого, сохраняя оболочку и показывая только разрешённые действия.

#### Scenario: Данные ещё загружаются

- **GIVEN** пользователь открыл разрешённый раздел, запрос к локальному серверу отправлен и конечный результат ещё не получен
- **WHEN** область содержимого находится в loading состоянии
- **THEN** пользователь видит обозначенный процесс загрузки внутри сохранённой оболочки
- **AND** элементы управления, которым нужны ещё не полученные данные, недоступны до подтверждённого результата
- **Не происходит:** loading не показывается как пустой список, ошибка или готовые актуальные данные

#### Scenario: Успешный ответ не содержит объектов

- **GIVEN** локальный сервер успешно ответил, что в разрешённом разделе нет доступных объектов
- **WHEN** загрузка завершается подтверждённым пустым результатом
- **THEN** область содержимого показывает фактическое empty-состояние с причиной отсутствия данных
- **AND** доступное следующее действие показывается только если эффективные права разрешают его выполнить
- **Не происходит:** пустое состояние не маскируется бесконечной загрузкой и не предлагает запрещённое создание

#### Scenario: Ошибка запроса не становится empty

- **GIVEN** пользователь открыл разрешённый раздел, но локальный API вернул ошибку вместо результата
- **WHEN** запрос завершается отказом
- **THEN** область содержимого переходит в error state с безопасным retry или иным разрешённым действием
- **AND** отсутствие ответа отделено от подтверждённого нулевого количества объектов
- **Не происходит:** ошибка не отображается как «данных нет» и не считается успешной загрузкой

### Requirement: AC-007 Различимые error, offline и permission-denied состояния

The system SHALL показывать error, offline и permission-denied как разные базовые состояния с понятной причиной на доступном уровне, разрешённым следующим действием и сохранением безопасного состояния данных.

#### Scenario: Локальная ошибка операции

- **GIVEN** пользователь имеет право на действие и локальный сервер доступен, но операция завершается доменной ошибкой
- **WHEN** Admin Web UI получает нормализованный отказ
- **THEN** область содержимого показывает error state с пользовательским сообщением и допустимым следующим действием
- **AND** прежнее подтверждённое состояние сохраняется либо явно отмечается как требующее обновления
- **Не происходит:** error не отображается как success, empty или потеря всей оболочки

#### Scenario: Потеря связи с локальным сервером

- **GIVEN** разрешённый раздел показывал подтверждённые данные, после чего локальная связь стала недоступна
- **WHEN** UI обнаруживает отсутствие подтверждённой связи
- **THEN** область показывает offline-состояние, а изменяющие элементы управления блокируются до resync
- **AND** последние подтверждённые данные, если они остаются видимыми, явно помечены как неактуальные
- **Не происходит:** новая команда не ставится в скрытую очередь и устаревшее состояние не выдаётся за актуальное

#### Scenario: Разрешение отсутствует

- **GIVEN** пользователь аутентифицирован, но сервер отказал в доступе к запрошенному маршруту или действию
- **WHEN** оболочка получает отказ авторизации
- **THEN** пользователь видит permission-denied состояние и разрешённый путь назад или к доступному разделу
- **AND** текст не раскрывает защищённые данные, существование скрытых объектов или технические секреты
- **Не происходит:** permission-denied не подменяется общей ошибкой с кнопкой повтора запрещённого действия

### Requirement: AC-008 Русская и английская локализация базового слоя

The system SHALL отображать foundation-навигацию, базовые состояния, dirty-state выбор и безопасные сообщения ошибок на русском и английском без обрезания критического смысла.

#### Scenario: Переключение между RU и EN

- **GIVEN** для всех foundation-ключей доступны локально поставляемые русские и английские строки
- **WHEN** для сессии выбирается русский, а затем английский язык
- **THEN** подписи sidebar, состояния и действия отображаются на выбранном языке
- **AND** маршрут, разрешения и несохранённые пользовательские данные не меняются из-за смены языка
- **Не происходит:** интерфейс не запрашивает перевод из внешнего облака и не смешивает языки в одном foundation-сообщении

#### Scenario: Длинная русская строка

- **GIVEN** согласованный viewport и системный масштаб, а русская критическая подпись длиннее английского эквивалента
- **WHEN** пользователь открывает sidebar, dirty-state выбор или базовое состояние с этой подписью
- **THEN** полный смысл доступен через утверждённую компоновку, перенос или доступное раскрытие
- **AND** элемент управления остаётся различимым и управляемым с клавиатуры
- **Не происходит:** смысл действия не исчезает из-за необозначенного многоточия, наложения или обрезания

#### Scenario: Отсутствует обязательный перевод

- **GIVEN** в выбранной локали отсутствует критический foundation-ключ
- **WHEN** компонент пытается показать связанную подпись или ошибку
- **THEN** проверка локализации фиксирует дефект и не принимает экран как завершённый
- **AND** безопасная политика языковой подстановки, если она утверждена, явно отмечает использованный язык
- **Не происходит:** необработанный ключ, пустая кнопка или сырой серверный текст не выдаются за корректный перевод

### Requirement: AC-009 Разделение критичности и содержания ошибки

The system SHALL хранить и отображать severity ошибки отдельно от безопасного пользовательского сообщения, следующего действия и технического контекста, раскрывая подробности только роли с соответствующим разрешением.

#### Scenario: Support Operator имеет право на диагностику

- **GIVEN** сервер вернул ошибку с severity, безопасным сообщением, следующим действием, техническим контекстом и correlation ID, а Support Operator имеет право видеть диагностику
- **WHEN** пользователь открывает подробности этой ошибки
- **THEN** сначала видны локализованное сообщение и следующее действие, а технический контекст доступен отдельным различимым блоком
- **AND** визуальная семантика соответствует severity, не изменяя содержание сообщения
- **Не происходит:** severity не вычисляется из произвольного текста, а технические подробности не смешиваются с основной инструкцией

#### Scenario: Роль не имеет диагностического разрешения

- **GIVEN** та же ошибка доступна пользователю без права видеть технический контекст
- **WHEN** пользователь открывает error state
- **THEN** видны только безопасное сообщение, severity на разрешённом уровне и допустимое следующее действие
- **AND** correlation ID может быть показан только в безопасной форме, если это разрешено политикой
- **Не происходит:** трассировка стека, секрет, токен, внутренний адрес или защищённые данные запроса и ответа не попадают в пользовательский текст

#### Scenario: Сервер вернул только сырой текст

- **GIVEN** ответ ошибки не соответствует нормализованному контракту и содержит необработанный технический текст
- **WHEN** foundation формирует пользовательское error state
- **THEN** используется безопасное локализованное сообщение о невозможности завершить действие
- **AND** несоответствие контракта фиксируется как диагностируемый дефект без раскрытия сырого текста пользователю
- **Не происходит:** необработанный серверный ответ не отображается напрямую и не получает случайную severity

### Requirement: AC-010 Черновой контракт семантических токенов

The system SHALL применять к оболочке и общим состояниям единый draft-каталог семантических токенов для поверхностей, текста, границ, интерактивных состояний, фокуса и severity без объявления спорных необработанных значений утверждённым visual baseline.

#### Scenario: Foundation-компоненты используют семантические роли

- **GIVEN** открыты sidebar, элемент навигации, dirty-state выбор и базовое error-состояние
- **WHEN** UX-рецензент выполняет аудит токенов этих компонентов
- **THEN** каждое визуальное значение сопоставлено с именованной семантической ролью каталога
- **AND** normal, hover, pressed, selected, focus, disabled, warning, error, critical, offline и permission-denied различимы согласованным способом
- **Не происходит:** компонент не вводит локальный цвет, тень, размер или состояние как скрытый новый token

#### Scenario: Акцентный цвет ещё не утверждён

- **GIVEN** источники предлагают разные акцентные значения, а UX approval отсутствует
- **WHEN** создаётся макет или проверяемый прототип foundation
- **THEN** компонент ссылается на draft-семантическую роль акцента без утверждения конкретного значения baseline
- **AND** открытый вопрос и блокирующая проверка контраста остаются видимыми в evidence
- **Не происходит:** использованное в одном макете конкретное значение цвета не становится нормативным и не копируется локально в другие компоненты

### Requirement: NFR-001 Штатная работа без внешней сети

The system SHALL выполнять foundation-сценарии в локальном контуре без обязательного интернета, CDN, внешних шрифтов, внешних API или облачной телеметрии.

#### Scenario: Внешний исходящий трафик заблокирован

- **GIVEN** локальный контроллер и его API доступны, а весь исходящий интернет-трафик заблокирован
- **WHEN** пользователь загружает Admin Web UI и проходит разрешённый foundation-путь
- **THEN** оболочка, шрифты, иконки, RU/EN и базовые состояния загружаются из локально поставляемых ресурсов
- **AND** навигация и допустимые локальные действия работают без внешнего соединения
- **Не происходит:** отсутствие CDN, облачного API или внешнего шрифта не оставляет пустой экран и не блокирует штатный путь

#### Scenario: Сетевой аудит обязательных запросов

- **GIVEN** включена запись сетевых обращений для загрузки оболочки, смены языка и показа базовых состояний
- **WHEN** проверяющий выполняет основной и краевой foundation-сценарии
- **THEN** протокол содержит только локальные обязательные обращения в пределах утверждённого контура
- **AND** любой необязательный внешний адрес, если он когда-либо будет предложен, не участвует в успешности сценария
- **Не происходит:** обязательный запрос к интернету, CDN, внешнему шрифту, облачному API или телеметрии не остаётся незамеченным

### Requirement: NFR-002 Аутентификация и серверный RBAC

The system SHALL требовать действующую аутентификацию и серверную проверку RBAC для каждого защищённого маршрута, ресурса и действия, используя клиентскую видимость только как представление разрешений.

#### Scenario: Разрешённое действие подтверждено сервером

- **GIVEN** аутентифицированная сессия имеет серверное разрешение на конкретный маршрут и действие
- **WHEN** пользователь выполняет действие через разрешённый элемент управления
- **THEN** сервер повторно проверяет субъект, действие и ресурс и возвращает результат только при действующем разрешении
- **AND** UI показывает подтверждённый результат и сохраняет трассируемый контекст проверки без секрета
- **Не происходит:** наличие видимой кнопки само по себе не считается доказательством авторизации

#### Scenario: Подделанный запрос или истёкшая сессия

- **GIVEN** пользователь изменил клиентское состояние либо сессия истекла, а сервер не подтверждает разрешение
- **WHEN** отправляется прямой защищённый запрос вне разрешённого UI-пути
- **THEN** сервер отказывает, а оболочка показывает безопасное auth или permission состояние
- **AND** защищённые данные и изменение ресурса отсутствуют в результате
- **Не происходит:** подмена роли в браузере, прямой API-запрос или кешированный элемент управления обходят RBAC

### Requirement: NFR-003 Клавиатурная достижимость и управляемый фокус

The system SHALL позволять пройти критические foundation-пути с клавиатуры, показывать видимый фокус и предсказуемо перемещать его при навигации, диалоге и состоянии ошибки.

#### Scenario: Навигация без мыши

- **GIVEN** аутентифицированный пользователь открыл оболочку и не использует pointing device — указывающее устройство
- **WHEN** пользователь последовательно применяет Tab, Shift+Tab и Enter или Space к sidebar
- **THEN** каждый разрешённый интерактивный пункт получает видимый фокус и может открыть соответствующий раздел
- **AND** порядок фокуса следует смысловой последовательности и после перехода приводит к различимому началу нового содержимого
- **Не происходит:** скрытый, запрещённый или невидимый элемент управления получает рабочий фокус

#### Scenario: Фокус в dirty-state выборе

- **GIVEN** клавиатурный пользователь инициировал переход из dirty-контекста
- **WHEN** появляется выбор «Сохранить», «Не сохранять» или «Отмена»
- **THEN** фокус перемещается внутрь выбора, все три действия достижимы и результат озвучивается семантически доступным способом
- **AND** после «Отмена» фокус возвращается к инициатору перехода, а после успешного перехода — к началу нового содержимого
- **Не происходит:** фокус не уходит под перекрывающий слой, не теряется и не зацикливается вне доступных действий

### Requirement: NFR-004 Контраст и WCAG как блокер Ready

The system SHALL использовать для текста, элементов управления, фокуса и семантических состояний только сочетания токенов, прошедшие проверку по утверждённому уровню WCAG; отсутствие утверждённого уровня или положительного протокола блокирует Ready.

#### Scenario: Проверка после утверждения уровня

- **GIVEN** уполномоченные владельцы утвердили уровень WCAG и перечень проверяемых foundation-состояний
- **WHEN** независимый рецензент измеряет текст, границы элементов управления, фокус и warning, error, critical, offline, permission-denied на утверждённых поверхностях
- **THEN** каждое сочетание имеет воспроизводимый результат pass или fail по принятому методу
- **AND** только прошедшие сочетания допускаются в baseline-кандидат
- **Не происходит:** визуальная похожесть, брендовый приоритет или проверка только обычного текста заменяют измерение всех обязательных состояний

#### Scenario: Уровень не утверждён или проверка не пройдена

- **GIVEN** уровень WCAG ещё не выбран либо хотя бы одно обязательное сочетание получило fail или not-run
- **WHEN** change оценивается для перехода в Ready
- **THEN** `NFR-004` остаётся открытым блокером с указанием отсутствующего решения или непройденного сочетания
- **AND** статус draft сохраняется до решения и повторной проверки
- **Не происходит:** неизвестный порог, среднее значение по палитре или ручное исключение без решения владельца не считаются pass

### Requirement: NFR-005 Совместимость через discovery-матрицу

The system SHALL считаться совместимым только с теми комбинациями браузера, ОС, viewport, zoom, системного масштаба и целевого оборудования Admin Web UI, которые утверждены после discovery и прошли foundation-сценарии.

#### Scenario: Формирование матрицы совместимости

- **GIVEN** Product и QA определили кандидатные среды без объявления их поддерживаемыми
- **WHEN** проверяющий выполняет shell, sidebar, dirty state, базовые состояния, RU/EN и keyboard/focus в каждой кандидатной комбинации
- **THEN** протокол фиксирует точные версии и pass, fail, partial или not-run для каждого сценария
- **AND** утверждённая поддерживаемая матрица формируется только из воспроизводимых результатов и решения владельцев
- **Не происходит:** фраза «современный браузер» или успешный прогон в одной среде не распространяет поддержку на остальные

#### Scenario: Среда отсутствует в утверждённой матрице

- **GIVEN** браузер, ОС или режим масштаба не исследован либо исключён из принятой матрицы
- **WHEN** в этой среде запускается Admin Web UI
- **THEN** результат не используется как evidence поддерживаемой совместимости до отдельного прогона и решения
- **AND** если среда заявлена обязательной для выпуска, её отсутствие остаётся блокером
- **Не происходит:** неизвестная комбинация не получает статус поддерживаемой по внешнему сходству или предположению

### Requirement: NFR-006 Производительность через измеряемый discovery

The system SHALL получить baseline и порог производительности foundation-путей на утверждённом целевом оборудовании по воспроизводимой методике до заявления performance pass, не подставляя числовое значение заранее.

#### Scenario: Discovery фиксирует исходные измерения

- **GIVEN** определены проверяемая сборка, целевая среда, объём тестовых данных и сценарии загрузки оболочки, навигации, dirty-state выбора и resync
- **WHEN** проверяющий выполняет согласованное число cold и warm прогонов
- **THEN** протокол сохраняет сырые результаты, условия, commit SHA и способ агрегации для каждого сценария
- **AND** Engineering/Product используют эти данные для отдельного утверждения метрики и порога
- **Не происходит:** единичное субъективное наблюдение «быстро» или число из другого продукта не становится baseline

#### Scenario: Порог или целевое оборудование не утверждены

- **GIVEN** измерения отсутствуют, целевое оборудование не выбрано либо владелец не утвердил порог и метод агрегации
- **WHEN** change оценивается для перехода в Ready
- **THEN** `NFR-006` остаётся открытым блокером с перечислением недостающих данных
- **AND** существующие функциональные прогоны сохраняются только как функциональное evidence
- **Не происходит:** отсутствие порога не интерпретируется как отсутствие ограничений и не получает performance pass
