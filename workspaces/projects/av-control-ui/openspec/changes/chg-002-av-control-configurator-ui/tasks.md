# Срезы поставки для ASE — конфигуратор AV Control

Термины документа: `ASE` — исполнительная инженерная роль поставки; `Ready` — подтверждённая готовность к реализации; `change` — пакет изменений OpenSpec; `Outcome` — измеримый целевой результат; `draft` — черновик; `Pack` — утверждаемый пакет определения продукта; `evidence` — проверочное доказательство; `SHA` — идентификатор проверяемого коммита. `Dirty-state` — состояние несохранённых изменений; `selection` — единый текущий выбор объекта; `preflight` — проверка готовности; `preview` — предварительный просмотр; `deploy` — активация проекта; `rollback` — возврат предыдущей версии; `import/export` — ввоз и вывоз проектных данных; `fault-injection` — контролируемое внесение отказа; `model diff` — сравнение проектной модели; `cloud` — внешнее облако; `focus` — клавиатурный фокус.

Статус: `draft`.

Задачи являются подсказками для будущей поставки после Ready. Они не заменяют Pack, не разрешают реализацию и не закрываются только unit/e2e-тестами. Каждый наблюдаемый прогон выполняется на одном SHA и связывается с соответствующим требованием из `specs/configurator-ui/spec.md`.

Владельцы выполнения и evidence неназначены. Redmine: `Не создана`.

## 0. Discovery и условия начала

До реализации владелец результата должен назначить владельцев продукта, риска, данных метрик, реализации и приёмки, а также связать будущий Outcome с созданной Redmine-задачей. Пока этого нет, change остаётся draft.

- [ ] 0.1 На доступном текущем процессе провести исходные прогоны готовой комнаты, добавления устройства, ручного проекта, исправления preflight, preview, deploy/rollback, import/export и работы без оборудования; записать завершённость без помощи, причины остановки, время как наблюдение и критические ошибки (`AC-011`–`AC-020`).
- [ ] 0.2 По исходным прогонам утвердить baseline, target, минимальную выборку, сегменты и validation window; до утверждения не использовать экспертно выбранные числа как критерий готовности (`AC-011`–`AC-020`).
- [ ] 0.3 Зафиксировать representative dataset плотного проекта, целевое железо, браузер, viewport и числовой порог до проверки производительности (`NFR-014`).
- [ ] 0.4 Утвердить серверные контракты ревизий, разрешений, preflight, preview, deploy/rollback, import/export, шаблонов, защиты и эмулятора; UI не должен придумывать поля ответа (`AC-011`–`AC-020`, `NFR-011`–`NFR-015`).
- [ ] 0.5 Evidence discovery содержит протокол, запись экрана, среду, SHA, роль, начальную ревизию и результат каждого пути; отсутствие рабочего baseline фиксируется как наблюдаемый факт, а не заменяется числом (`AC-011`–`AC-020`).

## 1. Создание проекта

### `AC-011` — мастер готовой комнаты и мастер устройств

- [ ] 1.1 На экране создания Integrator Engineer видит отдельные действия «Готовая комната» и «Вручную», а в открытом проекте — действие «Добавить устройство»; выбор мастера показывает фактический состав до применения (`AC-011`).
- [ ] 1.2 Подтверждение готовой комнаты создаёт один неактивный editable draft, а дерево, рабочая область и инспектор показывают одни и те же generated-сущности (`AC-011`).
- [ ] 1.3 В открытом проекте мастер устройства добавляет один подтверждённый change-set и не меняет несвязанные сущности (`AC-011`).
- [ ] 1.4 При пустом каталоге или отсутствующем драйвере мастер сохраняет введённые значения, называет недостающие данные и не создаёт partial graph (`AC-011`).
- [ ] 1.5 Evidence: одна непрерывная запись обоих мастер-путей, model diff каждого применения, снимок no-data/error и подтверждение отсутствия active version (`AC-011`).

### `AC-012` — ручной проект

- [ ] 1.6 Выбор «Вручную» создаёт пустую структуру без устройств, драйверов, тегов, связей, сценариев и клиентских элементов, добавленных без действия инженера (`AC-012`).
- [ ] 1.7 При пустом локальном каталоге ручной draft остаётся редактируемым и показывает доступные типы и локальный путь получения недостающих данных (`AC-012`).
- [ ] 1.8 Прямой маршрут пользователя без create permission показывает forbidden и не создаёт draft или системный корень (`AC-012`).
- [ ] 1.9 Evidence: запись создания, snapshot исходной модели, server response запрета и проверка отсутствия новой записи проекта (`AC-012`).

## 2. Единое рабочее пространство

### `AC-013` — дерево, рабочая область и инспектор

- [ ] 2.1 После открытия проекта три зоны одновременно показывают одно имя и одну подтверждённую ревизию (`AC-013`).
- [ ] 2.2 При пустом selection инспектор показывает «Объект не выбран», не сохраняет свойства прежнего объекта и предлагает выбрать объект (`AC-013`).
- [ ] 2.3 После серверного удаления выбранного объекта все зоны убирают его, очищают stale-свойства и переводят selection/focus в безопасный контекст (`AC-013`).
- [ ] 2.4 Evidence: запись открытия, снимок общего контекста ревизии и fault-прогон удаления выбранного объекта (`AC-013`).

### `AC-014` — drag-and-drop и selection

- [ ] 2.5 Выбор объекта из дерева и из рабочей области поочерёдно показывает одну идентичность во всех зонах и не создаёт dirty-state (`AC-014`).
- [ ] 2.6 Допустимый drop заранее называет действие и после подтверждения создаёт одну мутацию; итоговый объект выбран во всех зонах (`AC-014`).
- [ ] 2.7 Несовместимый target и серверный forbidden оставляют source, target, selection, ревизию и dirty-state без изменений (`AC-014`).
- [ ] 2.8 Повтор доставки той же подтверждённой операции не создаёт дубль объекта или связи (`AC-014`).
- [ ] 2.9 Evidence: видео selection, model diff валидного drop, model diff без изменений для invalid/forbidden и журнал повторной доставки (`AC-014`).

### `AC-015` — ручная правка generated-сущностей

- [ ] 2.10 Инженер изменяет свойство сущности мастера тем же инспектором, что и у ручной сущности, и видит согласованный dirty-результат во всех зонах (`AC-015`).
- [ ] 2.11 Инженер перемещает, связывает и после просмотра зависимостей удаляет разрешённую generated-сущность; отмена destructive confirmation не меняет модель (`AC-015`).
- [ ] 2.12 Невалидное значение показывает правило, сохраняет последнее подтверждённое значение модели и оставляет поле доступным для исправления (`AC-015`).
- [ ] 2.13 Запрет edit/delete объясняется protection или server permission, а не происхождением от мастера (`AC-015`).
- [ ] 2.14 Evidence: model diff редактирования и удаления, запись отмены, snapshot validation error и server forbidden (`AC-015`).

### `NFR-011` — целостность и dirty-state

- [ ] 2.15 После каждой мутации UI показывает dirty относительно конкретной saved revision; статус saved появляется только после серверного подтверждения новой ревизии (`NFR-011`).
- [ ] 2.16 При уходе из dirty-проекта действия save, discard и stay дают три разные проверяемые постусловия и не теряют данные скрыто (`NFR-011`).
- [ ] 2.17 Failed save сохраняет edit session и dirty-state, а конфликт ревизий блокирует overwrite до утверждённого явного решения (`NFR-011`).
- [ ] 2.18 Import и deploy не стартуют из неизвестного или частично сохранённого состояния (`NFR-011`).
- [ ] 2.19 Evidence: snapshot ревизий до/после, запись трёх навигационных решений, fault-injection save и конфликт двух ревизий (`NFR-011`).

## 3. Проверка и preview

### `AC-016` — preflight

- [ ] 3.1 На fixture с block и warn список раздельно показывает severity, объект, причину и действие перехода каждой проблемы (`AC-016`).
- [ ] 3.2 «Перейти» раскрывает нужную ветку, выбирает объект во всех зонах, ставит focus на точное поле и позволяет вернуться к прежней проблеме (`AC-016`).
- [ ] 3.3 Block отключает deploy и не обходится прямым URL; warn остаётся в подтверждении разрешённого продолжения (`AC-016`).
- [ ] 3.4 После изменения проекта прежний результат становится stale; недоступный preflight не трактуется как success и сохраняет проект (`AC-016`).
- [ ] 3.5 Evidence: видео перехода block/warn, snapshot disabled deploy, запись stale-состояния и fault-прогон недоступного сервиса (`AC-016`).

### `AC-017` — preview

- [ ] 3.6 Preview показывает имя проекта, исходную ревизию, dirty/saved источник и заметную маркировку режима просмотра (`AC-017`).
- [ ] 3.7 Изменение проекта помечает preview stale; перестроение связывает его с новой ревизией (`AC-017`).
- [ ] 3.8 Проект без клиентской поверхности показывает empty state и переводит к месту настройки, не создавая интерфейс автоматически (`AC-017`).
- [ ] 3.9 Ошибка renderer оставляет конфигуратор и проект открытыми, показывает инженерный контекст и не переключается на live runtime (`AC-017`).
- [ ] 3.10 Evidence: запись preview двух ревизий, snapshot empty/error и командный или сетевой журнал, подтверждающий отсутствие команд реальному оборудованию (`AC-017`).

### `NFR-013` — инженерная диагностика

- [ ] 3.11 Ошибки save, preflight, preview, import, emulator и deploy показывают объект или область, операцию, location, ревизию, разрешённую категорию и correlation context, если он предоставлен (`NFR-013`).
- [ ] 3.12 При отсутствии backend-details UI прямо указывает ограничение диагностики и не выдумывает причину (`NFR-013`).
- [ ] 3.13 Fixture с password, token и private key подтверждает маскирование в UI, DOM и разрешённой копии деталей (`NFR-013`).
- [ ] 3.14 Evidence: набор error screenshots, связь с локальным журналом по correlation context и privacy review маскирования (`NFR-013`).

## 4. Deploy и восстановление

### `AC-018` — atomic deploy и rollback

- [ ] 4.1 Подтверждение deploy называет проект, saved revision, current active version, warnings и состояние rollback-point до отправки команды (`AC-018`).
- [ ] 4.2 UI не показывает success на принятии запроса и меняет active version только после подтверждённого atomic commit и итоговой проверки (`AC-018`).
- [ ] 4.3 Fault-injection до commit сохраняет прежнюю active version; fault-injection во время контролируемого применения показывает запуск и подтверждённый результат rollback (`AC-018`).
- [ ] 4.4 После потери связи UI держит итог неопределённым до resync и показывает фактическое состояние операции и active version (`AC-018`).
- [ ] 4.5 Dirty project, stale preflight и server forbidden блокируют deploy через control и прямой маршрут без изменения active version (`AC-018`).
- [ ] 4.6 Evidence: server version snapshots, журнал этапов, две fault-injection записи, reconnect/resync и model check сохранённого неуспешного draft (`AC-018`).

## 5. Переносимость, повторное использование и защита

### `AC-019` — import/export, шаблоны и защита

- [ ] 5.1 Export серверной части не включает клиентскую часть, export клиентской части не включает серверную, а обе операции показывают ревизию и применяемую политику (`AC-019`).
- [ ] 5.2 До import UI показывает формат, версию, состав, совместимость, конфликты и change-set; подтверждение создаёт одну draft revision (`AC-019`).
- [ ] 5.3 Повреждённый, несовместимый и запрещённый import не меняет current draft, dirty-state или active version (`AC-019`).
- [ ] 5.4 Сохранение комнаты или блока создаёт локальный шаблон с видимым составом; применение показывает change-set и создаёт редактируемые сущности (`AC-019`).
- [ ] 5.5 Protection запрещает подтверждённые сервером операции через control, клавиатуру и прямой маршрут и сохраняется при поддерживаемом transfer (`AC-019`).
- [ ] 5.6 Evidence: оба export-артефакта, round-trip model comparison, preflight после import, записи corrupt/incompatible cases, применение шаблона и server forbidden защиты (`AC-019`).

### `NFR-015` — deterrence без ложной crypto-гарантии

- [ ] 5.7 Все экраны защиты перечисляют фактически ограниченные операции и используют формулировку product-level restriction без обещаний шифрования, DRM или невозможности копирования (`NFR-015`).
- [ ] 5.8 Изменённый клиентский запрос и прямой маршрут получают server forbidden независимо от disabled/hidden control (`NFR-015`).
- [ ] 5.9 Read-only пользователь видит границы защиты, включая отсутствие гарантии против копирования файла или анализа вне AV Control (`NFR-015`).
- [ ] 5.10 Evidence: content review всех protection-текстов, security negative test альтернативных маршрутов и подтверждение неизменности project/policy metadata (`NFR-015`).

## 6. Работа без оборудования и внешней сети

### `AC-020` — отсутствие оборудования и эмулятор

- [ ] 6.1 При отключённых физических устройствах инженер создаёт и сохраняет draft, выполняет статический preflight и preview, а hardware-dependent проверки перечислены отдельно (`AC-020`).
- [ ] 6.2 Явный запуск emulator session маркирует simulated-значения в дереве, рабочей области, preview и результате теста (`AC-020`).
- [ ] 6.3 Остановка сессии не записывает simulated-state как real и не меняет project definition (`AC-020`).
- [ ] 6.4 Недоступный, неподдерживаемый или истёкший эмулятор сохраняет partial progress и оставляет зависимые проверки not-run/blocked (`AC-020`).
- [ ] 6.5 Evidence: запись работы с физически отключённым стендом, сравнение проекта до/после emulator session и три negative fixtures доступности (`AC-020`).

### `NFR-012` — локальная работа без cloud

- [ ] 6.6 При заблокированных внешних маршрутах и доступных локальных сервисах загружаются все обязательные ресурсы и проходят создание, редактирование, preflight и preview (`NFR-012`).
- [ ] 6.7 Сетевой аудит не показывает обязательных запросов к CDN, внешним шрифтам, cloud catalog, telemetry SaaS или внешнему renderer (`NFR-012`).
- [ ] 6.8 Отсутствующий локальный каталог, driver, template или emulator package показывает offline-путь получения и не запускает cloud fallback (`NFR-012`).
- [ ] 6.9 Evidence: network capture при deny-all external policy, перечень локально загруженных ресурсов и запись missing-package state (`NFR-012`).

## 7. Плотные списки и доступность

### `NFR-014` — масштаб плотных списков

- [ ] 7.1 На утверждённом discovery-наборе дерево, каталог, preflight, шаблоны и import conflicts сохраняют filter, sort, grouping, count и readable row state в утверждённом пороге (`NFR-014`).
- [ ] 7.2 Selection остаётся привязанным к идентичности объекта при виртуализации, сортировке, сворачивании и обновлении (`NFR-014`).
- [ ] 7.3 Фильтр без совпадений показывает условия и clear action; refresh error оставляет прежний список как stale (`NFR-014`).
- [ ] 7.4 До утверждения dataset и порога performance-проверка отмечается непройденной, а не закрывается субъективной оценкой (`NFR-014`).
- [ ] 7.5 Evidence: зафиксированный dataset, среда, измерения, запись selection stability и no-data/refresh-error cases (`NFR-014`).

### `NFR-016` — keyboard и focus

- [ ] 7.6 Без мыши пройти создание или открытие проекта, выбор объекта, изменение свойства, preflight, переход к проблеме, preview и разрешённое подтверждение deploy (`NFR-016`).
- [ ] 7.7 Keyboard alternative операций add/move/link использует те же targets, validation и server permissions, что drag-and-drop (`NFR-016`).
- [ ] 7.8 Dialog, wizard и error details удерживают focus внутри временного слоя и возвращают его к инициатору либо точному следующему control (`NFR-016`).
- [ ] 7.9 Focus остаётся видимым в selected, error и disabled окружении и не выражается только цветом (`NFR-016`).
- [ ] 7.10 Evidence: непрерывная keyboard-only запись, focus-order log, снимки focus states и negative test недопустимого keyboard target (`NFR-016`).

## 8. Сводное evidence и решение по срезу

- [ ] 8.1 Для каждого сценария `AC-011`–`AC-020` и `NFR-011`–`NFR-016` существует запись результата на одном SHA с датой, ролью, средой, начальными данными и постусловием.
- [ ] 8.2 Основной, error, forbidden и no-data прогоны не заменены только автоматическими тестами; приложены визуальные, модельные, сетевые, recovery или security evidence по природе требования.
- [ ] 8.3 Непройденный пункт отмечен непройденным и связан с дефектом или открытым блокером; скрытый пропуск не закрывает срез.
- [ ] 8.4 Traceability показывает, что каждый requirement имеет минимум один основной и один негативный evidence-прогон, а deploy/rollback, offline, protection и dirty-state имеют fault/negative evidence.
- [ ] 8.5 Пилот не начинается, пока не назначены владельцы, не создана Redmine-связь, не утверждены метрики и не закрыты блокирующие контракты.
- [ ] 8.6 Создание Pack, передача ASE и реализация выполняются отдельными шагами только после человеческого подтверждения change; эти задачи сами по себе не дают такого разрешения.
