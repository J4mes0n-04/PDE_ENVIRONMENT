# Проектное решение — конфигуратор AV Control

Термины документа: `UI` — пользовательский интерфейс; `change` — пакет изменений OpenSpec; `Outcome` — измеримый целевой результат; `draft` — черновик; `Pack` — утверждаемый пакет определения продукта; `source of truth` — авторитетный источник состояния. `Dirty-state` — состояние несохранённых изменений; `selection` — единый текущий выбор объекта; `drag-and-drop` — перетаскивание; `preflight` — проверка готовности; `preview` — предварительный просмотр; `deploy` — активация проекта; `rollback` — возврат предыдущей версии; `import/export` — ввоз и вывоз проектных данных; `change-set` — согласованный набор изменений; `generated graph` — созданный мастером граф сущностей; `stale` — устаревшее относительно текущей ревизии состояние; `read-only` — режим без изменения данных; `project protection` — проектная политика ограничений; `deterrence` — сдерживание обычных действий без криптографической гарантии; `focus` — клавиатурный фокус; `cloud` — внешнее облако; `fault-injection` — контролируемое внесение отказа.

Статус: `draft`.

Документ описывает UI- и интеграционный подход для одного будущего Outcome. Он не определяет внутреннюю реализацию соседних сервисов, не заменяет Pack и не разрешает разработку. Все неизвестные контракты и числовые пороги остаются блокерами из `proposal.md`.

## Подход

### Граница результата

Конфигуратор предоставляет инженерной роли один непрерывный путь:

1. создать проект мастером или вручную;
2. редактировать проект в едином рабочем пространстве;
3. проверить проект и перейти к каждому дефекту;
4. открыть безопасный preview текущего черновика;
5. отправить сохранённую ревизию на атомарный deploy;
6. увидеть подтверждённую активную версию либо результат возврата предыдущей;
7. при необходимости перенести или повторно использовать проект без потери целостности.

UI не является source of truth для разрешений, active version, preflight и rollback. Он показывает подтверждённое сервером состояние и не заменяет отказ локальной имитацией успеха.

### Контекст открытого проекта

Все зоны конфигуратора используют один контекст открытого проекта. В нём различаются:

- идентичность проекта;
- подтверждённая сервером сохранённая ревизия;
- редактируемое состояние текущей сессии;
- признак dirty и перечень ещё не подтверждённых изменений;
- один текущий выбранный объект;
- результат preflight и ревизия, для которой он получен;
- результат preview и ревизия, из которой он построен;
- подтверждённая active version;
- текущая deploy/rollback-операция;
- контекст оборудования: реальное доступно, реальное недоступно или simulated.

Ревизия preflight и preview становится stale после изменения проекта. UI явно показывает устаревание и не разрешает использовать stale preflight как основание deploy.

### Создание проекта и добавление устройств

#### Мастер готовой комнаты

- Инженер выбирает типовой вариант из локально доступного каталога.
- До применения UI показывает состав, который будет создан: доступные категории сущностей, зависимости и обнаруженные отсутствующие данные.
- Применение создаёт один change-set в редактируемом draft, а не active project.
- Если обязательный драйвер или другая зависимость отсутствует, мастер остаётся на текущем шаге, показывает конкретную причину и не создаёт половину комнаты.
- После применения все созданные сущности доступны в дереве, рабочей области и инспекторе.

Точный состав generated graph не фиксируется до утверждения доменного контракта. UI обязан показать фактический состав до подтверждения и результат после него.

#### Мастер устройств

- Инженер запускает мастер из текущего проекта и выбирает устройство из локального каталога.
- UI показывает, какие связанные сущности предлагается добавить и какие существующие сущности будут использованы.
- Подтверждение применяет один change-set только к выбранной области; существующий проект вне change-set не перезаписывается.
- Конфликт имени, адреса, capability или драйвера объясняется до записи.
- Отмена возвращает к прежнему проекту без скрытых сущностей.

#### Полностью ручной проект

- Инженер получает пустую структуру с обязательным системным корнем, если такой корень требует утверждённая модель.
- Никакие устройства, драйверы, теги, связи, сценарии или UI-элементы не добавляются скрыто.
- Инженер создаёт поддерживаемые сущности последовательно через явные команды.
- Пустой локальный каталог не блокирует открытие ручной структуры; недоступная операция показывает, каких данных не хватает.

Состав обязательного системного корня остаётся блокером контракта. UI не должен выдавать автоматически созданный предметный объект за «пустой проект».

### Единое рабочее пространство

Рабочая поверхность состоит из трёх одновременно доступных зон:

- дерево показывает иерархию и типы сущностей проекта;
- рабочая область или холст показывает связи, компоновку или предметное представление текущего контекста;
- инспектор показывает свойства ровно одного текущего выбранного объекта либо явное состояние «объект не выбран».

Панели не загружают независимые проектные копии. Каждое подтверждённое изменение проходит через общий слой команд модели и возвращает единый результат всем зонам.

Выбор объекта имеет стабильную идентичность, а не только позицию строки. Фильтрация, сортировка, сворачивание ветки или виртуализация списка не должны переносить selection на соседний объект.

Если выбранный объект удалён подтверждённой операцией:

- selection очищается или переводится на однозначно определённого родителя;
- инспектор не продолжает показывать удалённые свойства;
- рабочая область не оставляет активные handles удалённого объекта;
- focus переводится к ближайшему безопасному контексту.

### Selection и drag-and-drop

#### Selection

- Выбор из дерева, холста или инспектора обновляет единый selection-контекст.
- Остальные зоны либо выделяют тот же объект, либо показывают понятный признак, что объект скрыт текущим фильтром или находится вне видимой области.
- Переход от preflight-проблемы сначала открывает нужный контекст, затем выбирает объект и ставит focus на проблемное поле или элемент.
- Выбор не меняет проект и сам по себе не создаёт dirty-state.

#### Drag-and-drop

Drag-and-drop использует двухфазное UI-поведение:

1. до drop проверяются тип источника, тип target, разрешение и известные ограничения;
2. при подтверждённом drop отправляется одна доменная команда модели.

Для допустимого target UI до отпускания показывает конкретный результат: добавить, переместить, связать или заменить. Для недопустимого target показывается причина, а не только запрещающий курсор.

При отказе сервера после drop:

- оптимистическое отображение, если оно использовалось, полностью отменяется;
- исходный объект и selection восстанавливаются;
- dirty-state соответствует фактической модели;
- ошибка содержит операцию, source, target и доступный следующий шаг.

Повторная доставка одной операции не должна создавать дубль. Способ идемпотентности определяет серверный контракт; UI evidence сравнивает модель до и после.

Каждое критическое drag-and-drop действие имеет клавиатурный эквивалент: выбрать объект, вызвать команду «Добавить», «Переместить» или «Связать», выбрать допустимый target и подтвердить теми же правилами валидации.

### Ручная правка результата мастера

Generated-сущность не получает специальный режим, запрещающий обычное редактирование. После применения мастера инженер может:

- открыть объект из дерева или рабочей области;
- изменить разрешённые свойства в инспекторе;
- переместить или связать объект;
- удалить объект после отображения зависимостей и последствий;
- отменить операцию до подтверждения;
- повторно запустить preflight.

Поле может быть read-only только по доменному ограничению, защите проекта или серверному разрешению. UI показывает конкретную причину. Фраза «создано мастером» сама по себе не является причиной запрета.

Если значение не проходит локальную или серверную проверку, последнее подтверждённое значение не перезаписывается, поле остаётся доступным для исправления, а проект сохраняет dirty-state введённой попытки настолько, насколько это допускает безопасная модель.

### Dirty-state и сохранение

Признак dirty вычисляется относительно последней подтверждённой сервером сохранённой ревизии.

- После доменной мутации проект становится dirty.
- После подтверждённого save UI получает новую сохранённую ревизию и снимает dirty.
- При failed save dirty остаётся, введённые данные не выдаются за сохранённые.
- При переходе к другому проекту, закрытии поверхности или действии, которое заменит текущий draft, пользователь получает явный выбор: сохранить, отбросить или остаться.
- «Сохранить» продолжает переход только после подтверждённого save.
- «Отбросить» возвращает последнюю подтверждённую ревизию и явно сообщает, какой draft отброшен.
- «Остаться» не меняет проект и возвращает focus к месту вызова.

При конфликте ревизий UI не перезаписывает серверное состояние автоматически. Он показывает обе известные ревизии, блокирует destructive continuation и предлагает только действия, предусмотренные утверждённым merge/reload-контрактом. Пока контракт не утверждён, безопасное поведение — сохранить локальный ввод в сессии, не заявлять save и запросить явное обновление.

Import, применение шаблона и deploy считаются операциями, способными заменить или зафиксировать большую область. Они обязаны пройти ту же dirty-state проверку до начала.

### Preflight

Preflight запускается для конкретной сохранённой ревизии и возвращает:

- итоговый статус проверки;
- отдельные коллекции блокеров и предупреждений;
- объект или область проекта;
- человекочитаемую инженерную причину;
- доступное действие исправления;
- location descriptor, достаточный UI для перехода;
- технический контекст, если он разрешён политикой.

UI не придумывает severity из текста. Блокер определяется серверным результатом и отключает deploy для этой ревизии. Предупреждение не маскируется под успех: оно остаётся видимым, а продолжение требует явного действия по утверждённой политике.

Переход к проблеме:

1. открывает нужную ветку дерева или режим рабочей области;
2. снимает фильтр только после понятного уведомления либо показывает, что объект скрыт;
3. выбирает объект в едином selection;
4. переводит focus на конкретное поле или элемент;
5. сохраняет возможность вернуться к списку на прежнюю позицию.

После изменения проекта результат preflight помечается stale. Deploy требует новый успешный preflight той же сохранённой ревизии.

Если preflight service недоступен, UI сохраняет проект, показывает инженерную ошибку и блокирует deploy. Недоступность проверки не трактуется как отсутствие проблем.

### Preview

Preview строится из выбранной сохранённой или текущей редактируемой ревизии по явному правилу. UI всегда показывает:

- имя проекта;
- идентификатор или другой однозначный признак исходной ревизии;
- dirty или saved источник;
- режим `preview`;
- выбранный viewport или профиль клиента, если он доступен;
- stale-состояние после последующего изменения проекта.

Preview является read-only относительно реального runtime:

- взаимодействия меняют только локально отображаемое preview-состояние;
- команды устройствам, room runtime и реальной active session не отправляются;
- simulated data маркируются;
- отсутствие клиентского представления даёт empty state с переходом к месту настройки.

Ошибка renderer не закрывает конфигуратор и не меняет проект. UI показывает технический контекст по `NFR-013`, оставляет предыдущий preview только как явно устаревший и предлагает повторить построение после исправления.

### Atomic deploy и rollback

UI допускает deploy только если одновременно истинны условия:

- пользователь получил серверное разрешение;
- проект сохранён и имеет однозначную ревизию;
- preflight относится к той же ревизии;
- блокеров нет;
- предупреждения обработаны по утверждённой политике;
- нет уже выполняющейся несовместимой операции.

Перед подтверждением UI показывает:

- проект и ревизию;
- текущую active version;
- предполагаемую новую версию;
- предупреждения;
- наличие или статус создаваемого rollback-point, если это подтверждено сервером;
- последствия и единственное явное действие запуска.

После запуска UI различает «запрос принят», «проверяется», «применяется», «проверяется результат», «успех», «ошибка» и «rollback выполняется». Точные transport-состояния определяет контракт, но промежуточное состояние никогда не отображается как успех.

Сервер обязан выполнить проектную активацию атомарно. UI считает deploy успешным только после получения:

- подтверждённой active version;
- результата итоговой проверки;
- доступного rollback-point или объяснения утверждённой политики.

При ошибке UI показывает:

- этап и причину;
- была ли новая версия активирована;
- какая версия активна сейчас;
- был ли rollback запущен;
- завершился ли rollback успешно;
- доступное следующее действие и технический контекст.

Если итог операции неизвестен из-за потери связи, UI не предполагает rollback или успех. После reconnect он запрашивает фактическую active version и состояние операции, затем показывает сверенный результат.

Draft, который отправлялся на deploy, сохраняется для исправления независимо от исхода активации. Ошибка deploy не должна уничтожать проектную работу.

### Import и export

Серверная и клиентская части выбираются независимо в пределах утверждённого формата.

Перед import UI выполняет или запрашивает:

- чтение метаданных без применения;
- проверку формата, версии, целостности и совместимости;
- определение состава;
- список конфликтов и предполагаемых изменений;
- проверку разрешения и защиты;
- dirty-state решение для текущего проекта.

Применение import является одной атомарной операцией к draft. При ошибке текущая ревизия не меняется, а файл не считается импортированным.

Export показывает выбранную часть, ревизию, применяемую защиту и исключаемые данные. UI не включает секреты только потому, что они присутствуют в модели; окончательный состав и маскирование задаёт серверный контракт.

Round-trip проверяется на поддерживаемых сущностях: export, import в чистый совместимый контекст, model comparison и preflight. Побайтовая идентичность не требуется, если формат канонизирует данные; семантические правила сравнения должны быть утверждены до Ready.

### Шаблоны

Инженер с подтверждённым разрешением может сохранить комнату или выбранный поддерживаемый блок как шаблон.

- UI показывает точный состав шаблона и исключённые зависимости.
- Применение шаблона сначала строит change-set и показывает конфликты.
- Отмена не меняет проект.
- Успешное применение создаёт обычные редактируемые сущности, если защита не задаёт иное.
- Отсутствующий шаблон или несовместимая версия даёт no-data/error state без частичного проекта.

Синхронизация с облачным каталогом не входит. Шаблоны доступны из локального хранилища или импортируемого артефакта.

### Проектная защита

Защита реализуется как policy metadata и серверная авторизация действий внутри продукта.

UI обязан:

- явно показать, что защищено и какие операции ограничены;
- назвать владельца или источник политики, если эти данные предоставляет контракт;
- блокировать обычные edit, copy, export или снятие защиты согласно серверному решению;
- повторно проверять разрешение на сервере;
- сохранять policy metadata при поддерживаемой передаче;
- не называть механизм шифрованием, DRM или гарантией невозможности копирования.

Прямой URL, восстановленное состояние браузера, drag-and-drop, клавиатурная команда или изменённый клиентский запрос не обходят серверный запрет. Если файл доступен вне продукта, UI честно сообщает, что product-level restriction не защищает от копирования средствами ОС или анализа содержимого.

Точные правила наследования и снятия защиты остаются блокером.

### Работа без оборудования и эмулятор

Отсутствующее физическое устройство имеет отдельное состояние «оборудование недоступно», которое не равно ошибке схемы проекта.

Без оборудования инженер может:

- создавать и редактировать устройства и их свойства;
- собирать связи и сценарии;
- сохранять partial progress;
- запускать статическую часть preflight;
- видеть, какие проверки требуют реального оборудования;
- открыть preview;
- использовать эмуляцию в пределах подтверждённых capabilities.

Эмулятор запускается явной командой и создаёт отдельную сессию. Во всех зонах simulated-значение визуально и текстово отличается от real/confirmed. Остановка или истечение доступности эмулятора не удаляет проект и не заменяет реальные статусы последним simulated-значением.

Перед production deploy проверки, зависящие от реального оборудования, должны получить фактический результат или остаться блокерами по серверной политике. Эмуляция не превращает неизвестную совместимость в успешную.

### Модель ошибок

Для инженерной роли ошибка содержит два слоя:

- основной: что не выполнено, какой объект или область затронуты и что можно сделать;
- диагностический: операция, location, ревизия, разрешённый код/категория, correlation context и ссылка на локальные логи или детали.

Диагностический слой:

- не показывает пароль, token, private key или другое секретное значение;
- не выводит необработанный stack trace вместо понятного действия;
- сохраняется при копировании в разрешённый отчёт только по политике;
- явно сообщает, если backend не предоставил техническую причину.

Ошибки не закрывают рабочий контекст без необходимости. Проект, selection, фильтр и введённые данные сохраняются, если это безопасно.

## Нефункциональные ограничения

### Целостность и dirty-state (`NFR-011`)

- Одна пользовательская команда создаёт не более одной согласованной доменной мутации.
- Статус saved появляется только после серверного подтверждения ревизии.
- Навигация и заменяющие операции используют save/discard/stay.
- Import и deploy не применяются к неизвестному или частично сохранённому состоянию.
- После ошибки UI сверяет фактическую ревизию и не продолжает из предположения.

### Offline-first без cloud (`NFR-012`)

- Все HTML, скрипты, стили, иконки, шрифты, справочные тексты и обязательные каталоги поставляются локально.
- При заблокированном внешнем маршруте конфигуратор продолжает работать с доступными локальными сервисами.
- Недостающий локальный пакет показывает конкретное действие загрузки или установки по утверждённому offline-процессу.
- Запрещены скрытые обращения к telemetry SaaS, cloud catalog, CDN, внешнему шрифту и внешнему preview renderer.
- Потеря локального сервера отличается от отсутствия интернета и не маскируется cloud fallback.

### Инженерная диагностика (`NFR-013`)

- Все критические операции показывают объект, операцию, ревизию и correlation context, если он предоставлен.
- Ошибка разрешения отличается от несовместимости, отсутствующих данных и transport failure.
- Технические детали доступны только инженерной роли и проходят маскирование.
- Отсутствие подробностей отображается как ограничение диагностики, а не пустая панель.

### Плотные списки (`NFR-014`)

К плотным спискам относятся дерево проекта, каталоги, preflight issues, результаты поиска, шаблоны и import conflicts.

На наборе, зафиксированном discovery, должны сохраняться:

- сортировка, фильтр, grouping и счётчик результата;
- стабильная selection по идентичности объекта;
- раскрытие и сворачивание без перехода selection на другую строку;
- клавиатурная навигация и видимый focus;
- переход к объекту из preflight;
- empty state после фильтра с действием очистки;
- восстановление позиции после возврата из инспектора или проблемы.

Числовой объём набора и response-time threshold не задаются этим draft. До их утверждения требование не считается закрытым.

### Граница защиты (`NFR-015`)

- Все тексты используют формулировки «ограничить редактирование/копирование в AV Control» или эквивалентный смысл.
- Запрещены обещания «невозможно скопировать», «зашифровано» и «защищено от извлечения», если отдельный криптографический механизм не утверждён.
- Сервер проверяет запрет независимо от состояния кнопки.
- Security evidence включает изменённый клиентский запрос и прямой маршрут, но не объявляет product restriction защитой файловой системы.

### Keyboard и focus (`NFR-016`)

- Все интерактивные элементы достигаются в логичном порядке клавишей `Tab` и обратным переходом.
- `Enter` или `Space` активирует control согласно его семантике; `Escape` закрывает временный слой без потери данных.
- Дерево поддерживает ожидаемую клавиатурную навигацию по узлам.
- Для drag-and-drop существует меню или команда с теми же допустимыми target и ошибками.
- При открытии dialog focus переходит в него, остаётся внутри до закрытия и возвращается к инициатору.
- После перехода к preflight-проблеме focus оказывается на проблемном поле или объекте.
- Focus не кодируется только цветом и остаётся видимым на selected, error и disabled окружении.

## Безопасность и данные

- UI доверяет серверной авторизации, а не скрытию control.
- Защищённые и запрещённые действия повторно проверяются сервером.
- Import считается недоверенным вводом и валидируется до применения.
- Export и диагностические детали исключают секреты по серверной политике.
- Preview изолирован от live-команд.
- Deploy требует явного подтверждения и актуальной ревизии.
- Критические изменения должны создавать audit-события по соседнему security-контракту; этот change показывает результат, но не проектирует хранилище аудита.
- Локальное кэширование не должно превращаться во второй source of truth. Состав и срок хранения кэша остаются частью технического решения и privacy review.

## Совместимость и миграция

- Старый проект допускается к import только после проверки версии и совместимости.
- Несовместимый артефакт не применяется частично и не меняет текущий draft.
- Миграция, если её предоставляет сервер, сначала показывает план и создаёт новую draft revision; active version не меняется.
- Export указывает формат и версию, когда контракт их определит.
- Шаблон наследует те же правила совместимости, что и импортируемая часть проекта.
- После import или migration обязателен новый preflight.
- Матрица поддерживаемых версий, браузеров и ОС остаётся блокером до Ready.

## Discovery и наблюдаемость

До числовой оптимизации фиксируются:

- сценарии и роли;
- целевая среда;
- representative project и dense dataset;
- начальная сохранённая ревизия и итоговая ревизия;
- завершённость пути без помощи;
- причина остановки;
- время выполнения как наблюдение, но не как target;
- число критических ошибок и необходимость подсказки;
- результат deploy/rollback;
- внешние сетевые обращения;
- keyboard/focus defects.

После baseline владельцы утверждают target и validation window. События аналитики, если они потребуются, должны храниться локально или быть отдельно явно разрешены; cloud telemetry по умолчанию запрещена.

## Зависимости и риски

### Зависимости

- Foundation предоставляет оболочку, вход, общие controls, route guards и визуальную семантику.
- Project Storage предоставляет проект, ревизии, сохранение, active/draft, import/export, шаблоны и конфликт версий.
- Каталог и Driver Engine предоставляют устройства, драйверы, capabilities и причины недоступности.
- Preflight service предоставляет severity и location descriptor.
- Preview renderer строит read-only представление конкретной ревизии.
- Deploy service предоставляет atomic commit, last-known-good, rollback-point и фактическую active version.
- Security service предоставляет authorization, audit и protection policy.
- Emulator предоставляет поддерживаемые simulated capabilities и статус лицензии.

Если зависимость недоступна, соответствующая операция блокируется локальным error state; остальная безопасная работа с проектом продолжается, где это позволяет контракт.

### Основные риски и меры

- Риск расхождения зон: одна project model, одна selection-модель, model diff в evidence.
- Риск потери данных: revision-aware dirty-state, save/discard/stay и fault-injection.
- Риск ложного deploy: успех только после подтверждённой active version.
- Риск неясного rollback: отдельное состояние операции и сверка после reconnect.
- Риск live-команд из preview: изолированный read-only command boundary и сетевой/командный аудит.
- Риск ложной безопасности: честный текст deterrence и серверный negative test.
- Риск скрытого cloud: network-deny test и локальная поставка ресурсов.
- Риск непригодности на больших проектах: discovery-набор, измеримый порог до Ready и стабильная идентичность selection.
- Риск недоступности без мыши: клавиатурные альтернативы и focus-аудит в каждом срезе.
- Риск превращения draft-визуала в baseline: UX approval остаётся отдельным gate.

### Остаточный риск draft

Пока не закрыты серверные контракты, роли, формат проекта, политика защиты, эмуляция и числовые пороги, design определяет только обязательное наблюдаемое поведение. Он не доказывает реализуемость конкретного API и не может перейти в Ready.

## Рассмотренные решения

- Отдельные экраны дерева, холста и свойств отклонены: они создают риск разных ревизий и selection.
- Мастер как закрытый генератор отклонён: он противоречит ручной доработке.
- Deploy текущего несохранённого состояния отклонён: нельзя однозначно доказать применённую ревизию.
- Preview на активном runtime отклонён: просмотр не должен посылать реальные команды.
- Частичный import отклонён: он нарушает атомарность и усложняет recovery.
- Cloud fallback отклонён: продукт должен работать offline-first.
- Защита только скрытием кнопки отклонена: нужна серверная проверка, но без ложного обещания криптографии.
- Mouse-only drag-and-drop отклонён: критическое действие требует клавиатурного эквивалента.

## Выпуск и восстановление

Будущая поставка разделяется на независимо проверяемые срезы, перечисленные в `tasks.md`. Каждый срез включается только после evidence на одном SHA.

При дефекте UI:

- возвращается предыдущая проверенная сборка;
- последняя подтверждённая сервером ревизия проекта и active version сохраняются;
- незавершённая операция сверяется с сервером перед повтором;
- draft не удаляется автоматически;
- stop-signal фиксируется и блокирует следующий срез.

При failed deploy восстановление выполняет deploy service. UI не реализует собственный частичный rollback и не закрывает ошибку до получения фактической active version.

Release owner, feature flag, допустимое время восстановления и production validation window не назначены. Это блокеры Ready, а не значения для самостоятельного заполнения.
