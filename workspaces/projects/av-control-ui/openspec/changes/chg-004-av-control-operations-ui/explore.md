## Confirmed facts

- Support Operator должен видеть общую health-картину сервера, комнат, клиентов, устройств, драйверов и сценариев, а затем переходить к проблемному компоненту, отфильтрованным событиям и разрешённому действию.
- Авторизованная роль должна формировать diagnostic bundle локально; секреты и запрещённые данные не должны попадать в результат, а внешняя передача допустима только отдельным явным действием.
- IT Admin должен выполнить первичную инициализацию контроллера, создать первого администратора, настроить сеть и NTP и увидеть результат проверки связности.
- IT Admin должен управлять пользователями и утверждёнными ролями. Security Auditor должен читать аудит без возможности изменения или удаления.
- Admin Web UI и API требуют аутентификации, серверной проверки RBAC и TLS. Критические действия должны оставлять tamper-evident audit event — событие аудита с обнаруживаемым нарушением целостности.
- Разрешённые события могут передаваться в явно настроенный SIEM/syslog; локальный аудит не должен зависеть от доступности внешнего получателя.
- Обновление ядра выполняется из локально загруженного offline-пакета. До установки показываются сведения о пакете и patch note, проверяются подпись, целостность и совместимость, создаётся restore point, а при сбое выполняется rollback.
- Если встреча активна, обновление не должно начинаться молча: IT Admin видит предупреждение и выбирает отложить либо осознанно продолжить в пределах своих прав.
- Backup должен создаваться и проверяться; совместимый backup должен восстанавливать систему на текущем или replacement controller — контроллере-замене — без ручной настройки каждого объекта.
- При несовместимом или повреждённом backup частичное применение запрещено, а текущая конфигурация должна сохраниться.
- В Safe Mode Admin Web UI остаётся доступным для диагностики, restore и rollback; Room Client показывает понятную заглушку и не предоставляет управление оборудованием.
- IT Admin должен видеть состояние лицензии, применимый лимит, фактическое использование и ограничения. Превышение лимита блокирует новое запрещённое действие, но не ломает активный runtime.
- Vendor Support получает только явный, ограниченный по времени, видимый и отзывной доступ; выдача, использование, истечение и отзыв должны попадать в аудит.
- IT Admin должен настраивать ретенцию логов и дампов и выполнять разрешённую очистку. При заполнении хранилища некритические записи ограничиваются, критические данные защищаются, а UI показывает причину и действие восстановления.
- Штатные эксплуатационные пути не должны требовать интернета, CDN, внешних шрифтов, обязательных облачных API или онлайн-доставки обновлений.
- Числовые baseline, target, размер выборки, validation window, пороги производительности и целевая аппаратная матрица не утверждены. Входной документ требует discovery-срез без выдумывания чисел.
- Предполагаемый риск — `R2`; будущему Outcome потребуется Full Pack после подтверждения change.

## Intended change boundary

Change описывает одну ролевую эксплуатационную поверхность Admin Web UI и связанную заглушку Room Client в Safe Mode. В него входят:

- health dashboard;
- triage и фильтры журналов;
- локальная подготовка diagnostic bundle и контроль privacy;
- первичная настройка первого администратора, сети и NTP;
- пользователи и роли;
- TLS, read-only аудит и настройка SIEM/syslog;
- offline update, patch note, restore point, проверка активной встречи и rollback;
- backup/restore, включая replacement controller;
- Safe Mode для Admin Web UI и Room Client;
- состояния и лимиты лицензии;
- временный Vendor Support;
- ретенция, очистка и storage-full recovery;
- discovery локальных продуктовых, надёжностных и производительных метрик без числовых обещаний.

Change не проектирует конфигуратор, обычный Room Client, kiosk/pairing, серверный runtime, форматы пакетов и backup, криптографические алгоритмы, облачный кабинет, онлайн-магазин лицензий или коммерческий checkout.

## Evidence intent

Черновик требует доказательств не только интерфейса, но и фактических ограничений:

- ролевые прогоны разрешённых и запрещённых маршрутов;
- fault injection для недоступного Monitoring, неуспешного update, restore и rollback;
- сетевой захват при заблокированном внешнем доступе;
- проверка TLS и серверного RBAC, а не только скрытых кнопок;
- проверка целостности и неизменяемости аудита;
- privacy fixtures с известными секретами и персональными полями для проверки bundle;
- восстановление на чистом совместимом replacement controller;
- клавиатурный прогон и проверка focus/error semantics;
- локальные сырые discovery-измерения с контекстом железа, браузера и размера данных без объявления порога успешности.

Успешные unit/e2e-тесты сами по себе не закрывают ролевые, security, privacy, recovery и outcome evidence.
