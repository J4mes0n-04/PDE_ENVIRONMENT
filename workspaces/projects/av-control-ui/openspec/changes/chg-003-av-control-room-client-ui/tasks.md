# Tasks: срезы поставки Room Client

## Delivery rules

Эти задачи являются подсказками будущей поставке ASE и не заменяют Pack, delta spec или Ready Review.

- [ ] До реализации назначить владельцев результата, продукта, риска, данных, выпуска и rollback; сейчас все владельцы неизвестны.
- [ ] До Ready создать связанную задачу Redmine; текущее состояние — `Не создана`.
- [ ] Зафиксировать один будущий Outcome для всего change, не разделяя эти требования между несколькими Outcomes без Definition Change.
- [ ] Утвердить API/WebSocket, pairing, kiosk, capability, cleanup, multi-panel, calendar/VKS и localization contracts либо оставить зависимый срез заблокированным.
- [ ] Утвердить матрицу панелей, browsers, viewport, ориентаций, языков и сетевых профилей.
- [ ] Для каждого прогона фиксировать SHA, дату, среду, устройство, browser, viewport, язык, сеть, requirement ID, ожидаемый и фактический результат.
- [ ] Не считать unit/e2e-тест единственным evidence: для пользовательских, recovery, kiosk и multi-panel путей обязательна наблюдаемая запись и сверка с server state.
- [ ] Непройденный пункт оставить открытым со ссылкой на дефект или блокирующий вопрос; скрытый пропуск не закрывает срез.

## Slice: pairing and kiosk readiness

### AC-021 Pairing панели, клиентский проект и kiosk

- [ ] Зафиксировать contract, по которому авторизованная роль выбирает конкретную панель, комнату и опубликованную версию клиентского проекта, а сервер атомарно подтверждает назначение.
- [ ] Реализовать unpaired, pairing, loading, ready и blocked состояния без показа данных чужой комнаты.
- [ ] После успешного назначения загрузить точную подтверждённую версию проекта и первый server snapshot до показа рабочего Room Client.
- [ ] Заблокировать повторное использование просроченного pairing request, назначение без права и активацию несовместимого проекта.
- [ ] При ошибке нового назначения сохранить прежнюю валидную привязку и версию проекта, если они существовали.
- [ ] Не объявлять панель готовой, пока системная оболочка не подтвердила kiosk lock.
- [ ] Прогнать основной сценарий: новая панель → pairing → выбранная комната → выбранный проект → locked kiosk → standby или active room.
- [ ] Прогнать отказ: просроченный request, недостаточное право, несовместимый проект и неподтверждённый kiosk не создают частичную привязку.
- [ ] Собрать evidence `AC-021`: синхронная запись административной стороны и панели, server record назначения, версия проекта и результат негативных прогонов.

### NFR-022 Блокировка kiosk

- [ ] Утвердить поддерживаемый системный kiosk mechanism и отдельный maintenance unlock; browser fullscreen не принимать как достаточную защиту.
- [ ] На каждой утверждённой панели проверить touch-жесты, browser navigation, task switching, системные shortcuts и доступные аппаратные controls обычного пользователя.
- [ ] Проверить, что перезапуск пользовательского клиента возвращает locked Room Client без доступа к desktop или настройкам ОС.
- [ ] Проверить maintenance flow с отдельной авторизацией, аудитом выхода и подтверждённым возвратом в lock.
- [ ] При невозможности lock перевести панель в blocked/maintenance и запретить production-ready status.
- [ ] Собрать evidence `NFR-022`: видеозапись escape test по каждой модели панели, запись авторизованного обслуживания и серверный/системный факт повторного lock.

### NFR-023 Offline-first без внешней зависимости

- [ ] Собрать обязательные scripts, styles, шрифты, иконки, переводы и другие runtime-assets в локальную поставку.
- [ ] Заблокировать внешний интернет при доступном локальном сервере и пройти загрузку, запуск, active controls и завершение.
- [ ] Выполнить сетевой аудит и подтвердить отсутствие обязательных CDN, cloud API, external font и analytics requests.
- [ ] Отключить необязательную calendar/VKS интеграцию и подтвердить, что базовые локальные room flows продолжают работать.
- [ ] Отдельно отключить локальный сервер и подтвердить переход в offline по `AC-027`, не смешивая server-offline с internet-offline.
- [ ] Собрать evidence `NFR-023`: сетевой trace, перечень локальных assets и видеозапись критического пути при заблокированном интернете.

## Slice: start and session continuity

### AC-022 Главный сценарий одним действием

- [ ] На standby-экране оставить одно визуально основное действие запуска без предварительного выбора инженерных параметров.
- [ ] После одного tap показать немедленный feedback и server-reported progress, временно исключив дублирующую отправку.
- [ ] Переводить Room Client в active только после server confirmation готовности.
- [ ] При server rejection вернуть подтверждённый standby/degraded state и показать разрешённый повтор или поддержку.
- [ ] Прогнать основной путь одним действием от standby до server-confirmed active.
- [ ] Прогнать многократный tap во время pending и подтвердить одну серверную команду без дублирующей сессии.
- [ ] Прогнать отказ запуска и убедиться, что UI не показывает ложную готовность.
- [ ] Собрать evidence `AC-022`: usability-запись, client/server trace команды и скриншоты standby, pending, active и rejection.

### AC-023 Продолжение активной комнаты

- [ ] При initial load, reload и reconnect запрашивать server state активной сессии до выбора стартового экрана.
- [ ] Для active session показать действие продолжения, текущий источник, подтверждённые controls и доступное завершение.
- [ ] Не создавать новую сессию и не показывать обычный старт как основной путь поверх active room.
- [ ] При server standby отбросить локальный active cache и показать чистый standby.
- [ ] Прогнать открытие второй панели и reload первой панели во время действующей сессии.
- [ ] Прогнать расхождение локального active state с server standby и подтвердить победу server snapshot.
- [ ] Собрать evidence `AC-023`: записи reload/continue, server session record и подтверждение отсутствия дублирующей сессии.

## Slice: sources and room controls

### AC-024 Выбор BYOD или источника

- [ ] Получать список источников и их доступность только из server capability.
- [ ] Сопоставить каждому источнику человекочитаемое RU/EN имя без внутренних входов, тегов, адресов и протоколов.
- [ ] Для выбора показывать pending, сохраняя различимым последнее подтверждённое состояние.
- [ ] Активировать новый источник только после server confirmation и распространять результат другим панелям.
- [ ] При исчезновении или rejection вернуть последнее подтверждённое состояние и предложить повтор или другой источник.
- [ ] Прогнать BYOD detection → понятное имя → выбор → server-confirmed active source.
- [ ] Прогнать исчезновение источника между отображением и выбором без ложного переключения и автоматического retry.
- [ ] Собрать evidence `AC-024`: запись UI, capability snapshot, command result и отсутствие инженерных подписей в RU/EN.

### AC-025 Controls комнаты с серверной обратной связью

- [ ] Сформировать видимость mute, громкости, camera actions и layout из server capability и permission.
- [ ] Для каждого control различать last confirmed value, pending и server-confirmed result.
- [ ] Исключить прямые обращения Room Client к оборудованию и ВКС-провайдеру.
- [ ] Утвердить server policy для частых последовательных изменений громкости до реализации batching или coalescing.
- [ ] При rejection восстановить последнее server-confirmed value и показать понятное следующее действие.
- [ ] Прогнать mute и громкость с подтверждением на исходной и второй панели.
- [ ] Прогнать разрешённые camera action и layout, а также отсутствие неподдерживаемых controls.
- [ ] Прогнать отзыв permission и server rejection без ложного applied state.
- [ ] Собрать evidence `AC-025`: синхронная запись UI и server state для каждого вида control, включая pending и rejection.

## Slice: finish, cleanup and standby

### AC-026 Завершение, очистка и standby

- [ ] Утвердить точный перечень очищаемых данных, сохраняемого аудита и server confirmation завершения.
- [ ] Отделить действие завершения от частых controls и применить подтверждение только по утверждённой политике.
- [ ] После действия показывать ending до подтверждённых закрытия сессии, разрешённого ВКС, очистки и reset комнаты.
- [ ] Показывать clean standby только после полного server confirmation.
- [ ] При частичном отказе сохранить ending/blocked, не разрешать конфликтующий новый старт и предложить разрешённый recovery.
- [ ] Прогнать успешное завершение с проверкой отсутствия данных предыдущей сессии в новом standby.
- [ ] Инъецировать отказ на этапе закрытия или очистки и подтвердить отсутствие ложного standby и потери обязательного аудита.
- [ ] Собрать evidence `AC-026`: пользовательская запись, server cleanup result, проверка данных до/после и негативный fault-прогон.

## Slice: connection resilience and source of truth

### AC-027 Потеря связи без очереди и resync

- [ ] Реализовать различимые online, offline и resyncing состояния.
- [ ] При disconnect сразу отключить server-dependent actions и пометить последнее отображение неактуальным.
- [ ] Не записывать offline tap как команду, retry job или deferred action.
- [ ] Если disconnect произошёл после отправки, но до ответа, не угадывать итог и не переотправлять команду автоматически.
- [ ] После reconnect запросить полный snapshot и включить controls только после его применения.
- [ ] При resync failure оставить controls заблокированными и показать повтор подключения или поддержку.
- [ ] Прогнать disconnect в active state, попытки каждого server-dependent action offline и reconnect.
- [ ] Проверить server logs: ни одна offline-команда не появляется после reconnect.
- [ ] Собрать evidence `AC-027`: network fault video, client/server logs, snapshot до/после и подтверждение отсутствия hidden queue.

### NFR-021 Сервер как источник истины

- [ ] Разделить client model на server-confirmed state, presentation state и кратковременный pending.
- [ ] Запретить кэшу, local storage и client project объявлять mutable room state подтверждённым.
- [ ] Утвердить contract freshness marker и способ различить command acceptance, rejection и authoritative state.
- [ ] При reload, reconnect и конфликте всегда применять server snapshot поверх локального представления.
- [ ] Прогнать accepted и rejected command и сопоставить UI с фактическим server state.
- [ ] Подменить локальный cache устаревшим значением и подтвердить, что snapshot его заменяет без записи на сервер.
- [ ] Собрать evidence `NFR-021`: state trace от action до render, server snapshot и тест конфликта локального кэша.

## Slice: user-safe failures

### AC-028 Понятные ошибки без инженерных терминов

- [ ] Составить RU/EN mapping безопасных пользовательских категорий ошибок к недоступной функции, следующему действию и пути поддержки.
- [ ] Оставить техническую причину в разрешённой диагностике, не передавая её как пользовательский текст.
- [ ] Добавить нейтральный fallback для неизвестной причины без ложного диагноза.
- [ ] Разрешить только нейтральный код обращения, не раскрывающий secret, адрес или внутренний объект.
- [ ] Прогнать известные ошибки запуска, источника, control, завершения и интеграции.
- [ ] Передать raw backend error и подтвердить, что UI не показывает driver, tag, protocol, transport, stack trace или внутренний адрес.
- [ ] Провести content review с End User и Support представителями после назначения конкретных согласующих.
- [ ] Собрать evidence `AC-028`: каталог проверенных сообщений RU/EN, screenshots, raw input для негативного теста и результат терминологического review.

## Slice: multi-panel consistency

### AC-029 Синхронизация нескольких панелей

- [ ] Утвердить серверный порядок конфликтующих команд и способ определения свежести state.
- [ ] Подключить каждую панель к server state stream без peer-to-peer authoritative sync.
- [ ] После server confirmation распространять итог всем панелям одной комнаты.
- [ ] На reconnect отставшей панели применять полный snapshot без отправки локальных значений.
- [ ] Прогнать изменение каждого основного control на первой панели и наблюдать автоматическое совпадение второй.
- [ ] Отключить вторую панель, изменить комнату на первой, reconnect вторую и проверить convergence.
- [ ] Отправить конфликтующие разрешённые actions с двух панелей и подтвердить единый server-decided result.
- [ ] Собрать evidence `AC-029`: одновременная видеозапись двух панелей, server ordering trace и проверка отсутствия stale overwrite.

## Slice: calendar and VKS boundary

### AC-030 Ограниченная область календаря и ВКС

- [ ] Утвердить минимальный calendar/VKS capability contract либо оставить интеграционный UI заблокированным.
- [ ] При утверждённом контракте показывать только server-provided read-only summary и общий server-side start/end.
- [ ] Не добавлять прямое подключение Room Client к calendar или VKS provider.
- [ ] Скрыть или безопасно отключить booking, редактирование, продление, неутверждённый автостарт и provider-specific controls.
- [ ] При деградации интеграции ограничить только зависимые actions и сохранить независимые room flows.
- [ ] Прогнать разрешённый read-only summary и общий запуск с server confirmation.
- [ ] Прогнать отсутствие контракта и убедиться, что нет mock-встречи, ложной доступности и незаявленных controls.
- [ ] Прогнать потерю интеграции во время active room и проверить понятную ограниченную деградацию.
- [ ] Собрать evidence `AC-030`: capability snapshot, UI-запись разрешённого минимума и negative scope audit.

## Slice: touch, responsive and localization

### NFR-024 Touch и адаптивность

- [ ] После утверждения матрицы подготовить набор viewport, ориентаций, системного масштаба и touch-устройств для обязательного прогона.
- [ ] Сделать start, sources, mute, громкость, camera, layout, finish и recovery достижимыми без hover-only информации и точного pointer.
- [ ] Развести частые controls и destructive finish так, чтобы обычный touch не создавал случайного завершения.
- [ ] Проверить normal, pressed, pending, disabled, error и focus для интерактивных элементов.
- [ ] Проверить reflow при смене ориентации, системного масштаба и длинных RU/EN строках.
- [ ] Прогнать полный критический путь touch на каждом утверждённом классе устройства.
- [ ] Прогнать узкий viewport и длинное сообщение ошибки без перекрытия, недостижимых controls и потери смысла.
- [ ] Собрать evidence `NFR-024`: visual regression, touch-видео и матрица фактических результатов по средам.

### NFR-025 Локализация RU/EN

- [ ] Зафиксировать утверждённый glossary для standby, start, active, source, mute, volume, camera, layout, finish, offline, resync и recovery.

- [ ] Запретить raw backend strings, localization keys и технический fallback в End User UI.
- [ ] Утвердить fallback policy; до решения отсутствие обязательной строки блокирует выпуск соответствующего сценария.
- [ ] Прогнать полный комнатный путь и все error/recovery состояния на русском языке.
- [ ] Повторить тот же набор на английском языке и подтвердить неизменность server state при переключении локали.
- [ ] Выполнить проверку отсутствующей строки и убедиться, что evidence остаётся непройденным, а raw key не появляется.
- [ ] Собрать evidence `NFR-025`: RU/EN screenshots или видео, автоматический отчёт полноты ресурсов и content review.

## Slice: metric and response-time discovery

### NFR-026 Discovery времени отклика

- [ ] Согласовать privacy-safe correlation между user action, первым feedback, command send, server result, authoritative event и final render.
- [ ] Инструментировать start, source selection, каждый вид control, finish, reconnect и resync без записи secrets и содержимого встречи.
- [ ] Для каждого прогона фиксировать устройство, browser, viewport, язык, сетевой профиль, сценарий и SHA.
- [ ] Отличать complete run от прогона с отсутствующей отметкой или прерыванием.
- [ ] Сформировать discovery-отчёт без числового pass threshold и без оценки вместо отсутствующих данных.
- [ ] На основании валидных прогонов передать владельцам данные для утверждения baseline, target, выборки и validation window.
- [ ] Не закрывать performance NFR самим фактом появления телеметрии.
- [ ] Собрать evidence `NFR-026`: схема измеряемой цепочки, обезличенный trace полного прогона, пример отклонённого неполного прогона и discovery-отчёт.

## Cross-requirement evidence and release gate

- [ ] Создать traceability от каждого `AC-021`…`AC-030` и `NFR-021`…`NFR-026` к основному и отказному сценарию, задаче и evidence.
- [ ] Проверить, что для каждого требования присутствуют минимум основной и error/forbidden/recovery прогон.
- [ ] Сверить визуальный результат с фактическим server state; screenshot без этой сверки не закрывает требование.

- [ ] Зафиксировать все открытые блокеры; change остаётся `draft`, пока владельцы и требуемые решения неизвестны.
- [ ] Не создавать Pack, Outcome, release evidence или ASE handoff из этого change до человеческого подтверждения и отдельного разрешённого шага.
