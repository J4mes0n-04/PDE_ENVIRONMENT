## Confirmed facts

- Room Client предназначен для End User и показывает понятное состояние помещения без тегов, драйверов, протоколов, транспортных ошибок и других инженерных сущностей.
- Сервер является источником истины. Клиент отображает серверное состояние и отправляет серверу намерения пользователя, но не управляет оборудованием напрямую.
- Панель должна пройти pairing, получить назначенный клиентский проект и работать в заблокированном полноэкранном киоск-режиме.
- Основной сценарий помещения запускается одним действием с главного экрана и показывает видимый ход подготовки или готовность.
- При уже активной комнате клиент должен предложить продолжение существующей сессии, а не создавать дубликат.
- Пользователь должен выбирать BYOD или источник по понятному имени и видеть подтверждённый сервером результат.
- В активной комнате требуются mute, громкость, камера и layout; доступность controls зависит от возможностей проекта, а итоговое состояние подтверждается сервером.
- Завершение должно закрывать сессию, очищать определённые политикой пользовательские данные и возвращать комнату в дежурное состояние.
- При потере связи клиент явно показывает offline, не ставит команды в скрытую очередь и после восстановления выполняет resync.
- Несколько панелей одной комнаты синхронизируются через состояние сервера.
- Штатная работа должна быть offline-first: без обязательного интернета, CDN, внешних шрифтов и облачных API.
- Room Client должен поддерживать русский и английский языки, touch-взаимодействие и адаптивное представление.
- Числовой baseline, target, выборка, окно проверки и пороги времени отклика не определены; input разрешает отдельный discovery-срез без выдумывания чисел.
- Календарь и ВКС зависят от неутверждённых контрактов. Создание брони с панели является заглушкой, а модель календарного и ВКС API остаётся блокирующим вопросом.
- Предполагаемый риск исходного UI-изменения — `R2`; будущий Outcome потребует полного рассмотрения безопасности, восстановления, rollout и rollback.
- Инициатор разрешил создать полный `draft` change с открытыми блокерами и разделил UI на четыре самостоятельных change; Room Client соответствует одному будущему Outcome.

## Scope finding

Этот change ограничен Room Client и панельной киоск-оболочкой. Он не переносит в себя Admin Web UI, конфигуратор, health, update, backup/restore или Safe Mode для административной роли.

Граница change проходит по наблюдаемому поведению:

1. Авторизованный инженер или администратор связывает панель, комнату и опубликованный клиентский проект.
2. End User видит дежурный или активный контекст комнаты.
3. End User запускает, продолжает, управляет и завершает комнатную сессию.
4. Клиент показывает только подтверждённое сервером состояние, безопасно переживает потерю связи и синхронизируется с другими панелями.
5. Неутверждённые календарные и ВКС-возможности остаются явно ограниченными и не имитируются в UI.

## Assumptions kept explicit

- Один Room Client change будет перенесён ровно в один будущий Outcome; это организационная граница, а не подтверждение готовности Outcome.
- Серверный контракт сможет предоставить достаточное состояние для snapshot/resync и capability-driven UI. Это допущение требует подтверждения Engineering Lead.
- Панельная оболочка сможет обеспечить системную kiosk-блокировку. Веб-страница сама по себе не считается достаточной защитой.
- Клиентский проект уже опубликован и совместим до назначения панели; создание и публикация проекта относятся к configurator change.
- ВКС может быть представлена только общей серверной возможностью запуска/завершения; поставщик, протокол и расширенные controls этим change не определяются.
