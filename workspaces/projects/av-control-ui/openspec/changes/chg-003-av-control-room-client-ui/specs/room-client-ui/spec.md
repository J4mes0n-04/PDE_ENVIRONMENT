# Delta for room-client-ui

## ADDED Requirements

### Requirement: AC-021 Pairing панели, клиентский проект и kiosk
The system SHALL позволять авторизованному Integrator Engineer или IT Admin связать панель с выбранной комнатой и опубликованным совместимым клиентским проектом, после чего панель показывает этот проект в заблокированном полноэкранном kiosk только при подтверждённых pairing, загрузке проекта и kiosk lock.

#### Scenario: Успешное подключение новой панели
- **GIVEN** непривязанная панель показывает действующий pairing request, опубликованный клиентский проект совместим, а авторизованный пользователь открыл управление выбранной комнатой
- **WHEN** пользователь подтверждает назначение этой панели, комнаты и клиентского проекта
- **THEN** сервер подтверждает единую привязку, а панель загружает назначенную версию проекта и актуальный snapshot комнаты
- **AND** панель входит в locked kiosk и показывает standby либо уже активную комнату
- **AND** административная сторона показывает панель связанной именно с выбранной комнатой и версией проекта

#### Scenario: Просроченный или запрещённый pairing
- **GIVEN** pairing request просрочен, уже использован либо пользователь не имеет права назначать панель
- **WHEN** пользователь пытается подтвердить назначение
- **THEN** новая привязка и назначение проекта не создаются, а панель остаётся в безопасном unpaired или прежнем подтверждённом состоянии
- **AND** пользователь видит понятное сообщение о невозможности подключения и разрешённое действие для повтора или запроса доступа
- **AND** панель не показывает ложный статус готовности и не получает данные другой комнаты

#### Scenario: Несовместимый проект или неподтверждённый kiosk
- **GIVEN** pairing разрешён, но выбранный проект несовместим либо системная оболочка не подтверждает kiosk lock
- **WHEN** система пытается завершить подключение панели
- **THEN** панель показывает безопасное blocked-состояние для обслуживания и не объявляется рабочей
- **AND** прежняя валидная привязка и рабочая версия проекта сохраняются, если они существовали
- **AND** частично загруженный проект не становится активным Room Client

### Requirement: AC-022 Главный сценарий одним действием
The system SHALL позволять End User запустить основной сценарий комнаты одним действием с главного standby-экрана и показывать подготовку либо подтверждённую сервером готовность без дополнительного выбора инженерных параметров.

#### Scenario: Успешный запуск комнаты
- **GIVEN** панель связана с сервером, Room Client находится в standby, а основной сценарий доступен пользователю
- **WHEN** пользователь один раз нажимает основное действие запуска
- **THEN** UI немедленно показывает, что действие принято, и отображает понятный ход подготовки
- **AND** после серверного подтверждения UI показывает готовность комнаты и доступные источники и controls
- **AND** повторное нажатие во время pending не отправляет дублирующий запуск

#### Scenario: Сервер отклоняет или не завершает запуск
- **GIVEN** Room Client находится в standby, но сервер отклоняет запуск либо сообщает о невозможности безопасно подготовить комнату
- **WHEN** пользователь нажимает основное действие запуска
- **THEN** UI не показывает комнату готовой и возвращается к подтверждённому сервером standby или degraded-состоянию
- **AND** пользователь видит простое объяснение доступного следующего действия или путь поддержки
- **AND** клиент не пытается локально завершить сценарий и не отправляет скрытые повторные команды

### Requirement: AC-023 Продолжение активной комнаты
The system SHALL при открытии, перезагрузке или повторном подключении Room Client распознавать подтверждённую сервером активную сессию, предлагать продолжить её и не создавать новую сессию поверх существующей.

#### Scenario: Продолжение действующей сессии
- **GIVEN** сервер сообщает, что в назначенной комнате уже активна сессия с подтверждёнными источником и состояниями controls
- **WHEN** пользователь открывает или перезагружает Room Client и выбирает продолжение
- **THEN** UI показывает текущий активный контекст и подтверждённые сервером источник, mute, громкость, камеру и layout
- **AND** доступно завершение существующей сессии
- **AND** новый запуск и дублирующая сессия не создаются

#### Scenario: Локальный экран устарел, а сервер завершил сессию
- **GIVEN** клиент ранее показывал активную комнату, но актуальный server snapshot сообщает standby
- **WHEN** клиент загружается или завершает resync
- **THEN** UI показывает standby и основное действие запуска вместо продолжения
- **AND** локальный active state отбрасывается
- **AND** клиент не восстанавливает завершённую сессию и не отправляет её прежние controls серверу

### Requirement: AC-024 Выбор BYOD или источника
The system SHALL показывать End User доступные BYOD и другие источники по понятным именам, отправлять выбор серверу и отмечать источник активным только после серверного подтверждения.

#### Scenario: Пользователь выбирает доступный источник
- **GIVEN** активная комната получила от сервера список capability с источником «Ноутбук пользователя» и другими понятными названиями
- **WHEN** пользователь выбирает «Ноутбук пользователя»
- **THEN** выбранный control показывает pending, а последнее подтверждённое состояние остаётся различимым
- **AND** после server confirmation «Ноутбук пользователя» отображается активным на всех связанных клиентах
- **AND** внутренний вход, адрес, тег и протокол не показываются пользователю

#### Scenario: Источник исчез или выбор отклонён
- **GIVEN** источник был показан доступным, но исчез до применения либо сервер отклоняет выбор
- **WHEN** пользователь выбирает этот источник
- **THEN** UI сохраняет или восстанавливает последний подтверждённый источник и не показывает ложное переключение
- **AND** пользователь видит понятное предложение повторить действие или выбрать другой доступный источник
- **AND** отклонённая команда не повторяется автоматически

### Requirement: AC-025 Controls комнаты с серверной обратной связью
The system SHALL показывать mute, громкость, камеру и layout только для разрешённых server capability, отображать pending после действия и считать новое значение применённым только после server confirmation.

#### Scenario: Изменение mute и громкости
- **GIVEN** активная комната сообщает доступные mute и громкость с последними подтверждёнными значениями
- **WHEN** пользователь изменяет mute или громкость на соответствующем control
- **THEN** control показывает pending и отправляет серверу одно намерение пользователя
- **AND** после server confirmation UI показывает подтверждённое значение
- **AND** другие связанные панели получают то же итоговое состояние

#### Scenario: Управление камерой и layout
- **GIVEN** сервер разрешает конкретные camera actions и варианты layout для активной сессии
- **WHEN** пользователь выбирает разрешённое camera action или layout
- **THEN** UI показывает ожидание и затем отображает подтверждённый сервером результат
- **AND** неподдерживаемые camera actions и layout не появляются как активные controls
- **AND** клиент не обращается к камере или ВКС-устройству напрямую

#### Scenario: Control запрещён или команда отклонена
- **GIVEN** capability отсутствует, право отозвано либо сервер отклоняет изменение
- **WHEN** пользователь открывает controls или выполняет ещё доступное на экране действие
- **THEN** запрещённый control отсутствует либо явно недоступен, а отклонённое значение возвращается к последнему server-confirmed state
- **AND** пользователь видит понятное доступное действие без инженерной причины
- **AND** UI не оставляет control в ложном применённом состоянии

### Requirement: AC-026 Завершение, очистка и standby
The system SHALL по явному действию End User завершать активную сессию через сервер, закрывать разрешённый ВКС-сеанс, очищать утверждённые пользовательские данные и показывать standby только после подтверждения завершения и очистки.

#### Scenario: Успешное завершение встречи
- **GIVEN** комната находится в подтверждённой active-сессии, а действие завершения доступно
- **WHEN** пользователь выбирает «Завершить» и выполняет требуемое политикой подтверждение
- **THEN** UI показывает ending, а сервер завершает сессию, закрывает активный ВКС-сеанс и выполняет утверждённую очистку
- **AND** после server confirmation UI показывает чистый standby для следующего пользователя
- **AND** данные предыдущей сессии и её controls больше не доступны End User

#### Scenario: Завершение или очистка не подтверждены
- **GIVEN** сервер не завершил один из обязательных этапов закрытия сессии или очистки
- **WHEN** пользователь запускает завершение
- **THEN** UI остаётся в ending или blocked-состоянии и не показывает ложный чистый standby
- **AND** пользователь видит разрешённый повтор или путь поддержки
- **AND** клиент не создаёт новую сессию поверх неподтверждённого завершения и не удаляет обязательный аудит

### Requirement: AC-027 Потеря связи без очереди и resync
The system SHALL при потере связи с локальным сервером явно показывать offline, блокировать server-dependent actions, не сохранять их в скрытую очередь и после reconnect включать controls только после полного server resync.

#### Scenario: Связь потеряна во время активной комнаты
- **GIVEN** Room Client показывает active-сессию и подтверждённые controls
- **WHEN** соединение с локальным сервером разрывается
- **THEN** UI сразу показывает заметное offline-состояние и помечает последнее подтверждённое состояние как неактуальное
- **AND** server-dependent controls становятся недоступными
- **AND** клиент не сообщает, что состояние комнаты изменилось после разрыва

#### Scenario: Пользователь нажимает control offline
- **GIVEN** Room Client находится offline
- **WHEN** пользователь пытается выбрать источник или изменить mute, громкость, камеру, layout либо завершить встречу
- **THEN** UI сообщает, что действие требует восстановления связи, и не принимает его как выполненное
- **AND** команда не сохраняется для последующей отправки
- **AND** после reconnect это offline-действие не выполняется автоматически

#### Scenario: Reconnect и полный resync
- **GIVEN** связь восстановлена после offline, а серверное состояние могло измениться с другой панели
- **WHEN** клиент повторно подключается
- **THEN** UI показывает resyncing и запрашивает полный актуальный snapshot
- **AND** controls включаются только после применения snapshot
- **AND** server state заменяет устаревшее локальное отображение, а не объединяется с ним

### Requirement: AC-028 Понятные ошибки без инженерных терминов
The system SHALL показывать End User простое описание недоступного результата, разрешённое следующее действие и при необходимости путь поддержки, не раскрывая драйверы, теги, протоколы, transport errors, stack trace и внутренние адреса.

#### Scenario: Известная техническая причина сопоставлена пользовательскому сообщению
- **GIVEN** сервер отклонил действие и сохранил техническую причину для разрешённой инженерной диагностики
- **WHEN** Room Client получает отказ
- **THEN** End User видит, какая пользовательская функция сейчас недоступна, и может повторить, выбрать альтернативу или обратиться за помощью
- **AND** сообщение не содержит имя драйвера, тега, протокола, транспорта, внутреннего устройства или stack trace
- **AND** технический контекст остаётся доступным только в разрешённой диагностике

#### Scenario: Неизвестная или несопоставленная ошибка
- **GIVEN** клиент получает неизвестную ошибку или raw backend text, для которого нет утверждённого пользовательского текста
- **WHEN** UI формирует сообщение End User
- **THEN** UI показывает нейтральное сообщение о недоступном действии и безопасный путь повтора или поддержки
- **AND** при необходимости показывается только нейтральный код обращения
- **AND** raw backend text не выводится и выдуманная причина не сообщается

### Requirement: AC-029 Синхронизация нескольких панелей
The system SHALL синхронизировать все панели одной комнаты через авторитетное server state так, чтобы подтверждённое действие на одной панели стало одинаково видимым на остальных, а устаревшая панель не перезаписывала новое состояние.

#### Scenario: Действие на одной панели отражается на другой
- **GIVEN** две панели связаны с одной комнатой, подключены к серверу и показывают одинаковое подтверждённое active-состояние
- **WHEN** пользователь меняет доступный control на первой панели и сервер подтверждает действие
- **THEN** первая и вторая панели отображают одно итоговое server-confirmed state
- **AND** вторая панель не требует ручного refresh
- **AND** панели не обмениваются авторитетным состоянием напрямую друг с другом

#### Scenario: Отставшая панель возвращается после offline
- **GIVEN** первая панель изменила состояние комнаты, пока вторая панель была offline
- **WHEN** вторая панель reconnect и выполняет resync
- **THEN** вторая панель применяет полный актуальный server snapshot и сходится с первой
- **AND** её устаревшие локальные значения не отправляются серверу
- **AND** никакая offline-команда второй панели не выполняется после reconnect

#### Scenario: Одновременные действия на двух панелях
- **GIVEN** две подключённые панели почти одновременно отправляют разрешённые конфликтующие действия
- **WHEN** сервер определяет порядок и итог
- **THEN** обе панели отображают один окончательный результат сервера
- **AND** локальное время нажатия не используется клиентом для самостоятельного разрешения конфликта
- **AND** ни одна панель не остаётся в постоянном расходящемся состоянии

### Requirement: AC-030 Ограниченная область календаря и ВКС
The system SHALL отображать календарные данные и разрешать общий запуск или завершение ВКС только как подтверждённые server capability, а создание брони, редактирование или продление встречи, неутверждённый автостарт и provider-specific controls SHALL оставаться недоступными до отдельного утверждённого контракта.

#### Scenario: Доступна утверждённая ограниченная интеграция
- **GIVEN** сервер предоставляет утверждённую read-only сводку ближайшей встречи и capability общего запуска ВКС
- **WHEN** пользователь открывает Room Client и выбирает разрешённый запуск
- **THEN** UI показывает только предоставленную сервером сводку и отправляет серверу общий запрос запуска
- **AND** активная ВКС отображается только после server confirmation
- **AND** клиент не соединяется напрямую с календарным или ВКС-провайдером

#### Scenario: Контракт или capability отсутствуют
- **GIVEN** calendar/VKS contract не утверждён, интеграция не настроена либо capability недоступна
- **WHEN** пользователь открывает standby или active Room Client
- **THEN** booking, редактирование, продление, автостарт и provider-specific controls отсутствуют либо безопасно недоступны
- **AND** mock-встреча и ложная доступность не показываются
- **AND** не зависящие от интеграции базовые сценарии комнаты продолжают работать

#### Scenario: Интеграция стала недоступна во время сессии
- **GIVEN** календарная или ВКС-интеграция была доступна, но сервер сообщает её деградацию
- **WHEN** Room Client получает новое состояние
- **THEN** UI ограничивает только зависимые actions и показывает понятное пользовательское сообщение
- **AND** техническая причина остаётся вне End User интерфейса
- **AND** клиент не подменяет недоступную интеграцию локальным поведением

### Requirement: NFR-021 Сервер как источник истины
The system SHALL использовать только server snapshot и server events как авторитетное состояние комнаты, сохраняя локально лишь presentation state и кратковременный pending, который не может подтвердить выполнение команды.

#### Scenario: Подтверждение и отклонение команды
- **GIVEN** клиент показывает подтверждённое значение control
- **WHEN** пользователь выполняет действие и ожидает server result
- **THEN** до server confirmation UI различает pending и последнее подтверждённое значение
- **AND** при подтверждении отображается server state, а при отклонении восстанавливается последнее server-confirmed value
- **AND** локальный optimistic result не становится окончательным

#### Scenario: Локальный кэш расходится с server snapshot
- **GIVEN** после перезагрузки, reconnect или открытия второй панели локально доступно устаревшее состояние
- **WHEN** клиент получает актуальный server snapshot
- **THEN** UI полностью применяет server state как авторитетное
- **AND** устаревший кэш не перезаписывает сервер и не создаёт новую сессию
- **AND** пользователь не видит локальное состояние как подтверждённый результат

### Requirement: NFR-022 Блокировка kiosk
The system SHALL на каждой поддерживаемой панели удерживать обычного пользователя внутри Room Client, блокировать штатные пользовательские способы выхода к операционной системе и разрешать обслуживание только через отдельный авторизованный maintenance flow.

#### Scenario: Обычное использование locked kiosk
- **GIVEN** связанная панель запущена в подтверждённом kiosk mode
- **WHEN** End User использует touch, системные gestures, browser navigation и доступные аппаратные действия обычного пользователя
- **THEN** панель остаётся внутри Room Client
- **AND** настройки ОС, desktop, task switcher и произвольная навигация не становятся доступны
- **AND** перезапуск пользовательского клиента возвращает панель в locked Room Client

#### Scenario: Авторизованное обслуживание и повторная блокировка
- **GIVEN** обслуживающая роль прошла отдельную авторизацию для maintenance
- **WHEN** она выполняет разрешённый выход из kiosk и затем завершает обслуживание
- **THEN** действие фиксируется согласно политике аудита, а панель возвращается в подтверждённый locked mode
- **AND** End User credentials или обычный жест не открывают тот же путь
- **AND** при неподтверждённом повторном lock панель не объявляется готовой к эксплуатации

#### Scenario: Kiosk lock не поддержан или нарушен
- **GIVEN** системная оболочка не может включить lock либо escape test выявил доступ к ОС
- **WHEN** панель проходит проверку готовности
- **THEN** проверка завершается отказом, а панель остаётся в maintenance или blocked-состоянии
- **AND** Room Client не маскирует проблему визуальным fullscreen
- **AND** production-ready evidence не создаётся

### Requirement: NFR-023 Offline-first без внешней зависимости
The system SHALL загружать обязательные assets и выполнять критические Room Client пути через локальный контур без обязательного интернета, CDN, внешних шрифтов, внешней аналитики и облачных API.

#### Scenario: Интернет заблокирован, локальный сервер доступен
- **GIVEN** доступ во внешнюю сеть заблокирован, а локальный сервер AV Control и назначенный клиентский проект доступны
- **WHEN** пользователь загружает Room Client, запускает или продолжает комнату, выбирает источник, управляет controls и завершает сессию
- **THEN** критические экраны и actions работают через локальный контур
- **AND** обязательные стили, шрифты, переводы и scripts загружаются локально
- **AND** сетевой аудит не показывает обязательных внешних запросов

#### Scenario: Необязательная внешняя интеграция недоступна
- **GIVEN** calendar/VKS или другой разрешённый внешний сервис недоступен, а локальный сервер работает
- **WHEN** пользователь открывает Room Client
- **THEN** только зависимая возможность скрыта или показывает безопасную деградацию
- **AND** базовые запуск, локальные источники, controls и завершение остаются доступны по server capability
- **AND** клиент не блокирует весь интерфейс ожиданием внешнего ресурса

### Requirement: NFR-024 Touch и адаптивность
The system SHALL сохранять читаемость, доступность критических действий и безопасное touch-взаимодействие на утверждённой матрице панелей, browser viewport, ориентаций и системного масштаба без перекрытия или потери смысла.

#### Scenario: Критический путь на touch-панели
- **GIVEN** Room Client открыт на каждом утверждённом touch-устройстве и viewport
- **WHEN** пользователь проходит запуск, выбор источника, mute, громкость, камеру, layout и завершение
- **THEN** все необходимые controls видимы, достижимы touch и различают normal, pressed, pending, disabled и error
- **AND** частое действие не перекрывает destructive action завершения
- **AND** выполнение не требует точного mouse pointer или доступа к hover-only информации

#### Scenario: Узкий viewport, смена ориентации или длинный текст
- **GIVEN** клиент показывает длинный русский или английский текст, а viewport, ориентация либо системный масштаб изменены в пределах утверждённой матрицы
- **WHEN** layout пересчитывается
- **THEN** основной action, текущий статус, доступное восстановление и завершение сохраняют полный смысл
- **AND** controls не перекрываются и не уходят в недостижимую область
- **AND** критическая инструкция не обрезается без доступного способа прочитать её полностью

### Requirement: NFR-025 Локализация RU/EN
The system SHALL предоставлять полный Room Client на русском и английском языках, включая состояния, actions, ошибки и recovery, без raw localization keys, непереведённых инженерных строк и потери критического смысла.

#### Scenario: Русский интерфейс полного комнатного пути
- **GIVEN** для панели выбрана русская локаль
- **WHEN** пользователь проходит standby, запуск, active room, источники, controls, завершение, offline и resync
- **THEN** все пользовательские подписи, состояния и доступные действия показаны на русском языке
- **AND** длинные строки сохраняют смысл в утверждённых viewport
- **AND** технические backend strings не подмешиваются в пользовательский текст

#### Scenario: Английский интерфейс и пользовательская ошибка
- **GIVEN** для панели выбрана английская локаль, а сервер отклоняет действие
- **WHEN** Room Client показывает active state и recovery message
- **THEN** controls, состояние ошибки и следующее действие показаны согласованным английским текстом
- **AND** внутренние идентификаторы и raw server error не используются как перевод
- **AND** смена локали не меняет server state комнаты

#### Scenario: Обязательный перевод отсутствует
- **GIVEN** проверка локализации обнаружила отсутствующую RU или EN строку для критического состояния
- **WHEN** формируется evidence выпуска
- **THEN** соответствующий сценарий отмечается непройденным
- **AND** runtime не должен показывать localization key или инженерный fallback End User
- **AND** требование не закрывается до добавления и review перевода

### Requirement: NFR-026 Discovery времени отклика
The system SHALL до утверждения performance threshold собирать воспроизводимую цепочку времени от действия пользователя до первого видимого feedback, server result и подтверждённого render для критических Room Client сценариев, не объявляя числовой pass criteria в этом draft.

#### Scenario: Полный валидный discovery-прогон
- **GIVEN** instrumented test build запущен на зафиксированных устройстве, browser, viewport, языке и сетевом профиле
- **WHEN** проверяющий выполняет запуск, выбор источника, изменение control, завершение и reconnect/resync
- **THEN** отчёт связывает user action, первый feedback, отправку команды, server acceptance или rejection, authoritative state и final render
- **AND** каждый результат связан со сценарием и SHA без pairing secrets и пользовательских данных встречи
- **AND** данные сохраняются для последующего утверждения baseline, target, выборки и validation window

#### Scenario: Неполный или прерванный discovery-прогон
- **GIVEN** в цепочке отсутствует временная отметка, среда не зафиксирована либо прогон прерван
- **WHEN** формируется discovery-отчёт
- **THEN** прогон явно помечается неполным и не используется как baseline
- **AND** отсутствие данных не заменяется оценкой или выдуманным значением
- **AND** отчёт не объявляет performance pass до человеческого утверждения порога
