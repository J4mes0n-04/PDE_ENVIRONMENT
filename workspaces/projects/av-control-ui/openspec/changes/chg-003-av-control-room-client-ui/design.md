# Design: Room Client и киоск-панель AV Control

## Status and intent

Проектное решение имеет статус `draft`. Оно описывает границы и проверяемое поведение одного будущего Outcome, но не выбирает framework, язык, протокол, поставщика ВКС или конкретную схему данных.

Решение строится вокруг четырёх инвариантов:

1. Сервер является единственным источником истины о комнате.
2. Клиент никогда не управляет оборудованием напрямую.
3. Потеря связи не создаёт скрытую очередь пользовательских команд.
4. End User видит состояние и доступное действие, а не инженерную причину.

Если требуемый серверный, kiosk, calendar или VKS-контракт отсутствует, функция остаётся недоступной и не имитируется локально.

## Approach

### Responsibility boundary

Room Client отвечает за:

- визуализацию подтверждённого состояния комнаты;
- сбор намерения пользователя;
- немедленный видимый feedback о принятом нажатии;
- отправку одной команды серверу;
- показ pending до подтверждения или отклонения;
- обновление по серверному snapshot или событию;
- безопасное отключение интерактивных controls при потере связи;
- понятное восстановление после ошибки;
- адаптивное RU/EN представление.

Сервер отвечает за:

- авторитетное состояние комнаты и активной сессии;
- проверку прав и capability;
- выполнение либо отклонение команды;
- последовательность конкурирующих команд;
- состояние устройств и сценариев;
- завершение сессии и очистку данных;
- snapshot/resync;
- распространение итогового состояния всем связанным панелям;
- технические подробности для диагностики и аудита.

Киоск-оболочка отвечает за системную блокировку выхода из клиента. Room Client может показать состояние kiosk, но веб-интерфейс сам по себе не считается механизмом защиты операционной системы.

### Client state model

Клиент должен различать следующие пользовательские состояния:

- `unpaired` — панель не связана с комнатой и показывает только безопасный pairing flow;
- `pairing` — запрос связи отправлен, но назначение ещё не подтверждено;
- `loading` — загружается опубликованный клиентский проект и первый серверный snapshot;
- `standby` — комната готова к запуску основного сценария;
- `starting` — одно действие принято, сервер готовит комнату, итог ещё не подтверждён;
- `active` — сервер подтверждает активную комнатную сессию и доступные capability;
- `ending` — сервер завершает сессию и выполняет очистку;
- `offline` — локальный сервер недоступен, controls отключены, последнее подтверждённое состояние помечено как неактуальное;
- `resyncing` — связь восстановлена, но новый авторитетный snapshot ещё не применён;
- `degraded` — часть функций недоступна, а безопасно доступные функции продолжают отображаться;
- `blocked` — продолжение невозможно без действия инженера, администратора или поддержки.

Переход в `active`, `standby` после завершения или новое выбранное состояние control происходит только по серверному подтверждению. Локальное нажатие может создать `pending`, но не авторитетный результат.

### Pairing, client project and kiosk

Поток `AC-021` разделяется на проверяемые этапы:

1. Непривязанная панель показывает pairing request без данных чужой комнаты.
2. Авторизованная роль на административной стороне выбирает конкретную комнату и опубликованный клиентский проект.
3. Сервер проверяет актуальность запроса, права, совместимость и уникальность назначения.
4. Панель получает подтверждённую привязку и идентифицируемую версию клиентского проекта.
5. Клиент загружает проект и первый snapshot.
6. Киоск-оболочка подтверждает locked mode.
7. Только после успешных этапов панель показывает standby или активную комнату как готовый рабочий клиент.

Просроченный запрос, несовместимый проект, недостаточные права или ошибка kiosk не должны оставлять частично рабочую панель с ложным статусом готовности. Существующая валидная привязка не заменяется до атомарного подтверждения новой.

Точная форма pairing code, срок его действия, повторное назначение и maintenance unlock остаются открытыми contract decisions.

### One-action start and active-room continuation

В standby существует одно визуально основное действие запуска (`AC-022`). Одно нажатие:

- немедленно показывает, что действие принято;
- временно блокирует повторную отправку того же намерения;
- отправляет серверу одну команду;
- показывает серверный прогресс в пользовательских состояниях;
- переводит UI в active только после подтверждения готовности.

Если сервер сообщает, что сессия уже активна, клиент не предлагает обычный новый старт как основной путь. Он показывает текущий контекст и действие продолжения (`AC-023`). После продолжения пользователь видит серверно подтверждённые источник, controls и доступное завершение.

Если локально сохранённый экран противоречит snapshot, выигрывает snapshot. Клиент не создаёт новую сессию и не восстанавливает локальную сессию поверх серверной.

### Sources and BYOD

Список источников формируется только из доступных серверных capability (`AC-024`). Каждый элемент имеет пользовательское имя; внутренние адреса, теги, порты и протоколы не используются как подпись.

Выбор источника проходит через `pending`:

- выбранный control показывает ожидание;
- повторные нажатия, способные создать дубли, ограничиваются до ответа;
- прежний источник остаётся последним подтверждённым состоянием;
- новый источник становится активным только после серверного события;
- при отказе или исчезновении источника UI возвращается к последнему подтверждённому состоянию и предлагает повтор или другой источник.

BYOD не получает особый обход серверной модели. Обнаружение личного устройства превращается в доступную capability и проходит тот же server-confirmed flow.

### Room controls

Mute, громкость, камера и layout отображаются по сочетанию server capability и разрешения пользователя (`AC-025`).

Общий control flow:

1. Клиент показывает последнее подтверждённое значение.
2. End User выполняет одно действие.
3. Control показывает pending, не заявляя новый результат окончательным.
4. Сервер подтверждает или отклоняет действие.
5. Клиент отображает авторитетное значение из server state.
6. Все другие панели получают то же итоговое состояние.

Неподдерживаемый control отсутствует либо явно недоступен с понятным объяснением. Нельзя показывать активный control, который локально меняется, но не связан с серверной capability.

Для часто изменяемого значения громкости точная политика объединения последовательных касаний требует server contract. До её утверждения нельзя создавать неконтролируемую клиентскую очередь.

### Finish, cleanup and standby

Действие завершения (`AC-026`) должно быть явно отделено от повседневных controls. Подтверждение применяется, если этого требует утверждённая политика предотвращения случайного завершения.

После действия:

- UI переходит в `ending`;
- сервер закрывает активную пользовательскую сессию и разрешённый ВКС-сеанс;
- сервер очищает утверждённые категории пользовательских данных;
- сервер сбрасывает состояние комнаты согласно проекту;
- клиент получает подтверждение результата;
- только затем отображается standby для следующего пользователя.

Частичный отказ не маскируется под успех. Клиент показывает, что завершение не подтверждено, блокирует создание конфликтующей новой сессии и предлагает разрешённый повтор или путь поддержки. Обязательный аудит не относится к очищаемым пользовательским данным.

Точный перечень очищаемых данных и подтверждение очистки остаются блокирующим решением.

### Connection loss and resync

При потере server connection (`AC-027`) клиент:

- сразу показывает заметное offline-состояние;
- оставляет последнее подтверждённое состояние только как помеченную неактуальную справку;
- отключает actions, которые требуют сервера;
- не принимает команду как выполненную;
- не сохраняет команду для последующей отправки;
- не повторяет автоматически команду с неизвестным итогом.

После reconnect клиент сначала переходит в `resyncing`, получает полный актуальный snapshot и только затем включает controls. Если связь оборвалась после отправки, но до ответа, клиент не угадывает результат и не переотправляет действие: окончательное состояние определяется snapshot.

Неуспешный resync сохраняет controls заблокированными и предлагает повтор подключения или поддержку. Старое локальное состояние не отправляется серверу.

### User-facing errors

Слой представления ошибок (`AC-028`) отделяет техническую причину от текста End User:

- серверная причина сопоставляется с безопасной пользовательской категорией;
- клиент сообщает, что сейчас недоступно;
- клиент показывает разрешённое следующее действие;
- при необходимости клиент показывает нейтральный код обращения для поддержки;
- технический контекст остаётся в серверной диагностике и operations UI.

Raw exception, stack trace, driver, tag, protocol, transport address, WebSocket и внутреннее имя устройства не должны попадать в пользовательский текст.

Если причина неизвестна, используется утверждённое общее сообщение без ложного объяснения. Неизвестная причина не должна подменяться выдуманным диагнозом.

### Multi-panel synchronization

Панели одной комнаты не синхронизируются peer-to-peer (`AC-029`). Каждая панель:

- получает server state;
- отправляет намерение серверу;
- отображает pending только для локального действия;
- принимает окончательный порядок и итог от сервера;
- сходится к одному состоянию с другими подключёнными панелями.

При одновременных командах сервер определяет результат. Точный механизм упорядочивания не задаётся этим change, но контракт должен позволять клиенту отличить более новое состояние от устаревшего. Форма revision marker остаётся открытой.

Offline-панель не может менять комнату. После reconnect она применяет полный snapshot и не публикует старое локальное значение.

### Calendar and VKS boundary

`AC-030` вводит deny-by-default для неподтверждённых интеграций:

- календарная сводка может отображаться read-only только из подтверждённого server state;
- запуск общей ВКС-команды возможен только как объявленная server capability;
- завершение активной ВКС может быть частью серверного finish flow;
- отсутствие интеграции не блокирует обычные Room Client сценарии, которые от неё не зависят.

Не входят и не должны появляться как работающие controls:

- создание брони с панели;
- редактирование встречи;
- продление слота;
- неутверждённый автостарт;
- provider-specific roster, chat, dial pad или другие возможности;
- прямое соединение клиента с календарным или ВКС-провайдером.

Если контракт отсутствует или integration degraded, соответствующая функция отсутствует либо безопасно недоступна; mock-данные и ложный успешный запуск запрещены.

## Non-functional design

### Server source of truth

Для `NFR-021` клиентская модель разделяет:

- подтверждённое состояние из snapshot/events;
- краткоживущее визуальное pending;
- локальные настройки представления, не меняющие комнату.

Кэш не становится авторитетным состоянием. При расхождении, reconnect, перезагрузке страницы и открытии второй панели серверный snapshot всегда побеждает.

Контракт должен однозначно сообщать актуальность snapshot/event и исход command result. Конкретные имена полей не определяются этим change.

### Kiosk lock

Для `NFR-022` kiosk обеспечивается поддерживаемой системной оболочкой:

- запуск клиента в locked fullscreen;
- блокировка обычных системных gestures, навигации и выхода;
- отсутствие доступного End User пути к настройкам ОС;
- отдельный авторизованный maintenance unlock;
- возврат в locked mode после обслуживания;
- отказ от статуса «готово», если lock не подтверждён.

Проверка проводится на каждой утверждённой модели панели. Browser fullscreen без системной блокировки не проходит требование.

### Offline-first

Для `NFR-023` все обязательные runtime-assets поставляются локально. Критические пути используют локальный сервер и не требуют CDN, внешних шрифтов, аналитики или cloud API.

Internet-offline и server-offline являются разными состояниями:

- при заблокированном интернете и доступном локальном сервере Room Client должен работать штатно;
- при недоступном локальном сервере применяется `AC-027`.

Необязательная внешняя интеграция не может блокировать запуск, базовые controls или завершение комнаты.

### Touch and responsive behavior

Для `NFR-024` layout проектируется от критических действий, а не от фиксированного макета:

- основное действие, источники, controls и завершение остаются достижимыми touch;
- интерактивные области не перекрываются и не требуют точного pointer;
- изменение viewport, ориентации или системного масштаба не скрывает критическое действие;
- длинный RU/EN текст переносится без потери смысла;
- destructive action визуально и пространственно отделено от частых controls;
- состояние focus не удаляется для browser-контекста.

Точные размеры touch-target и матрица viewport не придумываются; их утверждение является блокером.

### Localization

Для `NFR-025` все пользовательские строки находятся в RU/EN ресурсах. Динамические сообщения собираются из локализуемых шаблонов, а не конкатенацией технических фрагментов.

Обязательные состояния локализуются вместе: standby, starting, active, ending, offline, resyncing, degraded, blocked, pending, permission denied и user-facing errors.

Runtime не показывает localization key, raw backend string или обрезанную критическую инструкцию. Политика fallback требует утверждения; отсутствие перевода блокирует evidence соответствующего экрана.

### Response-time discovery

`NFR-026` не задаёт фиктивный performance threshold. Instrumented build и тестовый контур должны позволять связать:

- пользовательское действие;
- первый видимый feedback;
- отправку команды;
- серверное принятие или отклонение;
- авторитетный snapshot/event;
- финальный render;
- начало reconnect;
- применение полного resync.

Отчёт сохраняет сценарий, устройство, browser, viewport, язык и сетевой профиль. Неполная цепочка помечается невалидной для baseline. В payload измерений не попадают pairing secrets, персональные данные встречи, содержимое календаря или технические логи сверх необходимого контекста.

Порог, агрегирование, минимальная выборка и validation window утверждаются после discovery человеком.

## Data and security

Room Client обрабатывает только необходимое представление:

- привязку панели к комнате и клиентскому проекту;
- опубликованную версию клиентского проекта;
- server state комнаты и capability;
- активную сессию;
- ограниченные календарные/ВКС-данные при утверждённой интеграции;
- локаль и безопасные параметры представления;
- нейтральный код обращения.

Требования безопасности:

- pairing secret не отображается после завершения и не попадает в пользовательскую телеметрию;
- клиент не хранит постоянные административные credentials;
- route или gesture не обходят kiosk и authorization;
- запрещённая capability не появляется только из-за клиентской конфигурации;
- server-side authorization проверяет каждую команду;
- секреты, raw tokens и полные технические ошибки не отображаются;
- завершение очищает утверждённые пользовательские данные, но сохраняет обязательный аудит;
- локальные данные представления не позволяют восстановить чужую завершённую сессию.

Конкретная auth-модель, срок pairing request, retention и состав cleanup требуют решения владельцев.

## Dependencies and contracts

До реализации и проверки должны быть доступны или формально описаны:

- pairing service и права назначения панели;
- published client project contract и проверка совместимости;
- room snapshot и признак его актуальности;
- server events для active session, sources, controls, ending и standby;
- command result с различимыми accepted, rejected и unknown-after-disconnect состояниями;
- полный resync без client-side merge авторитетного состояния;
- capability и permission model;
- серверное упорядочивание конкурирующих команд;
- kiosk shell status и maintenance unlock;
- cleanup policy и подтверждение результата;
- RU/EN glossary и content policy;
- calendar/VKS capability contract;
- поддерживаемая device/browser/network matrix;
- telemetry/privacy contract для discovery.

Если контракт отсутствует, соответствующий slice не может быть объявлен завершённым.

## Compatibility and migration

- Новая панель получает только совместимый опубликованный клиентский проект.
- Обновление уже связанной панели не должно частично заменять проект; предыдущая рабочая версия сохраняется до подтверждённого переключения.
- При несовместимости панель сохраняет безопасное предыдущее состояние или pairing/blocked state и не показывает ложную готовность.
- После обновления клиент начинает с server snapshot, а не с миграции локального авторитетного состояния.
- Несколько версий панелей в одной комнате допустимы только при подтверждённой серверной совместимости; матрица версий остаётся открытой.
- Rollback клиента не откатывает server state комнаты без отдельного серверного решения.

## Recovery behavior

- Pairing failed: не создавать частичную привязку; сохранить предыдущую валидную привязку либо unpaired.
- Project load failed: не входить в рабочий kiosk как готовая панель; показать безопасный blocked state и путь обслуживания.
- Start rejected: вернуть standby или серверно подтверждённое active state; не показывать готовность.
- Source/control rejected: вернуть последнее подтверждённое значение; показать понятное действие.
- Finish incomplete: остаться в ending/blocked, не показывать чистый standby.
- Connection lost: отключить commands, не queue, после reconnect выполнить full resync.
- Resync failed: сохранить offline/blocked, не включать controls.
- Panel conflict: принять итог сервера, не применять локальный merge.
- Calendar/VKS unavailable: скрыть или отключить только зависимую capability; базовый room flow продолжает работать.
- Kiosk lock failed: заблокировать production-ready status и перейти в maintenance path.
- Localization asset failed: не показывать raw key или backend text; соответствующий выпуск блокируется.

## Observability and evidence

Пользовательский слой показывает безопасный статус. Инженерная наблюдаемость должна позволять связать действие, command result, state event и render с нейтральным correlation context, доступным только разрешённой роли.

Evidence собирается отдельно для каждого требования:

- основной путь;
- ошибка, forbidden path или recovery;
- среда и SHA;
- server/client trace без секретов;
- визуальная запись пользовательского результата;
- фактическое серверное состояние, подтверждающее отсутствие ложного успеха.

Успешный UI screenshot без проверки server state не закрывает server-authoritative требования.

## Trade-offs and rejected alternatives

- Optimistic final state отклонён: он быстрее выглядит, но может показать действие, которое сервер не выполнил. Допустим только видимый pending.
- Hidden offline queue отклонена: позднее выполнение команды опасно для комнаты и противоречит input.
- Peer-to-peer sync панелей отклонена: создаёт второй источник истины и неоднозначный конфликт.
- Browser-only fullscreen отклонён как достаточный kiosk: он не гарантирует блокировку ОС.
- Raw backend errors отклонены: они раскрывают инженерные сущности и не дают End User понятного действия.
- Прямая calendar/VKS интеграция из клиента отклонена: она создаёт внешнюю зависимость и обходит серверный контракт.
- Фиктивный performance target отклонён: сначала требуется discovery на утверждённой матрице.

## Open design decisions

До Ready должны быть утверждены:

- схема pairing lifecycle и maintenance unlock;
- способ определения свежести server state;
- command result и политика неизвестного итога после disconnect;
- управление быстрыми последовательными изменениями громкости;
- capability/permission model;
- cleanup policy;
- server ordering для multi-panel;
- calendar/VKS scope;
- RU/EN fallback;
- device/browser/touch matrix;
- performance threshold после discovery;
- rollout, rollback и владельцы.

Ни одно открытое решение не разрешается скрытым выбором реализации.
