# Бизнес-требование: единая система пользовательских интерфейсов AV Control

Документ подготовлен для OpenSpec intake и описывает бизнес-требования ко всему пользовательскому интерфейсу AV Control: административному веб-интерфейсу, конфигуратору, клиенту управления помещением и киоск-оболочке панели.

Документ не является макетом, дизайн-системой, Pack или техническим заданием на реализацию. Он фиксирует подтверждённые пользовательские задачи, ожидаемое поведение, границы, критерии и открытые решения, которые должны быть разобраны в OpenSpec change до создания Outcome.

## 2. Краткое резюме — обязательно

**Проблема:** UI AV Control описан несколькими документами разной зрелости. Функции, роли, сценарии, визуальные принципы и состояния ошибок существуют, но не сведены в единое проверяемое бизнес-требование. Из-за этого интерфейс может распасться на несогласованные поверхности, показать конечному пользователю инженерные сущности, превратиться в типовой SaaS-дашборд либо потерять ключевые offline-first и эксплуатационные сценарии.

**Кто сталкивается:** End User помещения, Integrator Engineer, Lead Integrator, IT Admin, Support Operator, Security Auditor и Vendor Support. Каждая роль должна видеть только относящиеся к ней разделы, действия и уровень технической детализации.

**Желаемое изменение:** создать единую систему интерфейсов с общей визуальной грамматикой и разными ролевыми поверхностями: Admin Web UI, конфигуратор, клиент комнаты и киоск-панель. Для каждого критического пути должны быть определены экран, состояние, действие пользователя, реакция системы, ошибка и восстановление.

**Ожидаемый бизнес-результат:** сократить путь от подготовки проекта до работающей комнаты, обеспечить выполнение основных комнатных сценариев за одно-два действия, повысить самостоятельность линейного интегратора и первой линии поддержки, не раскрывая конечному пользователю инженерные сущности.

**Почему сейчас:** PRD, PSD, Use Case и UI-материалы уже содержат достаточно сведений для систематизации, но сохраняют противоречия и открытые решения. Без единого input дальнейшие OpenSpec change, Pack и UI-реализация будут наследовать эти расхождения.

**Что точно не входит:** реализация кода, окончательные макеты всех экранов, произвольная глубокая кастомизация, облачная зависимость, онлайн-доставка обновлений, прямое управление оборудованием из клиента и изменение аппаратной части.

### 3.4. Масштаб проблемы

- Частота: UI используется при каждой настройке, встрече, диагностике, обновлении и административном действии.
- Количество затронутых пользователей или объектов: точное число не измерено; затрагиваются все человеческие роли AV Control и все помещения с клиентскими панелями.
- Потери времени: числовой baseline не измерен; North Star требует сократить подготовку спецификации и запуск типового помещения до одного рабочего дня каждый.
- Финансовое влияние: не измерено; ожидается влияние через время интегратора, стоимость поддержки и число выездов.
- Влияние на качество, безопасность или доверие: несогласованный UI может скрыть критическое состояние, показать лишние права, затруднить откат или сорвать встречу.
- Текущий обходной путь: участники читают разрозненные PRD/PSD/Use Case/UI-файлы и самостоятельно разрешают расхождения.

## 4. Текущая ситуация — обязательно

### 4.1. Как процесс работает сейчас

1. Продуктовые роли, функции и NFR описаны в PRD.
2. Архитектурные границы интерфейсов, offline-first и Safe Mode описаны в PSD.
3. Пользовательские сценарии разнесены по Use Case Specification и Logic & User Flows.
4. Визуальные принципы, токены, сетки и каталог элементов находятся в отдельных UI-документах разной зрелости.
5. Разработчик или дизайнер вручную собирает целевую картину и самостоятельно трактует конфликты.

### 4.2. Где возникает проблема

Проблема возникает до реализации и проверки UI: отсутствует один утверждённый входной документ, связывающий роль, пользовательскую ценность, поверхность, сценарий, критерий, NFR и источник. Особенно неоднозначны границы Admin Web UI, полная IA, права Support Operator, визуальный акцент, уведомления, загрузочные состояния и состав MVP панели.

### 4.3. Последствия без изменения

- Пользователь может увидеть инженерные сущности вместо понятного действия.
- Admin Web UI может превратиться в шаблонный SaaS-дашборд вместо профессионального инструмента.
- Конфигуратор, системное меню и панель могут получить несовместимые паттерны.
- Права и видимость разделов могут быть реализованы по догадке.
- Ошибки, offline и Safe Mode могут не иметь понятного пути восстановления.
- Дизайн может быть принят по внешнему виду без проверки бизнес-сценариев.
- Реализация и QSRE не получат воспроизводимую карту требований и evidence.

### 4.4. Почему существующее решение недостаточно

Существующие документы качественно описывают отдельные уровни, но различаются по статусу, глубине и терминологии. Они не дают единой трассировки `пользователь → задача → путь → возможность → AC/NFR → evidence`. Некоторые UI-решения обозначены как H/V, draft или `[?]`, а некоторые use case являются заглушками.

## 6. Пользовательские задачи (JTBD) — обязательно

**`JTBD-001`:** Когда участник входит в комнату для встречи, он хочет одним действием привести помещение в готовое состояние, чтобы начать работу без знания устройства AV-системы.

Критерий: после одного действия виден понятный прогресс или готовность, а инженерные сущности скрыты.

**`JTBD-002`:** Когда участник подключает BYOD или выбирает источник, он хочет выбрать понятное имя источника и сразу увидеть результат, чтобы не искать технический вход или протокол.

**`JTBD-003`:** Когда встреча закончена, пользователь хочет завершить сессию одним явным действием, чтобы закрыть ВКС, очистить пользовательские данные и вернуть комнату в дежурное состояние.

**`JTBD-004`:** Когда интегратор создаёт типовую комнату, он хочет начать с готового шаблона или мастера и затем вручную изменить любой результат, чтобы быстрее получить рабочий проект без потери контроля.

**`JTBD-005`:** Когда проект готовится без объекта, интегратор хочет работать с недоступными устройствами и эмуляцией, чтобы закончить большую часть конфигурации заранее.

**`JTBD-006`:** Когда проект готов к запуску, интегратор хочет увидеть полный preflight с точным местом ошибки и следующим действием, чтобы безопасно задеплоить проект.

**`JTBD-007`:** Когда помещение работает нестабильно, Support Operator хочет пройти от health к логам и diagnostic bundle, чтобы решить проблему первой линией или передать воспроизводимые данные вендору.

**`JTBD-008`:** Когда IT Admin обслуживает систему, он хочет видеть состояние, версии, обновления, backup и rollback в одном ролевом интерфейсе, чтобы восстановить работу без ручного вмешательства в проект.

**`JTBD-009`:** Когда возникает критический сбой, IT Admin хочет открыть Safe Mode, понять причину и выбрать restore/rollback, чтобы вернуть систему в безопасное рабочее состояние.

**`JTBD-010`:** Когда Security Auditor проверяет систему, он хочет прочитать неизменяемый аудит и ИБ-события без права редактирования, чтобы подтвердить соблюдение политики.

1. Безопасность людей, данных и оборудования важнее скорости.
2. Тиражируемость типовой комнаты важнее скорости первой уникальной комнаты.
3. Понятное действие End User важнее технической полноты на клиенте.
4. Для интегратора управляемость и диагностика важнее декоративности.
5. Проверяемое поведение важнее визуального совпадения с референсом.

## 8. Целевой результат и измерение — обязательно

### 8.1. Формулировка Outcome

Для End User, Integrator Engineer, IT Admin и Support Operator создать согласованную систему UI-поверхностей, в которой критические P0-пути выполняются без перехода в чужую роль, инженерные сущности скрыты от End User, а ошибки содержат понятное следующее действие. Числовой baseline и target требуют пилотного измерения.

### 8.3. Правило итогового решения

- `scale` — целевая доля всех ролевых P0-путей достигнута, guardrail не нарушены, блокирующие дефекты отсутствуют.
- `keep` — критические пути подтверждены в текущем масштабе, но данных недостаточно для расширения.
- `adapt` — отдельные пути не достигли цели либо остаются проблемы понятности, IA или восстановления без критического риска.
- `revert` — UI создаёт критический риск, блокирует работу комнаты, нарушает права или не позволяет безопасно восстановиться.

Конкретные пороги нельзя утвердить до ответа на `Q-UI-006`.

## 11. Сценарии использования — обязательно

### Сценарий `SCN-UI-001`: создать типовую комнату мастером

- Исполнитель: Integrator Engineer.
- Цель: получить редактируемый проект типовой комнаты.
- Предусловия: пользователь авторизован; доступен каталог готовых комнат и драйверов.
- Триггер: действие «Создать проект/комнату».
- Входные данные: тип помещения, оборудование, сценарии и тема.

Основной поток:

1. Инженер выбирает готовую комнату или мастер.
2. UI показывает шаги и текущий результат в рабочем пространстве.
3. Система создаёт устройства, драйверы, теги, связи, сценарии и стиль.
4. Инженер может изменить любой созданный элемент вручную.
5. Проект сохраняется как черновик и готов к preflight.

Альтернативный поток: инженер выбирает ручной режим и получает пустую структуру без мастера.

Ошибка и восстановление: отсутствующий драйвер или конфликт показывается на конкретном объекте и содержит действие перехода к исправлению; введённые данные не теряются.

Постусловия: существует редактируемый проект, но он не активен до deploy.

### Сценарий `SCN-UI-002`: проверить и задеплоить проект

- Исполнитель: Integrator Engineer.
- Предусловия: проект сохранён; роль имеет право deploy.
- Триггер: «Проверить готовность».

Основной поток:

1. UI запускает preflight.
2. Блокирующие ошибки и предупреждения разделены.
3. Для каждой проблемы видны объект, причина и следующий шаг.
4. После устранения блокеров инженер запускает deploy.
5. UI показывает совместимость, лицензию, rollback-point и итоговую проверку комнат.

Ошибка: неуспешный deploy атомарно возвращает предыдущую рабочую версию и показывает результат отката.

### Сценарий `SCN-UI-003`: начать встречу

- Исполнитель: End User.
- Предусловия: клиент связан с сервером; комната в стандартном режиме.
- Триггер: одно нажатие на основной сценарий.

Основной поток:

1. Пользователь видит главный экран без инженерных сущностей.
2. Нажимает основной сценарий.
3. UI показывает ход подготовки понятными состояниями.
4. После готовности доступны источник, mute, громкость, камера и завершение.

Ошибка: недоступное устройство не раскрывает протокол; UI предлагает доступное действие или помощь.

### Сценарий `SCN-UI-004`: завершить встречу

1. End User нажимает «Завершить».
2. UI подтверждает завершение, если это необходимо политикой.
3. Система закрывает ВКС, очищает пользовательские данные и возвращает комнату в дежурное состояние.
4. UI показывает готовность комнаты для следующего пользователя.

### Сценарий `SCN-UI-005`: потеря связи панели с сервером

1. Клиент теряет WebSocket/связь с сервером.
2. UI сохраняет последнее подтверждённое состояние только для отображения.
3. Показывается явный offline-overlay или состояние «нет связи».
4. Команды не ставятся в скрытую очередь.
5. После восстановления выполняется resync и UI показывает актуальное серверное состояние.

### Сценарий `SCN-UI-006`: triage и diagnostic bundle

1. Support Operator открывает health.
2. Выбирает проблемную комнату/компонент.
3. Переходит к отфильтрованным логам и событиям.
4. Применяет разрешённое сервисное действие или формирует bundle.
5. Bundle содержит версии, конфигурацию и диагностические сведения согласно политике privacy.

### Сценарий `SCN-UI-007`: Safe Mode

1. После повторных критических стартовых ошибок система входит в Safe Mode.
2. Room Client показывает понятную заглушку; управление оборудованием недоступно.
3. IT Admin открывает Admin Web UI.
4. Видит причину, доступные логи/crash dump, restore и rollback.
5. После восстановления UI подтверждает возврат в стандартный режим.

### Сценарий `SCN-UI-008`: offline-обновление

1. IT Admin загружает пакет.
2. UI показывает сведения о пакете и patch note.
3. Проверяются подпись, целостность, совместимость и активная встреча.
4. Создаётся точка восстановления.
5. UI показывает установку и итоговую проверку.
6. При сбое выполняется rollback и показывается его результат.

### Сценарий `SCN-UI-009`: управление пользователями и ролями

1. IT Admin создаёт или изменяет пользователя.
2. Назначает роль из утверждённой матрицы.
3. UI явно показывает доступные разделы и критические права.
4. Изменение фиксируется в аудите.

Ошибка: нельзя назначить несуществующую комбинацию прав или скрыто предоставить Vendor Support постоянный доступ.

### Сценарий `SCN-UI-010`: проверка аудита

1. Security Auditor открывает read-only аудит.
2. Фильтрует входы, изменения проекта/ролей, обновления, restore и сервисный доступ.
3. Может выгрузить разрешённые события в SIEM.
4. Не может изменить или удалить аудит.

- Ожидаемое доказательство: матрица ролей и запись ролевого прогона.
- ДАНО: пользователь каждой утверждённой роли.
- КОГДА: он входит в Admin Web UI или клиент.
- ТОГДА: видимость совпадает с утверждённой матрицей.
- И: запрещённый маршрут не открывается прямым URL.

### `AC-UI-002`: единая top-level навигация Admin Web UI

- Требование: основные разделы доступны из постоянной боковой навигации за одно действие, активный раздел различим, переключение не теряет несохранённые данные без решения пользователя.
- Доказательство: навигационный прогон и dirty-state сценарий.

### `AC-UI-003`: два способа создания проекта

- Требование: интегратор может выбрать мастер или ручной режим; мастер создаёт редактируемый результат, ручной режим не запускает автоматическое заполнение.
- Доказательство: два отдельных прогона.

### `AC-UI-004`: профессиональное рабочее пространство конфигуратора

- Требование: конфигуратор предоставляет единое дерево проекта, рабочую область/холст и инспектор; выбранный объект синхронно отражается в этих зонах.
- Доказательство: запись выбора, drag-and-drop и изменения свойства.

### `AC-UI-005`: preflight с переходом к проблеме

- Требование: каждая найденная проблема содержит объект, критичность, причину и действие перехода к месту исправления; блокеры отделены от предупреждений.

### `AC-UI-006`: атомарный deploy

- Требование: deploy либо активирует весь проверенный проект, либо сохраняет предыдущую рабочую версию; UI показывает итог и rollback-point.

### `AC-UI-007`: pairing и kiosk

- Требование: после pairing панель получает выбранный клиентский проект, открывает его в полноэкранном kiosk и не позволяет обычному пользователю выйти в ОС.

### `AC-UI-008`: главный сценарий комнаты

- Требование: End User запускает основной комнатный сценарий одним действием с главного экрана и получает видимую обратную связь.

### `AC-UI-009`: управление встречей

- Требование: выбор источника, mute, громкость, камера и layout применяются через понятные controls и подтверждаются актуальным состоянием сервера.

### `AC-UI-010`: завершение сессии

- Требование: действие «Завершить» закрывает пользовательскую сессию, очищает пользовательские данные и возвращает клиент в дежурное состояние.

### `AC-UI-011`: ошибка без инженерной терминологии

- Требование: End User видит состояние проблемы, доступное действие и путь эскалации без тегов, драйверов, протоколов и transport errors.

### `AC-UI-012`: потеря связи клиента

- Требование: при потере связи клиент явно показывает offline, не ставит пользовательские команды в скрытую очередь и после reconnect выполняет resync.

### `AC-UI-013`: health и triage

- Требование: Support Operator переходит от общей health-картины к проблемному компоненту, отфильтрованным событиям и разрешённому следующему действию.

### `AC-UI-014`: diagnostic bundle

- Требование: авторизованный пользователь формирует bundle из UI; результат содержит требуемые версии, состояния и логи и не включает запрещённые данные.

### `AC-UI-015`: Safe Mode

- Требование: в Safe Mode клиент показывает заглушку, а Admin Web UI предоставляет диагностику, restore и rollback без управления оборудованием.

### `AC-UI-016`: offline update и rollback

- Требование: IT Admin видит сведения о пакете, patch note, проверки, restore-point, прогресс, итог и журнал; сбой показывает результат автоматического rollback.

### `AC-UI-017`: backup/restore

- Требование: UI позволяет создать проверяемый backup и восстановить конфигурацию на совместимом контроллере без ручной донастройки каждого объекта.

### `AC-UI-018`: аудит read-only

- Требование: Security Auditor читает и фильтрует обязательные события, но не изменяет и не удаляет аудит.

### `AC-UI-019`: визуальная семантика состояний

- Требование: normal, hover, pressed, selected, focus, disabled, warning, error и critical различимы не только декоративным цветом и применяются одинаково в одной поверхности.

### `AC-UI-020`: ошибки, пустые и загрузочные состояния

- Требование: каждый P0-экран имеет определённые loading, empty, error, offline и permission-denied состояния с текстом и доступным действием.

### `AC-UI-021`: локализация

- Требование: критические подписи и controls читаются на русском и английском без обрезания смысла; интерфейс учитывает увеличение длины кириллицы.

### `AC-UI-022`: запрещённый generic UI

- Требование: сигнальные экраны не используют glassmorphism, декоративные градиенты/тени, чрезмерные скругления, маркетинговые блоки и generic AI-композицию.

### `AC-UI-023`: ручная правка после мастера

- Требование: любой результат мастера остаётся доступным для ручного изменения в тех же сущностях конфигуратора.

### `AC-UI-024`: видимость версий

- Требование: в диагностическом/административном контексте явно видны версии ядра, активного проекта и драйверов.

### `AC-UI-025`: временный Vendor Support

- Требование: IT Admin выдаёт ограниченный по времени видимый сервисный доступ, может его отозвать, а создание и отзыв фиксируются в аудите.

### 15.2. Контроли безопасности

- Аутентификация: обязательна для Web UI и API; клиентские учётные записи управляются сервером.
- Авторизация: role × action × resource; формальная матрица отсутствует и блокирует точный Pack.
- Аудит действий: вход, изменение проекта/ролей, update, import driver, restore и vendor access.
- Шифрование: TLS in transit; at-rest алгоритм требует отдельного решения.
- Секреты: не отображаются и не попадают в bundle в открытом виде.
- Удаление: обычный пользователь и интегратор не удаляют аудит.
- Внешняя передача: только явно настроенный SIEM, интеграция или handoff в поддержку.
- Неправильное использование: постоянный скрытый Vendor Support, прямой URL к чужому разделу и клиентское управление оборудованием должны блокироваться.

## 17. Совместимость и миграция — если применимо

- Поддерживаемые платформы: сервер — целевая Debian-ветка не утверждена; Admin/Client — браузеры и Tier 2 отечественные ОС требуют матрицы.
- Неподдерживаемые: сервер на отечественных ОС в текущем PSD.
- Обратная совместимость: ранее сохранённые проекты и last-known-good должны открываться/откатываться согласно версии формата.
- Изменения схемы данных: определяются Data Schema, не этим документом.
- План миграции: сначала токены и системные компоненты, затем сигнальные экраны и критические пути.
- Проверка миграции: старый проект импортируется, проходит preflight и не теряет сущности.
- Возможность отката: обязательна для active project и update; детали требуют contract.

## 20. Выпуск, включение и откат — обязательно

### 20.1. Стратегия выпуска

- Среды: макет → тестовый стенд → пилотное помещение → ограниченный production.
- Этапы: дизайн-система и сигнальные экраны → критические ролевые пути → полный P0.
- Feature flag: не определён; для рискованных разделов рекомендуется отдельное включение.
- Порядок: Admin auth/navigation → configurator → deploy → client/kiosk → monitoring/recovery.
- Ответственный: не назначен.

### 20.2. Условия продолжения

- Ролевая матрица согласована.
- P0 AC/NFR имеют evidence.
- Нет guardrail-нарушений.
- Offline и Safe Mode воспроизводимы.
- QSRE не выдал release hold.

### 20.3. Стоп-условия

- End User получает инженерные права или видит секреты.
- Комната не запускается/не завершается.
- Dirty data теряются без явного решения.
- Rollback/restore не восстанавливает рабочее состояние.
- UI требует внешнего облачного ресурса.

### 20.4. План отката

- Триггер: любой stop-condition.
- Способ: вернуть предыдущую версию UI/active project; выключить feature flag, если используется.
- Ответственный: IT/Release Owner, не назначен.
- Максимальное время: не определено.
- Данные: сохранить предыдущий active project и audit.
- Проверка: критический путь предыдущей версии проходит повторно.

## 27. Инструкции для OpenSpec intake — обязательно

1. Использовать только факты из перечисленных источников и ответов владельца.
2. Не превращать UI draft v0.1, гипотезы и допущения в утверждённый visual baseline.
3. Не придумывать владельцев, сроки, метрики, API, матрицу прав и решения `Q-UI-*`.
4. Сохранить идентификаторы `JTBD-*`, `VAL-*`, `JRN-*`, `CAP-*`, `AC-*`, `NFR-*`.
5. Каждый `CAP-UI-*` отразить как AC/NFR, scope.out или передачу соседней системе.
6. Для каждого пути `входит` создать основной, альтернативный и error/recovery сценарий.
7. Разделить UI на несколько change/Outcome, если один change не обеспечивает самостоятельный измеримый результат.
8. Человекочитаемый текст писать по-русски.
9. Не создавать Pack до подтверждения change человеком, кроме явно разрешённого draft.
10. Не запускать реализацию, `/opsx:apply` и архивирование change.
11. End User не должен получить инженерные термины или прямое управление оборудованием.
12. Любое визуальное решение из draft-источника помечать как требующее UX approval.
13. Сохранить offline-first и запрет обязательной облачной зависимости.

### 31.12. Ошибки и аварийные состояния — `ERR`

| ID | Условие | Обязательное UI-поведение |
| --- | --- | --- |
| `ERR-01` | Устройство не отвечает | Room Client показывает деградацию/действие; Admin — технический контекст |
| `ERR-02` | Сбой сценария | Комната возвращается в безопасное состояние; причина доступна в диагностике |
| `ERR-03` | JS crash | Ошибка изолируется; интегратор видит место и лог |
| `ERR-04` | Driver hang | Перезапуск/деградация отражаются в health |
| `ERR-05` | Deploy превышает лимит | Deploy блокируется; UI показывает usage и путь решения |
| `ERR-06` | Лицензия невалидна | Ограниченный режим и путь поддержки |
| `ERR-07` | Client потерял сервер | «Нет связи», без скрытой очереди, затем resync |
| `ERR-08` | Update failed | Автоматический rollback и уведомление IT |
| `ERR-09` | Driver update failed | Rollback драйвера и понятный итог |
| `ERR-10` | Project deploy failed | Atomic rollback проекта |
| `ERR-11` | Bad deploy/runtime | Возврат last-known-good |
| `ERR-12` | Restore failed | Применение останавливается без потери текущей конфигурации |
| `ERR-13` | Повторные стартовые ошибки | Safe Mode, crash dump, клиентская заглушка |
| `ERR-14` | Активный проект повреждён | Rollback или Safe Mode |
| `ERR-15` | Хранилище заполнено | Останавливаются некритические записи; IT получает действие |
| `ERR-16` | Сертификат истёк | Раннее предупреждение и безопасное ограничение TLS |
| `ERR-17` | ИБ-инцидент | Блокировка, аудит и SIEM |
| `ERR-18` | Интеграция недоступна | Запрос отклоняется; Admin видит диагностируемую причину |
| `ERR-19` | Отказ до начала рабочего дня | Triage, restore или last-known-good |
| `ERR-20` | Частичный отказ комнаты | Доступные функции продолжают работать, недоступные скрыты/помечены, End User получает действие |
