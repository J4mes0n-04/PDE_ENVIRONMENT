## Сигнал и подтверждение проблемы

Единый проверяемый контракт базового слоя Admin Web UI отсутствует: роли, навигация, доступ, dirty-state и общие состояния описаны в разных документах и могут быть реализованы несогласованно.

- Кто сталкивается: Integrator Engineer, IT Admin, Support Operator и Security Auditor при входе в административную оболочку.
- Что происходит сейчас: целевое поведение собрано из `REQ-UI-001`, proposal и delta spec, но работающий baseline оболочки не зафиксирован.
- Период и объекты: документы проекта на `2026-09-23`; число пользователей и помещений не измерено.
- Подтверждение: `workspaces/projects/av-control-ui/inputs/REQ-UI-001-av-control-interface.md`; `workspaces/projects/av-control-ui/openspec/changes/chg-001-av-control-ui-foundation/proposal.md`; `workspaces/projects/av-control-ui/openspec/changes/chg-001-av-control-ui-foundation/specs/ui-foundation/spec.md`.
- Уверенность: отсутствие единого контракта подтверждено документами. Числовой ущерб не измерен.
- Последствие без изменения: запрещённый маршрут, потеря черновика, ложный успех при ошибке или зависимость от внешней сети могут попасть в реализацию.

## Целевой результат и контракт метрики

Административные роли после входа работают в одной оболочке Admin Web UI: видят только разрешённые разделы, не теряют несохранённые изменения без явного решения и различают loading, empty, error, offline и permission-denied.

- Метрика: MET-UI-001: доля успешно завершённых foundation-путей
- Единица измерения: процент успешно завершённых валидных foundation-путей от числа начатых.
- Сегмент: административные роли из будущей матрицы прав. Тестовые невалидные прогоны исключаются.
- Исходный уровень: Не измерен
- Цель: Не определён до discovery-среза
- Источник: Протоколы usability-прогонов и записи сценариев на конкретном SHA
- Окно проверки: После пилотного выпуска; длительность не определена
- Правило решения: scale при утверждённой цели и отсутствии стоп-условий; keep при подтверждении только текущего масштаба; adapt при отсутствии достоверных данных; revert при запрещённом доступе, потере dirty-данных или обязательной внешней сети
- Владелец данных: Не назначен

Первый срез — discovery. Он фиксирует baseline, target, выборку и окно. До этого числовые значения не подставляются, а отсутствие данных не считается успехом.

- Административный пользователь: IT Admin. Он видит только разрешённые системные разделы и получает безопасный отказ на чужой маршрут.
- Затронутые роли: Lead Integrator, Support Operator и Security Auditor. Security Auditor не получает действия изменения.

## Область действия и нецели

### Входит в область действия

- Общая оболочка Admin Web UI после успешной аутентификации
- Боковая верхнеуровневая навигация по разрешённым сервером маршрутам
- Ролевая видимость разделов и действий
- Безопасный отказ при прямом URL, истории браузера и отзыве права
- Явный выбор сохранить, не сохранять или отменить для dirty state
- Различимые состояния loading, empty, error, offline и permission-denied
- Русская и английская локализация foundation-текстов
- Разделение severity, пользовательского сообщения и технического контекста ошибки
- Черновой каталог семантических токенов без утверждения visual baseline
- Discovery-срез MET-UI-001, совместимости, WCAG и производительности

Оболочка читает сессию, эффективные разрешения, реестр маршрутов, результат локального запроса и выбранную локаль. Доменные данные меняются только после явного сохранения через существующий серверный контракт.

### Не входит в область действия

- Реализация кода, OpenSpec apply, архивирование change и выпуск
- Конфигуратор проектов, мастер, preflight, preview и deploy
- Room Client, киоск, pairing и управление встречей
- Health, triage, diagnostic bundle, Safe Mode, обновление, backup и restore
- Серверная реализация auth, RBAC, API, хранилища и аудита
- Облачный кабинет, CDN, внешние шрифты и обязательные облачные API
- Утверждение акцентного цвета, постоянного header и notification center
- Мобильное системное меню и клиентские panel-layout

Скрытое расширение на `chg-002`, `chg-003` или `chg-004` запрещено. Эти changes остаются отдельными будущими Outcomes.

## Текущие и целевые сценарии

### Как есть сейчас

1. Требования к оболочке распределены между входным документом, proposal и черновыми UI-материалами.
2. Матрица прав, список разделов, WCAG, совместимость и порог отклика не утверждены.
3. Проверяющий не может принять один воспроизводимый foundation-путь как baseline.

### Целевой путь

1. Пользователь проходит аутентификацию.
2. Сервер возвращает эффективные разрешения и доступные маршруты.
3. Оболочка показывает только разрешённые разделы.
4. Пользователь открывает раздел одним действием боковой навигации.
5. При несохранённых изменениях оболочка требует сохранить, не сохранять или отменить.
6. Ошибка раздела остаётся в области содержимого и не разрушает оболочку.

### Ошибки и восстановление

- Прямой запрещённый URL не открывает данные и возвращает к разрешённому состоянию.
- Пустой успешный ответ отличается от ошибки загрузки.
- Offline не создаёт скрытую очередь команд.
- Ошибка сохранения оставляет введённые данные и не объявляет сохранение успешным.
- Полные GIVEN/WHEN/THEN сценарии переносятся в `specifications.md` из delta spec.

## Критерии приёмки

Каждый критерий проверяется записью на одном SHA. Полные сценарии находятся в `specifications.md`.

### AC-001

The system SHALL после успешной аутентификации показывать разрешённые административные разделы внутри одной общей оболочки Admin Web UI с постоянной областью верхнеуровневой навигации и областью содержимого.

Доказательство: запись перехода между двумя разрешёнными разделами и отказ одного раздела, при котором оболочка остаётся на месте.

### AC-002

The system SHALL показывать в оболочке только те разделы, объекты и действия, которые разрешены эффективными правами текущего пользователя, полученными от сервера.

Доказательство: ролевой прогон минимум двух разных эффективных наборов прав.

### AC-003

The system SHALL безопасно отказывать в открытии любого маршрута, ресурса или действия, для которого сервер не подтвердил разрешение, независимо от прямого URL, истории браузера или клиентской подмены состояния.

Доказательство: негативный прогон прямого URL и подмены клиентского состояния без раскрытия данных.

### AC-004

The system SHALL предоставлять постоянную боковую навигацию по разрешённым верхнеуровневым разделам, выполнять переход за одно явное действие и синхронизировать активный пункт с текущим маршрутом.

Доказательство: запись одного перехода и сверка активного пункта с маршрутом.

### AC-005

The system SHALL при попытке покинуть dirty-контекст требовать явный выбор «Сохранить», «Не сохранять» или «Отмена» и менять маршрут только в соответствии с подтверждённым результатом этого выбора.

Доказательство: три прогона выбора, включая ошибку сохранения без потери ввода.

### AC-006

The system SHALL явно различать загрузку и подтверждённое отсутствие данных в области содержимого, сохраняя оболочку и показывая только разрешённые действия.

Доказательство: отдельные кадры loading и empty для одного раздела.

### AC-007

The system SHALL показывать error, offline и permission-denied как разные базовые состояния с понятной причиной на доступном уровне, разрешённым следующим действием и сохранением безопасного состояния данных.

Доказательство: три отдельных прогона с разными следующими действиями.

### AC-008

The system SHALL отображать foundation-навигацию, базовые состояния, dirty-state выбор и безопасные сообщения ошибок на русском и английском без обрезания критического смысла.

Доказательство: парные кадры RU/EN критических подписей.

### AC-009

The system SHALL хранить и отображать severity ошибки отдельно от безопасного пользовательского сообщения, следующего действия и технического контекста, раскрывая подробности только роли с соответствующим разрешением.

Доказательство: прогон двух ролей на одной ошибке и проверка отсутствия секрета в пользовательском тексте.

### AC-010

The system SHALL применять к оболочке и общим состояниям единый draft-каталог семантических токенов для поверхностей, текста, границ, интерактивных состояний, фокуса и severity без объявления спорных необработанных значений утверждённым visual baseline.

Доказательство: инвентаризация токенов и явная пометка, что акцентный цвет не утверждён.

## Нефункциональные требования

### NFR-001

The system SHALL выполнять foundation-сценарии в локальном контуре без обязательного интернета, CDN, внешних шрифтов, внешних API или облачной телеметрии.

Доказательство: сетевой аудит при заблокированном внешнем доступе.

### NFR-002

The system SHALL требовать действующую аутентификацию и серверную проверку RBAC для каждого защищённого маршрута, ресурса и действия, используя клиентскую видимость только как представление разрешений.

Доказательство: security-прогон скрытого пункта меню и прямого запрещённого действия.

### NFR-003

The system SHALL позволять пройти критические foundation-пути с клавиатуры, показывать видимый фокус и предсказуемо перемещать его при навигации, диалоге и состоянии ошибки.

Доказательство: клавиатурный прогон без мыши.

### NFR-004

The system SHALL использовать для текста, элементов управления, фокуса и семантических состояний только сочетания токенов, прошедшие проверку по утверждённому уровню WCAG; отсутствие утверждённого уровня или положительного протокола блокирует Ready.

Доказательство: протокол контраста после закрытия `Q-006`. До ответа требование не пройдено.

### NFR-005

The system SHALL считаться совместимым только с теми комбинациями браузера, ОС, viewport, zoom, системного масштаба и целевого оборудования Admin Web UI, которые утверждены после discovery и прошли foundation-сценарии.

Доказательство: матрица прогонов после закрытия `Q-007`.

### NFR-006

The system SHALL получить baseline и порог производительности foundation-путей на утверждённом целевом оборудовании по воспроизводимой методике до заявления performance pass, не подставляя числовое значение заранее.

Доказательство: discovery-отчёт без заранее объявленного порога. Сам отчёт не закрывает performance pass.

## Анализ угроз

Основная угроза foundation — принять скрытие пункта меню за авторизацию, раскрыть запрещённый маршрут или потерять черновик при навигации.

Угрозы:

- Прямой URL открывает запрещённый раздел или его данные
- Клиентская подмена роли обходит серверный RBAC
- Навигация уничтожает несохранённые изменения без явного решения
- Offline-команда попадает в скрытую очередь и применяется позже
- Технический текст ошибки раскрывает секрет или инженерный контекст

Меры:

- Сервер подтверждает каждый маршрут, ресурс и действие
- Dirty-state требует сохранить, не сохранять или отменить
- Offline не создаёт скрытую очередь команд
- Технические подробности видны только разрешённой роли
- Штатная оболочка не зависит от внешней сети

Остаточный риск: Остаточный риск повышен, пока матрица прав, WCAG и контракты API не утверждены. Утвердил: Не назначен.

## Выпуск и откат

Порядок выпуска:

- Discovery метрик и матриц, затем проверяемый foundation-прототип, тестовый стенд, пилотный сегмент и ограниченный production

Условия остановки:

- Запрещённый маршрут или действие доступны
- Несохранённые изменения потеряны без явного отказа от них
- Ошибка, пустое состояние или offline показаны как успешный результат
- Оболочка требует интернет, CDN, внешний шрифт или облачный API

Откат:

- Вернуть предыдущий проверенный артефакт Admin Web UI, не изменяя серверные доменные данные, и повторить ролевые и dirty-state прогоны

Ответственный за выпуск и максимальное время отката не назначены. Эти значения нельзя выдумывать до закрытия `Q-001`.
