# Реальные проекты: Полная инструкция работы в окружении PDE

Данная инструкция описывает шаги для работы над реальным проектом в окружении PDE, начиная от формирования инициативы до появления воспроизводимого результата с подтверждающими Evidence.

## 1. Инициация проекта

1. Создайте отдельную директорию для каждого продукта или потоковой работы в `workspaces/projects/` с уникальным, читаемым на английском языке идентификатором (`project-id`). Пример: `smart-building-platform`.
2. Внутри каталога проекта заведите подкаталог `outcomes/<outcome-id>/` для каждого отдельного целевого результата (Outcome). Используйте стабильные и краткие идентификаторы (`OUT-001`, `OUT-AIR-01` и пр.).
3. Не используйте `workspaces/examples/` для реальных задач — он предназначен только для демонстрации.



## 2. Формирование продуктового определения

1. Изучите основы: прочитайте [PDE charter](../../governance/01-pde-charter.md), [глоссарий](../../governance/02-glossary.md) и описание жизненного цикла ([lifecycle](../../governance/09-lifecycle-and-gates.md)).
2. Определите сигнал — формализуйте исходную проблему или потребность. Зафиксируйте это событие с уникальным идентификатором (например, в Redmine с ссылкой).
3. Оформите проектный Outcome — создайте описание желаемого результата с критериями приёма (Acceptance Criteria) и нефункциональными требованиями (NFR).



## 3. Оформление Product Definition Pack

1. В каталоге Outcome создайте или скопируйте шаблоны `pack.md` и `pack.json` из `/templates`.
2. Заполните поля Pack, формально описав Outcome, AC, NFR, риски, ограничения и целевые измерения.
3. Применяйте только английские идентификаторы и полевая структура шаблонов для автоматизированной обработки.



## 4. Создание доказательств и артефактов

1. Все рабочие материалы, связанные с Outcome (результаты разработки, инструкции, Evidence), храните в подкаталоге Outcome.
2. Каждый артефакт Evidence сопровождайте стабильным идентификатором (`EVD-001`, `EVD-002` и т.д.) и кратким объяснением (по-русски).
3. Соблюдайте структуру: Signal → Outcome → Pack → Delivery Slice/PR → Evidence → Release → Outcome Check.



## 5. Ведение работы и контроль трассировки

1. Сопоставляйте Outcome с карточкой/таском в Redmine, указывая commit SHA для traceability.
2. Все изменения фиксируйте через Pull Request, сопровождая коммиты пояснениями.
3. Перед выпуском введите Evidence Bundle и инициируйте приемочное тестирование или экспертизу (QSRE, если интеграция включена).



## 6. Проверки и выпуск

1. Запускайте локальные скрипты проверки:
  - `pwsh ./scripts/validate-pack.ps1` — для Product Pack  
  - `pwsh ./scripts/validate-evidence.ps1` — для Evidence
2. После достижения критериев готовности проведите Ready Review и оформите необходимые handoff/документацию для внешних ASE/QSRE сред (если используются).
3. Проведите Outcome Check — формальную валидацию результата (`scale`, `keep`, `adapt`, `revert`) по чек-листу с подтверждающими Evidence.



## Принципы организации

- Нормативные (governance) документы не размещаются внутри проекта. Любое локальное ограничение описывайте отдельно, но оно не должно противоречить корневым правилам в `governance/`.
- Граница односторонняя: шаблоны, schema, skills, rules и scripts платформы могут и должны использоваться при создании файлов в `workspaces/projects/`. Создание и генерация проекта не изменяют файлы вне `workspaces/`.
- Соблюдайте прозрачную структуру для автоматизированной обработки и ручной проверки.
- Все шаги и артефакты должны быть воспроизводимы и проверяемы.

**Следуйте этим этапам, чтобы каждый проект имел четкое начало, прозрачные критерии качества, воспроизводимую реализацию и подтверждённый результат в среде PDE.**
