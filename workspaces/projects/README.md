# Реальные проекты: Полная инструкция работы в окружении PDE

Данная инструкция описывает шаги для работы над реальным проектом в окружении PDE, начиная от формирования инициативы до появления воспроизводимого результата с подтверждающими доказательствами.

## 1. Инициация проекта

1. Создайте отдельную директорию для каждого продукта или потоковой работы в `workspaces/projects/` с уникальным, читаемым на английском языке идентификатором (`project-id`). Пример: `smart-building-platform`.
2. Внутри каждого проекта обязательно создайте отдельный каталог `outcomes/`. Исходные документы проекта и созданные Outcomes нельзя смешивать в одном каталоге.
3. Для каждого отдельного целевого результата создайте собственный подкаталог `outcomes/<outcome-id>/`. Используйте стабильные и краткие идентификаторы (`OUT-001`, `OUT-AIR-01` и пр.).
4. Не создавайте `pack.md`, `pack.json`, передачу ASE, доказательства и другие файлы Outcome непосредственно в каталоге проекта или в корне `workspaces/projects/`.
5. Не используйте `workspaces/examples/` для реальных задач — он предназначен только для демонстрации.



## 2. Формирование продуктового определения

1. Изучите основы: прочитайте [PDE charter](../../governance/01-pde-charter.md), [глоссарий](../../governance/02-glossary.md) и описание жизненного цикла ([lifecycle](../../governance/09-lifecycle-and-gates.md)).
2. Поместите исходные документы в каталог соответствующего проекта и запросите их анализ. Агент сначала изучает материалы, отмечает противоречия и определяет недостающие сведения.
3. Если включён OpenSpec intake, агент создаёт change в `openspec/changes/<change-id>/` и не формирует Pack до подтверждения change.
4. До формирования итогового Outcome ответьте на уточняющие вопросы агента. Вопросы должны касаться только сведений, которых нет в документах или которые допускают несколько трактовок.
5. Обязательно уточняются пробелы в описании проблемы, ожидаемого результата, пользователей, области работ и нецелей, AC/NFR, метрик, рисков, безопасности, зависимостей, ограничений, владельцев, Redmine, выпуска и отката.
6. Пока блокирующие вопросы не закрыты, Outcome нельзя считать точным и готовым. По явному разрешению работника агент может создать только черновик с допущениями и блокирующими открытыми вопросами.
7. Определите сигнал — формализуйте исходную проблему или потребность. Зафиксируйте это событие с уникальным идентификатором, например в Redmine со ссылкой.
8. После получения ответов оформите целевой результат в отдельном каталоге `outcomes/<outcome-id>/` с критериями приёмки (AC) и нефункциональными требованиями (NFR).



## 3. Оформление пакета определения продукта

1. В каталоге результата создайте или скопируйте шаблоны `pack.md` и `pack.json` из `/templates`.
2. Заполните поля Pack, формально описав результат, AC, NFR, риски, ограничения и целевые измерения.
3. Если есть утверждённый OpenSpec change, перенесите сценарии командой `pwsh ./scripts/map-openspec-to-pack.ps1` в `specifications.md`.
4. Весь человекочитаемый текст пишите по-русски. На английском оставляйте только имена файлов, ключи JSON/YAML, устойчивые идентификаторы и служебные значения, необходимые автоматическим проверкам.



## 4. Создание доказательств и артефактов

1. Все рабочие материалы, связанные с целевым результатом (результаты разработки, инструкции и доказательства), храните в его подкаталоге.
2. Каждый артефакт доказательства сопровождайте стабильным идентификатором (`EVD-001`, `EVD-002` и т.д.) и кратким объяснением по-русски.
3. Соблюдайте структуру: сигнал → результат → Pack → срез поставки / PR → доказательство → выпуск → проверка результата.



## 5. Ведение работы и контроль трассировки

1. Сопоставляйте результат с задачей в Redmine, указывая SHA коммита для трассировки.
2. Все изменения фиксируйте через Pull Request, сопровождая коммиты пояснениями.
3. Перед выпуском сформируйте пакет доказательств и инициируйте приёмочное тестирование или экспертизу QSRE, если интеграция включена.



## 6. Проверки и выпуск

1. Запускайте локальные скрипты проверки:
  - `pwsh ./scripts/validate-pack.ps1` — для Product Pack  
  - `pwsh ./scripts/validate-evidence.ps1` — для доказательств
2. После достижения критериев готовности проведите проверку готовности и оформите необходимые документы передачи для внешних сред ASE/QSRE, если они используются.
3. Проведите формальную проверку результата с решением `scale`, `keep`, `adapt` или `revert` по контрольному списку и подтверждающим доказательствам.



## Принципы организации

- Нормативные (governance) документы не размещаются внутри проекта. Любое локальное ограничение описывайте отдельно, но оно не должно противоречить корневым правилам в `governance/`.
- Граница односторонняя: шаблоны, schema, skills, rules и scripts платформы могут и должны использоваться при создании файлов в `workspaces/projects/`. Создание и генерация проекта не изменяют файлы вне `workspaces/`.
- Соблюдайте прозрачную структуру для автоматизированной обработки и ручной проверки.
- Все шаги и артефакты должны быть воспроизводимы и проверяемы.

**Следуйте этим этапам, чтобы каждый проект имел четкое начало, прозрачные критерии качества, воспроизводимую реализацию и подтверждённый результат в среде PDE.**
