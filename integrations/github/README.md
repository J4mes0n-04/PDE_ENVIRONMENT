# Интеграция GitHub

## До первого слияния

1. Создать репозиторий GitHub из содержимого `PROD`.
2. Заменить временные значения в `.github/CODEOWNERS` на реальных пользователей или команды.
3. Защитить `main`: требовать Pull Request, одобрения и разрешения всех обсуждений.
4. Назначить обязательными проверками четыре workflow из `.github/workflows/`.
5. Запретить принудительную отправку изменений и удаление `main`.
6. Ограничить разрешения GitHub Actions значением `contents: read`, кроме отдельно утверждённых workflow.
7. Настроить окружения выпуска, если они появятся.

## Секреты

Локальные четыре validate/governance workflow не требуют секретов. Межрепозиторные уведомления используют GitHub Environment `notify-ase` и секреты `ASE_NOTIFY_APP_ID` / `ASE_NOTIFY_APP_PRIVATE_KEY`. Токен Redmine, токен Unleash, учётные данные OTLP и другие секреты добавляются только вместе с включением соответствующей интеграции. Секреты в Git не хранятся.

## Межрепозиторные уведомления

Пока reusable workflows в `engineering-control` не закреплены новым SHA, PDE запускает только ручные workflow:

- `notify-ase-ready.yml` — создаёт Issue в `ase-environment` после ручной проверки Ready;
- `listen-qsre-feedback.yml` — создаёт Issue в PDE по обратной связи QSRE.

Автоматизация не объединяет Pull Request, не меняет Pack и не принимает Ready-решение. `repository_dispatch` не используется, потому что GitHub требует для него `contents: write`. Порядок настройки GitHub App описан в репозитории `engineering-control` в `docs/github-app.md`.

Локальные четыре validate workflow остаются обязательными checks. Вызов `validate-pde.yml` из `engineering-control` подключается отдельным изменением после появления SHA, в котором этот файл уже есть.

## Рекомендуемые метки

`outcome`, `delivery-slice`, `definition-change`, `governance`, `risk-r2`, `risk-r3`, `waiver`, `integration`, `skill`.

## Работа сотрудника через fork

### Назначение модели

Fork — отдельная рабочая копия репозитория на GitHub, связанная с главным репозиторием. Сотрудник отправляет ветки в свой fork и предлагает изменения через Pull Request. Только принятое владельцем изменение попадает в `main` главного репозитория.

Локальный клон технически позволяет изменить любой файл, но такие изменения не становятся частью официальной среды сами по себе. Источником истины остаётся защищённая ветка `main` главного репозитория.

### 1. Создать разрешённый fork

1. Откройте страницу главного репозитория в GitHub.
2. Нажмите **Fork**.
3. Выберите только личную учётную запись или организацию, которую разрешил владелец репозитория.
4. Не меняйте видимость репозитория и не переносите его в другую организацию.
5. Если создание fork запрещено или кнопка недоступна, остановитесь и обратитесь к владельцу. Не создавайте независимую копию через загрузку архива или новый публичный репозиторий.



### 2. Клонировать fork и добавить главный репозиторий

Клонируйте именно свой fork:

```powershell
git clone https://github.com/<employee>/<repository>.git
Set-Location <repository>
```

Добавьте главный репозиторий как `upstream`:

```powershell
git remote add upstream https://github.com/<owner>/<repository>.git
git remote -v
```

Ожидаемая схема:

```text
origin    → fork сотрудника, куда он отправляет рабочие ветки
upstream  → главный репозиторий, откуда он получает утверждённые изменения
```

Если `upstream` уже существует, не добавляйте его повторно. Проверьте адрес командой `git remote -v`.

### 3. Синхронизироваться перед новой задачей

Не создавайте рабочие коммиты непосредственно в локальной ветке `main`. Перед началом каждой задачи обновите её из главного репозитория:

```powershell
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main
```

Если `--ff-only` сообщает о расхождении веток, не используйте принудительную отправку и не переписывайте историю самостоятельно. Сохраните незавершённую работу в отдельной ветке и обратитесь к владельцу.

### 4. Создать рабочую ветку

Используйте тип ветки, соответствующий задаче:

```text
outcome/<outcome-id>-<short-name>
slice/<slice-id>-<short-name>
definition-change/<change-id>-<short-name>
skill/<skill-name>-<short-name>
integration/<tool>-<short-name>
```

Например:

```powershell
git switch -c skill/pde-create-pack-improve-validation
```

Не используйте ветку `governance/...`, если владелец явно не поручил нормативное изменение.

### 5. Соблюдать границы изменений

Для обычной продуктовой задачи сотрудник изменяет только:

```text
workspaces/projects/<project-id>/
```

Для улучшения навыка через OpenSpace сотрудник изменяет только целевой каталог:

```text
.agents/skills/<skill-name>/
```

Без отдельного поручения владельца запрещено включать в рабочую ветку изменения из:

```text
governance/
architecture/
templates/
schemas/
scripts/
.github/
AGENTS.md
```

Не смешивайте продуктовое изменение и улучшение навыка в одном Pull Request. Если OpenSpace обнаружил проблему в нормативном документе, зафиксируйте наблюдение в описании Pull Request или отдельном предложении, но не исправляйте `governance/` самостоятельно.

### 6. Улучшать skills с помощью OpenSpace

1. Создайте отдельную ветку `skill/<skill-name>-<short-name>`.
2. Используйте только локальный режим OpenSpace. Облачный обмен и автоматические триггеры изменения skills должны оставаться выключенными.
3. Разрешайте OpenSpace работать только с `.agents/skills/` и локальными записями качества.
4. После предложения OpenSpace обязательно просмотрите изменения:

```powershell
git status --short
git diff -- .agents/skills
git diff -- governance
```

1. Команда `git diff -- governance` не должна показывать изменений. Если они появились, не добавляйте их в коммит и сообщите владельцу.
2. В описании Pull Request укажите исходный сигнал, ожидаемое улучшение навыка, способ проверки и затронутые файлы.

OpenSpace не утверждает новую версию навыка и не меняет главный репозиторий. Его результат является предложением до тех пор, пока владелец не примет Pull Request.

### 7. Выполнить локальные проверки

Перед отправкой ветки выполните базовые проверки:

```powershell
pwsh ./scripts/doctor.ps1
pwsh ./scripts/validate-repository.ps1
```

Если изменялся Pack:

```powershell
pwsh ./scripts/validate-pack.ps1
```

Если изменялись доказательства:

```powershell
pwsh ./scripts/validate-evidence.ps1
```

Не описывайте работу как завершённую, если обязательная проверка завершилась ошибкой.

### 8. Проверить состав коммита

Перед коммитом убедитесь, что в ветке нет секретов, локальной конфигурации, случайных файлов и изменений governance:

```powershell
git status --short
git diff
git diff --cached
```

Добавляйте файлы явно, а не весь каталог без проверки:

```powershell
git add .agents/skills/<skill-name>/
git commit -m "Improve <skill-name> skill"
```

Для продуктовой работы вместо каталога навыка укажите конкретный каталог проекта в `workspaces/projects/`.

### 9. Отправить ветку и открыть Pull Request

Отправьте рабочую ветку в свой fork:

```powershell
git push -u origin <branch-name>
```

В GitHub создайте Pull Request со следующими направлениями:

```text
base repository: главный репозиторий
base branch: main
head repository: fork сотрудника
compare branch: рабочая ветка сотрудника
```

Заполните шаблон Pull Request, приложите ссылку на Redmine и перечислите выполненные проверки. Для Pack и доказательств указывайте конкретные SHA и неизменяемые ссылки.

### 10. Дождаться решения владельца

После создания Pull Request сотрудник:

- отвечает на замечания;
- отправляет исправления в ту же рабочую ветку;
- повторно выполняет проверки;
- не объединяет Pull Request самостоятельно;
- не закрывает замечания владельца без исправления или согласованного объяснения;
- не создаёт новый Pull Request для каждой итерации одной задачи.

Изменение считается принятым только после успешных проверок, необходимого одобрения и слияния владельцем в `main`.

### Запрещённые действия

- отправлять изменения напрямую в `upstream/main`;
- использовать `force push` для `main`;
- добавлять токены, пароли, ключи API или локальные `.env` в Git;
- создавать публичную копию закрытого репозитория;
- обходить CODEOWNERS, обязательные проверки или запрос изменений;
- включать облачный режим OpenSpace;
- разрешать OpenSpace автоматически менять governance или выполнять merge;
- копировать полный Pack в Redmine или описание Pull Request.
