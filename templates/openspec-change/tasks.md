# Срезы поставки для ASE

Задачи не являются источником истины Pack. После Ready они могут войти в `ase-handoff.md`. Прохождение gates определяют `pack.json` и сценарии в `specifications.md`.

Каждый пункт — одна наблюдаемая проверка. Формулировка называет, кто действует, где, что делает, что видно и какой `AC-###` или `NFR-###` закрывается. Пункт без видимого результата и без идентификатора требования не считается проверкой.

Слабая формулировка: «проверить экран». Сильная: «Инженер на экране Э-1 нажимает „Создать комплект“ и видит только два способа: „Мастер“ и „Вручную“ (`AC-042`)».

Разбейте каждый `AC` и `NFR` change на отдельные пункты. Один идентификатор может дать несколько проверок: основной путь, пустое состояние, ошибка, запрещённый путь и сохранение уже введённых данных. Не объединяйте два разных результата в одном пункте.

## 1. Первый проверяемый срез

Название среза: что пользователь сможет сделать после этого инкремента.

- [ ] 1.1 Исходное состояние: <кто>, <какой экран открыт>, <какие данные уже есть>. Без этого срез не начинается.
- [ ] 1.2 <Кто> на <экране> выполняет <одно действие> и видит <конкретный результат> (`AC-000`).
- [ ] 1.3 После действия записаны или прочитаны только <названные данные>; остальные поля остаются <пустыми / прежними> (`AC-000`).
- [ ] 1.4 Пустое или отсутствующее состояние показывает <точный текст или элемент>, а не пустой экран (`AC-000`).
- [ ] 1.5 Ошибка <какое условие> оставляет пользователя на <том же экране>, показывает <сообщение> и не создаёт <лишнюю запись> (`AC-000`).
- [ ] 1.6 Запрещённый путь: <действие> не открывает <чужой экран / режим> и не меняет <данные> (`AC-000`).
- [ ] 1.7 Повтор того же действия не создаёт дубль <объекта или записи> (`AC-000`).
- [ ] 1.8 Уже введённые данные <поля> сохраняются после <отмены, возврата или повторного открытия> (`AC-000`).

## 2. Следующий срез, который зависит от первого

- [ ] 2.1 Срез 1 уже даёт <наблюдаемый результат>. Без него этот срез не проверяется.
- [ ] 2.2 <Кто> переходит из <места> в <место> и видит <что именно на экране> (`AC-000`).
- [ ] 2.3 Возврат назад показывает <прежнее состояние>, а не потерянные или чужие данные (`AC-000`).
- [ ] 2.4 Прямой переход по адресу или кнопке вне разрешённого пути возвращает на <экран> и не открывает <запрещённый раздел> (`AC-000`).

## 3. Нефункциональные проверки этого change

Отдельный пункт на каждое `NFR`. Признак должен быть наблюдаемым: размер, текст, палитра, место хранения, отсутствие сети, клавиатура.

- [ ] 3.1 На <экране> при <условии> выполняется <измеримый признак> (`NFR-000`).
- [ ] 3.2 На <экране> отсутствует <запрещённый визуальный или технический признак> (`NFR-000`).
- [ ] 3.3 Сценарий <название> проходит с клавиатуры без мыши: <клавиши> приводят к <результату> (`NFR-000` или `AC-000`).
- [ ] 3.4 Данные читаются и пишутся только в <хранилище>. Обращения к <запрещённому каналу> нет (`NFR-000`).
- [ ] 3.5 Текст <язык / алфавит> читается в <элементах интерфейса> без замены символов (`NFR-000`).

## 4. Доказательство среза

- [ ] 4.1 Для каждого пункта 1–3 есть прогон на одном SHA: скриншот, короткая запись или запись проверки с датой и идентификатором требования.
- [ ] 4.2 Пункт, который не удалось пройти, отмечен как непройденный и ссылается на открытый вопрос или дефект. Скрытый пропуск не закрывает срез.
