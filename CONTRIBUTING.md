# Внесение изменений

## Общий порядок

1. Создайте issue или Redmine item с причиной изменения.
2. Определите тип изменения: operational work, template, skill, integration, standard или policy.
3. Создайте ветку с понятным английским идентификатором.
4. Внесите минимальное изменение и обновите связанные артефакты.
5. Запустите локальные проверки из `scripts/`.
6. Создайте Pull Request по шаблону.
7. Получите review владельцев, указанных в CODEOWNERS.

## Имена веток

- `outcome/<outcome-id>-<short-name>`
- `slice/<slice-id>-<short-name>`
- `definition-change/<change-id>-<short-name>`
- `governance/<document-id>-<short-name>`
- `skill/<skill-name>-<short-name>`
- `integration/<tool>-<short-name>`

## Изменение governance

Изменение файла в `governance/` обязано:

- объяснять причину;
- указывать затронутые templates, rules, skills, CI и активные Outcomes;
- обновлять версию и историю документа;
- иметь approval нормативного владельца;
- не смешиваться с несвязанным продуктовым изменением.

Операционная работа в `workspaces/projects/` не изменяет платформенные файлы вне `workspaces/`. Изменение платформы, если оно нужно, оформляется отдельным Pull Request.

## Изменение skills

Для skill необходимо указать источник сигнала, ожидаемое улучшение и способ проверки. OpenSpace может предложить `FIX`, `DERIVED` или `CAPTURED`, но активация новой версии проходит через Pull Request.

## Язык и идентификаторы

Документы пишутся на русском. Имена файлов, каталогов, YAML/JSON полей и стабильные идентификаторы пишутся на английском. Термин при первом появлении расшифровывается на русском.
