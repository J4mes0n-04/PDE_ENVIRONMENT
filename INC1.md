# Создание, объединение и вывод сред PDE, ASE и QSRE в production

## 1. Назначение инструкции

Эта инструкция описывает путь от текущего состояния до целевой системы из трёх специализированных рабочих сред:

- **PDE Environment** — формирует проверяемое определение продукта и Product Definition Pack;
- **ASE Environment** — реализует утверждённое определение в коде;
- **QSRE Environment** — независимо проверяет качество, безопасность и готовность выпуска;
- **engineering-control** — хранит общую нормативную основу и машиночитаемые контракты обмена.

Инструкция относится к созданию самой платформы. Она не описывает отдельный продуктовый Outcome и не разрешает переносить рабочие проекты в нормативный репозиторий.

## 2. Целевая архитектура

```text
                         engineering-control
                  governance + contracts + schemas
                        versioned release/tag
                    /             |             \
                   v              v              v
          PDE Environment   ASE Environment   QSRE Environment
          определение       реализация        независимая проверка
                 |                |                   |
                 | PDE -> ASE     | ASE -> QSRE       |
                 +--------------->+------------------->+
                 ^                                    |
                 +----------- QSRE -> PDE -------------+

Redmine: состояние и приоритет работы
GitHub: версии, Pull Request, решения и неизменяемые ссылки
Cursor/Codex: агентная работа по правилам каждой среды
OpenSpace local: поиск и улучшение skills через предложение и Pull Request
Unleash: управляемое включение функций, когда потребуется release control
OpenTelemetry/Grafana: наблюдаемость, когда появится production-контур
```

Среды не копируют нормативные документы друг у друга. Каждая среда фиксирует конкретный release tag и полный commit SHA репозитория `engineering-control`.

## 3. Текущее состояние на дату создания инструкции

### Уже существует

- PDE-репозиторий `PDE_ENVIRONMENT` и его локальная копия `PROD`;
- нормативные документы PDE, шаблоны, validators, skills и четыре GitHub Actions workflow;
- отдельный публичный репозиторий `engineering-control`;
- защищённая ветка `main` в `engineering-control`;
- обязательные проверки `control` и `change-control`;
- staging snapshot нормативной основы PDE;
- три draft-контракта версии `1.0.0`:
  - PDE → ASE;
  - ASE → QSRE;
  - QSRE → PDE;
- примеры сообщений и матрица совместимости;
- запрет прямого автоматического изменения governance инструментом OpenSpace.

### Ещё не завершено

- `engineering-control` имеет `status: staging` и `authoritative: false`;
- контракты имеют статус `draft`;
- release candidate общей основы ещё должен быть формально выпущен;
- отдельные ASE и QSRE environments не созданы;
- PDE ещё не переведён на получение нормативной основы из `engineering-control`;
- межрепозиторная проверка совместимости не автоматизирована;
- не проведён сквозной shadow pilot PDE → ASE → QSRE → PDE;
- не принято production-решение;
- Redmine и организационные роли настраиваются отдельно и не считаются готовыми автоматически.

## 4. Неприкосновенные правила перехода

1. Ничего не удалять из действующего PDE до подтверждённого cutover и окончания периода отката.
2. Не перемещать `workspaces/` и реальные Outcomes в `engineering-control`.
3. Не считать staging snapshot источником истины, пока `authoritative: false`.
4. Все нормативные изменения проводить отдельным Pull Request с человеческим решением.
5. Не смешивать в одном Pull Request изменение governance, разработку среды и продуктовые файлы.
6. Не использовать плавающую ссылку только на `main` для зависимости между средами. Использовать tag и полный commit SHA.
7. Не передавать секреты, локальные `.env`, quality records OpenSpace и пользовательские данные между репозиториями через Git.
8. Не включать OpenSpace cloud mode и автоматическое обновление governance.
9. Не запускать production-процесс на несовместимых major-версиях контрактов.
10. Каждый этап должен иметь проверяемые входные условия, результат и способ отката.

## 5. Репозитории целевой системы

Рекомендуемая структура в GitHub:

```text
engineering-control   общая нормативная основа и контракты
pde-environment       определение продукта и рабочие PDE Outcomes
ase-environment       управление инженерной реализацией
qsre-environment      независимая проверка и выпуск
product-*             исходный код конкретных продуктов
```

### Что принадлежит `engineering-control`

- общая терминология и обязательные межсредовые нормы;
- общие schemas и templates;
- контракты PDE → ASE → QSRE → PDE;
- правила версионирования и совместимости;
- журнал изменений и release notes;
- validators общей основы.

### Что принадлежит конкретной среде

- `AGENTS.md`, rules и skills её роли;
- локальные адаптеры и настройки инструментов;
- operations/runbooks конкретной среды;
- собственные validators;
- рабочие артефакты, разрешённые этой средой;
- зафиксированная зависимость от версии `engineering-control`.

## 6. Этапы работ

### Этап 0. Сохранить контрольную точку

Перед структурными изменениями:

```powershell
git status --short --branch
pwsh ./scripts/doctor.ps1
pwsh ./scripts/validate-repository.ps1
git tag --list
```

Требования:

- рабочее дерево понятно и не содержит случайных изменений;
- действующая PDE baseline отмечена tag;
- tag отправлен в GitHub;
- известен полный commit SHA;
- создана резервная копия только средствами Git или проверенного backup-процесса.

Критерий завершения: PDE можно восстановить по tag и SHA без зависимости от незакоммиченных локальных файлов.

### Этап 1. Инвентаризировать PDE

Зафиксировать для каждого каталога:

- является ли содержимое общим, PDE-specific или рабочим;
- кто владелец;
- какой validator проверяет содержимое;
- можно ли переносить его в общую основу;
- содержит ли оно локальные данные или секреты.

Результат должен подтверждать:

- `governance/` — исходная нормативная база;
- выбранные schemas/templates — кандидаты в общую основу;
- `workspaces/` — остаётся только в PDE;
- PDE-specific skills/rules — не переносятся в control;
- локальные интеграции — не становятся общей нормой автоматически.

### Этап 2. Подготовить `engineering-control`

1. Скопировать только утверждённый baseline, сохранив происхождение в `source-baseline.yaml`.
2. Добавить `README.md`, `CHANGELOG.md`, CODEOWNERS, PR template и CI.
3. Настроить защиту `main`:
   - только Pull Request;
   - обязательные `control` и `change-control`;
   - разрешение обсуждений;
   - запрет удаления и force-push.
4. Не объявлять репозиторий authoritative на этом этапе.

Локальная проверка:

```powershell
pwsh ./scripts/validate-control.ps1
```

Критерий завершения: чистый `main`, зелёный CI, защищённая ветка и воспроизводимый staging snapshot.

### Этап 3. Зафиксировать межсредовые контракты

Обязательные контракты:

1. **PDE → ASE**: Pack SHA, риск, автономия, AC/NFR, scope, delivery slices, ожидаемые evidence и ограничения.
2. **ASE → QSRE**: Pack SHA, implementation SHA, карта требований к тестам, Evidence Bundle, release/rollback и остаточный риск.
3. **QSRE → PDE**: результат проверки и тип обратной связи `clarification`, `definition-change`, `defect` или `governance-signal`.

Для каждого контракта нужны:

- JSON Schema;
- версия SemVer;
- валидный пример;
- отрицательные тестовые примеры;
- владелец;
- правила совместимости;
- миграционная политика для breaking change.

Проверка:

```powershell
pwsh ./scripts/validate-contracts.ps1
pwsh ./scripts/validate-control.ps1
```

Критерий завершения: все три контракта валидируются, а среда с несовместимой major-версией блокируется до передачи работы.

### Этап 4. Выпустить `engineering-control` release candidate

1. Проверить, что `main` синхронизирован и CI зелёный.
2. Заменить `Unreleased` у `1.0.0-rc.1` на дату выпуска через Pull Request.
3. Получить человеческое решение о публикации prerelease.
4. Создать аннотированный tag `v1.0.0-rc.1` на проверенном commit.
5. Создать GitHub prerelease с известными ограничениями.
6. Записать полный SHA tag в release notes.

Release candidate не делает основу authoritative. Он создаёт неизменяемую версию для подключения и shadow-проверки.

### Этап 5. Создать каркасы ASE и QSRE

Создавать два отдельных репозитория. Не копировать целиком PDE.

Минимальный состав каждого:

```text
.github/
.agents/skills/
.cursor/rules/
.codex/
architecture/
config/
contracts/
integrations/
operations/
scripts/
templates/
AGENTS.md
CONTRIBUTING.md
README.md
```

#### ASE Environment должна

- принимать только валидный PDE → ASE handoff;
- подтверждать ACK или возвращать вопросы;
- связывать Pack SHA, PR и implementation SHA;
- создавать ASE → QSRE handoff;
- запрещать неявное изменение AC/NFR и scope;
- направлять смысловое изменение обратно в PDE через Definition Change.

#### QSRE Environment должна

- принимать валидный ASE → QSRE handoff;
- независимо проверять evidence, безопасность, release и rollback;
- фиксировать среду и время выполнения проверок;
- выпускать QSRE → PDE feedback;
- не исправлять Pack самостоятельно;
- блокировать release при отсутствии обязательных доказательств.

Критерий завершения: пустые среды проходят собственные validators и корректно отклоняют невалидные handoff-примеры.

### Этап 6. Подключить общую основу без удаления локальной PDE-базы

На первом шаге использовать **vendor snapshot** или другой детерминированный read-only механизм. Не использовать ручное копирование без метаданных.

Каждая среда должна хранить manifest примерно следующего смысла:

```yaml
control_repository: https://github.com/<owner>/engineering-control.git
control_tag: v1.0.0-rc.1
control_commit: <full-40-character-sha>
contract_major: 1
```

Обязательные проверки:

- tag существует;
- tag указывает на ожидаемый SHA;
- SHA имеет полный формат;
- control validator проходит;
- major-версии контрактов совместимы;
- vendor-копия не была изменена локально.

Исходный `governance/` PDE на этом этапе не удалять. Он остаётся rollback-базой и используется для сравнения.

### Этап 7. Добавить межрепозиторную автоматизацию

Рекомендуемый безопасный поток:

1. Новый prerelease `engineering-control` запускает проверку совместимости каждой среды.
2. Автоматизация создаёт предложение или Pull Request обновления pin.
3. CI среды загружает конкретный tag/SHA и выполняет contract tests.
4. Человек проверяет изменения и принимает Pull Request.
5. Автоматический merge нормативных обновлений запрещён.

Для GitHub Actions использовать минимальные permissions. Межрепозиторный токен хранить только в GitHub Secrets/Environment и выдавать ему минимально необходимые права. Предпочитать GitHub App с ограниченным доступом вместо персонального токена.

### Этап 8. Провести shadow pilot

Использовать учебный или ограниченный R1 Outcome без production-риска.

Пройти полный цикл:

```text
Signal
  → PDE Pack
  → Ready Review
  → PDE-to-ASE handoff
  → ASE ACK
  → implementation PR
  → Evidence Bundle
  → ASE-to-QSRE handoff
  → QSRE review
  → QSRE-to-PDE feedback
  → release/non-production deployment
  → Outcome Check
```

Проверить:

- трассировку идентификаторов и SHA;
- отсутствие ручного копирования Pack;
- обработку clarification и definition change;
- отклонение невалидного сообщения;
- совместимость версий;
- восстановление после отказа интеграции;
- время и понятность каждого handoff;
- отсутствие автоматического изменения governance.

Критерий завершения: полный цикл воспроизводим другим участником по документации, а найденные проблемы зарегистрированы и исправлены через Pull Request.

### Этап 9. Провести controlled cutover общей основы

Cutover разрешён только после shadow pilot.

1. Сравнить PDE governance и release candidate control побайтово или содержательно.
2. Закрыть расхождения отдельными решениями.
3. Утвердить общую основу.
4. Выпустить стабильный tag, например `v1.0.0`.
5. Обновить `source-baseline.yaml` или заменяющий его control manifest:
   - `status: active`;
   - `authoritative: true`.
6. Обновить pins PDE/ASE/QSRE через отдельные Pull Request.
7. Зафиксировать дату, владельца решения и rollback tag.
8. Оставить старую PDE-базу доступной в истории Git и контрольном tag.

Не удалять старые документы из истории. Если дубли в рабочем дереве больше не нужны, их удаление выполняется только отдельным миграционным PR после подтверждённого периода стабильности.

### Этап 10. Production readiness review

До production должны быть подтверждены следующие области.

#### Управление

- назначены владельцы и approvers;
- нет блокирующих placeholders;
- CODEOWNERS соответствует реальным GitHub users/teams;
- branch rules проверены тестовым PR;
- установлен review cycle нормативных документов;
- определён аварийный порядок изменения нормы.

#### Техническая готовность

- все validators зелёные локально и в CI;
- schemas имеют положительные и отрицательные тесты;
- pins используют tag + SHA;
- известен и испытан rollback;
- зависимости и runtime версии зафиксированы;
- secrets не находятся в репозиториях;
- backup и restore испытаны.

#### Безопасность и compliance

- заполнен реестр применимых требований;
- определена классификация данных;
- проведён threat analysis для R3 и критичных интеграций;
- настроены аудит и сроки хранения;
- определён порядок security incident;
- облачная передача данных включается только отдельным решением.

#### Эксплуатация

- есть runbooks для отказов GitHub, Redmine и межсредового обмена;
- определены SLO/SLI там, где они нужны;
- настроена эскалация;
- определён владелец каждого environment;
- проведено обучение сотрудников;
- выполнен production rehearsal.

### Этап 11. Включать дополнительные инструменты по необходимости

#### OpenSpace local

Включать сначала в shadow mode. Он может анализировать и предлагать изменения skills, но не менять governance, выполнять merge или передавать данные в cloud.

#### Unleash

Включать, когда нужен управляемый rollout функций. До этого `enabled: false` является нормальным состоянием.

#### OpenTelemetry и Grafana

Включать, когда определены telemetry requirements, владелец данных, endpoint, retention и dashboard/alert policy. Само значение `enabled: true` не означает готовность.

## 7. Версионирование

- `engineering-control` использует SemVer.
- Добавление необязательного поля без изменения смысла обычно совместимо.
- Удаление обязательного поля, изменение типа, enum или нормативного смысла требует новой major-версии.
- Среда не обновляет major-версию автоматически.
- Любое обновление pin проходит Pull Request и contract tests.
- Release notes перечисляют миграционные действия и известные ограничения.

## 8. Стратегия отката

Для каждого cutover заранее зафиксировать:

- предыдущий рабочий tag control;
- предыдущие pins всех сред;
- список изменённых workflow/secrets/settings;
- владельца решения об откате;
- максимальное допустимое время восстановления.

Откат выполняется через Pull Request, возвращающий pins к последней подтверждённой версии. История Git не переписывается, force-push не используется.

## 9. Финальный критерий production

Система считается production-ready только если одновременно:

- `engineering-control` — authoritative и имеет стабильный release;
- PDE, ASE и QSRE используют один совместимый control release по tag и SHA;
- три handoff-контракта имеют статус stable;
- сквозной цикл успешно пройден минимум одним контролируемым Outcome;
- CI не допускает обхода обязательных проверок;
- восстановление и rollback испытаны;
- роли, безопасность, compliance и эксплуатационные обязанности утверждены;
- документация позволяет новому сотруднику воспроизвести процесс без устных знаний.

## 10. Ближайшее следующее действие

На текущем состоянии следует:

1. подготовить Pull Request, заменяющий `1.0.0-rc.1 — Unreleased` на дату выпуска;
2. выпустить `engineering-control` prerelease `v1.0.0-rc.1`;
3. создать каркас `ase-environment`;
4. создать каркас `qsre-environment`;
5. подключить оба каркаса к `v1.0.0-rc.1` по tag и полному SHA;
6. после этого подключать PDE в shadow mode, не удаляя текущий `governance/`.
