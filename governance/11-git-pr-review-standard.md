## Ветки и Pull Request

- **Создание веток:**  
  Все изменения происходят в отдельных ветках, основанных на `main` или актуальном release-бранче. Прямая запись (`push`) в ветку `main` строго запрещена — даже для исправлений опечаток или мелких багов.  
- **Связь с задачей:**  
  Каждый Pull Request (PR) должен быть привязан к одной конкретной задаче или инициативе (Issue, Outcome, сигнал). Не допускается объединение нескольких крупных изменений, не связанных с одной Outcome.  
- **Структура описания PR:**  
  В описании PR в обязательном порядке указываются:  
  - **Redmine ID** (или идентификатор другой системы задач, если используется), — для прямой трассировки;
  - **Outcome ID** — уникальный идентификатор соответствующего Outcome, в рамках которого ведётся работа;
  - **Pack** — путь к `pack.md`, актуальная версия pack и SHA изменяемого commit;
  - **Risk** — описание/идентификатор затронутых рисков, ссылками на элементы Pack;
  - **AC/NFR** — чёткий список Acceptance Criteria и Non-Functional Requirements, которые реализуются/закрываются этим PR;
  - **Evidence** — перечень и ссылки на предоставляемое Evidence, прямо доказывающее выполнение требований (см. стандарт Evidence);
  - **Rollback impact** — ожидаемое влияние на rollback, наличие новых/изменённых процедур возврата, если актуально.
- **Изменения governance:**  
  При изменении нормативных документов или платформенных стандартов, в описании PR перечисляются все затронутые элементы governance:  
     - шаблоны (templates),  
     - правила (rules),  
     - skills,  
     - workflow (CI/CD, Github Actions и пр.),  
     - Outcomes,  
  с точным указанием путей и версий.

## Review

- **R0 – Авторская само-проверка и автоматизированные тесты:**  
  Изначально автор PR несёт ответственность за первичную проверку изменений и обеспечение прохождения базового CI/CD pipeline.  
  - Все автоматизированные тесты должны быть зелёными.  
  - PR должен быть минимально воспроизводимым и не ломать сборку/деплой.
- **R1 – Peer review (минимум один):**  
  Минимум один коллега (peer) проводит детальный просмотр кода, обсуждает и одобряет изменения.  
  - Особое внимание уделяется влиянию на критические участки, coverage по AC/NFR, корректности ссылок на evidence.
  - Все вопросы и замечания должны быть явно разрешены до merge.
- **R2 – PDE/Engineering review и QSRE function review:**  
  - Представитель PDE/Engineering оценивает изменения с точки зрения соответствия архитектуре, базовым стандартам и безопасности.  
  - Функция QSRE (если назначена) подтверждает, что изменения не противоречат требованиям надёжности, безопасности и процессов сопровождения.
- **R3 – Независимые approvals владельцев:**  
  Для особо критичных изменений или пакетов класса риска R2-R3 требуются отдельные approvals:  
    - Владелец продукта (product owner),  
    - Владелец риска/безопасности (risk/security owner),
    - Release-ответственный,
  каждый из которых должен дать явно зафиксированное одобрение изменений до слияния.

- **CODEOWNERS:**  
  Файл `CODEOWNERS` определяет обязательных владельцев по каждой области кода/директории/папке. До интеграции с GitHub Teams в файле могут стоять временные placeholders — они должны быть заменены реальными командами или пользователями до включения branch protection.  
  Проверяйте актуальность `CODEOWNERS` перед открытием PR, чтобы ревью увидели все требуемые владельцы.

## Merge

- **Merge разрешён только после успешного прохождения всех обязательных checks (CI, approvals согласно risk-классу) и разрешения всех обсуждений и комментариев.**
- **Force-push** в защищённые ветки (main, релизные) категорически запрещён. Любые экстренные исправления выполняются через отдельные PR.
- **Политика слияния (merge commit или squash):**  
  - Выбор типа merge (merge commit vs squash) определяется командой для данного репозитория и прописывается в настройках репозитория.  
  - Обоснование выбора фиксируется в документации или в README репозитория.
- **Запрет на автоматические слияния:**  
  Слияние через automation разрешено только если все заранее определённые требования review-чекпоинтов, тестов и CODEOWNERS выполнены без исключений.
- **Трассировка:**  
  После merge необходимо убедиться, что trail между задачей, Outcome, PR, evidence и релизной записью сохранён и прозрачен для проверки.
